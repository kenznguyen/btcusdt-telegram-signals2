# T0 Evidence Object / Checkpoint Contract v1

Date: 2026-11-10  
Repository: `kenznguyen/btcusdt-telegram-signals2`  
Branch: `feature/t0-centralized-data-feeder-p1-20261101`  
Contract status: **DRAFT v1 — DOCUMENTATION-ONLY — IMPLEMENTATION NOT AUTHORIZED BY THIS CONTRACT**  
Assurance target: T0 L4-Minimum evidence object/checkpoint design; no market-data-source independence requirement.

## 1. Purpose

Define a vendor-neutral, implementation-neutral contract for turning a precisely scoped T0 candle read snapshot into an identifiable Evidence Object and a verifiable Checkpoint.

The contract separates five claims that must never be conflated:

1. **Content identity:** which exact bytes and candle records are represented.
2. **Snapshot consistency:** which exact read boundary and query scope were used.
3. **Commit durability:** whether the underlying records crossed a specifically proven durable-commit boundary.
4. **Authenticity and custody:** who/what issued the evidence, how signing authority is controlled, and where independent copies are retained.
5. **Verification and freshness:** whether exact bytes, provenance, signatures, custody and monotonic history can be independently checked.

A digest proves byte identity only. A signature proves a key signed particular bytes only when the signature and key policy verify. Neither alone proves source truth, complete ingestion, durable storage, historical trust-at-time, independent custody, or that a checkpoint is the latest one.

## 2. Scope and non-goals

### In scope

- Canonical logical model for Evidence Object, Checkpoint Manifest, Signature Envelope, Custody Receipt and Verification Record.
- Exact binding of a checkpoint to T0 market identity, candle range, returned records, gaps, schema/source provenance and snapshot boundary.
- Fail-closed status dimensions and verification rules.
- Separation of issuer, signer, custodian, verifier and source-writer responsibilities.
- Compatibility with the current T0 BTCUSDT USD-M 15m/1h candle dataset and read-only candle API.

### Explicitly out of scope

- Changing the canonical candle schema, SQLite/PostgreSQL writer, Feeder, scheduler, API or consumer contract.
- Creating a new event ledger or treating candles as financial events.
- Selecting a signing algorithm, KMS/HSM, key provider, TSA, WORM provider, cloud account or storage region.
- Implementing key generation, signing, rotation, revocation, TSA submission, provider storage, restore or runtime inventory.
- Establishing RPO/RTO, trusted-time parameters, freshness TTLs, retention durations or numeric lag thresholds.
- Claiming exchange truth, independent market-data corroboration, or proof of historical signer trust without the required evidence.
- Granting deletion, archive, cleanup, compaction, vacuum, backup expiry, replica-removal or other destructive authority.

T0 canonical data and availability/recovery copies remain protected under RET-01 B. Option C — No Destructive Authority — remains in force. No default TTL or delete-after-read/use/verification/ACK behavior is introduced.

## 3. Normative language and assurance principles

MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are normative.

- Missing, conflicting, stale, inaccessible or unverifiable required evidence MUST fail closed.
- Unknown values MUST remain explicit; they MUST NOT be replaced with zero, empty success, inferred timestamps or assumed completeness.
- Every digest MUST be recomputed by the verifier from the exact bytes received.
- A mutable database row, API response, Git commit, CI artifact or log line MUST NOT be described as WORM or immutable storage merely because it is versioned or hash-addressed.
- The evidence issuer MUST NOT be the sole independent verifier of its own evidence.
- Independent evidence custody/readback is required for the L4-Minimum custody claim. Independence of market-data sources is not required by this contract.
- A timestamp generated by a local system clock is an observation, not trusted historical time.
- The absence of a TSA does not itself fail L4-Minimum; any claim requiring trusted historical time remains UNKNOWN/NOT ESTABLISHED without qualifying evidence.

## 4. Logical object model

The logical records below do not prescribe SQL tables, file formats, object-store APIs or a programming language.

### 4.1 Evidence Object

An Evidence Object is an immutable byte sequence plus a typed descriptor that binds the bytes to their meaning.

Required logical fields:

| Field | Type / rule | Meaning |
|---|---|---|
| `evidence_object_id` | opaque stable identifier | Unique identity; not derived from mutable display names |
| `object_type` | versioned enum | `T0_CHECKPOINT_MANIFEST`, `T0_CANDLE_SEGMENT`, `T0_SIGNATURE_ENVELOPE`, `T0_CUSTODY_RECEIPT`, `T0_VERIFICATION_RECORD` |
| `object_schema_version` | integer | Schema version of the exact object |
| `media_type` | string | Declared serialization/media type |
| `canonicalization_profile` | versioned identifier | T0-JCS-1 for v1 canonical wire bytes |
| `digest_algorithm` | enum | v1 requires SHA-256 |
| `content_digest` | lowercase hex | Domain-separated SHA-256 of exact canonical bytes per §5.1.C |
| `byte_length` | nonnegative integer | Exact byte length |
| `created_at_ms` | integer or null | Local creation observation only; not trusted time |
| `producer_identity` | opaque identity reference | Issuer/process identity evidence reference |
| `source_revision` | exact source commit SHA or null | Source provenance; null means NOT ESTABLISHED |
| `configuration_digest` | digest or null | Relevant effective configuration commitment |
| `retention_class` | enum | Governance classification; not a deletion instruction |

The object bytes and descriptor MUST be version-bound. Replacing bytes requires a new object identity and digest. An object ID MUST NOT be reused for changed content.

### 4.2 Checkpoint Manifest

A Checkpoint Manifest defines a frozen, exact T0 dataset view. It does not itself prove that the source database has a durable-commit guarantee.

Required top-level fields:

| Field | Rule |
|---|---|
| `checkpoint_id` | Stable opaque identifier |
| `checkpoint_schema_version` | Explicit version |
| `checkpoint_purpose` | E.g. `DATASET_SNAPSHOT`; no implicit TSA purpose |
| `market_identity` | Exact exchange, market type, symbol and volume unit |
| `source_backend` | `sqlite`, `postgresql`, or another explicitly versioned backend |
| `source_schema_revision` | Exact migration/schema identity |
| `source_code_revision` | Exact source commit SHA; otherwise NOT ESTABLISHED |
| `snapshot_boundary` | Evidence of the consistent read snapshot/transaction boundary |
| `partitions` | One or more independently described timeframe/range partitions |
| `content_root` | Digest over canonical ordered partition descriptors and row commitments |
| `predecessor_checkpoint_digest` | Prior checkpoint digest, or explicit null with reason |
| `issuer_identity` | Evidence reference for the checkpoint issuer |
| `created_at_ms` | Local observation only; not trusted historical time |
| `durability_claim` | Explicit enum; default `NOT_ESTABLISHED` until proven |
| `completeness_claim` | Explicit enum derived from exact expected/returned/gap evidence |
| `manifest_binding` | Not embedded in the manifest; supplied by the external Evidence Object descriptor/receipt that binds the serialized manifest bytes to its object ID and digest |

Each partition MUST include:

- `exchange=binance`, `market_type=USDT_PERPETUAL`, `symbol=BTCUSDT`;
- `timeframe` exactly `15m` or `1h`;
- `start_ms` inclusive and `end_ms` exclusive, both aligned to timeframe;
- `expected_candle_count`, `returned_candle_count`;
- strictly ascending candle opening timestamps, with no duplicates;
- explicit `gaps[]` and `coverage_complete`;
- first/last included open-time and close-time boundaries, nullable only when no rows exist;
- ordered candle-content digest and exact serialization profile;
- `dataset_version_observed` as an optional reference to the API response hash, never as a substitute for the checkpoint content root;
- `as_of_ms` where applicable and the rule used to select observations.

The checkpoint MUST describe 15m and 1h as separate partitions. It MUST NOT invent one global watermark by combining the two timeframes. A checkpoint may contain one timeframe only if its scope says so.

The serialized Checkpoint Manifest MUST NOT contain its own Evidence Object ID or digest. The external Evidence Object descriptor binds the exact manifest bytes to the object identity and digest. This prevents recursive/self-referential hashing. The top-level `content_root` commits only to the canonical partition descriptors and ordered row commitments; it excludes the external descriptor, signature envelope, custody receipt and verification records.

### 4.3 Candle row commitment

For v1, each candle row commitment MUST bind the exact persisted source fields:

- exchange, market_type, symbol and timeframe;
- open_time_ms;
- OHLCV as canonical decimal strings;
- available_at_ms.

The row commitment does not pretend that derived closeTimeMs, isClosed, availabilityKind, quality or source values are separately persisted. Such derived metadata, if needed, belongs in a separately versioned manifest section and MUST identify the serializer/profile that produced it. Nullable ingestion_batch_id is excluded from v1 row identity because it is not populated by the inspected canonical writer and is not present in the SQLite schema.

Rows MUST be ordered by open_time_ms ascending. Duplicate timestamps, implicit forward-fill, interpolation, synthetic rows, missing required values or unaligned timestamps invalidate a complete checkpoint.

The manifest MUST commit to the exact ordered row sequence, not merely row count or first/last timestamp. The verifier MUST recompute each partition digest and the top-level content root.

### 4.4 Snapshot boundary

A checkpoint issuer MUST identify how the source snapshot was obtained:

- backend and database identity reference;
- transaction/snapshot isolation semantics actually in force;
- snapshot/transaction identifier or an explicit `NOT_EXPOSED` state;
- start/end observation markers;
- writer generation/lease evidence where available;
- source schema and code revisions.

A read performed across multiple non-atomic queries MUST NOT be described as one consistent snapshot unless a contractually valid snapshot mechanism proves that property. The current in-memory feeder scheduler completion boundary is not a persisted checkpoint.

### 4.5 Durability evidence

Durability is an independent evidence dimension. The following values are defined:

- `NOT_ESTABLISHED`: no qualifying durable-commit evidence is bound.
- `COMMIT_OBSERVED`: a database transaction reported successful commit; no host/power-loss guarantee is implied.
- `DURABILITY_PROFILE_VERIFIED`: the exact backend/configuration/provider durability profile has qualifying evidence for its stated failure domain.
- `UNKNOWN`: outcome or evidence cannot be established.
- `REJECTED`: evidence contradicts the claimed commit boundary.

A checkpoint created from a successful read may still have `durability_claim=NOT_ESTABLISHED`. The contract MUST NOT promote `COMMIT_OBSERVED` to `DURABILITY_PROFILE_VERIFIED` without backend-specific configuration, storage semantics and bounded verification evidence.

Current source mapping does not establish project-specific SQLite synchronous/fsync/host-loss guarantees or PostgreSQL synchronous-commit/replication guarantees. Those claims remain NOT VERIFIED until separately evidenced.


### 4.6 G0.4 — Exact completeness oracle (2026-11-10)

**Disposition: F-03 RESOLVED AT CONTRACT-DESIGN LEVEL.** This oracle defines membership/completeness for one declared timeframe/range partition. It does not prove snapshot consistency, database durability, exchange truth, market-data correctness or trusted historical time.

#### A. Partition domain

For timeframe interval Δ (15m = 900000 ms; 1h = 3600000 ms), a partition MUST satisfy:

- start_ms and end_ms are nonnegative supported timestamps;
- start_ms < end_ms;
- start_ms mod Δ = 0 and end_ms mod Δ = 0;
- the exact domain is the half-open interval [start_ms,end_ms);
- expected_count N = (end_ms - start_ms) / Δ.

The expected open-time set is exactly E = {start_ms + k×Δ | integer k, 0 ≤ k < N}. No exchange response count, first/last timestamp, database row count or API coverage flag may redefine E.

#### B. Row membership and validation

Every returned row MUST satisfy all of the following before it can enter the partition commitment:

1. Exact exchange, market_type, symbol and timeframe match the partition identity.
2. open_time_ms belongs to E; rows outside the half-open range or off the Δ grid are INVALID, not silently ignored.
3. Each open_time_ms is unique and rows are strictly ascending by numeric open_time_ms.
4. close boundary is exactly open_time_ms + Δ and is exclusive.
5. available_at_ms is a valid nonnegative timestamp and is not earlier than the close boundary.
6. OHLCV and decimal values pass the source Candle validation rules.
7. No forward-fill, interpolation, synthetic insertion, deduplication-by-overwrite or silent correction is allowed.

The verifier independently recomputes the expected domain and membership from the preserved manifest and row bytes. It MUST NOT trust producer-supplied expected_count, returned_count, complete, gaps or datasetVersion without recomputation.

#### C. Exact completeness verdict

Let R be the set of validated unique returned open_time_ms values after applying the manifest's explicit as_of_ms selection rule.

- COMPLETE iff R = E, returned_count = expected_count = N, and the recomputed missing set is empty.
- INCOMPLETE iff all returned rows are valid members of E but R is a strict subset of E.
- INVALID iff any returned row violates identity, alignment, range, uniqueness, ordering, candle validation or canonical row encoding.
- UNKNOWN iff the verifier cannot establish the exact input set or membership because bytes are missing, a read/page failed, the query was truncated, the snapshot boundary is unproven where required, or the relevant source evidence is unavailable.

INVALID MUST NOT be downgraded to INCOMPLETE. UNKNOWN MUST NOT be promoted to INCOMPLETE or COMPLETE by assuming that unobserved rows are absent.

For a nonempty valid partition, a zero-row result is INCOMPLETE (all expected slots are missing), not a complete empty dataset. A zero-length range is invalid and cannot be used to manufacture a vacuous COMPLETE result.

#### D. Gap encoding

The missing set M = E minus R is recomputed by the verifier. Consecutive missing slots are coalesced into maximal half-open intervals:

- gap.start_ms is the first missing expected open time;
- gap.end_ms is one Δ interval after the final missing open time;
- gap.missing_count = (gap.end_ms - gap.start_ms) / Δ.

Gaps MUST be sorted, non-overlapping, aligned to Δ, contained in [start_ms,end_ms), and their total missing_count MUST equal expected_count - returned_count. Gaps are evidence of missing membership, not proof of why the row is missing.

When as_of_ms is present, it is part of the partition identity/selection rule and every returned row must satisfy available_at_ms <= as_of_ms. A missing slot MUST NOT be assigned a cause such as “not yet observed” unless separate source evidence establishes that cause. Completeness is evaluated against the full declared expected domain under the stated as-of filter; any excluded/missing expected slot makes that partition INCOMPLETE.

#### E. Partition and checkpoint aggregation

- Each timeframe/range is evaluated independently. M15 and H1 verdicts MUST NOT be combined into one expected-count arithmetic or watermark.
- A checkpoint-level COMPLETE claim is permitted only when every declared partition is COMPLETE and snapshot consistency is independently PASS for the exact combined snapshot.
- Any INVALID partition makes the checkpoint invalid for a COMPLETE claim.
- Any UNKNOWN partition or UNKNOWN snapshot consistency makes aggregate completeness UNKNOWN/NOT VERIFIED.
- Any INCOMPLETE partition makes aggregate completeness INCOMPLETE.
- A checkpoint may preserve an incomplete dataset as evidence, but it MUST label it INCOMPLETE and MUST NOT present it as a complete checkpoint.
- The content_root commits to the actual returned ordered rows and partition descriptors; the completeness verdict is separately recomputed and recorded. A digest does not prove completeness.

#### F. Fixed oracle examples

For M15, start_ms=0, end_ms=2700000, Δ=900000, so E={0,900000,1800000} and expected_count=3.

- Returned open times {0,900000,1800000}: COMPLETE; gaps=[]; returned_count=3.
- Returned open times {0,1800000}: INCOMPLETE; gaps=[{start_ms:900000,end_ms:1800000,missing_count:1}]; returned_count=2.
- Returned open times {0,0,1800000}: INVALID due to duplicate timestamp, even though the distinct-set count is 2.
- Returned open times {0,900001,1800000}: INVALID due to off-grid timestamp.
- No returned rows: INCOMPLETE with one gap [0,2700000), missing_count=3.
- Missing/truncated page or unavailable row bytes: UNKNOWN, not INCOMPLETE.

#### G. G0.4 disposition and limits

- Exact expected-domain formula, row membership, invalidity rules, as-of semantics, gap coalescing and aggregate verdict: **SPECIFIED**.
- F-03: **RESOLVED AT CONTRACT-DESIGN LEVEL**.
- Executable/property-based tests and cross-implementation verification: **DEFERRED TO G2**.
- Snapshot consistency remains a separate prerequisite; this oracle cannot repair a non-atomic read.
- This is same-session contract design/self-review, not independent review. No canonical database or runtime was accessed; no code, tests, Actions or provider operations were performed.



### 4.7 G0.5 — Backend-specific multi-partition snapshot protocol (2026-11-10)

**Disposition: contract design specified; implementation and deployment qualification remain NOT VERIFIED.** A checkpoint spanning multiple timeframe/range partitions MUST be read from one backend database identity and one pinned read transaction. Multiple calls to the current public read_window facade are not sufficient because each call opens its own connection/transaction.

#### A. Common requirements

1. One checkpoint MUST name exactly one source backend and one canonical database identity reference. A checkpoint MUST NOT combine rows read from SQLite and PostgreSQL or from different database instances.
2. All declared partitions MUST be read through the same connection and transaction. The transaction isolation mode, backend version, schema/migration identity and read-only status MUST be recorded.
3. The first consistent read establishes the snapshot. Every subsequent partition query and metadata query needed for the checkpoint MUST execute in that same transaction.
4. The producer MUST retain the exact returned row bytes in memory or a noncanonical staging buffer until all partition reads and validations complete. No partial manifest is emitted if any query fails.
5. A connection loss, transaction abort, timeout, schema change that invalidates the read, or uncertainty about whether every partition used the same snapshot yields snapshot_consistency=UNKNOWN and no COMPLETE checkpoint claim.
6. Snapshot consistency is independent of completeness and durability. A stable snapshot can be incomplete; a complete set of rows can still lack a proven common snapshot; neither proves durable commit.
7. Local start/end observation timestamps are operational metadata only, not trusted historical time.

#### B. SQLite profile

- Open one read-only connection to the selected canonical SQLite database.
- Start one explicit read transaction with BEGIN; the first SELECT establishes the SQLite read snapshot.
- Execute every partition SELECT, schema-version/migration metadata read and required source metadata read on that same connection before ending the transaction.
- Keep the transaction open until all requested rows have been fetched and validated. Do not open a second connection per timeframe or page.
- Record backend=sqlite, database identity reference, SQLite library version, journal mode observed, schema/migration identity, transaction mode=READ_TRANSACTION, and that a stable snapshot identifier is NOT_EXPOSED by this contract.
- WAL mode permits writers to continue while the reader retains its snapshot; it does not by itself prove durability or create an externally verifiable snapshot token.
- If the source is not in the expected journal mode or a stable same-transaction read cannot be established, snapshot consistency is UNKNOWN/BLOCKED; do not silently fall back to independent reads.

The current SQLite read_window implementation starts a read transaction per invocation, but it opens its own connection. It therefore supports a consistent individual read_window, not a multi-partition checkpoint snapshot across separate calls.

#### C. PostgreSQL profile

- Open one connection and one explicit read-only transaction.
- Set transaction isolation to REPEATABLE READ READ ONLY before the first data query.
- Execute every partition SELECT and all required metadata reads on that same connection/transaction.
- Record PostgreSQL server version, database identity reference, schema/migration identity, isolation=REPEATABLE READ, read_only=true, transaction start observation and snapshot token if the selected server exposes a suitable token. If no stable token is exposed, record snapshot_token=NOT_EXPOSED; do not synthesize one.
- A connection/transaction restart between partitions invalidates the common-snapshot claim.
- The current PostgreSQL read adapter already requests REPEATABLE READ READ ONLY for each read_window call, but each call opens a new connection/transaction. It therefore does not establish one common snapshot across multiple calls.

#### D. Checkpoint construction boundary

The producer MUST complete all reads inside the pinned transaction, validate partition membership/completeness, compute row and partition commitments, and capture the exact transaction/snapshot metadata before releasing the connection. It may serialize the manifest and compute its object digest after the read transaction ends because the exact rows and snapshot metadata have already been frozen. The manifest MUST distinguish “snapshot read completed” from “durable commit verified.”

If any required partition is read after the transaction has ended or through a separate connection, the producer MUST restart the entire checkpoint read from a new common snapshot; it MUST NOT merge the old and new result sets.

#### E. G0.5 disposition

- Same-connection/same-transaction requirement: **SPECIFIED**.
- SQLite: **READ TRANSACTION / FIRST SELECT SNAPSHOT / TOKEN NOT EXPOSED**.
- PostgreSQL: **REPEATABLE READ READ ONLY / same connection / snapshot token only if actually exposed**.
- Existing read_window facades: **INSUFFICIENT for a multi-partition common snapshot when invoked separately**.
- Runtime implementation, database configuration parity, backend-version qualification and concurrency tests: **NOT VERIFIED; deferred to G2/G4 after separate gates**.
- No canonical DB was opened and no runtime/database test was run. This is same-session design/self-review, not independent review.



### 4.8 G0.6 — Commit observation and durable-commit receipt semantics (2026-11-10)

**Disposition: contract design specified; no current T0 durability profile is certified.** A successful API response, completed read, visible row or datasetVersion MUST NOT be described as a durable-commit receipt.

#### A. Separate outcome states

A commit observation MUST use one of these states:

- COMMIT_OBSERVED: the writer received an unambiguous successful return from the database transaction commit boundary for the exact write operation.
- COMMIT_REJECTED: the database returned an explicit failure and the transaction was confirmed rolled back.
- COMMIT_OUTCOME_UNKNOWN: the writer lost the connection/process or otherwise cannot establish whether the transaction committed.
- DATA_PRESENT_MATCH: a later independent read found all expected keys and exact values, but the original transaction outcome is not established.
- DATA_PRESENT_CONFLICT: a later read found a conflicting value for one or more expected keys.
- DATA_ABSENT_AT_READBACK: a later read did not find one or more expected keys; this does not by itself establish the original transaction outcome.

DATA_PRESENT_MATCH MUST NOT be promoted to COMMIT_OBSERVED. An idempotent retry or pre-existing identical rows can explain a matching readback without proving that the specific attempted transaction committed.

#### B. Commit observation record

A future immutable Commit Observation record MUST bind:

- unique operation_id generated before the write attempt;
- exact source backend and database identity reference;
- source schema/migration revision and writer source commit SHA;
- exact writer/lease owner identity reference and lease generation (never lease secret);
- exact ordered row-key set and row-content commitment root for the attempted batch;
- attempted/validated/inserted/idempotently-matched row counts;
- database transaction result state from §4.8.A;
- backend-reported transaction identifier if genuinely exposed, otherwise explicit NOT_EXPOSED;
- local transaction-start and commit-return observation times, marked untrusted;
- effective durability-related configuration observed for that exact operation, including unavailable/unobservable settings;
- error class/reason when rejected or unknown.

The record is created outside the canonical candle row schema. This contract does not authorize adding columns/tables to T0 or changing the writer.

#### C. Post-commit receipt and readback

A Commit Receipt is a separate immutable evidence object created only after COMMIT_OBSERVED. It MUST bind the exact Commit Observation digest and operation_id, the batch commitment root, backend/database identity, and a post-commit readback result from a new read transaction.

The readback MUST compare exact row keys and canonical values, not only row counts. Its result is one of READBACK_MATCH, READBACK_MISSING, READBACK_CONFLICT or READBACK_UNKNOWN. The receipt records the readback snapshot boundary and limitations.

If the process terminates after database commit but before the Commit Observation/Receipt is durably preserved, the outcome remains COMMIT_OUTCOME_UNKNOWN or COMMIT_OBSERVED_UNRECORDED as applicable. Recovery may create a new reconciliation record, but MUST NOT fabricate a receipt for the lost original observation or infer the original commit from matching rows alone.

The receipt itself requires independent custody and readback under L4-Minimum. A receipt stored only in the same database, same VPS or GitHub does not independently establish custody or failure-domain durability.

#### D. Durability profile is a separate qualification

COMMIT_OBSERVED and READBACK_MATCH establish only a transaction result and subsequent data visibility. They do not establish survival of process crash, OS crash, power loss, host loss, volume loss or provider failure.

DURABILITY_PROFILE_VERIFIED requires all of the following for the exact backend/configuration/failure domain:

1. effective runtime/database settings captured from the actual target configuration (not inferred from source defaults);
2. documented database, filesystem, block-device and provider persistence semantics for the claimed failure domain;
3. exact source/configuration and infrastructure identity frozen in the evidence;
4. bounded destructive/fault testing on disposable isolated infrastructure only, with explicit separate authorization and recovery proof;
5. qualifying independent review and preserved test/readback evidence;
6. no extrapolation from SQLite to PostgreSQL or between providers/volumes/configurations.

Until these criteria pass, durability remains NOT_ESTABLISHED or UNKNOWN. No numeric RPO/RTO or host/power-loss survival claim is inferred.

#### E. TSA A eligibility boundary

For the selected A use case (dataset/checkpoint proof-of-existence), a TSA request MUST NOT be issued merely because a read or database COMMIT returned successfully. It remains blocked until the exact checkpoint's source rows have a qualifying DURABILITY_PROFILE_VERIFIED receipt under §4.8.D and the immutable manifest is frozen. A TSA token, if later separately authorized, proves only the narrowly scoped existence-by-time claim allowed by its verified policy; it does not repair missing durability evidence.

TSA remains asynchronous and outside the T0 write transaction and Feeder scheduling path. A TSA failure cannot roll back a valid candle commit.

#### F. G0.6 disposition

- Commit outcome states and lost-response semantics: **SPECIFIED**.
- Post-commit exact-row readback receipt: **SPECIFIED**.
- Backend-specific durability qualification: **NOT VERIFIED / NOT CERTIFIED** for current SQLite and PostgreSQL deployments.
- TSA A submission eligibility: **BLOCKED until DURABILITY_PROFILE_VERIFIED and separate G5/provider authorization**.
- Disposable fault testing, restore and provider/storage qualification: **NOT AUTHORIZED by G0–G3**; requires separate authorization.
- No canonical database, runtime, provider, VPS, storage, key or trust root was accessed or changed. No tests or Actions were run. Same-session design/self-review only.


## 5. Canonical serialization and digest rules

The normative v1 canonicalization profile is T0-JCS-1, defined in §5.1. It uses RFC 8785 JCS with stricter T0 schema rules. No production library/runtime is selected by this contract.

1. Canonical bytes are UTF-8 RFC 8785 JCS output without BOM or trailing newline.
2. Duplicate object keys, invalid UTF-8, invalid Unicode scalar sequences, unpaired surrogates, unknown schema fields and invalid enum values are rejected.
3. JSON floating-point and JSON integer values are forbidden in canonical wire objects. All logical integer quantities (including timestamps, counts and schema versions) are canonical unsigned base-10 strings. All market decimals are canonical decimal strings.
4. Nullable and omittable fields follow one fixed representation per schema version; no alternate encodings are permitted.
5. Arrays have schema-defined order. Candle rows are strictly ascending by numeric open_time_ms; partition descriptors are ordered by timeframe (15m then 1h), then numeric start_ms and end_ms.
6. A verifier MUST parse, validate, canonicalize and byte-compare the exact preserved input before accepting its digest.
7. Evidence Object content_digest is the domain-separated SHA-256 defined in §5.1.C, not an unprefixed hash. Row and partition commitments use their own domain-separated constructions.
8. The digest is carried by the external Evidence Object descriptor and MUST NOT be embedded recursively in the bytes it commits to.

The logical object model may represent timestamps/counts/schema versions as integer types. Their canonical wire representation is always a decimal JSON string to avoid IEEE-754 precision loss.

### 5.1 G0.3 — Canonical byte profile and content-root algorithm (2026-11-10)

**Owner decision under the user's G0–G3 automatic-approval delegation: adopt RFC 8785 JSON Canonicalization Scheme (JCS) with the T0 restrictions below.** Profile identifier: T0-JCS-1. This selects a normative byte algorithm; it does not select or authorize a production library, signer, key, provider, TSA or runtime integration.

#### A. Input and canonical JSON restrictions

1. Input MUST be valid UTF-8 without BOM. Invalid UTF-8, invalid Unicode scalar sequences and unpaired surrogates are rejected.
2. Duplicate JSON object keys MUST be rejected by the parser before canonicalization. Unknown fields are rejected for versioned T0 schemas; schema-defined extension points must be explicit.
3. Canonical output MUST follow RFC 8785 JCS exactly: ECMAScript-compatible JSON string serialization, no insignificant whitespace, deterministic object-key ordering by UTF-16 code units, and UTF-8 output. No Unicode normalization is performed; code points are preserved exactly. Schema identifiers/enums remain restricted to their declared ASCII values.
4. JSON floating-point numbers are forbidden. To avoid IEEE-754 loss for signed-64-bit timestamps and counts, every logical integer (timestamps, counts, schema versions, sequence numbers) is serialized as a canonical base-10 JSON string. The logical schema may retain integer types; the canonical wire representation is string-only for numeric quantities.
5. Canonical unsigned integer strings match 0|[1-9][0-9]*; no sign, leading zero, whitespace, exponent or decimal point. Range validation occurs before serialization against the logical field's declared range.
6. Market decimal strings MUST be finite, nonnegative, non-exponent decimal values; zero is exactly 0; nonzero values have no leading integer zero except the value below one, no trailing fractional zero, no plus sign, no whitespace and no exponent. The canonical grammar is 0|[1-9][0-9]*(\.[0-9]*[1-9])?|0\.[0-9]*[1-9]. Values are range/precision-validated against the Candle contract before serialization. This agrees with the inspected Candle normalization behavior for accepted nonnegative values.
7. Null versus omission is fixed by each schema version. A field declared nullable is always present with JSON null when absent; a field declared optional-but-omittable is omitted only when absent. The same logical object MUST NOT have multiple canonical representations.
8. Arrays have schema-defined order. Candle rows are strictly ascending by numeric open_time_ms; duplicate timestamps are rejected. Partition descriptors are ordered by timeframe (15m, then 1h), then numeric start_ms, then numeric end_ms. Any other array order is invalid.
9. Canonical bytes are the sole hash input. A verifier MUST canonicalize parsed logical content again and byte-compare it with the preserved input; merely parsing successfully is insufficient.

#### B. Canonical row object

The canonical row object commits to persisted, source-derived candle fields only:

- exchange, market_type, symbol, timeframe;

#### C. Domain-separated digest and Merkle construction

All byte lengths are unsigned 64-bit big-endian. All digest values are raw 32-byte SHA-256 values internally and lowercase 64-character hexadecimal in JSON.

- Evidence Object digest: SHA256(UTF8("T0-EVIDENCE-OBJECT-V1\0") || U64BE(canonical_bytes.length) || canonical_bytes).
- Candle row leaf: SHA256(UTF8("T0-CANDLE-ROW-V1\0") || U64BE(row_bytes.length) || row_bytes).
- Empty row-tree root: SHA256(UTF8("T0-EMPTY-ROWS-V1\0")).
- Merkle parent: SHA256(UTF8("T0-MERKLE-NODE-V1\0") || left_digest_32 || right_digest_32).
- At each Merkle level, adjacent nodes are paired in order. An unpaired final node is promoted unchanged to the next level (not duplicated). Repeat until one root remains. A single leaf is the root unchanged.
- Partition leaf: SHA256(UTF8("T0-PARTITION-V1\0") || U64BE(descriptor_bytes.length) || descriptor_bytes), where descriptor_bytes are JCS bytes for the exact partition descriptor.
- Checkpoint content_root is the Merkle root of the ordered partition leaves using the same parent rule. A checkpoint with no partitions is invalid; a declared empty range is represented by one partition descriptor with row_count "0", first_open_time_ms null, last_open_time_ms null and the empty row-tree root.

A partition descriptor MUST include the exact market identity, timeframe, half-open start_ms/end_ms, row_count, first_open_time_ms, last_open_time_ms and row_root. Each is schema-validated; integer quantities are canonical strings. It MUST NOT merge 15m and 1h. The top-level manifest digest commits to snapshot boundary, provenance, completeness result, ordered partition descriptors and content_root; content_root itself commits to the partition descriptors and ordered row commitments. The external object descriptor, signature envelope, custody receipt and verification records remain outside the manifest bytes to avoid recursive hashing.

## 6. Signature Envelope and owner-controlled signing boundary

A signature is a detached attestation over the exact Evidence Object digest and its declared purpose/context.

Required logical fields:

- `signature_envelope_id`;
- exact `evidence_object_id`, `object_type`, schema version and content digest;
- purpose/context string and signing-profile version;
- signer key identifier/fingerprint (never private key material);
- algorithm identifier and signature bytes;
- signing software/build identity;
- signing request/decision reference;
- signer authority/custody evidence reference;
- local signing observation time, explicitly not trusted time;
- verification references and current trust-policy snapshot reference.

Authority boundaries:

- The T0 candle writer/Feeder MUST NOT implicitly gain signing authority.
- The checkpoint producer MAY prepare unsigned canonical bytes but MUST NOT claim owner approval merely by producing them.
- Signing authority MUST be controlled by an owner-approved identity and policy, separate from ordinary ingestion credentials.
- The verifier MUST independently validate the exact signature bytes, digest, context, key identity and applicable trust policy.
- A valid signature MUST NOT be treated as proof of historical trust-at-signing-time without qualifying time and revocation evidence.
- Key generation, custody mechanism, algorithms, rotation, revocation and recovery remain OPEN owner/security decisions. No key operation is authorized.

A missing signature does not invalidate a content digest; it does prevent any claim requiring signer authenticity/owner authorization.

## 7. Custody Receipt and independent evidence copy

A Custody Receipt records that an exact Evidence Object was accepted/read back at a declared custody location.

Required fields:

- receipt ID and schema version;
- exact object ID, digest, byte length and media type;
- custodian identity and storage namespace reference;
- custody policy/profile version;
- write/acceptance result and independently performed readback result;
- readback digest and byte-length comparison;
- failure-domain classification;
- access-control/audit evidence reference;

L4-Minimum custody acceptance requires owner-controlled evidence retained outside both T0/VPS and GitHub failure domains, with demonstrated readback when T0/VPS is unavailable, GitHub is unavailable, and both are unavailable. The precise storage mechanism and custodian are not selected here.

Git history, a GitHub Release, or a short-lived Actions artifact MUST NOT be represented as independent custody outside the GitHub failure domain. GitHub may retain source and workflow evidence but is not the sole evidence archive.

## 8. Verification Record

Each verification is a new immutable record; later verification MUST NOT overwrite an earlier result.

Required fields:

- verification ID and exact object/checkpoint digest;
- verifier identity, software version and source/build digest;
- schema/canonicalization profile versions;
- recomputed digest and byte-length result;
- schema and semantic validation results;
- partition ordering, coverage and gap results;
- snapshot-boundary and durability-evidence results;
- signature verification and trust-policy snapshot results;
- custody receipt/readback results;
- latest-head/monotonic-anchor reference and comparison result;
- explicit unresolved limitations and reason codes;
- local verification time and its trust limitation.

The verifier MUST be able to operate offline over the preserved bytes and required trust/policy snapshots. Missing trust roots, missing anchor, inaccessible custody copy, stale/rolled-back anchor or incomplete object bytes MUST remain UNKNOWN/NOT VERIFIED or BLOCKED as appropriate.

## 9. Independent latest-head / rollback anchor

Checkpoint freshness cannot be inferred from the largest sequence number found in one mutable database or Git branch.

A separate owner-controlled monotonic anchor MUST identify the latest accepted checkpoint digest and its exact checkpoint identity. The anchor is itself an Evidence Object with independent custody/readback. It MUST be versioned, authenticated and retained outside T0/VPS and GitHub failure domains.

Required checks include:
- exact digest match to the checkpoint under review;
- monotonic advancement with no silent rollback or reuse;
- readback when T0/VPS is unavailable;
- readback when GitHub is unavailable;
- readback when both are unavailable;
- explicit handling of missing, stale, conflicting or inaccessible anchor evidence.

Until the anchor authority, format, custody and update protocol are owner-approved and verified, freshness/“latest checkpoint” claims MUST be `UNKNOWN / NOT VERIFIED`. This contract does not create an anchor or choose its provider.

Do not collapse all evidence quality into one mutable status. Preserve independent dimensions:

| Dimension | Values |

Aggregate dispositions:

No averaging, compensating control or promotion of UNKNOWN/PENDING/NOT VERIFIED to PASS is allowed. A content-integrity PASS does not imply snapshot, durability, signature, custody, freshness or independent-review PASS.
