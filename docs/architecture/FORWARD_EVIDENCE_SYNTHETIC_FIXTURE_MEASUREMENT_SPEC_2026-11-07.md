# Forward Evidence Synthetic Fixture & Measurement Specification (P1.6)

Date: 2026-11-07  
Status: DOCUMENTATION SPECIFICATION ONLY — no generator, benchmark, storage provider or runtime implementation is included.

## 1. Purpose and boundary

This specification defines deterministic, synthetic-only evidence fixtures and a reproducible measurement worksheet for the P1.5 envelope/recovery contract.

Goals:
- Measure canonical event and manifest byte sizes by event class and payload cohort.
- Measure segment/object counts, request counts, daily storage growth and retention growth.
- Measure local canonicalization/hash/signature throughput and Root B replay/restore throughput when a future approved harness exists.
- Produce workload inputs for provider-neutral and region-specific cost comparisons without assuming Singapore or any other region.
- Ensure another operator can regenerate exactly the same fixture bytes and compare SHA-256 digests.

Strict exclusions:
- No real account data, account identifiers, balances, positions, order IDs, API keys, exchange credentials or user personal data.
- No access to persistent account DB, T0 DB, T1 DB, VPS or prior external artifacts.
- No exchange connection, paper execution, order generation, canonical capture, cloud account, storage bucket, provider API, credentials or provisioning.
- No source/schema/workflow/runtime implementation or activation.
- No claim that any benchmark has been executed. All sizes, rates, thresholds and volumes remain unmeasured until a separate approved test run.

PAPER-only remains in force; `ai_execution_enabled=false`. Historical Dual Reconstruction remains UNAVAILABLE / BLOCKED; Option A strict predecessor chain remains unchanged.

## 2. Reproducibility identity

Every fixture run must be identified by an immutable run descriptor:

| Field | Rule |
|---|---|
| fixture_spec_version | `synthetic-evidence-fixture/1` |
| generator_source_sha | Full immutable commit SHA of the future generator; NOT AVAILABLE until implementation is separately approved |
| generator_build_digest | SHA-256 of reproducible build/package |
| seed | Fixed 256-bit hexadecimal seed, never generated from wall clock |
| namespace | Fixed UUID namespace reserved for synthetic fixtures |
| base_time_utc | Fixed RFC3339 UTC timestamp supplied in the run descriptor |
| event_mix_version | Immutable event count and class distribution table version |
| payload_profile | Immutable small/median/large/stress profile ID |
| canonicalization_profile | P1.5 JCS profile version and test-vector bundle digest |
| hash_signature_profile | P1.5 hash/signature profile version; private keys are disposable test-only keys |
| segment_policy | Fixed event-count and max-byte policy for the run |
| compression_profile | Explicit algorithm/version/level or NONE |
| environment | OS/architecture/runtime/CPU/memory/storage medium and tool versions |

The same descriptor and generator build MUST produce byte-identical canonical event files, segment files and manifests. Any changed output is a reproducibility failure until explained by a versioned specification change.

Never include secret/private keys in the run descriptor or fixture archive. A test-only signing key is generated deterministically only inside a disposable isolated test process if cryptographic test vectors require deterministic signing; the key is never reused outside the fixture.

## 3. Deterministic generation rules

### 3.1 Randomness and identities

- Use a deterministic counter-based byte stream derived from HMAC-SHA-256 with a fixed 32-byte seed and domain-separated labels such as `fixture/event-payload/v1`, `fixture/event-order/v1` and `fixture/mark-values/v1`.
- Each generated value is a pure function of (seed, domain label, stream ID, sequence, field path, sample index). Do not depend on process scheduling, filesystem order, wall clock, locale or platform random-number generators.
- Synthetic event IDs are UUIDv5 values derived from a fixed fixture namespace and the string `stream_id + ":" + sequence`. IDs must be unique within the fixture.
- Stream IDs and account-domain labels use reserved synthetic names such as `SYNTH-CORE-001`, `SYNTH-AI-001` and `SYNTH-LEGACY-001`. No real exchange account identifiers.
- The event's occurred/committed timestamps are generated from fixed base time plus deterministic offsets. No current-time lookup.
- Sequence allocation is deterministic and monotonic within each stream. Inter-stream ordering uses a fixed tie-break tuple: `committed_at_ms, stream_id, sequence`; preserve original stream-local order.
- All monetary and quantity fields are exact decimal strings under P1.5 grammar. Values are generated from integer units and explicit scale; never binary floating point.

### 3.2 Fixture event classes

Minimum coverage mix (percentages sum to 100; counts are generated by largest-remainder allocation with a fixed lexical tie-break):

| Event class | Share | Example event types |
|---|---:|---|
| Intent and signal | 6% | SIGNAL_CREATED, INTENT_CREATED |
| Risk decision | 8% | RISK_ADMITTED, RISK_REJECTED, KILL_SWITCH_CHANGED |
| Reservation | 8% | RESERVATION_CREATED, CONSUMED, RELEASED, EXPIRED |
| Order lifecycle | 12% | ORDER_ACCEPTED, ORDER_REJECTED, ORDER_PARTIAL, ORDER_FILLED, ORDER_CANCELLED |
| Position transitions | 14% | POSITION_OPENED, INCREASED, REDUCED, CLOSED, DCA_APPLIED, REVERSAL |
| Fee and adjustment | 8% | FEE_ACCRUED, REBATE, LEGACY_ADJUSTMENT |
| Funding | 8% | FUNDING_ACCRUED, FUNDING_CORRECTION |
| Mark and valuation | 10% | MARK_OBSERVED, VALUATION_COMPUTED |
| Config and strategy | 6% | STRATEGY_CONFIG_ACTIVATED, RISK_POLICY_CHANGED |
| Baseline and risk state | 8% | HWM_UPDATED, DAILY_BASELINE_ESTABLISHED, DAILY_BASELINE_ADVANCED |
| Recovery and audit | 6% | CHECKPOINT_SEALED, CHECKPOINT_INVALIDATED, REPLAY_COMPLETED, OBSERVER_ACK |

The fixture MUST also include explicit negative/edge records:
- duplicate delivery with same event ID and identical bytes;
- same event ID with different payload bytes;
- missing sequence and wrong previous hash;
- invalid signature, unknown key and revoked key;
- late event crossing a UTC boundary;
- partial-fill sequence followed by cancel/replace;
- reduce/close/reversal ordering;
- fee/funding UNKNOWN (not zero);
- stale/missing mark and clock uncertainty;
- Root B duplicate acknowledgement and crash around checkpoint commit.

Negative records are separate test vectors and MUST NOT be mixed into the clean baseline volume denominator.

### 3.3 Payload size cohorts

Generate three cohorts per event class:
- SMALL: compact but schema-valid payload, no optional extension fields.
- MEDIAN: representative nested payload with ordinary provenance and causal references.
- LARGE: upper-bound schema-valid payload with long but bounded IDs/reason strings and full source references.
- STRESS: separate adversarial payload tests for maximum allowed lengths, large causation arrays and many provenance references. Stress records are excluded from normal p95 workload unless the actual expected production mix justifies them.

Do not invent actual byte counts. Measure canonical bytes from generated outputs.

### 3.4 Scale profiles

Minimum independent fixture sizes:
- Smoke: 1,000 clean events.
- Baseline: 10,000 clean events.
- Scale: 100,000 clean events.
- Burst: same total count as Baseline, but concentrated into deterministic bursts and out-of-order delivery windows.
- Recovery: Scale fixture plus one separately retained checkpoint input and deterministic observer receipt sequence.

A profile may be extended only by versioning the run descriptor. Do not extrapolate benchmark performance from Smoke.

## 4. Canonicalization and integrity measurement

For every event:
1. Validate schema and project profile.
2. Produce UTF-8 RFC 8785 JCS bytes for `event_core` only.
3. Record byte length and SHA-256 event hash using the P1.5 domain separator.
4. Sign the exact P1.5 signature message with a disposable test key if and only if the cryptographic harness has been approved.
5. Verify signature independently using the public key.
6. Serialize the outer envelope for transport as a separate measured object; distinguish canonical event-core bytes from transport envelope bytes.

For every segment:
- Record raw event bytes, framing/delimiter overhead, segment total bytes, event count, first/last sequence, first/last event hash and segment digest.
- Measure compression separately (e.g. gzip with fixed implementation/version/level) but treat compressed and uncompressed objects as different immutable object identities.
- If compression is selected later, record algorithm/version/level, uncompressed digest and compressed digest. Do not silently recompress an object under the same identity.
- Measure manifest bytes including signature, key ID and version-bound storage metadata; storage version ID is available only after a provider test and must not be fabricated in synthetic local fixtures.

Report min, median, p90, p95, p99 and max event bytes per event class and overall. For each statistic, retain sample count and the exact cohort definition. Report segment and manifest distributions separately.

## 5. Segment batching matrix

Evaluate a matrix rather than selecting a batch policy prematurely:

| Policy ID | Event cap | Byte cap | Purpose |
|---|---:|---:|---|
| B1 | 100 | 1 MiB | small/low-latency segment candidate |
| B2 | 500 | 4 MiB | moderate batching candidate |
| B3 | 1,000 | 8 MiB | larger batching candidate |
| B4 | 5,000 | 32 MiB | throughput/storage request candidate |

These are experimental fixture settings, not approved runtime limits. Segment closes at the first cap reached. Preserve stream ordering and manifest coverage; never split a single event. Any event exceeding the configured segment byte cap must be rejected as a fixture-policy violation and reported, not silently truncated.

For each policy, report:
- number of segments and manifests;
- average/min/p95/max segment bytes;
- average events per segment;
- unfilled capacity at close;
- manifest-to-payload overhead ratio;
- number of upload-equivalent operations and expected retry/re-read operations;
- time to seal locally and verify bytes.

No upload is performed in this phase.

## 6. Synthetic daily workload model

Use parameterized workload inputs, not an assumed trading rate:

| Input | Meaning |
|---|---|
| E_day | total events generated per day |
| p_i | event class share for class i |
| S_i,p50 / S_i,p95 / S_i,max | measured canonical byte size by class |
| M_day | manifest bytes/day |
| C_raw | optional measured compression ratio |
| V_versions | retained object versions per logical object |
| R_retry | measured retry/read-back operation multiplier |
| A_day | audit/receipt/checkpoint bytes/day |
| H | retention horizon in days |
| Replicas | separately retained root count; Root A and Root B modeled independently |

Estimate raw daily bytes as:
`D_raw = E_day × Σ(p_i × S_i_mean) + M_day + A_day`

Use the measured mean for total volume and p95/max for capacity/burst planning. Do not multiply p95 by all events unless explicitly modeling a conservative stress bound.

Retention storage before provider-specific versioning/replication overhead:
`Storage(H) = D_raw × H`

For versioned/replicated storage, calculate each root independently:
`Storage_root = Σ(object_version_bytes) + manifest_versions + checkpoints + audit_objects`

Do not simply multiply by two if Root B has a different checkpoint cadence, compression policy, retention period or event duplication behavior. Report Root A and Root B line items separately.

The model MUST show sensitivity for event rate and event size (at minimum 0.5x, 1x, 2x, 5x of measured baseline). These are model multipliers, not claimed workload probabilities.

## 8. Throughput, recovery and spool measurements

When a future approved local harness exists, measure separately:
- canonicalization events/sec and CPU time/event;
- SHA-256 events/sec and CPU time/event;
- signature sign and verify operations/sec and p50/p95 latency;
- segment assembly and manifest seal throughput;
- Root B verification/reducer events/sec and checkpoint write latency;
- replay throughput with clean, duplicate, gap, late and invalid-event mixes;
- cold clean-room restore time from only retained evidence roots;
- spool growth in bytes/hour and time to full under Root B outage;
- catch-up rate after outage and time to drain backlog;
- peak memory, CPU, disk IO and temporary disk usage.

Run each measurement at least 5 times after one warm-up run. Report every sample, median, p95 where sample count supports it, min/max, environment and fixture SHA. Do not hide outliers or discard failed runs. For a small sample count, label p95 as low-confidence or omit it.

Recovery tests must verify output digests against independently generated expected checkpoints. Merely completing replay is not a successful restore.

## 13. P1.7 deterministic profile hardening (2026-11-07)

Reference: `docs/architecture/FORWARD_EVIDENCE_SYNTHETIC_FIXTURE_READINESS_REVIEW_2026-11-07.md`.

The following details are normative for a future synthetic-only generator; they do not authorize implementation.

### 13.1 Exact deterministic PRF byte framing

- Seed is exactly 32 bytes (64 lowercase hex in run descriptor); HMAC-SHA-256 key is those seed bytes.
- Message is ASCII `SYNTH-EVIDENCE-PRF-V1\n` || uint16be(domain UTF-8 byte length) || domain bytes || uint16be(stream UTF-8 byte length) || stream bytes || uint64be(sequence) || uint16be(field-path UTF-8 byte length) || field-path bytes || uint32be(sample_index) || uint32be(block_index).
- All integer encodings are unsigned big-endian. Domain/stream/path lengths >65,535 bytes and counters outside their widths are rejected. Sequence is 1..10^20−1 in the fixture and is serialized as 20 zero-padded decimal digits in events.
- HMAC output is 32 bytes. For longer output, increment block_index from zero and concatenate; truncate only the final block to requested length.
- No implicit separators, locale, filesystem order, wall clock or Unicode normalization. Known-answer vectors are required for empty path, UTF-8 non-ASCII labels, sequence boundaries and multi-block output before generator acceptance.

### 13.2 Identity, scenarios and causal validity

- Synthetic stream IDs are ASCII `[A-Z0-9-]{1,64}`. UUIDv5 name bytes are UTF-8 `stream_id + ":" + sequence20` using the fixed namespace in the run descriptor.
- Build deterministic scenario/state-machine bundles before allocating optional event-mix counts. Dependent events reference existing event IDs and legal prior state.
- Core/AI/Legacy streams have separate explicit scenario templates. The percentage table is a target distribution, not a reason to omit mandatory causal events or emit impossible transitions. Report target counts, mandatory causal overhead and actual counts.
- Clean fixtures contain only valid transitions. Each negative vector is a separate fault-injected derivative with its declared fault(s); it does not contaminate clean volume statistics.
- UNKNOWN fee/funding/mark is represented as a typed UNKNOWN state, never numeric zero.

### 13.3 Stream ordering and segment framing

- Each segment contains exactly one stream ID and contiguous sequence range; no cross-stream segment.
- Commit timestamps are nondecreasing within each stream. Sequence is authoritative within stream. Inter-stream ordering uses `committed_at_ms, stream_id, sequence20`; occurred_at never reorders committed stream history.
- Segment byte cap includes exact stored segment framing plus event transport bytes and excludes manifest bytes. The framing format/version is part of the run descriptor.
- Close before adding an event that would exceed the cap. Never split or truncate an event. An event larger than the cap is a separately reported rejected fixture case.

### 13.4 Manifest and storage receipt separation

- Local fixture creates immutable `manifest_core` containing schema/version, manifest ID, stream ID, contiguous range/count, first/last event hashes, previous manifest hash, segment byte length/digest, source schema/build/config identities, seal time and signature profile ID.
- For local tests, canonical manifest bytes are UTF-8 JCS(`manifest_core`), no BOM or trailing newline. Hash domain: `BTCUSDT-PAPER-MANIFEST-V1\n`; signature message: `BTCUSDT-PAPER-MANIFEST-SIGNATURE-V1\n` || raw 32-byte manifest hash.
- A post-upload `storage_receipt` is a separate append-only object created only after provider read-back. Local fixtures omit it; they must not fabricate provider version/generation IDs, retention state or durable-write receipts.
- Use published RFC 8032 vectors for crypto conformance. Any fixture-specific Ed25519 seed is derived with a separate domain label only in disposable process memory and must never be persisted/exported. This is not a key custody design.

### 13.5 Measurement statistics

For every event class/cohort and representation (event_core, transport envelope, segment, manifest, compressed object), report sample count, min, arithmetic mean, p50, p90, p95, p99, max and total bytes. Quantiles use nearest-rank: sorted value at rank ceil(p*n), 1-indexed. State clean/fault cohort separately. Define compression ratio as compressed bytes divided by uncompressed bytes. Retain all raw samples and exact fixture digest.

For timing/throughput, retain every run, warm-up marker, environment, fixture digest and failures. Five measured runs are exploratory evidence only; do not claim a statistically strong p95 from five samples.

A local Root B replay is labeled `LOCAL_REPLAY_SIMULATION`; it tests deterministic reducer/replay semantics only. It cannot satisfy independent-process, separate-admin, WORM, provider durability or provider clean-room restore acceptance.
