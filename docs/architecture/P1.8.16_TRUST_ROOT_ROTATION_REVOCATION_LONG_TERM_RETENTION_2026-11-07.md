## 4. Revocation policy and explicit limits

The implementation is deliberately fail-closed and does not infer a clean revocation state from missing data.

Policy outputs:
- `NOT_CHECKED_OFFLINE`: offline cryptographic verification; current revocation state is unknown.
- `REVOCATION_STATUS_NOT_EXPOSED`: online TUF root acquisition succeeded, but the GitHub CLI verification result does not expose a separate per-certificate revocation verdict.
- `REVOKED_REPORTED / REJECT`: a supplied record reports revocation; the policy blocks it.
- `REVIEWED_CLEAR_AUDIT_ONLY`: a clearance review is recorded, but admission remains blocked unless evidence authenticity is separately verified.

The policy module marks external evidence authenticity as `NOT_VERIFIED_BY_THIS_MODULE`. Automated OCSP/CRL/security-advisory ingestion and cryptographic authentication of external revocation records are **NOT IMPLEMENTED / NOT VERIFIED** in P1.8.16. No "not revoked" claim is made.

A root inventory removal is detected as a trust-root change and blocks CI pending review, but that event is not automatically classified as a confirmed certificate revocation.

## 5. Long-term evidence retention

The workflow now:
1. uploads evidence artifacts with `retention-days: 90`, subject to repository retention policy;
2. creates a retention manifest with source SHA, workflow run ID, file sizes and SHA-256 digests;
3. independently rechecks the complete payload in a separate job;
4. commits the signed subject ZIP, Sigstore bundle, checksum, retention manifest and root snapshot into Git history under `docs/evidence/p1-8/<source-sha>/`;
5. appends the root snapshot chain in the same archive commit.

Git history is persistent repository storage but **NOT WORM**. Repository administrators can rewrite or delete it. An independent offline export or separately controlled immutable storage copy is still recommended and is **NOT AUTOMATED / NOT VERIFIED** here.
