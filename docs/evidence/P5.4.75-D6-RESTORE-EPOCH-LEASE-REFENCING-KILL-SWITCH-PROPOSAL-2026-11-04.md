# P5.4.75 — D6 Restore Epoch, Lease Re-fencing and Kill Switch Recovery Proposal

Date: 2026-11-04 (Asia/Ho_Chi_Minh)
Branch: `feature/p5-4-1-post-merge-validation-20261103`
Status: **APPROVED — OWNER DECISION RECORDED 2026-11-04 (Asia/Ho_Chi_Minh)**
Scope: architecture proposal only. No restore, database access, device access, lease mutation or writer operation.

## 1. Objective and boundary

Define a fail-closed recovery protocol so that restoring an older valid snapshot cannot resurrect stale writers, lease generations, queued intents, order-book assumptions or risk permissions.

D6 is a recovery-control contract. It does not prove that a backup is valid (D3/D4/D5), and does not authorize production restore, canonical DB access, Android runtime activation or live execution.

The system remains paper-only with `AI_EXECUTION_ENABLED=false`.

## 2. Proposed recovery authorities

Separate these identities and responsibilities:

- **Restore Epoch Authority:** monotonic authority outside the restored SQLite file and outside any snapshot being restored. It allocates a unique, strictly increasing epoch and must never roll back with the database.
- **External Recovery Latch:** durable deny-writes/deny-execution control outside the restored database. It defaults to asserted on startup uncertainty, restore start, owner-stop uncertainty or failed recovery.
- **Canonical Host / Lease Authority:** after recovery, the Android Canonical Host owns lease generation and validates fencing tokens at every canonical write as required by D2. The restored lease generation is data to inspect, never the authority to resume writes.
- **Kill Switch:** separate durable deny-execution state. It must be asserted before restore and remain asserted until an explicit authorized readiness acknowledgement.
- **Recovery Operator:** an explicitly authorized human role that approves the recovery plan and separately acknowledges readiness. The identity, authorization source and audit evidence must be defined before implementation.

No authority may be stored solely inside the database it is responsible for recovering.

## 3. Proposed D6 sequence

### D6.1 — Enter recovery deny state

1. Assert the external Recovery Latch and Kill Switch before any restore-related mutation.
2. Close admission to new writers and new execution intents.
3. Stop all known writer-capable processes/services and prevent automatic restart.
4. Record a recovery operation ID, requested snapshot/manifest identity, initiating principal, reason and start time.
5. If latch assertion cannot be confirmed, fail closed and do not proceed.

### D6.2 — Prove prior owners stopped

- Require positive evidence that every previously authorized writer/lease owner is stopped or fenced.
- A process list, timeout, lost heartbeat or network disconnection alone is not proof.
- Unknown owner, unreachable owner or uncertain stop outcome blocks restore.
- Record owner identity, last observed lease generation, stop/fence evidence and verifier result.
- Do not infer that a restored lease record proves the former owner stopped.

### D6.3 — Allocate a new restore epoch

- Allocate a unique monotonically increasing epoch from the external Restore Epoch Authority after recovery deny state is asserted and prior owners are proven stopped.
- Persist the epoch and recovery operation ID in the external authority before replacing canonical data.
- The authority must reject rollback, duplicate allocation and reuse for another recovery operation.
- If allocation outcome is uncertain, query the authority by idempotency key; do not allocate a second epoch blindly and do not proceed until the outcome is resolved.
- Epoch allocation is irreversible; failed recovery consumes the epoch.

### D6.4 — Validate and restore accepted snapshot

- Accept only a snapshot with a published immutable D3 identity and passing physical, D4 migration-chain, D5 schema and SQLite/domain verification evidence.
- Verify manifest/backup identity and physical digest before restore.
- Restore into an isolated staging target; never overwrite the active canonical target before staging validation succeeds.
- Verify openability, SQLite integrity, foreign-key/domain invariants, D2 cursor vector, Ledger/audit sequence, Risk↔Ledger binding, D4 migration authority/chain and D5 schema digest.
- Reconcile that all state required by the restore plan is represented; explicitly list external state that is not part of the snapshot.
- Publish/switch the restored target only through a separately reviewed atomic activation protocol. If activation cannot be proven atomic and recoverable, stop with the external latch asserted.
- Do not repair, auto-migrate, seed, initialize or silently normalize a restored database during verification.

### D6.5 — Re-fence all leases and invalidate stale state

- Establish a new lease generation strictly greater than every generation observed in the restored snapshot and every generation issued by the external authority.
- The external authority's monotonic floor is authoritative; restored values can never lower it.
- Bind the new lease generation to the allocated restore epoch and canonical host identity.
- Require host-side fencing validation on every canonical write, not merely at process startup.
- Invalidate all pre-restore write capabilities, idempotency reservations whose outcome is uncertain, queued execution intents, cached order-book snapshots, and any signal/decision whose market-data cursor or risk provenance is no longer current.
- Recompute or explicitly invalidate derived risk state before any writer admission.
- If any stale capability cannot be enumerated or invalidated, remain blocked.

### D6.6 — Keep Kill Switch asserted and perform readiness checks

Required checks before readiness acknowledgement:
- correct active database identity and accepted snapshot/manifest;
- D3/D4/D5 verification evidence tied to the restored snapshot;
- restore epoch and lease generation durably recorded by external authorities;
- all prior owners stopped/fenced;
- no stale writer capability or pending ambiguous transaction;
- Market Data cursor/gap/backfill consistency;
- Ledger sequence/audit consistency and Risk↔Ledger binding;
- external Recovery Latch still asserted;
- Kill Switch still asserted;
- `AI_EXECUTION_ENABLED=false` and paper-only execution mode verified;
- audit trail complete and recovery operation outcome unambiguous.

A failed or unknown check blocks acknowledgement.

### D6.7 — Explicit acknowledgement and controlled release

- Require a distinct, authenticated and authorized human acknowledgement referencing the recovery operation ID, restore epoch, snapshot identity and readiness evidence digest.
- The acknowledgement must be durable and auditable.
- Release the external Recovery Latch only after acknowledgement is verified.
- Keep the Kill Switch asserted after latch release unless a separate explicit authorization policy permits clearing it. D6 approval itself must never clear the Kill Switch.
- Writer admission, if ever authorized, is a separate capability decision and must require the current epoch/generation fence.
- Any crash, timeout, process death, authority unavailability or uncertain acknowledgement/release outcome returns to fail-closed state; reconcile external authority before retry.

## 4. Proposed failure semantics

- Latch assertion failure, unknown prior owner, uncertain stop, epoch authority unavailable, ambiguous epoch allocation, invalid manifest, failed staging verification, uncertain publication, lease re-fencing failure, stale capability not invalidated, failed readiness check or incomplete audit => **BLOCKED**.
- On BLOCKED, Recovery Latch and Kill Switch remain asserted; no writer or execution capability is granted.
- Never roll back the external epoch or lease-generation floor to match restored database contents.
- Never automatically clear latch/Kill Switch on process restart, health check success or elapsed timeout.
- Never interpret an incomplete/unknown operation result as success.
- Recovery retry must be idempotent by recovery operation ID and must reconcile the last durable external-authority state before taking another action.

## 5. Required audit evidence

Proposed immutable recovery record:
- recovery operation ID and initiating principal/reason;
- requested and accepted snapshot/manifest/physical digest;
- external latch assertion and release events;
- prior owner inventory and stop/fence proofs;
- restore epoch authority identity, allocated epoch and idempotency key;
- staging target identity, verification report and publication/switch outcome;
- restored D2 cursor vector, D4 migration chain and D5 schema digest;
- previous and new lease generation, authority floor and fencing test evidence;
- invalidated intent/capability/cache inventory;
- Kill Switch state transitions;
- readiness checks, acknowledgement principal/signature/time and evidence digest;
- final status: BLOCKED / READY-ACKNOWLEDGED / LATCH-RELEASED (never imply writer enabled).

Audit evidence must be stored outside the restored database or in an independently durable append-only authority so restore cannot erase the recovery history.

## 6. Fixture-only acceptance plan (specified, not implemented)

1. Restore epoch authority allocates strictly increasing epochs across simulated restores.
2. Restoring an older DB cannot lower the external epoch floor.
3. Duplicate recovery operation ID is idempotent and does not allocate a second epoch.
4. Uncertain epoch allocation is reconciled before proceeding.
5. Unknown prior writer blocks recovery.
6. A lost heartbeat alone does not satisfy owner-stop proof.
7. Failure to assert external latch blocks all subsequent stages.
8. Invalid physical snapshot digest blocks staging.
9. D4 migration-chain mismatch blocks staging.
10. D5 schema digest mismatch blocks staging.
11. SQLite integrity or domain invariant failure blocks publication.
12. Staging verification failure leaves active target unchanged.
13. Uncertain publication keeps latch asserted and blocks writers.
14. Restored lease generation below external floor is re-fenced upward.
15. Stale fencing token is rejected on every canonical write.
16. Old queued intents and idempotency ambiguities are invalidated/blocked.
17. Cached order-book snapshots and stale signal provenance are invalidated.
18. Risk↔Ledger mismatch blocks readiness.
19. Kill Switch remains asserted through readiness checks and latch release.
20. Missing/unauthorized acknowledgement blocks latch release.
21. Process death at every stage leaves recovery fail-closed after restart.
22. Authority outage or audit write failure blocks progression.
23. Repeated recovery retries reconcile the same operation ID without double activation.
24. D6 flow never enables live execution; `AI_EXECUTION_ENABLED=false` remains enforced.

All tests use disposable fixtures and fake authorities only. No canonical DB, Android device, Feeder, exchange, production restore or writer is involved.
