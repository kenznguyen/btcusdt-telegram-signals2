# P5.4.82 — Provider-Neutral Key Custody and Recovery Architecture Proposal

**Date:** 2026-11-04  
**Status:** PARTIALLY APPROVED — D82-A ACCEPTED; D82-B–D82-J OPEN  
**Scope:** Architecture and control-plane contract only; no provider selection or runtime authorization.

## 1. Purpose

Define provider-neutral boundaries for the P5.4.81-approved cryptographic profile: AES-256-GCM envelope encryption, one random 256-bit DEK per Backup ID, and Ed25519 manifest signatures with a signing key separate from payload-encryption keys.

This proposal addresses custody, least privilege, recovery, dual control, audit evidence, key rotation and CI isolation. The owner has accepted D82-A's independent escrow recovery model alongside primary KMS/HSM routine operations; no KMS/HSM vendor, storage provider, jurisdiction or concrete escrow implementation is selected.

## 2. Governing decisions and non-goals

This proposal is subordinate to D2–D7, P5.4.80 and approved P5.4.81. It must not weaken:
- independent trust boundaries for capture, encryption, destination, signing, restore approval, decryption, recovery audit and CI;
- authenticated manifest binding of snapshot-image and encrypted-object digests;
- fail-closed verification and D3/D4/D5 integrity/domain checks;
- D6 restore epoch, external Recovery Latch, writer fencing and separate readiness/acknowledgement gates;
- D7 independent immutable destination, read-back verification, protected last-known-good and authenticated restore approval.

Non-goals: implementation, key generation, KMS/HSM or storage account access, provider procurement, Android keystore substitution for a remote KEK, canonical DB access, backup/restore execution, fixture execution, Feeder/exchange access, Kill Switch/latch changes or writer activation.

## 3. Threat model and trust boundaries

Assume CI credentials, an Android app process, a backup destination credential, a restore operator account or one administrative identity may be compromised independently. Also assume provider outage, API throttling, accidental key disablement, loss of an operator device, partial rotation, stale cached metadata and uncertain remote-operation outcomes.

The architecture must prevent:
1. CI or ordinary app identities from invoking production key operations.
2. Destination administrators from decrypting payloads or signing manifests.
3. Signing identities from decrypting payloads.
4. A single routine operator from unilaterally approving and completing a sensitive recovery.
5. A restored database, backup manifest or stale app process from authorizing its own key access or writer admission.
6. A key/provider outage from causing fallback to plaintext, a local ad-hoc key, a second writer or an unverified backup.

Provider administrators remain a residual high-trust role. Provider-side administrative compromise, collusion among the required recovery approvers and loss of all independent recovery material cannot be eliminated by this proposal; these risks require explicit owner acceptance and operational controls.

## 4. Provider-neutral logical components

The following are logical interfaces, not selected products or concrete APIs:

| Component | Responsibility | Must not do |
|---|---|---|
| Key Policy Authority | Owns immutable key IDs, purpose, state, policy version and allowed operations | Hold plaintext backup payloads |
| KEK Custody Adapter | Wraps/unwraps a DEK through an approved external KMS/HSM boundary | Sign manifests or approve restores |
| Manifest Signing Adapter | Signs canonical manifest bytes and exposes trusted public-key metadata | Decrypt payloads |
| Recovery Approval Authority | Validates authenticated, independent approvals and recovery case state | Directly modify restored DB or clear writer gates |
| Immutable Audit Sink | Records append-only control-plane events and evidence references | Store plaintext DEKs or secret key material |
| CI Fake Provider | Deterministic test double with synthetic keys and isolated fake storage | Reach production endpoints or reuse production identities |

Each adapter must expose a versioned, typed contract and stable error taxonomy. Provider-specific SDKs belong behind adapters; provider error text must not become the application policy contract.

## 5. Key inventory and metadata contract

Every key reference must be an opaque immutable identifier, never key bytes. The registry record should include:
- key ID and immutable key-version ID;
- purpose: `PAYLOAD_KEK`, `MANIFEST_SIGNING`, or separately approved recovery purpose;
- algorithm/profile and adapter-contract version;
- provider reference and provider account/tenant identity (non-secret);
- state: `PENDING`, `ACTIVE`, `DECRYPT_ONLY`, `SUSPENDED`, `REVOKED`, `DESTROY_PENDING`, `DESTROYED`;
- creation/activation/retirement timestamps and actor/audit-event references;
- allowed operations and workload identity policy version;
- rotation predecessor/successor links;
- recovery policy version and evidence references where applicable.

Do not put secret values, plaintext DEKs, access tokens, private signing material or recovery shares in the registry, manifest, logs, CI artifacts or Android preferences. Do not rely on a mutable alias alone to identify the exact key version used for a backup.

## 6. Workload identity and least privilege

Proposed identity classes:
- **Capture/encrypt workload:** may request a fresh per-backup DEK and wrap it; cannot unwrap old DEKs unless a separately approved workflow requires it.
- **Manifest signer:** may sign only approved canonical manifest payloads; cannot unwrap DEKs.
- **Destination writer/read-back verifier:** may write/read immutable objects; cannot invoke cryptographic key operations.
- **Restore verifier:** may authenticate manifests and request a narrowly scoped unwrap after restore authorization; cannot approve its own request.
- **Recovery approvers:** authenticate and approve a recovery case; cannot access key bytes or directly run restore.
- **Audit writer:** append-only event submission; cannot alter prior events.
- **CI:** synthetic test identity only, network-denied from production KMS/HSM and storage.

Prefer short-lived workload identity credentials and audience-/purpose-bound authorization over long-lived static secrets. Exact federation mechanism is provider-specific and remains undecided. No secret may be embedded in source, mobile APK, repository variables, workflow artifacts or handoff documents.

## 7. DEK lifecycle and backup binding

1. For each Backup ID, request a cryptographically secure fresh 256-bit DEK through the approved adapter.
2. Use the DEK only for that backup payload; enforce the approved AES-256-GCM nonce/tag/AAD profile.
3. Wrap the DEK under an exact immutable KEK version and store only the wrapped DEK plus key-version references in the authenticated backup envelope/manifest contract.
4. Bind Backup ID, profile version, KEK key-version ID, wrapped-DEK digest/length and immutable object identities in authenticated metadata. Exact canonical field names and serialization require a separate contract review.
5. Zeroize in-memory plaintext DEK material as far as the selected runtime/library permits; document residual copies, crash dumps and managed-runtime limitations.
6. A DEK is never reused across Backup IDs. Retry semantics must not silently create a second ciphertext/nonce pairing under the same DEK/nonce tuple. An uncertain encryption outcome is abandoned and reconciled using immutable object identity; do not guess whether a nonce was consumed.

## 8. Rotation, suspension and revocation

- KEK rotation creates a new immutable key version; it does not rewrite historical manifests or silently relabel old wrapped DEKs.
- Historical backups remain decryptable only through their recorded KEK version or an explicitly audited rewrap operation that preserves the original payload digest and records old/new key-version references.
- Signing-key rotation publishes a versioned trusted public-key set with validity intervals and explicit revocation semantics. Historical signature verification must use the recorded signer identity and policy applicable to the backup, while honoring compromise/revocation policy.
- `SUSPENDED` blocks new operations pending investigation; it is not equivalent to destruction.
- `REVOKED` blocks new use. Whether a revoked version remains usable for historical verification/decryption is an explicit incident-policy decision; never infer permission from provider availability.
- Destruction requires proof of retention expiry or approved exception, dependency inventory, dual approval, immutable audit record and a post-action verification. Destruction is irreversible and must never be triggered by ordinary cleanup or CI.

## 9. Recovery-key custody and break-glass process

No recovery method is selected in this proposal. Candidate models requiring separate owner selection include:
- provider-native multi-party recovery controls;
- independent escrow of a recovery capability under a separately governed authority;
- threshold-controlled recovery material with geographically and administratively separated custodians.

Do not choose ad hoc printed keys, a single operator-held export, a single cloud account, or a copy in the repository/Android device as a recovery design.

Proposed recovery workflow:
1. Open a uniquely identified recovery case with reason, affected Backup IDs/key versions, incident severity and requested operation.
2. Verify requester identity using an independent authentication channel; a GitHub approval/comment alone is not key authorization.
3. Confirm that the recovery request is not originating solely from the restored database, the destination provider or the workload requesting decryption.
4. Require at least two independent authorized approvers for break-glass recovery; approvers must be distinct from requester and executor. Final threshold, role roster, quorum failure handling and emergency exception remain owner decisions.
5. Bind approvals to a canonical request digest, scope, expiry, nonce and one-time case ID. Reject replay, changed scope, expired approval and duplicate completion.
6. Recovery authority issues a short-lived, single-purpose authorization to the restore verifier. It does not export raw KEK/private signing material.
7. Verify manifest signature, encrypted-object identity/digest/length, decrypt/authentication tag, snapshot-image digest and D2–D5 checks in isolated staging.
8. Record each approval, policy decision, key operation, provider request ID, result and evidence digest in the independent audit sink.
9. Keep D6 Recovery Latch and Kill Switch asserted; key recovery success is not restore readiness and does not admit writers.
10. Close the case only after independent evidence review. Any timeout or uncertain provider outcome leaves the case pending/blocked for reconciliation, not presumed successful.

## 10. Restore authorization separation

Key recovery/decryption authorization is only one gate. It cannot:
- allocate or advance Restore Epoch Authority;
- prove prior writers stopped or fenced;
- change Lease Generation;
- publish a restored canonical DB;
- release Recovery Latch;
- clear Kill Switch;
- authorize Feeder, exchange connectivity or writer admission.

These remain independent D6/D7 decisions with separate authenticated approvals and audit evidence.

## 11. Audit event contract

Append-only events should capture:
- event ID, case ID, correlation ID and monotonic sequence from the audit authority;
- UTC timestamp as diagnostic metadata, not ordering authority;
- actor/workload identity, authentication context and policy version;
- operation, purpose, key ID/version, Backup ID and object ID/version;
- approval references and canonical request digest;
- provider adapter/version and provider request ID;
- outcome class, retryability, uncertainty flag and evidence digest;
- previous-event digest or equivalent tamper-evidence mechanism, subject to separate audit-store design.

Never log plaintext keys, DEKs, private signing material, credentials, decrypted payloads or sensitive recovery shares. Audit retention, independent replication, tamper-evidence anchoring and privacy/data-residency policy remain open.

## 12. Failure handling — fail closed

| Failure | Required behavior |
|---|---|
| KMS/HSM unavailable or throttled | No plaintext/local-key fallback; retry only under bounded idempotent policy; preserve case state |
| Wrap/unwrap timeout with unknown outcome | Mark outcome uncertain; reconcile by provider request ID; do not repeat blindly |
| Unknown key/version/profile | Reject operation and preserve evidence |
| Key suspended/revoked/destroyed | Deny operation according to explicit state policy |
| Manifest signature invalid or signer untrusted | Reject before decryption |
| GCM tag/AAD mismatch | Reject payload; never publish staging output |
| Approval replay/expiry/scope mismatch | Reject and audit |
| Audit sink unavailable | Deny sensitive key/recovery operations unless a separately approved tamper-evident durable queue policy exists |
| Partial rotation | Keep old key version available under policy; do not claim rotation complete |
| Recovery quorum unavailable | Remain blocked; no single-person bypass by default |
| Provider identity/account mismatch | Deny and alert; no implicit account fallback |

No fail-open mode is proposed. Any emergency exception requires an explicit owner-approved policy and cannot bypass D3/D6 integrity, fencing or writer gates.

## 13. CI and fixture boundary

CI must use synthetic keys, fake KMS/HSM adapters and fake immutable storage. Production endpoints should be unreachable by network policy, not merely absent from test configuration. CI must not receive production credentials or trusted production identity tokens.

The approved fixture inventory remains **96 specified, NOT IMPLEMENTED / NOT RUN**. Candidate P5.4.82 fixture additions (not yet approved and not included in that count) should cover:
- two-person approval and requester/executor separation;
- approval digest/scope/expiry/replay binding;
- recovery-case idempotency and uncertain provider outcomes;
- key-state transition and partial rotation;
- historical verification across signing-key rotation/revocation;
- audit sink outage and tamper detection;
- CI production-endpoint isolation;
- no transition from key recovery success to D6/D7 writer readiness.

Fixture implementation/execution requires separate authorization.
