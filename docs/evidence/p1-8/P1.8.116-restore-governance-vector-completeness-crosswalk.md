# P1.8.116 — Restore Governance Vector Completeness Crosswalk

**Version:** P1.8.116-v1  
**Closes:** IR115-01 (documentary design clarification)  
**Status:** DOCUMENTARY CONTRACT — NOT IMPLEMENTED / NOT ACTIVE / NOT AUTHORIZED

## 1. Purpose and boundary

This document closes the missing revision-domain crosswalk between P1.8.110 restore reconciliation and the complete P1.8.93 protected decision vector.

It defines the minimum evidence that must be reconciled at one restore cut. It does not select a registry, transaction coordinator, provider, identity system, or storage backend. It does not execute or authorize restore, lifecycle mutation or deletion.

## 2. Normative completeness rule

A Restore Governance Binding MUST include a versioned, immutable crosswalk to **every applicable field** of the P1.8.93 protected decision vector for the exact restore scope. The binding MUST identify the authoritative source, immutable revision/sequence, scope, evidence reference and reconciliation result for each field.

The binding consists of:
- Restore Run ID and Restore Epoch;
- Governance Epoch and issuer evidence;
- exact snapshot identity, generation and consistency point;
- authenticated contiguous operation-history high-water mark (HWM);
- governance reconciliation cut ID;
- versioned protected-vector schema ID;
- per-domain revision/evidence entries below;
- canonical manifest/digest of the complete binding;
- explicit completeness result and unresolved-item list.

A digest proves integrity of the included bytes, not completeness of the required domains. Completeness requires a schema-versioned inventory of required domains and a result for each one.

## 3. P1.8.93 field-by-field crosswalk

| P1.8.93 protected field | Required restore-bound evidence |
|---|---|
| Request ID and immutable approval-package digest | Exact request/approval identities relevant to any in-scope operation, including terminal/unknown status |
| Exact operation and object identity | Operation type, immutable object identity, dataset/version and exact scope |
| Object generation/version/ETag | Snapshot generation plus reconciled current generation; no substitution by name/path |
| Dataset and immutable dataset-version identity | Canonical dataset/version identity and lineage manifest |
| Lifecycle-policy revision | Authoritative policy revision and classification revision effective at the reconciliation cut |
| Dependency-registry revision | Registry revision plus exact unresolved dependency set |
| Consumer availability-declaration revision / owner-attestation reference | Per applicable consumer: consumer identity, exact declaration revision, attestation identity/revision, scope and validity/reconciliation state |
| Hold-registry revision and exact applicable hold scope | Hold revision, active/revoked status, scope, issuer and effective ordering evidence |
| Copy/backup/recovery disposition revision | Per source and copy: disposition revision, copy identity/generation, restore/recovery relationship and evidence reference |
| Authorization ID, executor identity and revocation epoch | Authorization/revocation revision and proof that pre-restore capabilities are invalidated |
| Mutation ID and idempotency key | Per-object operation identity and deduplication/reconciliation state |
| Trusted ordering/validity evidence | Trusted-time/order evidence and policy/profile revisions required by P1.8.107/P1.8.112 |
| Verifier and audit-evidence requirements | Verifier profile/revision, audit policy revision, evidence availability and unresolved verification state |

A field may be represented by a parent revision only if the authoritative schema explicitly guarantees that the parent revision transitively commits to the exact child record set. The binding MUST name that schema guarantee and include a verifiable child-set digest or equivalent proof. A generic registry revision, object manifest or snapshot digest MUST NOT be assumed to cover consumer attestations or copy/recovery dispositions.

## 4. Reconciliation cut and atomicity

All entries MUST refer to one logically consistent reconciliation cut. Where source systems cannot share a transaction, the binding MUST carry a proven cross-domain ordering/consistency token or an independently verified reconciliation protocol that proves no relevant update was omitted.

If a domain is unavailable, has a gap, has non-contiguous history, has conflicting revisions, cannot prove its scope, or cannot be tied to the same cut, the binding is INCOMPLETE and the restore remains QUARANTINED.

A later governance event invalidates the prior binding for decisions affected by that event. A restore epoch MUST NOT silently reuse a prior authorization, approval or mutation capability.

## 5. Fail-closed cases

| Condition | Required disposition |
|---|---|
| Missing protected-vector domain | INCOMPLETE / QUARANTINED |
| Consumer declaration exists but attestation/revision cannot be authenticated | UNKNOWN / QUARANTINED |
| Copy manifest exists but disposition revision is absent | UNKNOWN / QUARANTINED |
| Snapshot and operation-history HWM do not share a proven cut | QUARANTINED |
| HWM has gaps or unauthenticated segments | QUARANTINED |
| Revision changes during reconciliation | Restart reconciliation under a new cut; old binding invalid |
| Parent revision is claimed to cover child records without schema proof | NOT VERIFIED / QUARANTINED |
| Pre-restore authorization appears current after restore | Treat as invalid; require new authorization under the new governance epoch |

No timeout, heartbeat absence, snapshot age or successful restore response releases quarantine.
