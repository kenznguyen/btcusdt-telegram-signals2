## 2. DEC-01 — Signing-key revocation: option C approved

### Normative direction

1. A key whose revocation is authoritative and effective must not authorize events outside its permitted validity interval.
2. If the verifier cannot establish key status, trusted signing time, or the applicable revocation policy, the event must be rejected or quarantined; it must never be silently accepted.
3. An event claiming to have been signed before revocation is not automatically valid. It may be accepted only if trusted timestamp evidence and the versioned policy establish that it falls within the key's permitted interval.
4. If the revocation authority or status service is unavailable, stale beyond the eventual configured maximum cache age, or contradictory, fail closed and quarantine/reject according to the implementation's auditable reason code.
5. Preserve key ID, public-key fingerprint, policy version, trusted timestamps, status source/version, decision and reason. Never log private key material.

### Parameters deliberately not yet selected

The following must be frozen in a later detailed specification before V07:

- old/new key rotation overlap interval;

- reason-code taxonomy and audit retention.

## 3. DEC-02 — Checkpoint membership: option C approved

### Normative direction

Use a hybrid policy with three distinct responsibilities:

- **Event time (occurred_at) plus watermark:** determines the logical event-time window and whether the window is sufficiently complete to be considered for sealing.
- **Commit time (committed_at):** proves that an event is durably committed before it can be included in a sealed checkpoint.
- **Seal time (sealed_at) and boundary (boundary_at):** freeze the checkpoint membership decision and its immutable audit record.

Required invariants:
1. An event cannot enter a checkpoint unless it satisfies the versioned event-time/window and watermark rule and has durably committed before the applicable seal gate.
2. A checkpoint's membership and digest are immutable after seal.
3. An event arriving or committing too late for a sealed checkpoint must not be silently inserted into or used to rewrite that checkpoint.
4. Late events must use a separately versioned late-event/correction path, preserving original event identity, original checkpoint reference, correction lineage and audit history.
5. Missing, invalid, future-dated or untrusted timestamps cannot be guessed; hold/reject/quarantine according to a predeclared reason.
6. Boundary equality, watermark advancement, allowed lateness, correction sequencing and replay behavior must be deterministic and reproducible.

### Parameters deliberately not yet selected

The following must be frozen before V08:
- watermark generation and advancement rule;
- allowed lateness / grace interval;
- exact inclusion rule at boundary_at equality;
- authoritative clock and maximum clock uncertainty;
- late-event/correction record schema and downstream reconciliation behavior;
- behavior when a checkpoint seal races a durable event commit.

**Gate:** DEC-02 direction is APPROVED. V08 remains BLOCKED until these parameters, fixtures and barrier schedules are versioned. This document does not authorize checkpoint implementation or execution.
