# P1.8.82 — Deletion Authorization and Execution Contract

Date: 2026-11-09
Status: **DESIGN ONLY — NOT IMPLEMENTED / NOT ACTIVE / NOT AUTHORIZED**

## 1. Purpose and boundary

This contract specifies the authorization and execution boundary after a dataset/version has passed a read-only eligibility review. It complements:
- `docs/architecture/DATA_DELETION_SAFETY_CONTRACT.md`;
- `docs/architecture/CENTRAL_DATA_LIFECYCLE_POLICY.md`;
- `docs/architecture/DATASET_CONSUMER_CONTRACT.md`;
- `docs/evidence/p1-8/P1.8.80-retention-and-eligibility-policy.md`;
- `docs/evidence/p1-8/P1.8.81-dependency-and-consumer-governance-contract.md`.

It is a logical contract only. It does not define a production API, schema, workflow, credential, storage adapter, executor, scheduler, or operational runbook. It does not authorize a deletion dry-run against real storage or any destructive action.

**Core rule:** eligibility, approval, execution authorization, execution, and independent verification are distinct gates. Passing one gate never implies permission to pass the next.

## 2. Authority model and separation of duties

### 2.1 Roles

| Role | Permitted responsibility | Prohibited authority |
|---|---|---|
| Requester | Submit a purpose-bound request for an exact immutable scope | Cannot approve own request, grant execution authority, or execute |
| Dataset steward | Attest identity, classification, provenance, owner obligations and impact | Cannot unilaterally approve shared-data deletion |
| Consumer owner | Confirm, dispute or release only its own exact dependency | Cannot release another consumer's dependency or approve dataset deletion |
| Lifecycle reviewer | Assess retention, eligibility, holds, dependencies, copies, archive alternatives and evidence | Cannot modify evidence to manufacture eligibility |
| Independent approver | Approve/reject the exact request and evidence package | Cannot widen scope, act as requester, or execute the deletion |
| Execution authority | Perform final rechecks and issue a narrow execution authorization | Cannot change the approved manifest or waive failed gates |
| Storage executor | Execute only the authorized operation on exact object identities | Cannot assess eligibility, approve, release dependencies, widen scope or make policy decisions |
| Independent verifier | Verify actual post-operation state and residual objects independently of executor result | Cannot rely solely on executor exit code or self-attestation |
| Auditor | Read the complete decision and evidence chain | No implicit mutation or execution authority |

### 2.2 Separation rules

1. Requester and independent approver must be distinct authenticated principals.
2. The lifecycle reviewer must not be the sole approver of the same request.
3. The storage executor must not approve the request or issue its own execution authorization.
4. The independent verifier must be independent of the executor's success assertion and execution process.
5. A single human may hold multiple operational roles in a personal project only if a separately approved compensating-control design proves equivalent independence. No such exception is currently approved.
6. Role delegation must be explicit, scoped, attributable, revocable and auditable; shared credentials are prohibited.
7. Missing identity, ambiguous delegation, unavailable approver, or unverifiable separation fails closed.
8. No quorum or minimum approver count is inferred here. The approval model remains an owner decision.

## 3. Immutable request and manifest contract

Every request must bind to a canonical immutable manifest. The manifest must contain, at minimum:

- request ID and schema/manifest version;
- exact dataset ID, immutable dataset version and object identities;
- storage namespace/provider/account/container/table/database identity as applicable;
- object generation/version identifiers where the storage system supports them;
- exact operation requested and its semantic effect;
- source lineage, copy identity and copy class;
- object count, byte/count summary where measurable, and completeness declaration;
- cryptographic digest algorithm identifier and digest over canonicalized manifest bytes;
- classification, steward and requester identity;
- retention/eligibility policy version;
- dependency-registry decision revision and consumer release evidence references;
- holds, incident/legal/audit/recovery checks and their evidence references;
- archive/rebuildability assessment and copy disposition references;
- evidence timestamps, provenance and freshness decision reference;
- required post-operation verification method and expected residual-state criteria.

### 3.1 Scope constraints

- No wildcard, mutable alias, prefix, broad predicate, dynamic query, “older than” selector or runtime-discovered expansion may be authorized directly.
- If a query is used during discovery, its result must be materialized into a fixed manifest, independently reviewed, and frozen before approval.
- Manifest canonicalization and digest rules must be deterministic and versioned. The exact encoding, hash algorithm and signing format remain OPEN.
- Any object addition, removal, replacement, version change, operation change, digest mismatch or scope ambiguity creates a new request and invalidates prior approvals.
- Storage identity must be resolved to immutable object identity immediately before authorization and rechecked by the executor before mutation.
- If the storage system cannot provide stable object identity or enforce exact-scope preconditions, that adapter is not eligible for destructive use.

## 4. Approval package and invalidation

The approval package is an immutable snapshot containing:
1. canonical manifest and digest;
2. request purpose and rationale;
3. eligibility assessment and class policy;
4. dataset steward attestation;
5. authoritative dependency-registry decision point and all unresolved-dependency results;
6. holds and legal/incident/security/audit checks;
7. recovery, rebuildability and archive alternative evidence;
8. complete copy/backup/replica/export disposition analysis;
9. requester, reviewer and approver identity/delegation evidence;
10. proposed operation, exact target adapter and verification plan;
11. policy/contract versions and evidence provenance.

An approval is valid only for this exact package. It is invalidated by any change to:
- manifest bytes/digest, dataset version, object generation or operation;
- policy/contract version or applicable classification;
- dependency, hold, owner, copy inventory or recovery state;
- evidence integrity or approved freshness status;
- requester, reviewer, approver, delegation or target executor/adapter;
- authorization conditions or required verification method.

An invalidated approval returns the request to the appropriate review stage. It must never be silently carried forward.

## 5. Authorization lifecycle

Logical states:

`REQUESTED → REVIEWED_ELIGIBLE → APPROVED → FINAL_RECHECK → AUTHORIZED → EXECUTING → RECONCILIATION_REQUIRED → VERIFIED_COMPLETE`

Alternative terminal/pre-execution outcomes: `REJECTED`, `CANCELLED`, `EXPIRED`, `INVALIDATED`.

These labels are conceptual design states, not runtime enums.

### 5.1 Independent approval

- Approval must identify the exact manifest digest, policy version, operation, conditions, approver and evidence package.
- Approval is a decision on the request; it is not a storage capability or permission to execute.
- Silence, timeout, lack of objection, consumer ACK, owner inactivity or prior approval of a similar request is not approval.
- Approval must be explicit, authenticated, attributable and durably recorded.
- A request that changes after approval requires fresh review and approval.

### 5.2 Grace and cancellation

- A pre-execution review/grace phase may be required by policy, but its duration is OPEN and must not be guessed.
- The request must expose an explicit cancellation path before destructive execution begins.
- Cancellation must be durably recorded and must revoke any not-yet-used execution authorization associated with the request.
- Cancellation racing with authorization or executor start must be serialized by an authoritative state transition. If ordering cannot be proven, block and reconcile.
- Expiry is not approval, release of dependency, or permission to retry.
- No numeric grace period, cancellation deadline, approval expiry or authorization lifetime is selected here.

### 5.3 Final recheck and authorization issuance

Immediately before issuing execution authorization, the execution authority must independently re-evaluate:
- manifest digest and immutable object resolution;
- current policy and classification;
- authoritative dependency registry revision and all dependency/hold states;
- consumer availability and copy/backup disposition;
- incident/legal/security/audit/recovery holds;
- evidence integrity and freshness under an approved policy;
- requester/approver separation and delegation validity;
- adapter capability, exact-scope enforcement and independent verifier readiness;
- cancellation, expiry, prior execution and unresolved reconciliation state.

Any changed, missing, stale, contradictory or unavailable input invalidates the approval and blocks authorization.

The authorization must bind:
- unique authorization ID;
- request ID and exact manifest digest;
- exact operation and target adapter/storage namespace;
- exact object identities and preconditions;
- permitted executor principal/workload identity;
- issue/expiry conditions under an owner-approved lifetime policy;
- unique idempotency key;
- maximum permitted operation scope/count/bytes if measurable and approved;
- required audit event and independent verification contract;
- policy and contract versions.

The authorization must be single-purpose and non-transferable. It cannot be reused for a different manifest, operation, adapter, object generation or request.

## 6. Executor capability boundary

The executor is a constrained mechanism, not a policy engine.

Before each destructive mutation it must:
1. authenticate its workload identity;
2. validate authorization authenticity, validity, revocation and exact scope;
3. verify manifest digest and object generation/preconditions;
4. confirm the request is not cancelled, invalidated, expired or already in unresolved execution;
5. enforce object-level allowlist and operation restrictions;
6. record a durable intent before mutation where the adapter can support it;
7. perform only the authorized operation;
8. record per-object outcomes and evidence without exposing deleted payload or secrets.

The executor must not:
- discover additional targets and add them to the manifest;
- expand prefixes, aliases, predicates or wildcards;
- release dependencies or holds;
- decide retention or eligibility;
- reinterpret archive as deletion or vice versa;
- bypass fencing, storage version preconditions or access controls;
- silently skip failures and report overall success;
- perform cascading deletion of copies, backups, replicas, exports, caches, models, ledgers or evidence;
- retry an ambiguous destructive operation without reconciliation.

If an adapter cannot enforce the required preconditions and scope boundary, execution is blocked for that adapter. Adapter-specific SQLite, PostgreSQL, object-store, backup and archive safeguards remain to be designed in P1.8.83 and subsequent implementation review.

## 7. Idempotency, retries and ambiguous outcomes

### 7.1 Idempotency contract

- Every execution intent has a unique idempotency key bound to request ID, authorization ID, manifest digest, operation and adapter.
- Repeating the identical request with the same key must return/reconcile the prior durable outcome, not create a second semantic operation.
- Reusing a key with different content must be rejected and audited.
- Idempotency records must survive the failure/recovery scenarios relevant to the adapter; durability and retention details remain OPEN.

### 7.2 Outcome classes

| Outcome | Required handling |
|---|---|
| NOT_STARTED | Evidence proves no mutation began; authorization may be reconsidered only after fresh checks |
| COMPLETED_PENDING_VERIFICATION | Executor reports completion; independent verifier has not confirmed it |
| PARTIAL | Some exact targets changed and others did not; freeze affected scope and reconcile |
| AMBIGUOUS | Mutation may have occurred but authoritative outcome is unknown; do not retry |
| FAILED_BEFORE_MUTATION | Verified no target changed; preserve evidence and return to review/authorization as appropriate |
| FAILED_AFTER_MUTATION | Some mutation may have occurred; reconciliation required |
| SCOPE_MISMATCH | Actual target differs from authorized manifest/precondition; stop immediately and treat as a safety incident |
| VERIFIED_COMPLETE | Independent verifier confirms all authorized outcomes and residual criteria |

Executor exit code, API response, job status or log message alone cannot establish VERIFIED_COMPLETE.

### 7.3 Retry rule

- Retry is permitted only when the prior outcome is independently established and the same exact idempotency intent is safe to resume under adapter-specific semantics.
- Ambiguous or partial outcomes require reconciliation first.
- A new manifest, authorization or idempotency key must not be generated merely to bypass an unresolved prior operation.
- No blind retry, compensating deletion or inferred rollback is permitted.

## 8. Cancellation, revocation and interruption

- Before execution begins, cancellation/revocation must prevent executor start.
- Once execution begins, revocation prevents any not-yet-started work where safely enforceable; it cannot claim to reverse completed mutations.
- The executor must stop on scope mismatch, authorization invalidity, integrity failure, hold/dependency change, registry uncertainty or adapter safety failure.
- A process crash, network loss, worker restart or lost response transitions the affected request to reconciliation unless durable evidence proves no mutation began.
- Recovery must query authoritative execution records and actual storage state before resuming.
- No automated rollback or compensating deletion is authorized.

## 9. Independent verification and completion

The verifier must be logically and operationally independent from the executor's success assertion and must use a separately defined evidence path.

Verification must establish:
- the exact authorized manifest was the only scope acted upon;
- each target's resulting state matches the requested operation;
- object generations/preconditions were honored;
- no unauthorized adjacent object or copy was changed;
- partial/residual objects, references, indexes, metadata and storage-specific remnants are accounted for;
- required manifests, approvals, audit events and tombstones remain discoverable and intact;
- consumer/dependency and copy lifecycle state remains consistent;
- verification evidence identifies its method, source, timestamp, verifier and policy/contract version.

If a storage backend cannot independently prove absence/presence or residual state, the result remains NOT VERIFIED and the adapter cannot be approved for destructive use.

Completion requires both:
1. executor operation record; and
2. independent verification record.

A successful executor response without independent verification remains COMPLETED_PENDING_VERIFICATION, not complete.

## 10. Audit and evidence requirements

The audit chain must record:
- request, manifest and digest;
- all state transitions and actors;
- reviewer/approver decisions and reasons;
- final recheck inputs and authoritative registry decision point;
- authorization issuance, scope, expiry/revocation and idempotency key;
- executor intent, per-object outcomes and errors;
- cancellation/interruption/reconciliation events;
- independent verification and residual-state results.

Audit records must be tamper-evident under a separately approved evidence-store design. They must not retain deleted payload, credentials, secrets or unnecessary sensitive data. Tombstone and audit retention durations remain OPEN and are not specified by this contract.

## 11. Failure matrix

| Failure | Mandatory behavior |
|---|---|
| Requester equals approver | Reject; separation-of-duties failure |
| Reviewer/approver identity unavailable | Block |
| Manifest/digest changed | Invalidate approval; new review |
| Object generation changed | Block; resolve exact new identity through a new request |
| Policy or hold changes after approval | Invalidate and re-review |
| Registry unavailable or stale | Block authorization |
| Consumer dependency uncertain | Block |
| Copy inventory incomplete | Block |
| Authorization expired/revoked | Do not start; reconcile if already executing |
| Cancellation races with execution | Serialize; if ordering unknown, reconcile |
| Adapter cannot enforce exact scope | Block adapter |
| Lost response after mutation | AMBIGUOUS; no blind retry |
| Partial deletion | Freeze affected scope; reconcile |
| Executor claims success but verifier unavailable | NOT VERIFIED |
| Residual objects or adjacent mutation detected | Reconciliation/safety incident; no further destructive action |
| Audit evidence missing or inconsistent | Block completion; preserve protective state |
