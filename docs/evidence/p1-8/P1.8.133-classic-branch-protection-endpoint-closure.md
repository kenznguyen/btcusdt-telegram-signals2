Official source: GitHub REST API — Protected branches:

## 2. Added candidate endpoint

| ID | Read-only endpoint | Fine-grained permission | Response allowlist | Limitations |
|---|---|---|---|---|
| EP-10 | `GET /repos/{owner}/{repo}/branches/{branch}/protection` | Repository `Administration: read` | required status checks and app IDs; enforce_admins state; required review count; code-owner/stale-review/last-push settings; dismissal restrictions; bypass pull-request allowances; push restrictions; linear-history, force-push, deletion, conversation-resolution and branch-lock settings | Availability depends on repository plan and protection configuration; 404 is not proof that no other ruleset applies |

The endpoint's documented read permission is `Administration: read`. Do not confuse it with the corresponding PUT/DELETE endpoints, which require write permission. The candidate allowlist must reject all write methods.

### 2.1 Response minimization

The response can include user, team and app objects, including identity and URL fields. Persist only the fields required to establish control:
- user: stable ID/login only where needed;
- team: stable ID/slug only where applicable;
- app: stable ID/slug only where applicable;
- booleans, counts, check names and policy values relevant to branch protection.

Exclude avatar URLs, profile URLs, email/contact data, unrelated descriptions and all unneeded nested fields. Do not follow URLs returned in the response. Do not retrieve team membership or app credentials as part of EP-10.

### 2.2 Branch selection

The branch set for a future execution must be frozen in the approved scope manifest. At minimum, consider the repository's default branch if it is returned by the separately approved EP-01 metadata read. Any additional branch requires explicit inclusion in the manifest. Do not enumerate arbitrary branches or infer all branch coverage from one branch response.

### 2.3 Interpretation and gaps

- A successful EP-10 response reports classic protection for that exact branch.
- A 404 may mean protection is not configured or the endpoint is unavailable for the resource/plan; it does not establish absence of repository or organization rulesets.
- EP-07 repository rulesets and EP-08 active branch rules remain required complementary surfaces.
- The response's bypass/dismissal/restriction fields must be interpreted as the exact documented configuration, not as a complete graph of every actor able to administer or bypass it.
- Organization-level inherited settings and actors remain UNKNOWN unless independently covered by a separately approved source.
- If the endpoint omits a field, is inaccessible or returns a partial object, record UNKNOWN/NOT VERIFIED for that control.
