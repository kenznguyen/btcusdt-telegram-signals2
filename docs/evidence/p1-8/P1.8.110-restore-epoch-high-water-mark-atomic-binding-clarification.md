# P1.8.110 — Restore Epoch / High-Water-Mark Atomic Binding Clarification

**Version:** P1.8.110-v1  
**Closes:** P1.8.109 IR109-01 (MAJOR)  
**Depends on:** P1.8.93, P1.8.105, P1.8.107, P1.8.109  
**Type:** Documentation-only contract clarification  
**Status:** DESIGN CLARIFICATION RECORDED — ISSUER/IMPLEMENTATION OPEN — RESTORE NOT AUTHORIZED

## 1. Purpose and boundary

This clarification removes ambiguity between Restore Run ID, Restore Epoch, Governance Epoch and the operation-history high-water mark. It defines their distinct identities and the atomic binding that a future implementation must prove.

It does not select an epoch issuer, event store, transaction coordinator, provider, numeric encoding or runtime design. It does not authorize restore, staging, reconciliation execution, mutation or deletion.

## 2. Normative identity separation

The following values MUST remain distinct:

| Value | Meaning | Mutability |
|---|---|---|
| Restore Run ID | One attempted restore/recovery procedure | Unique per attempt |
| Restore Epoch | Recovery generation for the restored environment/scope | Newly issued for each accepted restore attempt |
| Governance Epoch | Lifecycle authority generation that fences decisions and authorizations | Monotonic in its authoritative governance domain |
| Snapshot ID + consistency point | Exact data snapshot and its declared cut | Immutable reference |
| Operation-history HWM | Exact last contiguous, independently authenticated operation-history position included in reconciliation | Immutable per reconciliation manifest |
| Governance revision vector | Exact policy, dependency, hold, revocation, tombstone and authorization-revocation revisions | Pinned per decision |

No timestamp, snapshot sequence, database sequence, Restore Run ID or host clock may substitute for another value.

## 3. Required binding record

A future restore-boundary record MUST bind, as one immutable versioned record:

- restore_run_id;
- restore_epoch and its issuer/authority evidence;
- governance_epoch and its issuer/authority evidence;
- exact snapshot_id and consistency_point;
- operation_history_source_id and history partition/stream identity;
- operation_history_hwm, including partition positions where the source is partitioned;
- proof that the HWM is contiguous and authenticated, with explicit gap detection;
- governance revision vector at the same declared reconciliation cut;
- exact restore scope, dataset/version and object/copy manifest digest;
- issuance and observation evidence with trusted-time semantics under P1.8.107;
- unique binding-record ID, policy/profile revision and verifier result.

A record with a missing field, unproven source, gap, ambiguous cut or mismatched scope is INVALID and leaves the scope QUARANTINED.

## 4. Ordering and atomicity requirements

1. Restore Epoch and Governance Epoch are separately identifiable values, even if a future authority emits them in one signed envelope.
2. The authoritative issuer MUST guarantee uniqueness within its declared scope and reject reuse or rollback. The mechanism and guarantee remain OPEN.
3. A restore attempt MUST acquire an exclusive, fenced recovery generation before it can publish a reconciliation cut. Concurrent attempts for the same governed scope MUST be serialized by an authoritative mechanism; a client-side mutex or wall-clock order is insufficient.
4. The new Governance Epoch, operation-history HWM and governance revision vector MUST be atomically bound to the same reconciliation decision/cut. If the selected systems cannot share a transaction, a separately proven linearizable protocol is required. Sequential reads followed by an unrelated write are insufficient.
5. A second restore, epoch change, governance revision change or history advancement before finalization invalidates the earlier uncommitted binding. The earlier attempt remains historical and quarantined; it cannot overwrite the newer generation.
6. The finalization event MUST be durably recorded before any readiness proposal. The event must include the binding-record digest and exact predecessor/fencing token.
7. No global ordering is inferred between unrelated scopes unless the future authority explicitly proves it.

## 5. Required state dispositions

| Condition | Required disposition |
|---|---|
| Both epochs independently verified and HWM/revision vector atomically bound | Binding may proceed to remaining reconciliation gates |
| Restore Epoch available but Governance Epoch missing/stale | QUARANTINED |
| Governance Epoch valid but HWM has a gap or is unauthenticated | NOT_READY |
| HWM valid but governance revision vector is from a different cut | REJECT_BINDING / QUARANTINED |
| Concurrent restore or epoch supersession detected | Earlier attempt FENCED; reconcile, do not finalize |
| Issuer unavailable, rollback possible or uniqueness unproven | BLOCKED |
| Ordering or atomic coupling cannot be proven | UNKNOWN / HOLD |
| Snapshot claims a newer epoch without independent issuer proof | Reject snapshot claim |

## 6. Authorization consequences

- Every pre-restore execution authorization remains invalid, regardless of its encoded epoch or expiry.
- A binding record does not create a new deletion authorization.
- Restore READY remains a scoped recovery-readiness result only.
- A new lifecycle decision, independent approval, exact-scope execution authorization and P1.8.93 mutation-boundary fence would still be required for any future destructive operation.
- No consumer, T0/T1 layer, storage adapter or restore worker may mint or advance Governance Epoch by itself.

## 7. Documentary fixture requirements

Future frozen tests must cover: concurrent restore attempts; duplicate epoch issuance; epoch rollback after snapshot restore; HWM gap; HWM partition mismatch; governance revision vector from a different cut; HWM advancing during binding; second restore superseding the first; issuer outage; valid epochs with mismatched scope; replay of the same binding record; and stale pre-restore authorization reuse.

Expected results are deterministic reject, fence or quarantine. These are specification cases only; no test code or execution is included.

## 8. OPEN items

Epoch issuer and trust model; monotonicity/rollback proof; uniqueness scope and encoding; concurrency serialization mechanism; operation-history source and partition semantics; HWM completeness proof; transaction/linearizability mechanism; trusted-time profile; identity and reviewer roles; retention and audit guarantees remain OPEN. No numeric or provider-specific value is inferred.
