## 1. Purpose and authority

This addendum resolves the documentary findings IR130-01/02/03 by:
- mapping a conservative set of candidate GitHub REST read endpoints to documented fine-grained permissions;
- distinguishing token permission from the authenticated actor's separate role prerequisites;
- making owner-namespace resolution conditional on repository metadata;
- excluding secret metadata endpoints from the first inventory phase;
- identifying response fields and visibility limitations that prevent unsupported assurance claims.

Official GitHub REST documentation consulted for this design is listed in Section 7. This is documentation research only. No endpoint was called, no live repository metadata was inspected, and no credential was used.

P1.8.131 does not authorize inventory execution. P1.8.129 remains NOT APPROVED FOR EXECUTION pending separate owner approval.

## 2. Owner namespace resolution and bounded scope

The locator `kenznguyen/btcusdt-telegram-signals2` does not by itself prove whether `kenznguyen` is a personal account or an organization. Do not assume an organization.

The first candidate endpoint, if separately approved, is:
- `GET /repos/{owner}/{repo}`

Use only an explicit response allowlist:
- repository `id`, `node_id`, `name`, `full_name`, `visibility`, `archived`, `disabled`, `default_branch`;
- owner `id`, `login`, `type`.

Never persist the full unfiltered response. GitHub documents that `temp_clone_token` may appear in a repository response; treat it as sensitive and exclude it before any evidence persistence. Also exclude unrelated security/configuration fields unless separately approved.

The returned owner `type` determines the next scope:
- If `User`: no organization-level endpoint is applicable merely because the account owns a repository. Do not perform an organization sweep.
- If `Organization`: parent-organization policy may be read only for the minimum policy values that directly govern this repository, subject to a separately approved organization metadata scope and the endpoint matrix below.
- If owner type is absent, ambiguous or inconsistent: stop owner-scope expansion and mark inherited organization scope UNKNOWN/NOT VERIFIED.

The branch name in P1.8.129 is documentary source context, not an API authorization boundary.

## 3. Candidate endpoint matrix — repository metadata phase

The following matrix is a design allowlist, not a call list. All rows require a future explicit owner approval. Permission names below refer to fine-grained personal access token / GitHub App permission categories as documented by GitHub; exact credential type and endpoint availability must be rechecked at execution time.

| ID | Read-only endpoint | Documented fine-grained permission | Response handling / limits | Decision |
|---|---|---|---|---|
| EP-01 | `GET /repos/{owner}/{repo}` | Repository `Metadata: read` | Strict allowlist of repository identity/status and owner `type`; exclude `temp_clone_token` and all unneeded fields | Candidate |
| EP-02 | `GET /repos/{owner}/{repo}/actions/permissions` | Repository `Administration: read` | Actions enabled/allowed policy only; never call corresponding PUT endpoints | Candidate |
| EP-03 | `GET /repos/{owner}/{repo}/actions/permissions/workflow` | Repository `Administration: read` | Default GITHUB_TOKEN permission and PR-approval setting; read only | Candidate |
| EP-04 | `GET /repos/{owner}/{repo}/actions/permissions/selected-actions` | Repository `Administration: read` | Conditional: only if EP-02 reports `allowed_actions=selected`; read only | Conditional candidate |
| EP-05 | `GET /repos/{owner}/{repo}/actions/workflows` | Repository `Actions: read` | Workflow IDs, names, state and paths/metadata only; no workflow file contents, run logs or dispatch | Candidate |
| EP-06 | `GET /repos/{owner}/{repo}/environments` | Repository `Actions: read` | Allowlist environment ID/name and protection-rule type/required-reviewer metadata; minimize personal/team fields | Candidate |
| EP-07 | `GET /repos/{owner}/{repo}/rulesets` | Repository `Metadata: read` | Ruleset metadata; `bypass_actors` is not returned to callers without write access to the ruleset, so bypass actor coverage remains UNKNOWN | Candidate with limitation |
| EP-08 | `GET /repos/{owner}/{repo}/rules/branches/{branch}` | Repository `Metadata: read` | Active rules applying to the specified branch; disabled/evaluate rulesets are not returned; not a complete substitute for EP-07 | Candidate with limitation |
| EP-09 | `GET /orgs/{org}/actions/permissions` | Organization `Administration: read` | Only if EP-01 proves owner type `Organization`; parent policy only; separately approve this organization-scoped permission | Conditional candidate |

The endpoint matrix does not authorize:
- any POST, PUT, PATCH or DELETE request;
- endpoints that mint registration/JIT tokens or credentials;
- workflow dispatch, enable/disable, rerun, approve or cancel actions;
- any endpoint whose required permission is write;
- broad organization enumeration unrelated to this repository.

### 3.1 Explicitly excluded endpoints and reasons

| Endpoint family | Reason for exclusion |
|---|---|
| `GET /repos/{owner}/{repo}/actions/runners` | Although the fine-grained permission is documented as repository `Administration: read`, GitHub also states the authenticated user must have repository admin access. Do not use an admin-role collector for this inventory. Runner inventory/assignment remains UNKNOWN. |
| `GET /repos/{owner}/{repo}/collaborators` | GitHub states the authenticated user must have write, maintain or admin privileges on the repository. A token permission label of `Metadata: read` does not remove this actor-role prerequisite. Exclude rather than use a privileged collector. |
| `GET /repos/{owner}/{repo}/actions/secrets` | Secret metadata is excluded by default in this first phase. Secret names and timestamps can themselves disclose sensitive operational information. No secret endpoint is required for the initial repository-policy inventory. |
| `GET /repos/{owner}/{repo}/actions/organization-secrets` | Excluded with all secret metadata endpoints; organization-wide secret binding is not required for the initial phase. |
| `GET /repos/{owner}/{repo}/environments/{environment_name}/secrets` | Excluded with all secret metadata endpoints. |
| `GET /repos/{owner}/{repo}/actions/secrets/public-key` | Excluded; returns key material used in secret-management operations and is unnecessary for read-only policy inventory. |
| `GET /repos/{owner}/{repo}/keys` | Excluded from first phase; response includes SSH public-key material. Deploy-key authority cannot be fully inventoried under this metadata-only allowlist and remains UNKNOWN. |
| Any repository Contents/Git data endpoint | Excluded; source-content review requires separate proposal and approval. |

A 403, 404, missing field or empty response is not proof that a control, actor or credential does not exist. Record the exact visibility limitation and mark the affected scope UNKNOWN/NOT VERIFIED.

## 4. Actor-role prerequisites versus token permissions

For every candidate endpoint, separately record:
1. token/App fine-grained permission category and access level;
2. authenticated principal's actual GitHub role/eligibility prerequisite;
3. resource owner type and repository scope;
4. whether endpoint response is complete for the claim being assessed.

A token configured with read permissions is not sufficient evidence that the authenticated actor is a non-privileged identity. Conversely, an endpoint's read permission does not prove the endpoint reveals every relevant bypass actor or inherited grant.

If an endpoint requires the collector to hold write, maintain or admin privileges, it is excluded from this least-privilege collection phase. Do not use a privileged actor simply to increase inventory coverage.

## 5. Secret-metadata safety decision

Secret metadata is **excluded by default** from P1.8.129 Phase 1 and from this first execution proposal.

GitHub's documented list endpoints return metadata without revealing encrypted secret values, but the metadata includes names and timestamps and may include visibility/selected-repository information. This is still sensitive operational metadata. The inventory does not need it to establish the initial repository policy baseline.

Any later request to collect secret metadata must be a separate opt-in proposal with:
- exact endpoint and fine-grained permission;
- explicit metadata fields to be retained;
- response-schema review against the current official docs;
- an allowlist filter applied before logging, display or persistence;
- proof that no encrypted value, public-key material or unexpected field is retained;
- separate owner approval.

If response shape changes or filtering cannot be proven safe, do not call the endpoint and retain UNKNOWN/NOT VERIFIED.

## 6. Acceptance limitations

Even after a future approved collection of EP-01 through EP-09:
- collaborator roster may remain UNKNOWN because the documented endpoint requires a privileged actor;
- runner identities/assignment may remain UNKNOWN because the documented repository endpoint requires repository admin access;
- ruleset bypass actors may remain UNKNOWN because GitHub withholds `bypass_actors` unless the caller has write access to the ruleset;
- deploy-key metadata remains UNKNOWN because its endpoint is excluded;
- secret-derived credential provenance remains UNKNOWN because secret metadata is excluded;
- workflow source, third-party action pinning, artifact/cache provenance and untrusted input flow remain UNKNOWN because repository contents are excluded;
- external provider, OIDC trust and organization-level identity paths remain NOT VERIFIED unless a separate scope-specific proposal is approved.

Therefore this metadata-only phase cannot by itself establish a complete technical Option C enforcement PASS. It can produce bounded partial evidence and identify which remaining claims need separate safe evidence.
