## 1. Decision status and binding baseline

The approved policy directions remain unchanged:
- DEC-01 = C: quarantine/fail-closed whenever key validity, trusted signing time or revocation state cannot be proven.
- DEC-02 = C: hybrid event-time + watermark + durable commit-time checkpoint membership, immutable sealed checkpoints and an explicit late-event/correction path.
- DEC-03 = B: RPO/RTO values remain planning targets only, not approved SLOs or measured capabilities.

P1.8.33 does not reopen or weaken those policy directions. It asks the owner to resolve the detailed parameters needed to construct deterministic fixtures and a later, separately authorized staging proposal.

### Decision vocabulary

- **Owner decision required:** select one policy behavior or approve an exact parameter value.
- **Evidence-derived value:** must be measured from a defined dataset/environment before it can be proposed; do not guess it.
- **Implementation-specific value:** must be taken from the selected provider/database/runtime contract after that choice is separately made.
- **Not authorized:** no live key action, provider selection, provisioning, restore, fault injection or workflow dispatch is permitted by this package.

## 2. DEC-01 / V07 — Revocation parameter decisions

### 2.1 Recommended control model

Retain the approved C behavior:
1. Unknown, unavailable, stale, contradictory or unverifiable revocation state fails closed.
2. Ambiguous events are quarantined with a stable reason code and immutable audit record.
3. A claimed pre-revocation event is eligible for acceptance only when a trusted timestamp proof establishes signing time inside the key's permitted validity interval and the owner-approved historical-event rule permits it.
4. No client-supplied timestamp alone can establish signing time.
5. Quarantine release is a separately authorized, auditable decision; it must not silently rewrite the original decision.

This is a recommendation for implementing the approved policy, not authorization to provision or operate keys.

### 2.3 Required V07 fixture matrix

Freeze fixture bytes and expected outcomes for:
- active key / valid timestamp;
- event signed before revocation and received after revocation;
- event signed at exact revocation effective time;
- event signed after effective revocation;
- timestamp authority unavailable, stale, contradictory or proof-invalid;
- cache age just below, exactly at and just above the selected maximum;
- propagation at and beyond the selected bound;
- old/new key immediately before, at and after rotation boundaries;
- expired key, unknown key and revoked key;
- quarantine release by authorized and unauthorized principals;
- deterministic replay of each decision.

Every fixture must record key ID, public-key fingerprint, policy version, signed_at proof reference, received_at, revoked_at, cache age, authority version, reason code and final disposition. Never place private keys or credentials in evidence.

### 2.4 V07 exit criteria

V07 can move from BLOCKED to READY-FOR-REVIEW only when:
- all V07-D1 through V07-D9 decisions are recorded with units and boundary semantics;
- trust-anchor and proof-validation design has independent security review;
- all fixtures and expected outcomes are immutable and hashed;
- cache and propagation values have evidence or an explicit conservative owner-approved bound;
- no key material is provisioned or operated as part of this documentation gate.

READY-FOR-REVIEW is not execution authorization.

## 3. DEC-02 / V08 — Checkpoint parameter decisions

### 3.1 Recommended control model

Retain the approved hybrid model:
- event time selects logical window membership;
- watermark declares event-time completeness;
- durable commit time proves the event was persisted before the seal gate;
- checkpoint sealing is immutable;
- late events after seal use a separately sequenced and auditable correction path.

A checkpoint must not be declared complete merely because a wall-clock timer elapsed or because an event-time interval ended.

### 3.2 Owner decision register

| ID | Parameter / decision | Choices or required input | Recommended disposition | If unresolved |
|---|---|---|---|---|
| V08-D1 | Window convention | Interval shape, timezone, precision and calendar/session rules | Prefer UTC and a half-open interval [start,end) to avoid double membership at adjacent boundaries; owner must approve | BLOCK V08 |
| V08-D2 | Watermark algorithm | Source of watermark, monotonicity, advancement trigger and idle-partition handling | Monotonic watermark derived from explicitly tracked source progress; do not infer from local timer alone | BLOCK V08 |
| V08-D3 | Allowed lateness | Exact duration and units; whether global or partition-specific | Derive from measured event-ingestion lateness distribution plus explicit risk margin; no guessed value | BLOCK V08 |
| V08-D4 | Watermark equality | Whether watermark == window end is sufficient to seal | Define one exact comparison rule and test equality; no implementation-default ambiguity | BLOCK V08 |
| V08-D5 | Clock source/uncertainty | Authoritative clock, synchronization method, maximum uncertainty and behavior when exceeded | Record source and measured uncertainty; if uncertainty exceeds approved bound, hold/quarantine rather than guess | BLOCK V08 |
| V08-D6 | Commit-time source | DB commit timestamp, durable WAL/transaction marker or equivalent provider-specific proof | Use the actual durable commit boundary of the selected persistence implementation; must be verified, not assumed | BLOCK V08 |
| V08-D7 | Seal/commit race | Serialization/barrier rule when eligible event commit races with checkpoint seal | One deterministic linearization point: commit before seal gate is eligible; after gate is excluded from sealed checkpoint and routed to correction | BLOCK V08 |
| V08-D8 | Late-event correction | Correction event schema, sequence, parent checkpoint, reason, replay/idempotency and downstream reconciliation | Append-only correction lineage; never mutate sealed checkpoint contents | BLOCK V08 |
| V08-D9 | Invalid/future timestamp | Maximum future skew and missing/malformed timestamp handling | Reject/quarantine; numeric skew limit must be measured/approved | BLOCK V08 |

### 3.3 Required V08 fixture matrix

For each configured boundary, create fixtures at:
- one precision unit before the boundary;
- exactly equal to the boundary;
- one precision unit after the boundary.

Also include:
- watermark below, equal to and above window end;
- event received before and after allowed-lateness cutoff;
- event committed immediately before and after seal barrier;
- commit/seal race under deterministic barriers;
- idle and delayed source partition;
- missing, malformed, future-dated and excessive-clock-uncertainty event;
- late event after seal and correction replay/duplicate;
- correction ordering, correction chain break and correction conflict.

The fixture oracle must assert membership, seal eligibility, checkpoint digest immutability, correction lineage and idempotent replay.

### 3.4 Evidence-derived parameter workflow

Do not choose allowed lateness by intuition. A future read-only measurement proposal should:
1. identify the exact source feed and event population;
2. distinguish event time, first trusted receipt time and durable commit time;
3. report sample size, observation window, missing/outlier policy and clock uncertainty;
4. calculate lateness distributions (including high quantiles and worst observed values);
5. quantify the operational cost of a longer wait versus the risk of late corrections;
6. propose a bound with safety margin for owner review.

No feed collection, VPS read, runtime probe or staging measurement is authorized by this document.

### 3.5 V08 exit criteria

V08 can move from BLOCKED to READY-FOR-REVIEW only when:
- V08-D1 through V08-D9 have exact values, units and equality semantics;
- lateness is supported by an identified measurement set or an explicitly owner-approved conservative bound;
- all boundary/race/correction fixtures and expected outputs are frozen and hashed;
- durable commit evidence is tied to the selected storage implementation;
- independent review confirms sealed checkpoint immutability.

READY-FOR-REVIEW is not execution authorization.

## 4. DEC-03 — Restore measurement and acceptance decisions

### 4.1 Approved planning targets (unchanged)

| Metric | Planning target | What it does not mean |
|---|---|---|
| Acknowledged-transaction RPO | 0 within a declared and tested durability boundary/failure domain | Not zero loss across all provider, region or site failures |
| Snapshot RPO | ≤5 minutes | Not a measured capability until committed-data gap is measured in rehearsals |
| Staging RTO | ≤60 minutes | Not a measured recovery time or production SLO |
| Restore rehearsals | 3 independent runs | Not three retries of one restore or three runs sharing an unexamined single point of failure |

No target is promoted to an SLO by P1.8.33.

| RST-D2 | Durable ACK point | Exact API/observer ACK point, transaction commit boundary, flush/sync semantics and durability level | ACK only after the selected implementation's documented durable commit boundary; prove by transaction IDs and independent observer | BLOCK RPO=0 claim |

| RST-D9 | Rollback/cleanup | Disposable resources, access revocation, deletion verification and evidence retention | Tested cleanup plan and post-cleanup inventory before any execution authorization | BLOCK restore |

### 4.3 Proposed measurement definitions for owner approval

- **Acknowledged transaction RPO:** count and identify every transaction acknowledged before the declared failure cut. After restore, reconcile the exact IDs and payload digests. RPO=0 passes only if every transaction in that declared population is present and valid for the tested failure domain.
- **Snapshot RPO:** record the snapshot's consistent recovery point and compare it with the declared failure cut using the committed-data watermark/transaction population. Report both elapsed time and missing committed transaction IDs; a time-only calculation is insufficient.
- **RTO:** elapsed time from the single approved start event to the moment all frozen service-ready, integrity and reconciliation checks pass. Preserve timestamps and clock uncertainty.
- **Independent rehearsals:** each run has a unique run ID, snapshot ID, target instance/volume identity, manifest, raw logs, restored-state digest and independent artifact-hash verification. Shared provider and source-snapshot dependencies must be disclosed.

These definitions are proposed for owner approval and must be reconciled with the actual selected database/provider contract before testing.

### 4.4 Restore exit criteria

Restore can move from BLOCKED to READY-FOR-REVIEW only when RST-D1 through RST-D9 are frozen, the measurement formula and readiness oracle are independently reviewed, and a separate staging plan identifies exact resources, expiry, cost ceiling, data classification, rollback and approver. No restore rehearsal is authorized by reaching READY-FOR-REVIEW.
