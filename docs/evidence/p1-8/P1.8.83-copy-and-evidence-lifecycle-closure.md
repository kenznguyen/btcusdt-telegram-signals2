# P1.8.83 — Copy and Evidence Lifecycle Closure

Date: 2026-11-09
Status: **DESIGN-ONLY CLOSURE — RUNTIME INVENTORY NOT VERIFIED — NOT IMPLEMENTED / NOT ACTIVE / NOT AUTHORIZED**

## 1. Purpose and scope

P1.8.83 closes the design gaps between:
- `docs/architecture/DATA_COPY_BACKUP_REPLICA_LIFECYCLE_CONTRACT.md`;
- `docs/evidence/p1-8/P1.8.80-retention-and-eligibility-policy.md`;
- `docs/evidence/p1-8/P1.8.81-dependency-and-consumer-governance-contract.md`;
- `docs/evidence/p1-8/P1.8.82-deletion-authorization-and-execution-contract.md`;
- `docs/architecture/DATA_DELETION_SAFETY_CONTRACT.md`.

This supplement defines copy inventory completeness, recovery-chain integrity, evidence/tombstone lifecycle, and storage-adapter safety requirements at the contract level.

It does not inspect or enumerate actual runtime copies, select a provider, implement an adapter, choose a storage topology, define retention durations, or authorize archive, expiry, compaction, cleanup, vacuum, deletion, restore, or other mutation.

**Boundary:** a documented inventory schema is not proof that inventory is complete. A contract for an adapter is not evidence that an adapter exists or is safe.

## 2. Normative invariants

1. Every separately addressable representation is a distinct governed copy, including partial, transformed, compressed, encrypted, temporary, offline and external representations.
2. Source dataset lifecycle, consumer dependency, copy lifecycle, deletion request/execution and evidence lifecycle remain separate state domains.
3. No source-to-copy or parent-to-child disposition cascade is implied.
4. A source hold is protective across every known copy containing, representing or deriving from its scope. Unknown lineage remains protected.
5. Unknown copy identity, location, ownership, completeness, lineage, consistency, key dependency, restore capability or external distribution blocks destructive disposition.
6. Inventory completeness must be demonstrated against declared discovery boundaries; absence from a registry is not proof of absence.
7. A backup is not a verified recovery point until its complete dependency chain and restore result are independently evidenced.
8. Revoking access, expiring credentials, deleting payload, destroying encryption keys and deleting evidence are distinct operations with separate authority and proof.
9. Tombstones and audit evidence must not contain deleted payload, credentials, key material or unnecessary sensitive content.
10. No adapter may claim success solely from an API response, process exit code, object listing, database row count or local log.
11. All unknown, partial, stale, contradictory or ambiguous outcomes remain protective and NOT VERIFIED.
12. T0 remains an independently governed canonical data asset. This contract grants no deletion authority over T0 or its recovery copies.

## 3. Copy identity and inventory completeness

### 3.1 Required copy record

Every discovered copy must be represented by a stable identity record with these fields, where applicable:

| Field | Required meaning |
|---|---|
| Copy identity | Stable copy ID, copy class and identity version |
| Source identity | Dataset ID, immutable version ID, source manifest/digest |
| Location identity | Provider/account/region/namespace/container/database/path or equivalent; secrets excluded |
| Scope | Full, incremental, partition, filtered, transformed, sampled, partial or UNKNOWN |
| Lineage | Parent copy, source objects, transformation and schema/format versions |
| Ownership | Producer, custodian, consumer owner and responsible authority |
| Lifecycle | Current copy state, creation event, last independently verified observation |
| Consistency | Snapshot point, transaction/log sequence, watermark or equivalent |
| Integrity | Digest/checksum evidence, algorithm identifier, verification method and result |
| Dependencies | Consumers, parent/child copies, backup-chain members, indexes, keys and restore prerequisites |
| Holds | Source-inherited holds, copy-specific holds, legal/incident/security/audit holds |
| Recovery | Intended recovery point, dependencies, procedure and restore evidence |
| Distribution | Known recipients, transfer destinations, unmanaged/external destination uncertainty |
| Evidence | Provenance, observation timestamp, source system, collector identity and evidence reference |

A field that does not apply must be explicitly marked NOT_APPLICABLE with rationale. Missing fields must not be silently interpreted as empty or false.

### 3.2 Inventory coverage model

Inventory completeness must be evaluated separately for each discovery boundary:

- authoritative databases and their backup/log chains;
- replicas, snapshots and failover copies;
- object stores, versioned objects and multipart/incomplete uploads;
- filesystem volumes, snapshots and mounted/shared paths;
- exports, downloads, transfer staging and external recipients;
- local/working copies and research workspaces;
- caches, materializations, feature stores and derived datasets;
- model/training/inference artifacts and experiment outputs;
- CI artifacts and evidence bundles;
- tombstone, audit and authorization evidence stores;
- encryption/key-management dependencies and escrow/recovery metadata.

Each boundary receives one of these evidence outcomes:

| Outcome | Meaning | Disposition consequence |
|---|---|---|
| VERIFIED_COMPLETE_WITHIN_SCOPE | Discovery method and boundary are defined, source authority is known, coverage reconciled, exceptions resolved | May be used as one input to review; not an authorization |
| PARTIAL | Some locations, classes, periods or identities are missing | Block |
| UNKNOWN | Discovery boundary or authoritative source is not known | Block |
| CONFLICTED | Sources disagree about identity, count, lineage, state or ownership | Block |
| STALE | Evidence no longer meets an approved freshness rule | Block pending refresh |
| NOT_APPLICABLE | Boundary is explicitly excluded with approved rationale | Scope exclusion only; cannot conceal unknown copies |

A global statement of completeness is valid only if every applicable boundary has a verified outcome and every exception is resolved. No approved freshness window currently exists; therefore no evidence can be promoted to current merely because it is recent by an invented threshold.

### 3.3 Discovery and reconciliation rules

- Compare authoritative source inventories with independent storage observations where available.
- Reconcile object identities, versions/generations, counts, sizes, partitions, backup-chain references, lineage and known recipients.
- Preserve unknown/unregistered copies as protective inventory entries.
- Duplicate-looking objects must not be merged without proof of identical content, semantics, lineage and obligations.
- A missing object may indicate deletion, relocation, access failure, inventory gap or provider inconsistency; classify as UNKNOWN until independently resolved.
- Inventory reconciliation is read-only unless separately authorized for a distinct operational purpose.
- A copy inventory must record its own evidence provenance and cannot self-certify its completeness.

## 4. Backup-chain and recovery-point lifecycle

### 4.1 Recovery-point identity

A recovery point must identify the complete dependency set required to restore it, including where applicable:
- base/full backup;
- incremental/differential members;
- WAL, transaction logs, binlogs or equivalent continuous logs;
- metadata/catalog/schema and tablespace or object manifests;
- encryption key identifiers and key availability evidence (never key material);
- consistency marker, transaction/log sequence and source version;
- restore tooling/procedure and compatible version;
- required configuration and external dependencies.

The recovery point is the unit of recoverability assessment. A file or backup object in isolation is not a recovery point.

### 4.2 Chain integrity rules

- A retained recovery point must retain every required chain member and metadata dependency.
- Removing one chain member is blocked if it invalidates any retained recovery point, unless an independently verified alternative chain satisfies all obligations.
- A newer backup does not automatically supersede an older recovery point; coverage, consistency, obligations and restore proof must be compared.
- Successful upload, checksum match, backup job status or catalog entry does not prove recoverability.
- Restore evidence must name the exact recovery point and chain, target environment class, procedure/tool version, integrity checks, observed outcome and independent verifier.
- A restore test does not authorize deletion of the source or any other backup.
- No restore, chain pruning, backup expiry or key destruction is authorized by this contract.

### 4.3 Recovery disposition states

Conceptual copy-level outcomes:

- RECOVERY_REQUIRED — required by an active obligation.
- RESTORE_EVIDENCE_MISSING — restore capability not demonstrated.
- CHAIN_INCOMPLETE — one or more required dependencies missing or unverified.
- ALTERNATIVE_RECOVERY_VERIFIED — an independently tested alternative satisfies an explicitly approved obligation.
- DISPOSITION_REVIEWABLE — may enter exact-scope review only; not authorization.
- DISPOSITION_BLOCKED — unknown, conflicted, held, incomplete or unsafe.

These are documentary terms, not runtime enums or lifecycle automation.

## 5. Evidence, audit and tombstone lifecycle

### 5.1 Evidence classes

| Evidence class | Examples | Preservation rule |
|---|---|---|
| Decision evidence | Request, eligibility, approvals, authorization, policy/manifest digests | Retain while needed to prove authority and decision lineage |
| Execution evidence | Intent, per-object outcome, adapter response, interruption and reconciliation records | Retain while operation outcome or dispute remains unresolved and thereafter under approved audit policy |
| Verification evidence | Independent before/after observations, residual checks, verifier identity and method | Preserve to substantiate the disposition claim |
| Lineage evidence | Source/version, transformation, model/schema, parent/child and consumer references | Preserve while derived claims, artifacts or obligations depend on it |
| Recovery evidence | Backup chain, restore procedure, consistency point, restore result | Preserve while recovery obligations or claims depend on it |
| Operational evidence | Lease/fencing, writer controls, incident and integrity events | Govern under the relevant operational/audit obligation |
| CI/research evidence | Workflow run, commit SHA, test report, artifact identity and provenance | Do not treat as substitute for production/runtime evidence |

### 5.2 Tombstone minimum content

A tombstone is a metadata statement that a specific object/copy/version has undergone a governed lifecycle event. It is not the deleted payload and is not proof by itself that deletion succeeded.

Where applicable, it records:
- tombstone ID and schema version;
- exact source/copy/object identity and immutable version;
- manifest digest and operation;
- request, approval and authorization identifiers;
- policy and contract versions;
- execution intent and outcome references;
- independent verification reference and result;
- event timestamps and authenticated actor identities;
- reason/category and reconciliation status;
- known residual references or unresolved exceptions.

Tombstones must exclude payload bytes, credentials, tokens, private keys, encryption key material, unnecessary personal data and sensitive content copied from the deleted object. Hashes or identifiers that could expose sensitive content require a separate classification decision.

### 5.3 Evidence integrity and retention

- Evidence authenticity, integrity, retrievability and semantic validity are separate claims.
- Evidence must have provenance, content identity/digest, creation context and verification status.
- Evidence-store failure, missing evidence or digest mismatch blocks completion claims.
- Evidence must be protected from alteration by the actor whose action it proves, subject to a separately designed evidence authority.
- Tombstones and audit records have their own lifecycle and must not be cascaded with payload deletion.
- Deleting or expiring evidence requires a separate exact-scope governance decision and must not erase the minimum record needed to establish prior authority and outcome.
- No numeric retention period, legal hold taxonomy, immutable-storage provider, evidence freshness window or cryptographic scheme is selected here.

## 6. Storage-adapter safety profiles

These profiles state minimum capabilities a future adapter must prove before it can be considered for a separately approved operation. They do not claim that the current system has these capabilities.

### 6.1 SQLite databases and filesystem copies

Required proof before any future destructive adapter approval:
- exact database file identity and stable location/volume identity;
- identification of associated WAL, shared-memory, journal, snapshot and backup files relevant to the operation;
- transaction/consistency boundary and active-reader/writer considerations;
- writer-fencing and lease state resolved by the authoritative T0 governance path;
- backup/restore dependency and integrity evidence;
- prevention of path traversal, symlink substitution, mount/path aliasing and accidental parent-directory scope expansion;
- atomic intent/outcome evidence and independently observable post-operation state;
- proof that an operation cannot remove an active canonical database or required sidecar/backup chain through a broad file match.

No direct T0 SQLite deletion, WAL truncation, checkpoint, vacuum, compaction, file replacement or filesystem cleanup is authorized.

### 6.2 PostgreSQL and compatible relational stores

Required proof:
- exact cluster/database/schema/table/partition/object identity and ownership;
- transaction snapshot/consistency point and active dependency/reference checks;
- WAL/archive chain, base backup, replication slot and replica dependencies where applicable;
- foreign-key, view, materialized-view, trigger, partition and external consumer impact;
- privilege separation and transaction boundaries;
- exact row/object manifest or immutable partition identity; broad predicates are insufficient;
- independent catalog/storage verification and recovery-point proof.

No DROP/TRUNCATE/DELETE/VACUUM, partition detach, WAL removal, slot removal, replica removal or database lifecycle operation is authorized.

### 6.3 Object storage and versioned object stores

Required proof:
- provider/account/region/bucket/container and exact key plus immutable version/generation;
- versioning, retention lock, legal hold, replication, multipart-upload and object-lock semantics;
- exact version deletion versus delete-marker semantics;
- replication status and destination-copy identity;
- inventory/list consistency guarantees and independent version-level lookup;
- lifecycle policy interaction and proof that no provider rule will perform an unapproved cascade;
- per-object outcomes and post-operation version inventory.

A key name alone is not an immutable identity. No bucket lifecycle rule, bulk delete, delete marker, version purge, multipart abort or replication cleanup is authorized.

### 6.4 Exports, local files and external destinations

Required proof:
- exact file/object identity, content digest, format and completeness scope;
- source lineage, classification, owner, custodian and recipient/destination;
- local path and volume identity with symlink/alias protections;
- transfer receipt and recipient acknowledgement as evidence of transfer only, not deletion;
- separate evidence for access revocation, local removal and external recipient disposition;
- bounded claims: an unknown/unmanaged destination prevents claiming global copy removal.

No broad directory cleanup, wildcard file deletion, credential revocation or external deletion request is authorized.

### 6.5 Caches, materializations, features and model artifacts

Required proof:
- exact cache/materialization/artifact identity and consumers;
- exact source versions, transformation/code/config/model versions and all inputs;
- deterministic rebuild or validated restore proof;
- no independent audit, research, strategy, ledger or decision lineage obligation;
- dependency release by each owning consumer and current authoritative registry state;
- separate treatment of model/training artifacts and CORE_LEDGER/AI_LEDGER lineage.

A TTL, cache label, successful rebuild of a different version or model retraining does not authorize deletion. No cache eviction or artifact cleanup is authorized.

### 6.6 Adapter approval gate

An adapter cannot be approved for destructive use until it demonstrates:
- exact identity and scope enforcement;
- fail-closed behavior under missing/stale/conflicting authorization;
- concurrency/race protection and immutable precondition checks;
- durable idempotency and intent/outcome records;
- safe interruption and ambiguous-result handling;
- no cascade beyond authorized objects;
- independent verification capability;
- recovery and audit evidence preservation;
- negative tests for scope mismatch, identity substitution, stale authorization, registry outage, hold change, duplicate request, partial failure and lost response.

P1.8.83 defines no adapter implementation or test execution. Test vectors and evidence requirements are design criteria only.

## 7. Relationship between source, copy and evidence disposition

A lifecycle decision must explicitly identify three separate scopes:

1. **Source scope:** canonical/derived dataset version and its own lifecycle state.
2. **Copy scope:** each replica, backup, export, local copy, cache or materialization with its own identity and disposition decision.
3. **Evidence scope:** manifests, approvals, audit, tombstones, verification and recovery records required to explain the source/copy history.

A decision affecting one scope cannot silently affect the others. In particular:
- source deletion does not imply copy deletion;
- copy disposition does not imply source deletion;
- payload deletion does not imply tombstone/audit deletion;
- evidence retention does not imply retention of the original payload;
- access revocation does not prove physical deletion;
- encryption-key destruction is not a substitute for governed disposition unless separately assessed and approved.

## 8. Blocking conditions

The following conditions block disposition and leave the affected copy protected/unknown:
- incomplete or unbounded inventory;
- unresolved source/copy identity or lineage;
- unknown external recipients or destinations;
- missing or inconsistent backup-chain membership;
- unverified recovery point or unavailable encryption-key dependency;
- active, stale, unknown or disputed consumer dependency;
- inherited or copy-specific hold;
- registry, evidence store or storage adapter unavailable;
- adapter cannot enforce exact immutable scope;
- evidence freshness policy not defined or evidence cannot be shown to meet it;
- ambiguous prior operation, partial outcome or missing independent verification;
- any potential collateral effect on T0 canonical data, CORE_LEDGER, AI_LEDGER or required audit evidence.

No timer, stale review date, missing heartbeat or storage pressure overrides these blockers.
