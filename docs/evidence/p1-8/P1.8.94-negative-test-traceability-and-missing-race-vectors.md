## 1. Purpose and strict boundary

This document establishes explicit traceability from all 45 original P1.8.84 negative cases (N01–N45) to the 47 baseline P1.8.90 vectors and supplements missing cases with additional deterministic race vectors.

The result is a test specification catalogue, not executable test code or evidence of passing tests. No fixture, runner, adapter, workflow, CI job or runtime control is created. All future execution must be separately authorized and confined to synthetic identities and isolated disposable storage. Canonical T0, T1–T4, real ledgers, VPS, production credentials, backups and external recipients are excluded.

## 2. Traceability rules

- COVERED means an existing P1.8.90 vector directly tests the essential negative condition.
- COVERED_BY_COMBINATION means multiple vectors are required to establish the full original case.
- EXPANDED means the baseline vector is supplemented by one or more race vectors below.
- ADDED means this document introduces a new vector because the original catalogue did not isolate the required condition.
- No mapping means the case is uncovered; no original case is treated as covered merely because its topic is mentioned in prose.
- A mapped vector is a specification reference only. All cases remain NOT_RUN.

## 5. Deterministic event schedules and assertions

Every concurrency vector must specify a total order for the events it controls, or explicitly assert BLOCKED/UNKNOWN when the system cannot prove an order. Use barriers/latches or a deterministic scheduler; never use sleep durations as correctness evidence.

Minimum schedules:

### 5.1 Hold vs mutation
- Schedule A: final decision snapshot → mutation intent durable → hold commit → mutation boundary.
- Expected: if hold commit is ordered first, mutation rejected with no side effect.
- Schedule B: mutation commit → hold commit → delayed mutation response.
- Expected: the committed object is recorded as preceding the hold; all later objects are blocked.
- If the authoritative order is unavailable, classify UNKNOWN; do not infer from response order.

### 5.2 Policy/dependency revision vs multi-object batch
- Object A commits under revision r.
- Policy or dependency revision r+1 commits before object B's mutation boundary.
- Expected: preserve A result; reject B's stale vector; invalidate old approval/authorization as required; reconcile and re-review.

### 5.3 Authorization/cancellation vs in-flight mutation
- Authorization revocation/cancellation and mutation are released at a deterministic shared barrier.
- Expected: authoritative linearization determines whether the object committed; no client timestamp or HTTP response order substitutes for that decision.
- Unknown order means reconciliation and no subsequent object operation.

### 5.4 Audit/registry outage after side effect
- Mutation side effect commits; audit or registry response is withheld/fails before outcome persistence.
- Expected: no batch success, no next object operation, durable intent retained; independent read-only oracle establishes actual object state before any retry.

## 6. Required test schema and independent oracle

Every vector must bind:
- P1.8.84 source case and P1.8.90/P1.8.94 test IDs;
- immutable spec version and exact source SHA;
- synthetic namespace and proof of isolation;
- initial request/domain/object states and revisions;
- exact event schedule, barrier and fault point;
- exact authorized and observed object sets;
- expected state transitions and adapter call count;
- unique idempotency/mutation identities;
- independent oracle source and trust boundary;
- audit/registry observations and residual classification;
- synthetic-only cleanup/containment plan;
- runner/toolchain identity and artifact provenance if separately approved.

The oracle must not be the executor's own mutable log or response path. It must independently establish whether a side effect occurred, which exact object generation was affected, and whether any out-of-scope object changed. If it cannot, result is NOT_VERIFIED or NOT_TESTABLE, never PASS.

## 7. Result vocabulary and coverage status

Use the P1.8.90 result vocabulary unchanged:
- PASS — deterministic fixture and independent oracle prove the expected property.
- FAIL — forbidden mutation/transition or required behavior violation observed.
- BLOCKED — required precondition/dependency unavailable.
- NOT_TESTABLE — deterministic fixture or independent oracle unavailable.
- NOT_VERIFIED — evidence insufficient or conflicting.
- NOT_RUN — no execution occurred.

A suite cannot be reported PASS if any required vector is BLOCKED, NOT_TESTABLE or NOT_VERIFIED. All vectors in this document are currently NOT_RUN.
