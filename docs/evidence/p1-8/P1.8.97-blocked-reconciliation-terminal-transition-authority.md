## 1. Purpose and governing boundary

This document closes the transition-authority ambiguity identified in P1.8.96 for BLOCKED resolution, reconciliation resume, expiry, revocation and observer-triggered reconciliation.

It is subordinate to the Data Deletion Safety Contract, P1.8.82, P1.8.85, P1.8.86 and P1.8.92. It governs deletion-request orchestration only. Dataset, dependency, hold, copy, approval, authorization, per-object execution and evidence remain separate authoritative state domains.

This is a documentary protocol. It does not select an identity provider, trusted-time source, event store, registry, transaction mechanism, quorum or numeric freshness/lifetime. It does not create a new operational role, grant self-approval, authorize a destructive action or implement a state machine.

## 2. Authority vocabulary

The following authority labels refer only to the existing role boundaries already defined in P1.8.82 and P1.8.92:

- **Reporter / observer:** any authenticated component or person permitted to submit an observation or suspected fault. Report-only. Cannot resolve BLOCKED, resume reconciliation, expire/revoke authorization, approve or authorize mutation.
- **Authoritative domain owner/issuer:** the authority already responsible for the relevant source of truth (for example, consumer owner for its own dependency declaration; hold authority for hold state; policy owner for policy revision; authorization authority for authorization status). May attest only facts within its domain.
- **Lifecycle reviewer:** evaluates whether submitted authoritative evidence resolves the eligibility/lifecycle blocker. Cannot manufacture a domain fact, release another consumer's dependency, revoke a hold outside its authority, or issue execution authorization.
- **Independent verifier:** establishes actual per-object and residual outcomes independently of the executor. Its attestation is evidence, not permission to resume or execute.
- **Execution authority:** performs final recheck and issues, narrows or revokes execution authorization within its approved delegation. It cannot approve its own request or substitute for the independent verifier.
- **Request orchestrator:** records a state transition only after validating the required authority, event, revision and guard. It is not an independent decision-maker and cannot infer missing authority.

A role label, service account, signature or separate process does not by itself prove independence. The unresolved personal-project approver/compensating-control decision remains OPEN. No single-owner self-approval is permitted by this document.

## 4. BLOCKED resolution protocol

A BLOCKED state is not cleared by a timeout, retry, new heartbeat, operator assertion or disappearance of an error message.

The resolution package must contain:

1. the exact blocker ID and original failed guard;
2. authoritative attestation from the owner/issuer of the affected domain;
3. immutable source object/dependency/hold/policy/availability revision and evidence digest;
4. actor identity and delegation proof, bounded to the relevant domain;
5. conflict check against all other blockers and active holds;
6. fresh dependency, copy, recovery and evidence checks relevant to the blocker;
7. lifecycle-review decision with prior and resulting request revisions;
8. an idempotent durable event linking the resolution to the original blocker.

If the blocker cannot be attributed to one authoritative domain, if source revisions conflict, or if evidence provenance is unresolved, remain BLOCKED. A blocker resolution does not itself restore approval or execution authorization.

### 4.1 Re-entry selection

- Use ELIGIBILITY_REVIEW when eligibility evidence, policy, dependency, hold, copy, recovery or classification needs to be re-evaluated.
- Use FINAL_RECHECK only when the exact approval package remains valid and the issue was confined to a final authorization precondition.
- If manifest, policy, object generation, material evidence, hold/dependency/copy revision or operation changed, invalidate approval and return through the required earlier review/approval stage; if exact scope changed, require a new request.
- If any mutation outcome is ambiguous, do not use BLOCKED → FINAL_RECHECK as a shortcut; use reconciliation first.

## 5. Reconciliation resume protocol

RECONCILIATION_REQUIRED is protective and cannot transition directly to EXECUTING.

The reconciliation package must partition every manifest object into exactly one of:
- CONFIRMED_UNTOUCHED;
- CONFIRMED_MUTATION_COMMITTED;
- CONFIRMED_PARTIAL_OR_RESIDUAL;
- OUTCOME_AMBIGUOUS;
- OUT_OF_SCOPE_CHANGE_DETECTED.

The package must identify the independent observation source, object generation/version, evidence provenance, event ordering, audit continuity and any collateral effects. No object may be omitted. If any object remains OUTCOME_AMBIGUOUS or OUT_OF_SCOPE_CHANGE_DETECTED, execution cannot resume; maintain reconciliation or terminate the request with a bounded NOT_VERIFIED result.

A resume decision requires both:
1. lifecycle reviewer acceptance that the reconciliation evidence is complete within its declared boundary; and
2. execution authority's new final recheck and fresh exact-scope authorization.

The prior authorization is never silently revived. Any material change requires a new approval package; a changed scope requires a new request. No rollback is inferred. Previously committed objects remain historical outcomes; remaining objects are separately gated.

## 6. Expiry and revocation ordering

Expiry and revocation are control-plane events, not storage mutations.

- Expiry before the first mutation boundary may terminalize the exact request/approval/authorization only when trusted ordering proves no mutation began.
- If expiry is observed after a mutation may have begun, the request enters reconciliation; expiry cannot erase or relabel per-object outcomes.
- Revocation must be serialized against each object mutation boundary. If revocation commits first, that object mutation is rejected. If mutation commits first, preserve its outcome and stop later objects. If ordering is unknown, stop and reconcile.
- A revoked/expired authorization is never reactivated. A new authorization requires a new final recheck and all applicable approvals.
- No numeric expiry lifetime, clock skew, propagation SLA, grace period or evidence freshness limit is chosen here.

## 7. Terminal-state and observer constraints

1. REJECTED, CANCELLED, EXPIRED and VERIFIED_COMPLETE_WITHIN_SCOPE remain terminal for their exact request identity, subject to the documented partial-outcome and reconciliation rules.
2. REVOKED is terminal for the exact authorization, not proof that the request or storage state is terminal. If mutation may have begun, request state is RECONCILIATION_REQUIRED.
3. NOT_VERIFIED is not success and cannot be cleared by executor self-attestation.
4. An observer can report a condition and cause a protective block/quarantine. It cannot resolve a blocker, accept reconciliation, approve, authorize, release a dependency or attest a storage outcome.
5. Request orchestrator may persist only transitions whose authority and guards are independently validated; it cannot promote an untrusted report into authoritative domain evidence.
6. If event order, authority, source revision, trusted time or audit continuity is unavailable, retain the more protective state.

## 8. Deterministic acceptance requirements

Future isolated tests must assert at minimum:
- an observer can trigger protective quarantine but cannot clear it;
- a domain owner attestation for one dependency cannot resolve a hold/policy blocker;
- BLOCKED → ELIGIBILITY_REVIEW requires blocker-specific evidence and re-evaluation;
- BLOCKED → FINAL_RECHECK is denied if approval/package revisions changed;
- reconciliation cannot resume with any ambiguous object;
- independent verifier attestation is distinct from lifecycle-review acceptance and execution authorization;
- expiry before first mutation is terminal only with trusted ordering proof;
- expiry after possible mutation routes to reconciliation;
- revocation-before-mutation blocks the object; mutation-before-revocation preserves the committed object and stops subsequent objects;
- unknown ordering blocks further mutation;
- a revoked authorization cannot be reused or reactivated;
- partial cancellation preserves all per-object outcomes and unresolved NOT_VERIFIED status.

These are design assertions, not executed tests.
