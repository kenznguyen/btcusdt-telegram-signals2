## 2. V07 — Trusted timestamp and revocation

### 2.1 RFC 3161 implications

RFC 3161 defines a timestamp token as proof-of-existence for the datum represented by its message imprint. The requester must verify that the returned imprint and hash algorithm match the request, validate the TSA token signature and certificate identity, check the policy, and use the nonce/local-time mechanism to assess timeliness and replay.

The token's `genTime` is UTC. Optional `accuracy` expresses deviation around that time; if absent, accuracy may be specified through other means such as the TSA policy. Token ordering is not automatically established across tokens: absent an affirmative ordering property, timestamps can be ordered only when the time difference exceeds the sum of their accuracies.

**Design consequence:** preserve the exact signature bytes and immutable verification context in the timestamped object; preserve the complete token, TSA certificate chain, policy identifier, request/response, nonce and verification result. Do not interpret absent accuracy as zero. Do not infer a universal maximum accuracy, response delay, token lifetime, cache age or acceptable TSA policy from RFC 3161.

Primary source: RFC 3161, https://www.rfc-editor.org/rfc/rfc3161.html

### 2.2 Revocation evidence

RFC 6960 defines distinct OCSP time fields:
- `thisUpdate`: when the indicated certificate status was most recently known to be correct;
- `nextUpdate`: when newer status information is expected to be available by;
- `producedAt`: when the responder signed the response;
- `revocationTime`: when the certificate was revoked or placed on hold.

Before accepting a signed OCSP response, a client must verify the requested certificate identity, response signature, responder identity and authorization, freshness of `thisUpdate`, and (when present) that `nextUpdate` is later than local current time. A `good` response is not, by itself, proof that a certificate was ever issued or that it was valid at an arbitrary historical instant. RFC 5280 also describes CRL publication and the dependence of “suitably recent” status on local policy.

**Design consequence:** keep historical eligibility separate from token validity and signature validity, as already required by P1.8.38. Preserve raw signed OCSP/CRL evidence and its retrieval/provenance metadata. Unknown, stale, unauthorized, unavailable or contradictory status must not be silently converted to GOOD. The exact historical decision rule, revocation equality semantics, freshness/cache bounds, responder trust, and quarantine-release authority remain owner decisions requiring a frozen policy and evidence.

Primary sources:
- RFC 6960, https://www.rfc-editor.org/rfc/rfc6960.html
- RFC 5280, https://www.rfc-editor.org/rfc/rfc5280.html

## 3. V08 — Event-time watermark and durable checkpoint

### 3.1 Stream-processing semantics

Apache Flink documentation distinguishes event time (timestamp carried by the event) from processing time and uses watermarks to signal progress in event time. Out-of-order and late events make a finite waiting policy a trade-off: waiting longer can include more late data but increases latency; a finite policy cannot guarantee that no later event will ever arrive.

Flink's checkpoint documentation describes a checkpoint as a consistent point across input streams plus operator state. Recovery restores operator state and replays source records. “Exactly once” means each event affects managed state exactly once; end-to-end exactly-once additionally requires replayable sources and transactional or idempotent sinks.

**Design consequence:** the project's approved hybrid model (event-time + watermark + durable commit-time boundary, immutable sealed checkpoint, append-only correction path) must retain separate proofs for:
1. source progress/watermark and its partition/source membership;
2. event-time window membership and late-event disposition;
3. checkpoint state and input offsets;
4. durable commit acknowledgement from the actual persistence layer;
5. correction/replay lineage and idempotency.

A watermark reaching a window end is not, by itself, proof that the corresponding checkpoint or database commit is durable. Flink's exactly-once semantics cannot be transferred to a different runtime or sink without implementation-specific proof.

Primary sources:
- Flink time and watermarks, https://apache.googlesource.com/flink/+/master/docs/content/docs/concepts/time.md
- Flink stateful stream processing, https://github.com/apache/flink/blob/master/docs/content/docs/concepts/stateful-stream-processing.md
- Flink fault tolerance, https://apache.googlesource.com/flink/+/master/docs/content/docs/learn-flink/fault_tolerance.md

### 3.2 Candidate assessment

| Candidate mechanism | What it can establish | What it cannot establish alone |
|---|---|---|
| Event-time watermark | Declared progress under a defined source/watermark policy | No future late event; durable storage |
| Checkpoint + source offsets | Recoverable consistent stream state, if runtime/source contracts hold | Database durability or sink atomicity without integration |
| Transactional sink | Atomic/consistent output under its transaction contract | Correct source membership or business reconciliation |
| Idempotent append-only correction | Safe repeated correction under stable identity and dedupe contract | Correctness of the original window/watermark policy |

**V08 disposition:** OPEN/BLOCKED. Keep UTC half-open windows, monotonic watermark, durable commit boundary, immutable checkpoints and separate correction stream as approved policy directions. Watermark generation, allowed lateness, idle-source handling, clock uncertainty, partition membership, commit linearization and correction semantics remain OPEN pending implementation-specific evidence.

## 4. Restore — Backup, WAL and recovery proof

PostgreSQL's continuous-archiving/PITR documentation describes recovery by restoring a base filesystem backup and replaying archived WAL. WAL replay can recover to a selected point after the base backup, and continuous WAL archiving supports a sequence of recoverable states. This is a documented PostgreSQL capability, not evidence that this project's backup chain, provider, storage, retention, credentials or restore procedure is configured correctly.

**Design consequence:** a restore evidence package must bind:
- database/version/configuration and backup method;
- base-backup identity, checksum/manifest and completion state;
- continuous WAL range, continuity and archive integrity;
- recovery target and actual replay endpoint;
- frozen committed transaction population at the selected ACK boundary;
- missing/extra transaction reconciliation and content digests;
- measured RPO/RTO with explicit clock start/stop definitions;
- failure-domain assumptions, operator identity, logs, artifacts and cleanup evidence.

A backup job reporting success is not a restore proof. A successful database startup is not business-state reconciliation. The existing targets (ACK RPO 0 within tested boundary/failure domain; snapshot RPO ≤5 minutes; staging RTO ≤60 minutes; three independent rehearsals) remain planning targets only, not SLOs or demonstrated capabilities.

Primary source: PostgreSQL 17, Continuous Archiving and PITR, https://www.postgresql.org/docs/17/continuous-archiving.html

**Restore disposition:** OPEN/BLOCKED. No provider, failure domain, retention, WAL archive topology, RPO/RTO formula refinement, or operational rehearsal is selected or authorized.
