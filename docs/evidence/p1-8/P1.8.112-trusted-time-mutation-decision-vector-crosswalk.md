# P1.8.112 — Trusted-Time to Mutation Decision-Vector Crosswalk

**Version:** P1.8.112-v1  
**Closes:** P1.8.109 IR109-03 (MAJOR)  
**Depends on:** P1.8.34, P1.8.36, P1.8.93, P1.8.105–P1.8.107, P1.8.109  
**Type:** Documentation-only cross-contract mapping  
**Status:** CROSSWALK RECORDED — TRUST PROFILE/ATOMIC RECHECK OPEN — NOT IMPLEMENTED

## 1. Purpose and boundary

This document maps P1.8.107 trusted-time evidence into the protected decision vector required by P1.8.93. It defines exact evidence pinning and invalidation requirements without asserting that an implementation can enforce them atomically.

No TSA, trust anchor, revocation source, clock, registry, transaction coordinator, adapter or numeric threshold is selected. No mutation, staging, key/TSA operation or deletion is authorized.

## 2. Normative crosswalk

The protected vector MUST contain immutable references and pinned revisions for each applicable field below. A generic `trusted_time_evidence` pointer is insufficient.

| Protected vector field | Required binding from P1.8.107 | Validation / failure disposition |
|---|---|---|
| Decision/request identity | decision ID, request ID, approval-package digest | Exact immutable identity; mismatch rejects |
| Object/subject binding | exact dataset/version, object/copy identity and generation, event/subject ID | Evidence for another object/event is rejected |
| Trusted-time evidence identity | evidence ID, immutable version, manifest digest, raw token/record digest | Missing or mutable reference blocks |
| Time semantic | explicit type: signed_at, TSA genTime, received/observed, revocation effective time, durable commit, seal, authorization or restore boundary | Semantic substitution is rejected |
| Source and profile | authority/source ID, proof/profile ID and revision, algorithm/canonicalization revision | Unknown or unapproved profile blocks |
| Event binding | exact signed bytes/signature imprint or event digest and P1.8.36 context binding | Imprint/context mismatch rejects |
| Time value and precision | original value, declared precision, accuracy/uncertainty interval and units | Missing units/uncertainty or incomparable intervals HOLD |
| Trust state | historical policy revision, trust-anchor/chain references and validation result | Missing/corrupt historical material is INDETERMINATE |
| Revocation state | authority/source revision, effective-time semantics, observation evidence, status and reason | Unknown, stale, conflicting or unavailable state fails closed |
| Freshness | evidence observation time, class-specific freshness policy revision and measured age result | Threshold remains OPEN; absent policy or stale proof blocks |
| Authorization binding | authorization ID, scope, executor identity, issued/expiry semantics and revocation epoch/revision | Wrong scope, expired, revoked or ambiguous status rejects |
| Restore binding | Restore Epoch, Governance Epoch, HWM binding-record ID/digest where relevant | Stale/pre-restore context rejects |
| Final mutation check | final-check ID, exact vector digest, authoritative decision revision and mutation-fence result | Must be atomically coupled to mutation boundary; otherwise adapter INELIGIBLE |
| Audit/verification | verifier identity/profile, result, reason code, evidence manifest and durable intent reference | Missing durable evidence blocks start or causes UNKNOWN after possible side effect |

The crosswalk is versioned. A future schema must preserve source field semantics and cannot collapse multiple time domains into one timestamp.

## 3. Invalidation and recheck rules

Any material change to one of the following invalidates the pinned decision vector before mutation:

- trusted-time evidence bytes, digest, source or profile revision;
- historical trust-policy, trust-anchor, certificate-chain or revocation evidence;
- revocation effective-time interpretation or authoritative revision;
- freshness policy, observed age or uncertainty disposition;
- authorization scope, expiry, revocation epoch or executor identity;
- Restore Epoch, Governance Epoch, HWM binding or restore quarantine state;
- object generation, policy, dependency, hold, copy disposition or lifecycle revision;
- verifier profile/result or required audit/intent evidence.

The final check MUST re-evaluate the exact pinned revisions at the P1.8.93 mutation linearization point. A preflight validation followed by an unrelated storage operation is insufficient. If the registry and backend cannot establish one atomic/transactionally coupled decision, the adapter remains INELIGIBLE for destructive use.

If trust/revocation evidence becomes unavailable during final recheck, the result is REJECT/HOLD. If a side effect may already have occurred and evidence continuity is lost, result is OUTCOME_UNKNOWN and independent reconciliation is required; no blind retry.

## 4. Time semantics that must not be conflated

- `signed_at` is a signer/client assertion, not trusted proof by itself.
- TSA `genTime` supports only the P1.8.36 bounded claim that the exact timestamped signed object existed no later than the authority's asserted time, subject to token validation.
- `received_at` / observed time describes observation, not signing or commit.
- Revocation effective time is governed by the revocation authority's semantics, not local receipt time.
- Durable commit time must be tied to the actual persistence commit boundary.
- Seal time must be tied to the authoritative V08 seal barrier.
- Authorization issue/expiry and restore boundaries require their own trusted ordering evidence.

Intervals that overlap, values from incomparable domains, or absent precision do not establish precedence. Fail closed.

## 5. Verification and fixture requirements

Future synthetic fixtures must include exact object match/mismatch; signature imprint mismatch; stale evidence; changed trust profile; revoked/unknown key; revocation arriving before and after authorization; uncertainty overlap; expired authorization equality; restore epoch mismatch; HWM mismatch; changed hold after preflight; evidence source outage at final check; evidence revision change between preflight and mutation; and ambiguous post-submission outcome.

Tests must verify that any material change invalidates the prior vector and that no mutation occurs when final atomic recheck cannot be proven. These are specification cases only; no test code or execution is included.
