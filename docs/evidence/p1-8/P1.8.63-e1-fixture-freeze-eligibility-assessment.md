## 1. Decision rule

A fixture may be frozen only if its exact bytes, serialization, expected oracle and all parameters required to interpret that oracle are already fixed by an approved policy or implementation-independent contract. A symbolic case may be specified while remaining unfrozen. A test profile or arbitrary precision value must not be introduced merely to make a fixture executable.

## 3. Determination

No new V07 fixture can be fully frozen without selecting unresolved cryptographic, TSA, trust, revocation or nonce-profile parameters.

V08 half-open UTC semantics are approved, but exact byte fixtures still depend on timestamp precision/serialization and source/commit implementation contracts. A symbolic boundary specification is valid; claiming frozen executable bytes would overstate the current decision state.

Restore fixtures depend on a declared database/backup/WAL implementation and failure domain. A generic synthetic file cannot establish compatibility with an unselected production candidate.

Therefore:
- Keep P1.8.58 as a parameterized specification.
- Keep V08-E1 and RST-E1 IDs as proposed categories.
- Do not create arbitrary test-only profiles, timestamp precision, provider assumptions or database formats.
- Do not dispatch E1 tests simply to obtain a green result disconnected from a frozen acceptance contract.
- Existing FV-01–FV-13 remain historical synthetic evidence only.

## 4. Owner decision readiness

No new numeric/provider/implementation decision is ready from documentary evidence alone. The next legitimate owner decision requires a concrete candidate profile or implementation choice supported by additional evidence. No generic approval is requested.

If a later candidate is proposed, the decision package must include exact options, source clauses, compatibility consequences, measurable evidence, residual uncertainty and what the decision would not authorize.
