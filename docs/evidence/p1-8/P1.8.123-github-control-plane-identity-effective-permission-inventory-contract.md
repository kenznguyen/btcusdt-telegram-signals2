**Version:** P1.8.123-v1  
**Date:** 2026-11-09  
**Branch:** `feature/t0-centralized-data-feeder-p1-20261101`

## 1. Purpose and decision boundary

This contract defines how a future, separately authorized, read-only assessment must inventory identities and effective permissions that could influence repository automation, credential issuance, workflow execution or external storage access.

It responds to P1.8.122 finding IR122-01. It is an inventory specification, not evidence that any current identity has destructive capability. It does not select a provider, change repository settings, inspect secret values, grant/revoke permissions, activate workflows or enable destructive operations.

**Option C — No Destructive Authority remains the approved default.** No worker, adapter, service, operator, workflow or individual may receive destructive lifecycle authority. Unknown or incomplete inventory is NOT VERIFIED and cannot be treated as absence of capability.

## 2. Scope of identity inventory

A future inventory must cover all applicable identity classes, including indirect, inherited, delegated, temporary and emergency paths.

### 2.1 GitHub Actions execution identities

- Workflow-level and job-level `permissions`, including implicit/default `GITHUB_TOKEN` scope.
- Reusable workflows, called workflows, composite actions and action dependencies; caller/callee permission inheritance and pinning.
- Workflow triggers and dispatch paths: push, pull_request, workflow_dispatch, workflow_call, schedule, repository_dispatch, release, issue/comment and other enabled event sources.
- Environment protection rules, required reviewers, branch/tag restrictions, deployment gates and any bypass actors.
- Repository, organization and environment variables/secrets as metadata only: name, scope, availability, creation/rotation metadata where exposed, and consuming workflows. Never retrieve, print, export or copy secret values.
- Artifact, cache, package, release and deployment permissions where they can convey executable code, credentials or privileged state.
- Workflow concurrency/cancellation and rerun/retry paths where they can repeat or bypass a governed step.
- Workflow provenance, pinned action/workflow references and untrusted input paths that could influence privileged jobs.

### 2.2 GitHub principals and credentials

- Human users, teams, repository roles and organization roles relevant to administration or workflow control.
- GitHub Apps: installation scope, repository selection, permission grants, token issuance and owning principal.
- Personal access tokens (classic and fine-grained): metadata, owner, scopes/permissions, repository/resource scope, expiry and revocation status where safely visible.
- Deploy keys and SSH keys: repository scope, read/write designation, owner/host linkage and lifecycle metadata.
- Bot/service accounts and machine identities.
- Organization/repository administrators and actors able to change workflow files, protection rules, environments, secrets, runners or app installations.
- Delegation, team nesting, outside collaborators, inherited organization access, break-glass and recovery accounts.

### 2.3 Runner and execution-host identities

- GitHub-hosted runner class and any privileged runner labels/groups.
- Self-hosted runner registration, group/repository/organization scope, host owner and administrator boundary.
- Host OS/service identity, persistent workspace, mounted volumes, cached credentials and metadata of credential sources.
- Network reachability and trust paths from runner to external control planes and storage endpoints.
- Runner lifecycle, isolation, cleanup, ephemeral/persistent status and compromise/replacement process.

No host command, filesystem inspection, credential extraction or runner job is authorized by this document.

### 2.4 OIDC and external identity federation

- OIDC issuer, audience, subject claims and trust-policy conditions.
- Workflow/repository/ref/environment claim restrictions and reusable-workflow claim semantics.
- Cloud role/service-principal assumption paths, session duration, session tags and permission boundaries.
- Trust-policy administrators and paths able to widen claims, audiences, subjects or role trust.
- Credential exchange and revocation boundaries, including whether a workflow can obtain an external token without exposing a stored secret.

### 2.5 External storage/provider control plane

For every provider or storage account already identified in approved documentation (without selecting a new provider), a future inventory must map:
- human, service, workload and support identities;
- account/project/tenant, bucket/container/database and object-level scopes;
- list/read/write/delete/versioning/retention/legal-hold/restore/admin/policy-management capabilities;
- inherited roles, resource policies, ACLs, organization policies and cross-account trust;
- versioning, retention lock, object lock, backup, lifecycle and recovery control-plane administration;
- audit-log readers/writers and any actor able to alter or suppress evidence;
- emergency/support access and provider-managed principals.

Provider-specific permissions and semantics remain NOT VERIFIED until separately assessed. No provider endpoint is contacted by this contract.

## 3. Effective-permission model

The inventory must not equate a displayed role name with actual authority. For each principal and execution path, derive the effective capability set from the union of applicable direct, inherited, group, organization, repository, environment, workflow, runner, federated and provider grants, then account for explicit denies, boundaries, conditions, resource policies and reachable credential-minting paths.

Record both:
1. **Control-plane authority** — ability to change code, workflows, protections, secrets metadata, runner configuration, identity trust, policy or role assignments.
2. **Data-plane authority** — ability to read, write, overwrite, delete, archive, purge, alter retention/holds, restore, or modify audit/evidence objects.

Repository write permission is not automatically storage deletion permission; however, the ability to alter a privileged workflow, mint a credential, change OIDC trust or release a secret may create an indirect path. These paths must be traced end-to-end rather than assumed harmless.

### 3.1 Capability classification

Every discovered capability/path must be classified as one of:

- `READ_METADATA`
- `READ_DATA`
- `WRITE_NONDESTRUCTIVE`
- `MUTATE_REVERSIBLE`
- `DESTRUCTIVE_DATA` (delete, purge, destructive overwrite/truncate, destructive archive/cleanup)
- `RETENTION_OR_HOLD_ADMIN`
- `IDENTITY_OR_POLICY_ADMIN`
- `CREDENTIAL_MINT_OR_DELEGATE`
- `AUDIT_EVIDENCE_ADMIN`
- `UNKNOWN`

Classification is per resource and operation, not merely per identity. An identity with no direct destructive permission may still have an indirect path through workflow modification, credential issuance, role assumption, runner administration or policy changes.

### 3.2 Unknown and conflicting states

- Missing API visibility, inaccessible scope, incomplete pagination, inconsistent snapshots, opaque provider semantics or untraceable delegation => `UNKNOWN / NOT VERIFIED`.
- Conflicting grants/denies or ambiguous precedence => `UNKNOWN / HOLD` until independently resolved.
- A missing inventory row is not proof that a principal, credential, runner or access path does not exist.
- No timeout, stale inventory, token expiry assumption or successful workflow run may convert UNKNOWN to NONE.
- Do not test a suspected destructive capability by attempting a destructive action.

## 4. Required inventory record

Each principal, credential class, workflow path, runner and resource binding must have a stable inventory record with, where applicable:

| Field | Required meaning |
|---|---|
| `inventory_id` | Stable unique record identifier |
| `principal_type` / `principal_id` | Human, team, App, token owner, runner, workload, provider identity; opaque identifier where needed |
| `source_system` | GitHub organization/repository, runner control plane, OIDC issuer or provider |
| `resource_scope` | Exact organization/repository/environment/runner/resource/account scope |
| `credential_kind` | Token, App installation, deploy key, OIDC federation, host identity or none |
| `grant_source` | Direct, inherited, team, org, repo, environment, workflow, runner, federation or provider policy |
| `capabilities` | Operation-level classified capabilities |
| `delegation_path` | Complete chain to effective principal/resource, or UNKNOWN |
| `mint_or_modify_authority` | Whether it can issue credentials or alter policy/workflows/identity |
| `conditions_and_denies` | Conditions, boundaries, explicit denies and unresolved precedence |
| `owner_and_independence` | Accountable owner and whether independence is evidenced |
| `lifecycle_state` | Active, expired, revoked, suspended, unknown |
| `observed_at` | Trusted/recorded observation time and uncertainty where available |
| `source_revision` | API snapshot, policy revision, commit or provider evidence identity |
| `evidence_ref` | Immutable pointer/digest to non-secret evidence |
| `review_status` | PASS, PARTIAL, BLOCKED, UNKNOWN or NOT VERIFIED |
| `limitations` | Visibility gaps, pagination, unverified semantics and excluded scopes |

Never include raw token values, private keys, passwords, secret contents, recovery codes or other authentication material in inventory records or evidence artifacts. Redact sensitive principal attributes not needed to establish authority.

## 5. Graph and path-completeness requirements

The final inventory must represent principals, credentials, workflows, runners, trust policies, resources and administrators as a directed relationship graph. Edges must distinguish at least:

- `OWNS`
- `MEMBER_OF`
- `INHERITS_ROLE`
- `CAN_EDIT_WORKFLOW`
- `CAN_TRIGGER_WORKFLOW`
- `USES_CREDENTIAL`
- `CAN_MINT_CREDENTIAL`
- `CAN_ASSUME_IDENTITY`
- `RUNS_AS`
- `CAN_ADMINISTER_RUNNER`
- `CAN_CHANGE_PROTECTION`
- `CAN_CHANGE_SECRET_METADATA_OR_BINDING`
- `CAN_CHANGE_TRUST_POLICY`
- `CAN_CHANGE_PROVIDER_POLICY`
- `CAN_ACCESS_RESOURCE`
- `CAN_ALTER_AUDIT_EVIDENCE`

Every path from a human or automation principal to a data-plane capability must be traceable, including indirect paths. Graph closure requires declared scope, complete pagination, source revision/time, and independent completeness review. Absence of a path may be asserted only for the bounded, fully inventoried scope.

## 6. Option C acceptance rules

The inventory supports Option C only if the bounded evidence demonstrates that no enabled principal or reachable execution path has destructive data-plane capability, and no uncontrolled path can mint or delegate such capability.

The following are not sufficient:
- a workflow file that appears not to call delete;
- a repository role label without effective-permission resolution;
- absence of visible secrets without checking metadata/bindings and OIDC federation;
- separate account names without proving independent control;
- a disabled workflow without proving it cannot be enabled or bypassed by an administrator;
- a provider role name without mapping resource policies and inherited grants;
- a successful read-only test as proof that destructive actions are impossible.

If any scope or path is unknown, report **PARTIAL / NOT VERIFIED**, retain the protective block and do not claim Option C is technically enforced. If destructive capability is discovered, record a security finding and stop; do not revoke, edit, disable or otherwise remediate it without separate explicit owner approval and a reviewed change plan.

## 7. Future execution phases and authorization gates

This document authorizes no execution. Any future work must be proposed and approved separately in distinct gates:

1. **Read-only metadata inventory proposal:** exact repositories/orgs, APIs, actor, scopes, pagination, evidence handling and rate/visibility limits. No secret values and no provider data-plane probes.
2. **Independent inventory review:** reconcile direct/inherited/delegated paths and verify graph completeness.
3. **Remediation proposal, if needed:** separately enumerate changes, blast radius, rollback and owner approval. No automatic remediation from an inventory finding.
4. **Enforcement verification proposal:** only after separately approved changes, define safe non-destructive evidence for effective permission boundaries. Never validate by attempting deletion or destructive mutation.

Approval of P1.8.123 is approval of this documentary contract only. It does not authorize phases 1–4.

## 8. Evidence and status contract

A future inventory evidence package must contain:
- exact repository/organization/provider scopes and explicit exclusions;
- collection method and API/source versions;
- collection identity and proof of read-only scope;
- observation time, source revisions and pagination/completeness markers;
- normalized principal/credential/workflow/runner/resource inventory;
- effective-permission and credential-mint/delegation graphs;
- capability classification and UNKNOWN/NOT VERIFIED register;
- immutable evidence manifest and digests without secret material;
- independent reviewer disposition and residual-risk statement.

Status vocabulary:
- **PASS:** all declared scope and paths are completely inventoried and no destructive path is found within that bounded scope.
- **PARTIAL:** useful evidence exists but one or more paths/scopes remain unresolved.
- **BLOCKED:** required source access, completeness or independence prerequisite is absent.
- **NOT VERIFIED:** no defensible conclusion can be made for the claim.
- **NOT RUN:** no collection or test was executed.

A PASS is always scope-bounded; it must never be generalized to unenumerated organizations, repositories, providers, accounts, runners or identities.
