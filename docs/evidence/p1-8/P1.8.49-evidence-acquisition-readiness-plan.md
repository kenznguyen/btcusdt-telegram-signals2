**Version:** P1.8.49-v1  
**Type:** Documentation-only plan for future evidence acquisition  
**Depends on:** P1.8.33–P1.8.48  
**Status:** PLAN COMPLETE — NO DATA ACQUIRED — PERMISSIONS NOT REQUESTED/GRANTED  
**Authorization:** Documentation only. This plan does not authorize provider access, live data collection, VPS/runtime probes, key operations, staging, restore or fault injection.

## 1. Purpose

Define what evidence would be needed before proposing values for the remaining measurement-dependent V07/V08/Restore parameters. This plan prevents unsupported thresholds and distinguishes documentary evidence from measurements of actual behavior.

No sample size, observation duration, percentile, tolerance, provider, clock source or numeric threshold is assigned here. Those must be justified in a separately reviewed measurement protocol before any data is collected.

## 2. Evidence classes

- **E0 — Public/documentary contract:** published authority/provider specifications, API semantics, database durability documentation and versioned protocol documents. Reading public documentation does not prove deployed behavior.
- **E1 — Controlled synthetic fixture:** deterministic bytes/events and expected outputs; proves only the tested fixture implementation, not provider behavior.
- **E2 — Authorized non-production measurement:** isolated test authority, test-only keys, synthetic feeds or disposable infrastructure; requires exact scope and permission.
- **E3 — Operational measurement:** live feed/VPS/database/provider observation. Requires separate explicit owner permission, read scope, credential/network boundaries, retention and rollback plan.
- **E4 — Staging execution evidence:** exact production-equivalent isolated staging. Requires separate explicit staging authorization and all P1.8.26/P1.8.28 entry gates.

Evidence classes are not interchangeable. E0/E1 cannot be represented as E2/E3/E4.

### 4.1 Lateness measurement safeguards

Any future lateness study must:
1. Define the exact source feed and population before collecting observations.
2. Keep event time, first trusted receipt time and durable commit time separate.
3. Record clock uncertainty and source partition identity for every observation.
4. Declare missing, duplicate, delayed, corrected and outlier treatment before analysis.
5. Report sample count, observation window, distribution and tail behavior without silently dropping inconvenient observations.
6. Separate observed maximum from a proposed operational bound and explain any safety margin.
7. Freeze the dataset digest and analysis code/version before owner review.

This plan authorizes no collection from Binance or any live feed, no VPS read and no runtime probe.

## 6. Permission request template — only when a gate is reached

Before any E2/E3/E4 acquisition requiring new access or side effects, prepare a separate request containing:
- exact parameter IDs and evidence question;
- target system/provider/feed/host and environment;
- read/write/network scope and credentials class (never include secret values);
- sample population and time window, or deterministic test case list;
- expected side effects and explicit proof of no exchange/order/live-trading path;
- resource, cost and expiry bounds;
- rollback/cleanup and access revocation;
- evidence artifact schema, hashing and retention;
- stop conditions and responsible approver.

No permission request is implied by this template. Ask only when the exact proposal is ready. If permission is denied or withheld, keep the item OPEN/BLOCKED and continue only with non-operational documentation.
