## 3. Findings

### IR145-01 — MAJOR: Evidence that the obligation inventory is complete is not operationally or logically specified

P1.8.144 requires the obligation inventory to be “complete for the declared scope” and requires each domain to be APPLICABLE, NOT APPLICABLE with rationale, or UNKNOWN. It does not define the minimum proof that the declared scope itself is complete.

The current contract does not require a reconciled source register covering, at minimum, authoritative policy sources, consumer/dependency registries, hold sources, copy/backup/export inventories, recovery catalogs, audit/incident registers and known external custodians. Nor does it define how omissions, inaccessible sources, stale snapshots, conflicting registries or unenumerated external copies invalidate a completeness claim.

Without a completeness proof, a perfectly populated obligation table can still omit an obligation and produce a false floor.

Required closure:
- define a bounded source-of-truth and evidence-source manifest for each assessment scope;
- require reconciliation/coverage evidence and explicit treatment of inaccessible or non-authoritative sources;
- require completeness limitations, snapshot times, freshness and unresolved gaps to be recorded;
- state that absence from an incomplete source is not proof of non-existence;
- keep the result BLOCKED_UNKNOWN / FLOOR_NOT_ESTABLISHED where source coverage cannot be demonstrated.

This is a documentary requirement for any future assessment, not authorization to perform an inventory now.

### IR145-02 — MAJOR: Obligation end semantics need typed terminal states and recurring/indefinite obligation handling

The formula `candidate_floor = max(proven_end(o_i))` is safe only if each applicable obligation has a valid terminal end event. P1.8.144 does fail closed when an end is missing, but it does not define a typed end-state vocabulary that distinguishes:
- a fixed minimum retention period reaching its end;
- an event-driven dependency release;
- a hold that remains active or is explicitly released;
- a recurring or rolling obligation that can renew;
- an indefinite/ongoing obligation with no terminal event;
- a superseded policy or obligation whose successor remains applicable.

A reviewer could otherwise mistake a past milestone or one completed cycle for closure of a recurring obligation.

Required closure:
- define obligation states such as ACTIVE, SATISFIED, RELEASED, SUPERSEDED_WITH_SUCCESSOR, INDEFINITE and UNKNOWN;
- require an authoritative, scope-bound terminal event for SATISFIED/RELEASED;
- require successor linkage for superseded obligations;
- make ACTIVE, INDEFINITE, recurring-with-open-cycle and UNKNOWN states block floor establishment;
- explicitly prohibit calculating a finite floor by assigning an artificial end to an ongoing obligation.

### IR145-03 — MODERATE: Copy and backup-chain floor aggregation needs explicit graph semantics

P1.8.144 correctly says each copy has its own identity and that backup chains are assessed as recoverable units. It does not fully specify how a copy-specific floor relates to a chain-level recovery obligation, shared deduplicated chunks, snapshots, manifests, incremental dependencies and restore points.

A file-level assessment could appear complete while an enclosing chain or shared storage object still has a recovery obligation; conversely, chain-level retention should not silently be treated as a blanket disposition rule for unrelated copies.

Required closure:
- model copy nodes and backup-chain/restore-set relationships explicitly;
- distinguish object-local obligations from inherited or shared chain obligations;
- require the assessment scope to include every graph edge needed to prove recoverability and lineage;
- state that a chain/member with unresolved shared dependencies blocks only the declared affected scope, without authorizing cascade treatment;
- preserve the independent lifecycle identity of each copy and the source.

### IR145-04 — MODERATE: RET-02 copy eligibility needs an explicit noncanonical boundary

P1.8.143 permits individually identified **noncanonical** copies to enter future read-only assessment. P1.8.144 §6.6 discusses copies, backups, replicas and exports generally but does not restate that boundary at the point where class-specific rules are applied.

Required closure:
- state explicitly that RET-02 copy review applies only to individually identified noncanonical copies;
- T0 canonical data and copies/replicas/backups whose role is to preserve T0 canonical availability or recovery remain protected under RET-01 unless a separate exceptional owner decision is approved;
- no copy may inherit eligibility solely because it is technically redundant or reproducible;
- preserve no-cascade and copy-specific obligation checks.

### IR145-05 — MINOR: Reviewer independence and competency evidence are underspecified

P1.8.144 requires an independent reviewer but does not require the assessment record to show how the reviewer is independent of requester, data custodian, obligation owner and any future executor, nor how domain competence is established for legal, security, recovery or model-lineage conclusions.

Required closure:
- add reviewer role, competency basis, conflict-of-interest declaration and separation from requester/custodian/approver/executor;
- require specialist/legal determinations to be attributed to an appropriately competent authority rather than inferred by a technical reviewer;
- retain the existing rule that no review itself grants mutation authority.
