# P1.8.100 — BLOCKED Transition Restriction and Observer-Only Quarantine

Date: 2026-11-09
Remediates: P1.8.99 IR2-01 (MAJOR)
Status: DOCUMENTARY DESIGN ONLY — NOT IMPLEMENTED / NOT ACTIVE / NOT AUTHORIZED

## 1. Purpose and boundary

This record narrows the request-level BLOCKED state so it cannot hide an in-flight or potentially committed mutation. It clarifies that an observer may report a fault and trigger a protective quarantine signal, but cannot rewrite canonical request state, declare a storage outcome, clear quarantine, or authorize a retry.

This is subordinate to the Data Deletion Safety Contract, P1.8.82, P1.8.85, P1.8.86, P1.8.92, P1.8.93 and P1.8.97. It is a documentary transition rule only. No implementation, registry, event store, adapter, trusted-time source, role model, provider or numeric parameter is selected. No destructive authority is granted.

## 2. Canonical distinction: request state vs protective quarantine

These are separate facts and must not be represented as interchangeable states:

- **Canonical request state** is the lifecycle state committed by the request orchestrator after validating the transition authority, durable event, revision and guard.
- **Protective quarantine** is a monotonic safety latch attached to the affected request/object scope. It blocks further mutation/authorization while a report or conflict is assessed. It is not a substitute canonical state and cannot erase execution history.
- **Observer report** is an untrusted or domain-limited observation. It is evidence input only; it is not a state transition decision.
- **Reconciliation requirement** is mandatory whenever a mutation intent may have been accepted, a side effect may have begun, an outcome is ambiguous, or ordering cannot be proven.

Quarantine may be raised conservatively by an authorized safety mechanism on an observer report. It may only be cleared through the applicable authoritative review and fresh execution-authority recheck. A report cannot directly set, clear or resolve the canonical request state.

## 3. BLOCKED is pre-mutation only

The canonical request state BLOCKED is permitted only while the request is provably pre-mutation. Eligible source states are limited to pre-mutation states in the canonical crosswalk, including eligibility review, approval review, approved, awaiting execution authorization and final recheck, provided no object mutation intent has been durably accepted and no side effect may have begun.

The following transitions are prohibited:

- EXECUTING → BLOCKED;
- VERIFICATION_PENDING → BLOCKED;
- any state with an accepted mutation intent, submitted backend operation, lost response after submission, partial result, uncertain object outcome or unknown mutation ordering → BLOCKED;
- any observer report → canonical BLOCKED state without orchestrator validation of the pre-mutation guard.

For an in-flight or potentially mutated request, the canonical transition is RECONCILIATION_REQUIRED. Protective quarantine may be raised concurrently, but cannot replace that transition.

If the system cannot determine whether mutation intent or a side effect began, treat it as possibly begun and route to RECONCILIATION_REQUIRED. Never infer pre-mutation from missing logs, absent response, process death, timeout, lease expiry or an observer's statement.

## 4. Transition authority and event table

| Condition | Initiator | Durable event | Required guard | Canonical result |
|---|---|---|---|---|
| Pre-mutation eligibility/approval/final-recheck guard fails | Request orchestrator | BlockedStateCommitted | Exact request revision; complete manifest; positive pre-mutation status; blocker and source revision | BLOCKED |
| Observer reports suspected fault before mutation | Observer submits report; orchestrator validates | ObserverReportRecorded; optionally ProtectiveQuarantineCommitted | Report is attributed and preserved as an observation; no observer authority to set canonical state | Canonical state unchanged; quarantine may be raised |
| Observer reports fault while mutation may have begun | Observer submits report; orchestrator enforces safety | ObserverReportRecorded; ReconciliationRequired | Exact request/object scope; uncertainty retained; no assumption about backend outcome | RECONCILIATION_REQUIRED; quarantine raised |
| Any system detects ambiguous in-flight outcome | Request orchestrator | ReconciliationRequired | Per-object intent/outcome references and last durable revisions; unknowns remain explicit | RECONCILIATION_REQUIRED |
| BLOCKED blocker is resolved | Domain owner attests; lifecycle reviewer accepts | BlockerResolutionAccepted | P1.8.97 resolution package; all blockers re-evaluated; exact revisions | ELIGIBILITY_REVIEW or FINAL_RECHECK only under its existing stricter guard |
| Quarantine clearance | Lifecycle reviewer accepts evidence; execution authority separately performs final recheck | ProtectiveQuarantineClearanceAccepted; FinalRecheckResumed | No unresolved observer conflict; source revisions current; required proof and approval remain valid; old authorization not revived | Quarantine cleared for exact scope; canonical state advances only by valid transition |

The orchestrator is a transition recorder, not a substitute for domain authority. The observer is report-only. The lifecycle reviewer cannot authorize mutation. Execution authority cannot attest storage facts on behalf of the independent verifier.

## 5. Mandatory fail-closed decision rule

Define the mutation-start predicate over the exact immutable manifest:

- `intent_accepted(object)`: a durable mutation intent for that exact object generation has been accepted at the authoritative mutation boundary;
- `side_effect_possible(object)`: a backend submission, committed effect, partial effect, lost response, or unorderable operation could have occurred;
- `outcome_ambiguous(object)`: the actual object result is not independently established.

BLOCKED is admissible only if every manifest object is positively proven to satisfy all of:
1. intent not accepted;
2. no backend submission or side effect began;
3. no ambiguous/lost-response record exists;
4. no unresolved mutation-order event exists.

If any object fails, is unknown, or lacks complete evidence, canonical state must be RECONCILIATION_REQUIRED. This section defines the rule; the exact evidence protocol is further constrained by P1.8.102.

## 6. Observer-only quarantine requirements

An observer report must include, where available, request/object identity, source domain, observed revision, event reference, observation time with its trust classification, evidence digest and uncertainty. Missing fields reduce evidentiary weight; they do not authorize the observer to infer an outcome.

Quarantine semantics:
- raising quarantine is protective and may block new mutation attempts;
- quarantine is scoped to the exact request/object/domain evidence, with broader scope only where a separately authorized safety rule requires it;
- quarantine does not cancel or reverse a mutation already submitted;
- quarantine does not prove no mutation occurred;
- quarantine does not release dependencies, holds or copies;
- quarantine cannot be cleared by timeout, heartbeat, disappearance of an alert or the same observer's uncorroborated assertion;
- a quarantine-clear event is durable, revision-bound and independently reviewable.

When quarantine is raised during execution, stop scheduling subsequent object mutations and reconcile every object whose intent or outcome may be affected. Preserve already committed outcomes; never relabel them as untouched.

## 7. Required negative cases

The following are specification additions to P1.8.94; they are not executable tests:

- NEG-STATE-05: EXECUTING or VERIFICATION_PENDING receives a generic BLOCKED request. Expected: reject BLOCKED; enter RECONCILIATION_REQUIRED and retain per-object uncertainty.
- NEG-OBS-01: observer report attempts to directly write canonical request state or clear quarantine. Expected: reject authority; record report only.
- NEG-OBS-02: observer report raises quarantine after a mutation may have begun. Expected: quarantine blocks future operations but canonical state becomes/remains RECONCILIATION_REQUIRED; no assertion that prior mutation was undone.
- NEG-STATE-06: mutation-start evidence is missing or contradictory. Expected: treat as possibly begun; BLOCKED prohibited; reconciliation required.

## 8. Acceptance and unresolved items

Design acceptance:
- [x] BLOCKED restricted to positively established pre-mutation states.
- [x] EXECUTING/VERIFICATION_PENDING and uncertain mutation paths route to RECONCILIATION_REQUIRED.
- [x] Observer report is separated from canonical state authority.
- [x] Protective quarantine is distinct, scoped, durable and cannot clear itself.
- [x] No timeout, heartbeat or missing log is treated as proof of no mutation.
