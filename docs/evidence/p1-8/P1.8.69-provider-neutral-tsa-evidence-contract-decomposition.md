## 1. Purpose

Decompose the P1.8.67 architecture into implementation-neutral evidence records and interface responsibilities. This is a contract for future design review, not a database schema, migration, API implementation, or authorization to modify T0.

The decomposition must preserve these invariants:

- T0 ingestion and durable commit do not depend on TSA availability.
- A timestamp intent can be retried without losing the identity of the original checkpoint.
- A network attempt and its outcome are recorded independently; timeout means UNKNOWN, not FAILED or NOT ISSUED.
- Every token is verified independently and remains linked to the exact request attempt and immutable signed checkpoint object.
- Historical evidence is append-only; later verification does not overwrite the original evidence or decision.
- Provider-specific fields remain adapter metadata and do not leak into the core evidence identity.

## 2. Logical evidence records

The names below are conceptual labels. They do not prescribe table names, column names, storage technology or implementation shape.

### 2.1 Checkpoint reference

Represents the immutable object selected for timestamping.

Required logical fields:

- stable checkpoint identity;
- checkpoint format/schema version;
- immutable event/ledger range or content-set reference;
- exact signed-object reference or preserved bytes;
- digest algorithm identifier and recomputed digest;
- reference to the P1.8.36 binding context;
- durable-commit evidence reference and its declared semantics;
- checkpoint seal status and creation provenance.

The record must not assert that a database commit is durable merely because a checkpoint was generated. The actual commit/WAL boundary remains implementation-specific and OPEN.

### 2.2 Timestamp intent

Represents the stable request objective for one checkpoint and one approved timestamp profile.

Required logical fields:

- stable intent ID;
- checkpoint ID and exact expected imprint;
- requested profile/policy identifier (versioned project profile, not a hard-coded vendor assumption);
- creation time and source provenance;
- current derived lifecycle status;
- references to every request attempt;
- reconciliation/exception history.

The intent ID remains stable across retries. It identifies the business/evidence objective, not an individual HTTP/RFC 3161 request. It must not be regenerated simply because a worker retries.

### 2.3 Request attempt

Represents one concrete protocol submission attempt.

Required logical fields:

- unique attempt ID;
- parent timestamp intent ID;
- provider adapter identity and adapter/configuration version;
- endpoint/profile identifier as observed at the time (sensitive credentials are never stored here);
- exact serialized RFC 3161 request bytes and digest;
- request nonce and nonce-profile metadata, where used;
- submission start/end observations and transport result;
- attempt outcome: RESPONSE_RECEIVED, DEFINITIVE_ERROR, or UNKNOWN;
- retry linkage and reason code.

A retry is a new attempt, not a mutation of the previous attempt. An attempt that times out after transmission remains UNKNOWN until reconciled; the system must not assume the TSA did not issue a token. Any nonce behavior, uniqueness requirements and retry timing remain OPEN pending the approved profile.

### 2.4 Token evidence

Represents one raw timestamp token returned by a provider.

Required logical fields:

- unique token-evidence ID;
- parent attempt ID and timestamp intent ID;
- original response bytes and cryptographic digest;
- parsed token identity: TSA name/issuer identity and serial number;
- message-imprint algorithm/value;
- policy OID and `genTime`;
- accuracy/ordering fields exactly as present (absence remains absence);
- signer certificate and chain references;
- raw response receipt provenance.

A token is untrusted input until the independent verifier completes. Parsing success is not verification success. Distinct valid tokens for the same intent must not be collapsed into one record.

### 2.5 Verification record

Represents one immutable verification decision over one token under one versioned trust profile.

Required logical fields:

- verification ID and token-evidence ID;
- verifier software/version and profile/configuration version;
- trust-anchor and certificate-policy snapshot references;
- recomputed expected imprint and comparison result;
- nonce/policy/algorithm/signature/certificate-path results;
- timestamp accuracy and clock-uncertainty evaluation;
- revocation evidence references and historical-time decision;
- terminal disposition: VERIFIED, REJECTED, or QUARANTINED;
- structured reason codes, verification time and reviewer/automation provenance.

A later verification under a new trust profile creates a new verification record. It does not rewrite the earlier result. The currently preferred interpretation can be derived from records under an approved policy, but the history remains immutable.

### 2.6 Revocation evidence

Represents raw signed OCSP or CRL material for the exact certificate/issuer relationship.

Required logical fields:

- evidence ID and exact certificate/issuer identifiers;
- evidence type (OCSP response or CRL);
- original signed bytes and digest;
- signer/responder identity and authorization result;
- CertID/issuer scope;
- `thisUpdate`, `nextUpdate`, `producedAt`, `revocationTime` where present;
- retrieval time and retrieval source;
- signature/path/freshness verification result;
- reference to the verifier profile used.

A parsed GOOD/REVOKED value without the original signed evidence is insufficient as the sole long-term record. Current GOOD must not be promoted to proof of historical validity.

### 2.7 Evidence package manifest

Provides a durable inventory of all bytes and provenance required for later verification.

Required logical fields:

- manifest ID/version;
- checkpoint and intent identifiers;
- all request attempts and token evidence references;
- all verification records and revocation evidence references;
- exact checkpoint object reference/bytes;
- certificate chain and policy-document snapshots;
- archive object digests, sizes, media types and integrity results;
- verifier and trust-profile versions;
- package creation/provenance and retention classification.

The manifest itself must be integrity-protected. Its storage, retention, immutability and restore guarantees require a separate implementation-specific review.

## 3. Relationship model

```text
Checkpoint 1
    |
    +---- Timestamp Intent 1
              |
              +---- Attempt 1 ---- Token Evidence 1
              |                         |
              |                         +---- Verification 1
              |                         +---- Revocation Evidence refs
              |
              +---- Attempt 2 ---- Token Evidence 2
              |                         |
              |                         +---- Verification 2
              |
              +---- Attempt 3 ---- UNKNOWN (no response captured)
              |
              +---- Evidence Package Manifest
```

One checkpoint may have multiple timestamp intents only when a distinct approved profile/purpose is explicitly defined. One intent may have multiple attempts. One attempt may produce no token, one token, or a response that contains multiple protocol-level items only if the selected profile explicitly permits and defines that case. One token may have multiple immutable verification records over time/profile versions.

No cardinality or uniqueness constraint is implemented or approved by this document.

## 4. State and transition contract

### 4.1 Two independent intent projections

Do not compress proof quality and request-delivery progress into one status. They answer different questions and must be projected independently from append-only records.

**Proof availability** (derived from token-level verification records):

- NONE: no token evidence has been received;
- VERIFIED: at least one token passes every required check under the currently approved profile;
- INDETERMINATE: no token is currently VERIFIED and at least one candidate is pending, quarantined or otherwise unresolved;
- REJECTED: no token is VERIFIED, all received candidate tokens have deterministic rejection results, and no request attempt remains unresolved.

**Attempt resolution** (derived only from request-attempt outcomes):

- NO_ATTEMPTS: no submission attempt has been created;
- IN_PROGRESS: at least one attempt is actively being submitted or captured;
- UNKNOWN_OUTCOME: at least one submitted attempt has no definitive captured outcome;
- ALL_RESOLVED: every recorded attempt has a definitive captured outcome.

**Retry disposition** (derived from the approved retry policy and attempt history):

- NOT_ELIGIBLE: no retry is currently permitted or required;
- ELIGIBLE: a retry is permitted but has not been scheduled;
- SCHEDULED: a retry is durably scheduled;
- EXHAUSTED: automated retry has stopped under the approved policy; manual reconciliation remains possible.

Attempt-resolution labels are non-exclusive facts, not a single enum: IN_PROGRESS and UNKNOWN_OUTCOME may both be true when one attempt is active and another has an unknown outcome. ALL_RESOLVED is true only when every recorded attempt has a definitive outcome and no attempt remains active or unknown. NO_ATTEMPTS applies only when the attempt count is zero.

These dimensions are independent of proof availability and of each other. For example, `proof_availability=VERIFIED`, `attempt_resolution=UNKNOWN_OUTCOME`, and `retry_disposition=ELIGIBLE` means a valid proof exists, but a prior submission may still have produced another unobserved token and a retry is permitted. It must not be displayed as fully reconciled. A state of ALL_RESOLVED does not imply proof is VERIFIED; it only means all recorded attempts have known outcomes.

A later response appends new attempt/token/verification evidence and recomputes the projections; it never erases the earlier UNKNOWN attempt, rejected token or failed attempt. The project must define any combined display as a deterministic presentation of these separate dimensions, not as a new authoritative state.

### 4.2 Attempt outcome contract

| Outcome | Meaning | Required handling |
|---|---|---|
| RESPONSE_RECEIVED | Response bytes captured | Persist raw bytes before trust decision |
| DEFINITIVE_ERROR | A protocol/provider error response was captured | Preserve raw error and classify under versioned mapping |
| UNKNOWN | Request may have reached TSA but no definitive response was captured | Preserve attempt; reconcile or retry without assuming non-issuance |

A transport exception before any bytes are sent may be classified differently only when the client can prove that fact. Ambiguous delivery remains UNKNOWN.

### 4.3 Verification disposition

| Disposition | Meaning |
|---|---|
| VERIFIED | Every required check passed under a specific approved profile |
| REJECTED | A deterministic cryptographic or profile violation was proven |
| QUARANTINED | Required evidence is missing, stale, contradictory, unsupported or ambiguous |

Missing evidence must not be converted into REJECTED if it is merely unavailable, nor into VERIFIED by optimistic default. The reason code must distinguish invalid from indeterminate.

## 5. Idempotency, retry and duplicate rules

1. Stable intent identity is derived from the immutable checkpoint reference plus the approved purpose/profile version; the exact construction remains OPEN.
2. Every network submission has a new attempt identity. Attempt identity is not the same as intent identity.
3. The client records the attempt before external submission so a crash/timeout cannot erase the fact that a request may have been sent.
4. A retry must not mutate or delete prior attempt/request/response bytes.
5. Local processing of a repeated delivery is idempotent for the same exact response bytes and attempt identity.
6. A distinct token serial/signature/response remains a distinct evidence object even when it covers the same imprint.
7. A timeout is not proof of no issuance; the system must preserve an UNKNOWN outcome and reconcile it under a future approved procedure.
8. No exactly-once network-delivery claim is made. The target is durable intent plus at-least-once retry and idempotent local evidence processing.

Retry interval, maximum attempts, dead-letter behavior, nonce generation profile, retention of idempotency records and provider-specific duplicate handling remain OPEN.

## 6. Interface responsibilities

The following are responsibility boundaries, not finalized method signatures.

| Component | Owns | Must not own |
|---|---|---|
| Checkpoint producer | Freeze exact object and durable-commit reference | TSA network or provider trust decisions |
| Intent/outbox coordinator | Stable intent, durable scheduling and reconciliation | Token trust validation |
| Provider adapter | Transport, request encoding, raw response/error capture | Declaring a token VERIFIED |
| Protocol parser | Strictly parse untrusted RFC 3161/OCSP/CRL bytes | Trust policy or historical acceptance decision |
| Independent verifier | Imprint, nonce, policy, signature, chain, time and revocation validation | Mutating original evidence |
| Evidence archive | Preserve immutable bytes, manifests and provenance | Rewriting evidence to fit a new verifier |
| Status projector | Derive current status from append-only records | Deleting or rewriting attempt history |

All external responses are untrusted until validated. Provider adapter changes and trust-profile changes must be versioned and traceable.

## 7. Integrity and retention requirements

- Store raw protocol bytes in their original form; parsed fields are supplementary.
- Verify content digests on write, read and package export under a future approved integrity policy.
- Keep evidence package manifests linked to immutable object identifiers and checkpoint IDs.
- Preserve historical certificate chains, signed status responses, CRLs and policy snapshots.
- Retain old verifier/profile identifiers so a historical decision can be reconstructed.
- Any re-verification, algorithm migration or supplemental timestamp must append new evidence and never replace original bytes or decisions.
- Retention period, archive storage class, replication, immutability mechanism, backup/restore and deletion policy remain OPEN.

## 8. Security and operational edge cases

| Scenario | Contract disposition |
|---|---|
| Same intent delivered twice to coordinator | One logical intent; append/reconcile without duplicate intent side effects |
| Same request response delivered twice | Idempotent local ingestion; retain original response bytes once per exact evidence identity |
| Same token attached to a different checkpoint | Reject due to parent/imprint mismatch |
| Same intent receives two different valid tokens | Preserve both; verify independently; do not assume ordering across TSAs |
| Timeout after request transmission | UNKNOWN attempt; no assumption of non-issuance |
| Provider changes policy OID or certificate | New profile/configuration review; historical evidence retains original identifiers |
| OCSP GOOD response is stale or unauthorized | QUARANTINED/REJECTED according to whether failure is indeterminate or proven invalid |
| Verifier version changes | New verification record; preserve old record |
| Evidence archive returns different bytes for a digest | Integrity failure; quarantine package and preserve incident evidence |
| Checkpoint committed but intent missing | Reconciliation must discover and create intent idempotently, if supported by implementation |
| Intent exists but checkpoint cannot be retrieved | Quarantine; do not submit an unverifiable object |

## 9. OPEN decisions and non-goals

The following remain OPEN and are intentionally not assigned values:

- stable intent-ID derivation and database uniqueness constraints;
- exact checkpoint canonicalization, domain separation and digest/signature algorithms;
- nonce generation, size, reuse and interoperability profile;
- TSA policy OID, certificate profile, trust-anchor and rollover policy;
- accuracy/uncertainty, clock and revocation equality semantics;
- attempt timeout, retry, backoff, concurrency and exhaustion limits;
- queue/outbox storage, transaction coupling and reconciliation cadence;
- archive format, storage, retention, deletion and restore controls;
- provider failover, multi-provider quorum and ordering semantics;
- commercial SLA, legal admissibility, jurisdiction and customer-facing claims.

Non-goals: selecting a TSA, creating database schema, writing code, provisioning storage, acquiring credentials, sending provider email, calling TSA/OCSP endpoints, freezing E1 fixtures, executing tests, staging, restore or fault injection.

## 10. Acceptance criteria

This decomposition is suitable for implementation planning only after review confirms:

1. Intent identity and attempt identity are separate.
2. Unknown outcomes are represented explicitly.
3. Raw request/response and revocation evidence are preserved.
4. Token verification is independent from transport and parsing.
5. Verification decisions are immutable and versioned.
6. Provider-specific details do not leak into core evidence identity.
7. Retry/idempotency claims do not imply exactly-once network delivery.
8. All schema, numeric, provider, trust and runtime decisions remain OPEN until separately approved.
