# P1.8.26 — Production Verification Protocol

**Status:** DESIGN COMPLETE — NOT EXECUTED.  
**Production assurance:** NOT VERIFIED for all 13 fault/negative vectors.  
**Authorization boundary:** This document defines a future isolated verification plan. It does not authorize production integration, runtime changes, destructive fault injection, exchange connectivity, live trading, or changes to T0/T1/VPS/database/Feeder.

## 1. Objective and assurance model

Convert the 13 synthetic fault/negative vectors into reproducible verification cases for a production-equivalent implementation. Verification must run first in an isolated disposable staging environment using the exact candidate database/provider, event store, observer implementation, key-management integration, and runtime components intended for production.

A synthetic reference model or SQLite test adapter is not evidence for a different production implementation or provider. Evidence must identify the exact binary/source SHA, configuration digest (with secrets excluded), database/provider/version, infrastructure profile, test inputs, fault point, observed state before and after restart, logs, and artifact hashes.

### Assurance labels

- **SYNTHETIC PASS:** test passed only in a synthetic/reference model.
- **STAGING PASS:** test passed in an isolated production-equivalent staging environment with reproducible evidence.
- **PRODUCTION NOT VERIFIED:** no approved production evidence exists.
- **BLOCKED:** prerequisites, isolation, evidence, or safety controls are missing.
- **FAIL:** observed behavior violates the stated invariant.

No vector may be promoted to STAGING PASS by inference from a different vector or from a synthetic result. No STAGING PASS automatically authorizes production rollout.

## 2. Mandatory prerequisites before any execution

All items below must be satisfied and recorded before the first staging fault test:

1. A production candidate implementation exists and is pinned to an immutable source SHA and build artifact digest.
2. The exact database engine/provider, version, durability settings, filesystem/storage class, and topology intended for deployment are documented.
3. An isolated, disposable staging environment is provisioned separately from current T0/T1, the evaluation VPS, and any production-like data that must be preserved.
4. Staging uses synthetic accounts, synthetic events, and test-only signing keys. No exchange credentials, production keys, customer secrets, or live orders are permitted.
5. Network egress is denied by default. Explicit allow-listing is limited to required test dependencies; exchange/order endpoints remain blocked.
6. Snapshot/restore and environment teardown are rehearsed before destructive tests. A verified clean baseline is captured for every test batch.
7. Clock source, maximum clock uncertainty, event timestamp semantics, and permitted skew are specified.
8. Observer identities and authorization boundaries are explicit; test identities cannot impersonate production observers.
9. Test runner, fault injector, and evidence collector are versioned and independently identified.
10. A run manifest binds source SHA, build digest, configuration digest, environment identifier, provider/version, test case ID, and evidence artifact hashes.
11. Stop conditions are automated: unexpected external network access, non-test credentials, unbounded retries, unplanned writes outside the disposable environment, missing telemetry, or inability to restore baseline immediately stops the batch.
12. A separate explicit approval is obtained before any test that could affect a persistent shared service. This protocol alone grants no such approval.

If any prerequisite is missing, mark the affected case BLOCKED; do not substitute a weaker environment and claim equivalence.

## 3. Test-case protocol for the 13 vectors

Each case must execute at least once from a clean baseline, then repeat under process restart/replay where relevant. Concurrency and crash tests require controlled, repeatable fault points. Store the full event journal and state snapshots as test artifacts, with secrets redacted.

| ID | Test scenario | Required staging procedure | PASS criteria |
|---|---|---|---|
| V01 DUPLICATE_IDENTICAL_DELIVERY | Deliver identical canonical event bytes repeatedly, including after consumer restart and retry from a second worker. | Record event ID, canonical byte digest, accepted sequence, and durable side effects before/after replay. | Exactly one logical application; retries are acknowledged idempotently; no duplicate ledger/observer side effect; state and digest remain unchanged. |
| V02 SAME_EVENT_ID_CHANGED_BYTES | Re-submit an existing event ID with altered canonical bytes, including altered payload and metadata. | Attempt through normal ingress and recovery/replay paths. | Reject and alert; original durable bytes and state remain unchanged; no overwrite or second application occurs. |
| V03 MISSING_SEQUENCE | Omit one sequence, then deliver later sequence; repeat with delayed arrival of the missing event. | Exercise live ingest, restart, and replay. | Gap is detected; later event is not silently committed as a contiguous stream; recovery behavior is deterministic and auditable. |
| V04 WRONG_PREVIOUS_HASH | Supply a validly shaped event with an incorrect predecessor hash. | Test at ingress, replay, and checkpoint validation boundaries. | Hash-chain validation fails closed; checkpoint does not advance past invalid data; integrity incident is recorded. |
| V05 INVALID_SIGNATURE | Sign test payload with a different test key or mutate signed bytes after signing. | Verify exact canonical bytes at every trust boundary. | Signature verification rejects; event is quarantined/rejected; no downstream state mutation occurs. |
| V06 UNKNOWN_SIGNING_KEY | Submit otherwise valid signed event with unknown key ID. | Test before and after service restart and key-cache refresh. | Unknown key fails closed; no fallback or implicit trust; rejection is auditable. |
| V07 REVOKED_SIGNING_KEY | Revoke test key, then submit events signed before and after revocation boundary according to declared policy. | Exercise cache refresh, restart, delayed delivery, and key rotation overlap. | Behavior matches a documented effective-time policy; revoked key cannot authorize events outside its allowed interval; unknown revocation state fails closed. |
| V08 CHECKPOINT_BOUNDARY | Deliver an event whose occurrence time is before boundary but durable commit is after seal; also test missing timestamps and boundary equality. | Race event commit against checkpoint seal using deterministic barriers. | Checkpoint excludes or rejects late-committed pre-boundary events according to policy; no event is silently omitted or double-counted; boundary decision is reproducible. |
| V09 RECOVERY | Crash the consumer at each durable transition: before write, after write/before ACK, after ACK, and during replay. | Use process termination first; then host restart and storage restart only in disposable staging. | Recovery converges to one valid state; acknowledged work is durable; unacknowledged work is replayable; no loss, duplication, or invalid checkpoint. |
| V10 REDUCE_CLOSE_REVERSAL | Exercise partial reduction, exact close, over-reduction, duplicate close, and opposite-side reversal. | Replay command/event sequences through the actual ledger/position transition implementation. | Reductions preserve positive remaining quantity; close consumes exact remainder once; reversal requires prior close and references the correct predecessor; invalid transitions fail closed. |
| V11 UNKNOWN_FEE_FUNDING | Omit fee/funding fields, provide explicit unknown status, and delay final values. | Recompute equity before and after delayed fee/funding reconciliation. | Unknown never becomes zero by default; equity is marked incomplete/not valuation-ready; final recomputation is traceable and idempotent. |
| V12 STALE_MARK | Supply stale, future-dated, missing, invalid, and clock-uncertain marks. | Vary source timestamps, receive timestamps, and bounded clock uncertainty. | Mark is rejected when age/uncertainty exceeds policy; valuation and risk consumers receive not-ready status; no stale mark is silently treated as current. |
| V13 ROOT_B_DUPLICATE_ACK_CRASH | Use two independently authenticated test observers; duplicate ACK; terminate process after durable checkpoint write but before ACK; reopen and replay. | Repeat with database restart and controlled concurrent ACK submissions. | Duplicate ACK is idempotent only for same observer/event/digest; changed digest is rejected; durable checkpoint is recovered once; ACK counts and checkpoint digest remain consistent. |

## 4. Cross-cutting verification requirements

### 4.1 Durability and storage

- Verify database transaction boundaries and documented durability mode.
- Demonstrate acknowledged commits survive process termination and the provider's documented restart scenario.
- Test storage restart and host-level failure only in disposable staging with provider-approved fault methods.
- Do not claim power-loss or device-failure coverage unless the exact failure mode was actually induced and independently evidenced.
- Filesystem corruption tests must use disposable copies/volumes; never corrupt shared or production storage.

### 4.2 Concurrency and distributed execution

- Run at least two independent worker processes; multi-host tests require separate hosts and independently recorded identities.
- Force overlap at event append, observer ACK, checkpoint seal, and recovery boundaries.
- Record lock/fencing tokens, transaction IDs, observer IDs, sequence numbers, and final durable state.
- Verify stale lease holders cannot write after fencing and that opposing workers cannot both claim exclusive ownership.
- Repeat concurrency cases enough times to cover each deterministic interleaving; randomized stress runs supplement but do not replace deterministic cases.

### 4.3 Cryptographic key lifecycle

- Use test-only keys held by the intended key-management integration, not hard-coded fixtures alone.
- Verify unknown, revoked, expired, rotated, and unavailable revocation-state behavior.
- Record key IDs and public-key fingerprints only; never place private key material in logs or artifacts.
- Define effective-time semantics for late-arriving signed events before testing revocation.

### 4.4 Business-state consistency

- Compare event journal, observer acknowledgements, checkpoints, position ledger, fees/funding, and valuation outputs.
- Require deterministic reconciliation reports with zero unexplained differences.
- Opposing LONG/SHORT exposures must not be netted merely to make a reconciliation pass.
- No order placement or exchange write endpoint may be enabled during this protocol.

## 5. Evidence package contract

Every case must emit a machine-readable manifest and human-readable report containing:

- Protocol version and case ID (V01–V13).
- Repository, branch, exact source SHA, build artifact digest, test harness SHA.
- Workflow run ID, job IDs, and artifact IDs/retention expiry.
- Environment ID, provider, database engine/version, storage profile, topology, and clock source.
- Sanitized configuration digest; explicit confirmation that secrets and production credentials were absent.
- Baseline snapshot digest and post-test/recovery snapshot digest.
- Event IDs, sequence ranges, observer IDs, checkpoint IDs, and relevant transaction/fencing identifiers.
- Fault injection point and exact action/timestamp.
- Expected invariant, observed result, assertions, logs, and independent verifier result.
- Final status: PASS / FAIL / BLOCKED / NOT VERIFIED.
- Limitations, deviations, and cleanup/restore proof.

Artifacts must be retained in GitHub Actions and durable Git evidence according to repository policy. Do not store secrets, raw private keys, exchange credentials, or sensitive user data in evidence.
