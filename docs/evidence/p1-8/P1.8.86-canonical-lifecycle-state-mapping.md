# P1.8.86 — Canonical Lifecycle State Mapping

Date: 2026-11-09  
Status: DOCUMENTARY DESIGN ONLY — NOT IMPLEMENTED / NOT ACTIVE / NOT AUTHORIZED  
Closes review finding: DR-02 (MAJOR)

## 1. Purpose

This document defines the canonical state domains and their allowed conceptual relationships across dataset lifecycle, consumer dependencies, holds, copies, deletion requests, approvals, execution authorizations, per-object execution and evidence. It prevents separate contracts or future components from collapsing unrelated states into one global lifecycle enum.

This mapping supplements the governing lifecycle contracts. More protective interpretation wins. No state in this document grants archive, deletion or storage-mutation authority.

## 2. Independent state domains

### 2.1 Dataset lifecycle

- DISCOVERED — identity known, classification/ownership may remain incomplete.
- ACTIVE — retained and available under its current policy.
- REVIEW_REQUIRED — policy, demand or evidence review is due; data remains protected.
- ARCHIVE_CANDIDATE — archive may be evaluated; no archive authority.
- ARCHIVED — exact archive operation independently verified and archive availability obligations met.
- DISPOSITION_REVIEWABLE — may enter deletion eligibility review; not eligible or authorized by this label alone.
- DELETION_VERIFIED_WITHIN_SCOPE — exact authorized scope independently verified as disposed under declared semantics.
- BLOCKED — a known guard prevents transition.
- UNKNOWN — identity, state, policy or evidence cannot be established.

No automatic transition from age, TTL, inactivity, missing heartbeat or absent consumer observation is allowed.

### 2.2 Consumer dependency

- UNREGISTERED — no accepted registration record; does not prove no consumer exists.
- ACTIVE — dependency is registered and protective.
- RELEASE_REQUESTED — consumer requested release; still protective.
- RELEASE_REVIEW — ownership/identity/evidence is being reconciled; still protective.
- RELEASED — authoritative, authenticated, purpose-bound release by that consumer is committed.
- TRANSFER_PENDING — ownership transfer unresolved; protective.
- UNREACHABLE — consumer cannot be contacted; protective.
- CONFLICTED / UNKNOWN — inconsistent or unavailable state; protective.

ACK is an observation/receipt event, not a dependency state transition to RELEASED.

### 2.3 Hold

Use P1.8.85 states: DRAFT, ACTIVE, REVIEW_DUE, CHANGE_PENDING, REVOCATION_PENDING, REVOKED, SUPERSEDED, CONFLICTED, UNKNOWN. REVIEW_DUE and pending changes retain protection.

### 2.4 Copy lifecycle

- IDENTIFIED — exact copy identity recorded.
- INVENTORY_PENDING — lineage, owner, destination or completeness incomplete.
- VERIFIED_WITHIN_SCOPE — inventory evidence supports only the declared boundary.
- ACTIVE_COPY — retained copy with obligations.
- ARCHIVE_CANDIDATE — eligible for separate archive review only.
- ARCHIVED_VERIFIED — archive operation and required availability independently verified.
- DISPOSITION_REVIEWABLE — may enter its own eligibility process.
- DISPOSITION_IN_PROGRESS — exact authorized copy operation started.
- DISPOSITION_RECONCILIATION — partial, ambiguous or residual outcome.
- DISPOSITION_VERIFIED_WITHIN_SCOPE — declared copy operation independently verified.
- UNKNOWN / CONFLICTED — protective.

A source dataset transition does not automatically transition any copy.

### 2.5 Deletion request

- PROPOSED
- ELIGIBILITY_REVIEW
- ELIGIBLE_FOR_APPROVAL
- REJECTED
- APPROVED
- AWAITING_EXECUTION_AUTHORIZATION
- EXECUTION_AUTHORIZED
- EXECUTING
- RECONCILIATION_REQUIRED
- VERIFIED_COMPLETE_WITHIN_SCOPE
- CANCELLED
- EXPIRED
- BLOCKED

APPROVED is not EXECUTION_AUTHORIZED. EXPIRED does not authorize retry or cleanup. VERIFIED_COMPLETE_WITHIN_SCOPE requires independent verification and may not claim global deletion if copy inventory is incomplete.

### 2.6 Approval package

- NOT_CREATED
- DRAFT
- SUBMITTED
- APPROVED
- REJECTED
- INVALIDATED
- WITHDRAWN

Approval binds exact manifest, policy version, evidence revisions, dependency/hold decision point, identities, operation and verification plan. Any material change invalidates approval and requires a new review.

### 2.7 Execution authorization

- NOT_REQUESTED
- PENDING_FINAL_RECHECK
- AUTHORIZED
- REVOKE_PENDING
- REVOKED
- EXPIRED
- CONSUMED
- INVALIDATED
- CONFLICTED

Authorization is narrow, single-purpose, exact-scope and time-bounded only after a trusted-time policy is approved. No lifetime is set here. Authorization cannot be reused for a changed manifest or different operation.

### 2.8 Per-object execution

- NOT_STARTED
- PRECONDITION_CHECK
- MUTATION_SUBMITTED
- MUTATION_CONFIRMED
- OUTCOME_AMBIGUOUS
- PARTIAL
- BLOCKED
- RECONCILIATION_REQUIRED
- VERIFIED_WITHIN_DECLARED_SEMANTICS
- NOT_VERIFIED

Each object has an immutable identity and generation/version. A batch request does not imply atomicity across objects. Unknown outcome is not success and must not trigger blind retry.

### 2.9 Evidence lifecycle

- EXPECTED
- CAPTURED
- VALIDATED
- CONFLICTED
- STALE
- REVOKED
- RETAINED
- DISPOSITION_REVIEWABLE
- DISPOSITION_VERIFIED_WITHIN_SCOPE
- UNKNOWN

Evidence validity and evidence retention are separate. A stale evidence record is not silently deleted; it may be retained for audit or replaced by a newer linked record.

## 3. Cross-domain transition guards

A transition in one domain never grants a transition in another. Examples:
- dependency RELEASED does not set dataset DISPOSITION_REVIEWABLE;
- dataset ARCHIVED does not set copy ARCHIVED_VERIFIED;
- approval APPROVED does not set authorization AUTHORIZED;
- authorization AUTHORIZED does not set object MUTATION_CONFIRMED;
- executor MUTATION_CONFIRMED does not set request VERIFIED_COMPLETE_WITHIN_SCOPE;
- source hold REVOKED does not revoke a copy-specific hold;
- source deletion does not imply backup, replica, export or evidence deletion;
- request CANCELLED does not reverse already completed object mutations;
- evidence CAPTURED does not mean evidence VALIDATED.

Each transition must record source domain, prior state, new state, actor/service authority, event ID, exact subject, policy version, evidence reference and authoritative ordering token. State changes must be idempotent and reject stale revisions.

## 4. Terminality, invalidation and re-entry

Terminal states are terminal only within their own domain and exact version. A corrected request uses a new request identity linked to the prior request; it must not rewrite history. A new approval or authorization is required after invalidation, material evidence change, scope change, policy change or unresolved reconciliation.

CANCELLED, REJECTED, EXPIRED, BLOCKED and NOT_VERIFIED are not success. RECONCILIATION_REQUIRED remains protective until independently resolved. No automatic transition out of UNKNOWN, CONFLICTED or UNREACHABLE is permitted.

## 5. Canonical event and ordering requirements

Every state transition must bind:
- stable domain and entity ID;
- immutable entity version or generation;
- prior-state revision and resulting revision;
- event ID and idempotency identity;
- authenticated actor/service and authority;
- trusted ordering evidence, once separately selected;
- exact policy and contract version;
- evidence references and integrity digests.

Duplicate events are idempotently recognized; reordered or stale events are rejected or quarantined. If ordering cannot be established, preserve the more protective state and require reconciliation.
