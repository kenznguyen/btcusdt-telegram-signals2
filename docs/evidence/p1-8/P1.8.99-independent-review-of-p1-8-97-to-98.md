## 5. Findings

### IR2-01 — MAJOR: Generic transition to BLOCKED can bypass mandatory reconciliation for in-flight execution

**Evidence:** P1.8.97 §3, first row: “Any non-terminal state → BLOCKED”; compare P1.8.92 §4 and P1.8.97 §3/§5.

The generic row permits any non-terminal request state to enter BLOCKED. That includes EXECUTING and potentially VERIFICATION_PENDING. P1.8.92 instead requires an in-flight ambiguous, partial, conflicting or interrupted outcome to enter RECONCILIATION_REQUIRED. P1.8.97 also states that an observer may trigger protective quarantine.

Without a precise distinction, an observer report or generic guard failure could move an in-flight request to BLOCKED and obscure per-object uncertainty, bypassing the mandatory reconciliation path.

**Required correction:** restrict BLOCKED to pre-mutation eligibility/approval/final-recheck states. For EXECUTING, VERIFICATION_PENDING or any state where a mutation may have begun, route the event to RECONCILIATION_REQUIRED (or a narrowly defined protective quarantine that cannot replace the canonical request state). State explicitly that an observer cannot rewrite the canonical state directly.

### IR2-02 — MAJOR: Partial cancellation can be terminalized while object outcomes remain ambiguous

**Evidence:** P1.8.97 §3 row “RECONCILIATION_REQUIRED → CANCELLED_WITH_PARTIAL_OUTCOME”; §5; compare P1.8.92 §§2 and 6 and P1.8.84 N31/N32/N39.

The row permits transition after reconciliation even when “ambiguous objects remain NOT_VERIFIED.” P1.8.92 and P1.8.84 require reconciliation and verification of completed/remaining scope before a partial-cancellation terminal outcome. An unresolved object cannot simultaneously be a known reconciled outcome and an outstanding ambiguous operation.

**Required correction:** if any object remains OUTCOME_AMBIGUOUS, keep the request RECONCILIATION_REQUIRED (or NOT_VERIFIED where the applicable terminal rule is met); do not terminalize as CANCELLED_WITH_PARTIAL_OUTCOME. Permit partial-cancellation terminality only when every manifest object has a determinate disposition, all remaining operations are stopped, and residual/verification boundaries are explicit. If uncertainty is irrecoverable, preserve a NOT_VERIFIED outcome, not a successful or fully reconciled terminal label.

### IR2-03 — MAJOR: BLOCKED → FINAL_RECHECK guard does not state a positive proof that no mutation began

**Evidence:** P1.8.97 §3 row “BLOCKED → FINAL_RECHECK”.

The phrase “no mutation has begun under an ambiguous outcome” is not a crisp positive precondition. It can be read as excluding only ambiguous starts while leaving a known or partially committed mutation path insufficiently constrained. A direct transition from BLOCKED to FINAL_RECHECK is safe only if the request is proven pre-mutation and no object intent/side effect exists.

**Required correction:** require authoritative, complete proof that no object mutation intent was accepted and no side effect began for any manifest object, with all per-object states NOT_STARTED and no ambiguous/lost-response record. If this cannot be proven, require RECONCILIATION_REQUIRED.

### IR2-04 — OBSERVATION: Vector semantics are now materially stronger, but remain specifications

The five new vectors directly isolate the missing conditions. The distinction between NEG-REC-03 and NEG-ADP-07, NEG-T3-02 and NEG-T3-01, and NEG-EVD-06 and NEG-EVD-07 is sound. NEG-ADP-10 supplements rather than replaces backend-specific residual cases.

No vector has been executed. The catalogue remains NOT_RUN and is not executable coverage evidence.
