## 1. Binding policy and assurance rules

P1.8.30-v1 is the owner-approved policy baseline:
- DEC-01 = C: quarantine/fail-closed when key validity or revocation state cannot be proven.
- DEC-02 = C: hybrid event-time + watermark + durable commit-time checkpoint membership.
- DEC-03 = B: proposed RPO/RTO values remain planning targets, not approved SLOs or measured capabilities.

This document is subordinate to that baseline. If an acceptance rule conflicts with P1.8.30, stop and resolve the conflict in a new versioned decision record; do not silently reinterpret either document.

### Assurance labels

Every claim and evidence row must carry one of these labels:
- **SYNTHETIC:** deterministic local/reference-model evidence; not proof of target-provider or production behavior.
- **STAGING:** evidence from a named, isolated, disposable staging environment with recorded equivalence limits.
- **PRODUCTION:** evidence from the actual production topology and operational controls. No production execution is authorized by this document.

A PASS at one level cannot be promoted to another level. Environment equivalence is claim-scoped; there is no single global “equivalent” label.

## 3. Scenario corpus and denominator contract (F01)

For each vector and each test level, publish:
1. A stable scenario ID and immutable fixture digest.
2. A distinct base-event population with unique event IDs.
3. The number of generated deliveries, retries, duplicate attempts and replay attempts.
4. Inclusion/exclusion criteria, including why a scenario is representative.
5. Expected outcomes per base event and per attempt.
6. The observed outcome count and a machine-checkable reconciliation proving numerator ≤ denominator where applicable.
7. Any untested branches and the resulting assurance limitation.

A test may not claim “100% coverage” from a denominator that counts retries as independent base events. If scenario corpus breadth or denominator cannot be independently reconstructed, the vector is NOT VERIFIED regardless of a green test process.

## 4. Independent observer and principal contract (F02)

“Independent observer” means operational separation demonstrated by evidence, not merely two process names.

Before a concurrency or recovery run, record:
- unique principal/identity for each observer;
- issuer and credential fingerprint (never the secret);
- distinct authorization scope and access path;
- process, host and failure-domain placement;
- independent observation channel or independently collected output;
- clock source and uncertainty;
- evidence that neither observer can rewrite the other's evidence;
- shared dependencies, if any, and the limits those dependencies impose.

A second process using the same principal, credential, mutable result file or unverified shared host is not proof of independent observation. If the test objective requires independence and separation is not demonstrated, mark the claim BLOCKED/NOT VERIFIED.

## 5. Durability claim contract (F03/F04)

Use explicit durability levels. The run manifest must define the exact storage boundary and failure domain tested; do not infer a stronger level from a successful API response.

| Level | Claim boundary | Minimum evidence required |
|---|---|---|
| D0 | In-process acceptance only | State transition and process-local result; no durable claim |
| D1 | Process restart boundary | Restart/reopen proof and exact persisted state |
| D2 | Host or OS restart boundary | Target-environment restart evidence and post-restart integrity/reconciliation |
| D3 | Storage/device failure boundary | Approved disposable failure method, provider/storage semantics and independent integrity proof |
| D4 | Site/provider/failure-domain boundary | Explicit topology/failure-domain definition, independent surviving copy and recovery proof |

D0–D4 labels are not interchangeable with generic “durable.” If a level is not tested, state NOT TESTED. D3/D4 require a separate safe method review and explicit authorization; this document does not authorize destructive or provider-level fault injection.

### Durable ACK and acknowledged-transaction RPO

Before asserting acknowledged-transaction RPO 0, freeze:
- the exact ACK point and API response semantics;
- the transaction/commit boundary;
- the storage flush/sync guarantees relied upon;
- the failure domain against which zero loss is claimed;
- the observer that records ACK and its independent evidence;
- the post-failure reconciliation method and exact transaction population.

RPO 0 applies only to that tested boundary and failure domain. It is not a universal guarantee across untested provider-wide or regional failures.

## 6. DEC-01 / V07 acceptance contract — revocation

P1.8.30 option C is binding. Before V07 execution, the test specification must freeze these parameters (currently unresolved):
- trusted timestamp authority, proof format and verification procedure;
- maximum revocation-state/cache age and units;
- revocation propagation bound and authoritative effective-time source;
- rotation overlap interval and old-key acceptance cutoff;
- quarantine reason codes, operator/release authority and reprocessing procedure;
- behavior for unavailable, stale, contradictory or unreachable revocation state.

### Required fixtures and outcomes

| Fixture class | Required condition | Acceptance oracle |
|---|---|---|
| Valid active key | Signature valid; key active at trusted signing time | Accept only if all other event invariants pass |
| Revoked key, post-effective time | Trusted signing time is at/after effective revocation | Reject/quarantine; never accept |
| Claimed pre-revocation event | Signed before effective time with verifiable trusted timestamp | Apply frozen historical-validity rule; record proof and policy version |
| Unknown key | Key ID absent from trusted key registry | Reject/quarantine; no fallback trust |
| Unknown revocation state | Authority unavailable or status cannot be established | Fail closed; reject/quarantine |
| Stale cached state | Cache age exceeds frozen maximum | Fail closed; do not treat stale state as current |
| Conflicting status | Sources disagree or effective time is ambiguous | Quarantine; require auditable resolution |
| Rotation overlap | Old/new key events inside and outside frozen overlap | Deterministic acceptance/rejection at exact boundary |
| Forged timestamp | Timestamp proof invalid, missing or untrusted | Reject/quarantine; no client timestamp substitution |

Required evidence: fixture digest, public-key fingerprint, key ID, trusted timestamp proof reference, revocation status/version, policy version, decision/reason, and replay determinism. Never include private keys or secret credentials.

**V07 gate:** BLOCKED until all parameters, fixture bytes/digests, boundary cases, reason codes and expected outputs are frozen in a versioned test contract. Approval of the policy direction does not fill these parameter values.

## 7. DEC-02 / V08 acceptance contract — checkpoint membership

P1.8.30 option C is binding. Before V08 execution, freeze:
- watermark generation/advancement algorithm;
- allowed lateness/grace interval and units;
- event-time window definition and timezone/precision;
- inclusion rule at exact boundary equality;
- authoritative clock and maximum clock uncertainty;
- commit-time source and durable-commit evidence;
- seal race arbitration/barrier ordering;
- late-event/correction schema, sequence and reconciliation semantics.

### Required deterministic fixtures

| Fixture class | Required condition | Acceptance oracle |
|---|---|---|
| In-window committed event | Event time in window; watermark permits closure; durable commit precedes seal | Included exactly once |
| Event-time outside window | Durable event but event time outside target interval | Excluded from that checkpoint |
| Watermark not advanced | Window otherwise populated but completeness threshold not reached | Checkpoint cannot seal as complete |
| Late arrival before seal | Event time in window, arrives within frozen lateness rule | Apply frozen watermark rule deterministically |
| Late arrival after seal | Event arrives/commits after immutable seal | Original checkpoint unchanged; correction path required |
| Commit after seal barrier | Event time eligible but durable commit is later than seal gate | Excluded from sealed checkpoint |
| Exact boundary equality | Timestamp equals lower/upper boundary | Follow explicit inclusive/exclusive rule |
| Seal/commit race | Commit and seal contend at deterministic barrier | One defined serialization outcome; no ambiguous membership |
| Invalid/untrusted time | Missing, malformed, future-dated or excessive clock uncertainty | Hold/reject/quarantine; never guess |
| Replay/correction duplicate | Same late event/correction replayed | Idempotent correction lineage; no silent mutation |

For every fixture, capture event ID, occurred_at, received_at, committed_at, watermark value/version, boundary_at, sealed_at, checkpoint ID/digest, membership result and correction lineage where applicable.

**V08 gate:** BLOCKED until parameters, fixtures, barriers, equality semantics and correction contract are frozen and independently reviewed.

## 8. Restore acceptance contract (DEC-03)

DEC-03 option B retains planning targets only:
- acknowledged transaction RPO: 0, only for a declared tested durability boundary/failure domain;
- snapshot RPO: ≤5 minutes;
- staging RTO: ≤60 minutes;
- three independent restore rehearsals.

Before a restore proposal, define:
- source snapshot identity, creation/consistency point and digest;
- exact transaction population committed before snapshot and before failure;
- failure declaration and RTO start event;
- service-ready criteria and RTO stop event;
- how missing committed data is measured for snapshot RPO;
- integrity, event-chain, sequence/checkpoint and ledger reconciliation oracles;
- independence criteria for the three rehearsals (distinct run IDs and separately captured evidence; explain shared snapshot/provider dependencies);
- rollback/cleanup and evidence retention.

Each rehearsal must produce its own manifest, raw evidence, restored-state digest, reconciliation report and independent artifact-hash verification. Three retries of one restore process do not count as three independent rehearsals.

The target values are not measured capabilities or production SLOs. Restore acceptance remains BLOCKED until the measurement contract is frozen and a separate staging execution is explicitly authorized.

## 10. Evidence package and independent verification

Every executed run must contain:
1. Frozen run manifest and policy/contract digests.
2. Source commit SHA, tree SHA and exact test/harness revisions.
3. Scenario corpus and fixture digests.
4. Raw machine-readable event log and observer outputs.
5. Expected-vs-observed reconciliation, including base-event denominator and attempt counts.
6. Environment inventory and claim-scoped equivalence assessment.
7. Failure/barrier timeline with trusted timestamps and clock uncertainty.
8. Artifact manifest containing file path, byte length and SHA-256 for every evidence file.
9. Independent verifier identity and independently recomputed artifact hashes.
10. Final status per vector and per assurance level, including all exclusions and limitations.

An artifact hash copied from the producer's manifest is not independent verification. The verifier must obtain the artifact independently and recompute its digest. Missing artifacts, mismatched hashes, incomplete logs or non-reproducible denominators result in NOT VERIFIED.

## 11. Stop conditions

Stop the run and preserve evidence if:
- the source SHA, policy digest or manifest changes after freeze;
- a required principal/observer is not independent as declared;
- clocks exceed the frozen uncertainty bound;
- the provider/storage behavior differs from the declared contract;
- an unexpected write escapes the disposable test scope;
- a fixture or expected oracle is missing or modified;
- a destructive action is requested without separate authorization;
- raw evidence is lost, altered or cannot be independently hashed;
- observed behavior violates an invariant or cannot be deterministically explained.

Do not retry away a failure. Record the first failure, preserve state and logs, and open a new versioned review.
