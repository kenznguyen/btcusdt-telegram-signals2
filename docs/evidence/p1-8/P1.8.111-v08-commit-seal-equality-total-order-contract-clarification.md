# P1.8.111 — V08 Commit/Seal Equality and Total-Order Contract Clarification

**Version:** P1.8.111-v1  
**Closes:** P1.8.109 IR109-02 (MODERATE)  
**Depends on:** P1.8.34, P1.8.106, P1.8.109  
**Type:** Documentation-only checkpoint contract clarification  
**Status:** DESIGN CLARIFICATION RECORDED — ORDERING TOKEN/PROVIDER OPEN — NOT EXECUTED

## 1. Purpose and boundary

This contract freezes the disposition of commit/seal equality and overlapping time intervals. A timestamp comparison alone MUST NOT be treated as proof of transaction order.

It does not select a database, commit sequence, WAL/LSN mechanism, provider, clock, precision or watermark algorithm. It does not authorize collector/checkpoint changes, data writes, staging or lifecycle mutation.

## 2. Governing rules

1. Preserve P1.8.34: UTC half-open event-time windows `[start,end)`; watermark seal eligibility remains `watermark >= window_end`.
2. Preserve P1.8.106: checkpoint membership depends on explicit source progress, durable commit evidence, a deterministic seal gate and immutable checkpoint contents.
3. A transaction is included only if authoritative evidence proves its durable commit linearized before the seal barrier for the exact checkpoint generation.
4. A transaction is excluded from that sealed checkpoint only if authoritative evidence proves its durable commit linearized after the seal barrier. It must follow the separately governed late-event/correction path.
5. Equal timestamps, equal representable sequence values, overlapping uncertainty intervals, missing ordering tokens or incomparable ordering domains are **UNKNOWN / HOLD**. They are not rounded, tie-broken by wall clock, assigned by arrival order or guessed.
6. A correction does not mutate the sealed checkpoint and cannot retroactively change its membership.

## 3. Required total-order evidence

A future implementation MUST provide an authoritative order proof that binds:

- exact dataset ID/version, source and partition;
- exact checkpoint ID/generation and window boundaries;
- exact transaction/event ID and immutable payload digest;
- durable commit identity and implementation-specific commit position/token;
- seal-barrier identity and its durable position/token;
- ordering-domain identity and comparison semantics;
- clock source, precision and uncertainty evidence where timestamps are used;
- persistence/provider contract revision and verifier result.

The ordering token MUST be generated by, or transactionally coupled to, the actual durable commit/seal authority. It must be unique or otherwise totally ordered within its explicitly declared scope. A client timestamp, ingestion arrival time, API response time, queue offset from an unrelated domain or host-local sequence is not sufficient.

If the implementation cannot produce comparable commit and seal positions, it cannot claim deterministic membership for the affected boundary. That scope remains HOLD/BLOCKED pending an independently proven resolution.

## 4. Equality and interval disposition matrix

| Evidence relationship | Required disposition |
|---|---|
| Commit token strictly precedes seal token in the same proven ordering domain | Eligible for that checkpoint, subject to all other V08 gates |
| Seal token strictly precedes commit token in the same proven ordering domain | Excluded from sealed checkpoint; correction path |
| Same timestamp, different tokens with proven total order | Follow token order, not timestamp equality |
| Same timestamp and no comparable token | UNKNOWN / HOLD |
| Same representable sequence/position and no documented tie-order semantics | UNKNOWN / HOLD |
| Commit uncertainty interval overlaps seal uncertainty interval | UNKNOWN / HOLD |
| Clock intervals are disjoint but token/order domain is absent | Insufficient by itself; HOLD unless contract proves temporal comparison is authoritative |
| Missing commit receipt or durable boundary proof | BLOCKED |
| Missing seal-barrier proof | BLOCKED |
| Different or incomparable ordering domains | UNKNOWN / HOLD |
| Conflicting provider history and checkpoint manifest | CONFLICT / QUARANTINE |
| Watermark reaches window end but partition progress is incomplete | BLOCKED; watermark scalar cannot hide missing partitions |

No default precision, tolerance or tie-breaking rule is introduced.

## 5. Required fixture catalogue

Future frozen fixtures must include at least:

- commit strictly before seal;
- commit strictly after seal;
- exact same timestamp with distinct ordered tokens;
- exact same timestamp without ordering token;
- exact equal sequence/position with undocumented tie semantics;
- overlapping trusted-time uncertainty intervals;
- non-overlapping intervals but incomparable ordering domains;
- missing commit receipt;
- missing seal receipt;
- token from a different dataset/checkpoint generation;
- duplicated token and conflicting transaction ID;
- partition watermark complete while another partition is missing;
- late event routed to append-only correction;
- replay of the same checkpoint manifest;
- provider history contradicting the manifest.

Each fixture must assert exact membership, HOLD/BLOCKED/CONFLICT disposition and no mutation of an already sealed checkpoint. No fixture code or test execution is included.

## 6. Lifecycle effect

V08 closure is only one input to central lifecycle eligibility. A checkpoint that passes this contract does not release consumer dependencies, remove audit/replay/training/backtest demand, override holds, make source data disposable, or authorize archive/deletion.

T0 remains canonical and independently governed. T1–T4 consumers cannot mutate/delete T0 source versions. Source, checkpoint, correction and derived-output lifecycles remain separate.

## 7. OPEN items

Actual durable commit semantics; seal linearization mechanism; ordering-token format and uniqueness; provider/DB guarantee; partition progress and idle-partition policy; watermark algorithm; clock authority/precision/uncertainty; allowed lateness; correction schema and replay policy; verifier independence remain OPEN and require evidence plus separate approval.
