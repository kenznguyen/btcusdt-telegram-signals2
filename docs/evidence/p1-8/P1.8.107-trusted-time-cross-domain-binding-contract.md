# P1.8.107 — Trusted-Time Cross-Domain Binding Contract

**Version:** P1.8.107-v1  
**Type:** Documentation-only security and lifecycle contract  
**Depends on:** P1.8.26, P1.8.30, P1.8.34–P1.8.37, P1.8.93–P1.8.106  
**Status:** CONTRACT DRAFT RECORDED — TRUST PROFILE AND NUMERIC PARAMETERS OPEN — NOT EXECUTED  
**Authorization:** Documentation only. No TSA/provider selection, key operation, staging, runtime mutation or deletion is authorized.

## 1. Purpose and boundary

This contract closes P1.8.104 CCX-03 by defining shared semantics for trusted-time evidence used by V07 signature/revocation decisions, lifecycle evidence freshness, authorization expiry, restore reconciliation, V08 checkpoint/seal ordering and storage mutation fencing.

It prevents one domain's timestamp from being silently reused as proof for a different event or authority. It does not select a clock, TSA, revocation provider, database, timestamp protocol, trust anchor, numeric freshness limit or clock-uncertainty threshold.

Trusted time is evidence for a bounded temporal claim. It is not an approval, dependency release, deletion authorization, mutation receipt or proof of durable commit unless a separate contract explicitly binds it to that event and evidence source.

## 2. Binding time vocabulary

The following timestamps and temporal evidence MUST remain semantically distinct:

| Name | Meaning | What it does not prove |
|---|---|---|
| `signed_at` | Signer/client-declared signing time | Trusted time or exact signature creation time |
| TSA `genTime` | Time asserted by a validated timestamp authority for the exact timestamped imprint | Exact signature creation instant or signer intent |
| `received_at` | Time a receiving system observed an event | Event creation, source order or durable commit |
| `observed_at` | Time an observer recorded a state | Authoritative state transition unless bound to the authoritative event |
| `revoked_at` / effective time | Time/effective boundary assigned by the authoritative revocation policy/source | A trusted time unless source semantics and proof are validated |
| `commit_time` | Time associated with a persistence commit boundary | Durable commit unless implementation-specific proof establishes it |
| `seal_time` | Time associated with a checkpoint seal barrier | Complete source progress or commit ordering by itself |
| `authorization_issued_at` | Trusted issue-time evidence for a specific authorization | Authorization validity without scope, identity, policy and revocation checks |
| `authorization_expires_at` | Expiry boundary under a declared time policy | Automatic execution at expiry |
| `restore_boundary` | Identified restore event/epoch boundary | Governance currency unless independently reconciled |

Implementations MUST retain the original field names and provenance. Renaming or normalizing these values into one generic `timestamp` field is prohibited where it erases semantics.

## 3. Trusted-time evidence object

Any domain relying on trusted-time ordering or freshness must reference a versioned evidence object with, at minimum:

- immutable evidence ID and contract/profile revision;
- event ID and exact subject/object identity;
- claimed time and its semantic type;
- trusted source identity and proof/profile identifier;
- token/proof digest and the exact imprint/context it binds;
- asserted time, declared precision and uncertainty/accuracy representation;
- evidence acquisition/receipt time and receiving identity;
- validation result, trust-policy revision and trust-anchor references;
- revocation source/revision and effective-time semantics where applicable;
- verification software/profile version and reason/disposition;
- immutable evidence digest and provenance chain.

A timestamp proof must bind the exact event or signed object relevant to the decision. Reusing a valid token for a different payload, signature, authorization, checkpoint, restore event or mutation intent is invalid.

The concrete binary encoding, provider, protocol, algorithm, trust anchor, accuracy representation and evidence transport remain OPEN.

## 4. Temporal ordering and uncertainty

### 4.1 No false precision

A time value must be represented with its declared precision and uncertainty. Rounding, truncation, timezone conversion or serialization must not create an ordering that the source evidence does not establish.

If two time intervals are disjoint, their ordering may be considered only under the applicable domain contract and validated source semantics. If intervals overlap, equality is unresolved, or one side lacks a comparable trusted basis, ordering is indeterminate and the affected decision fails closed.

Do not resolve a boundary using client wall clock, receipt order, queue order, process scheduling, snapshot age or a guessed skew margin.

### 4.2 Equality and boundary semantics

Each domain must define its own boundary operator and exact object of comparison. The comparison must include precision and uncertainty.

- V07 key validity/revocation: historical acceptance is blocked when timestamp uncertainty overlaps the revocation boundary or equality semantics remain OPEN.
- V08 window closure: the approved watermark direction remains `watermark >= window_end`; clock uncertainty that prevents proving the required boundary results in HOLD/quarantine.
- Authorization expiry: expiry invalidates authority; it never triggers execution. Equality/precision handling remains OPEN until the authorization profile is approved.
- Restore epoch: restore ordering is established by the independently governed epoch and reconciled event history, not a wall-clock timestamp alone.
- Mutation fencing: the final protected decision must bind the exact trusted-time evidence revision and the relevant authorization/revocation state.

No one domain's equality rule may be imported into another without an explicit crosswalk.

## 5. Domain bindings

### 5.1 V07 signature and revocation

P1.8.36 remains the governing narrow claim: a valid timestamp imprint binding the exact signature bytes and immutable verification context establishes that this exact signed object existed no later than the TSA's asserted `genTime`, subject to token, trust, policy and accuracy validation.

It does not establish exact signature creation time. Historical acceptance additionally requires:

- exact signature/imprint binding;
- validated timestamp token and applicable historical trust policy;
- authoritative revocation source and effective-time semantics;
- demonstrable temporal separation within the permitted key-validity interval;
- approved equality and uncertainty handling.

Client `signed_at` and `received_at` cannot substitute for this proof. Unknown, stale, contradictory or unavailable revocation/time evidence fails closed and remains quarantined. Timestamp validation cannot clear quarantine or grant lifecycle authority.

### 5.2 Lifecycle evidence freshness and authorization

A lifecycle decision must pin the exact time evidence used to establish:

- evidence freshness at review and final recheck;
- approval and authorization issue/expiry;
- policy/revocation ordering;
- hold and dependency revision ordering;
- authorization revocation epoch;
- final mutation decision boundary.

Freshness is not a universal duration. Each evidence class requires a declared policy revision, source guarantee, measurement basis, units and uncertainty. Those limits remain OPEN.

A valid historical timestamp does not make a current dependency, hold, policy or revocation record fresh. A stale or unavailable current-state source blocks the decision.

### 5.3 V08 source progress, commit and seal

V08 event time, ingestion/receipt time, watermark observation time, durable commit time and seal barrier are distinct.

The evidence chain must bind the exact source-progress revision and partition set to the watermark; the exact durable transaction population to the persistence commit proof; and the seal barrier to the immutable checkpoint manifest.

Time ordering alone cannot prove source completeness or durable persistence. If the commit/seal order cannot be proven under the selected implementation's contract, the transaction remains unresolved and lifecycle closure is blocked.

### 5.4 Restore and governance epoch

A restore event must be bound to its unique restore run and independently issued governance epoch. The epoch and authoritative operation-history high-water mark must not be rollbackable with the restored snapshot.

Wall-clock restore time, snapshot creation time and database sequence are supporting metadata only; they do not replace the governance epoch or authenticated event replay. Pre-restore authorizations remain invalid regardless of their timestamp or snapshot status.

### 5.5 Storage mutation fencing

The protected decision vector for any future mutation must bind, at minimum:

- exact dataset/version/object generation and manifest;
- current policy and policy-revocation revision;
- dependency and hold revisions;
- copy/recovery and restore-governance epoch;
- V07 trust/revocation evidence revisions;
- V08 checkpoint/correction closure references where applicable;
- exact approval and execution authorization identity/revision;
- trusted-time evidence identity, source/profile, uncertainty and freshness disposition;
- authorization-revocation epoch and idempotency identity.

Any material change invalidates the pending decision and requires a fresh complete decision. A read-then-write check, wall-clock shortcut or polling-only fence is not an acceptable substitute for the approved atomic mutation-fencing contract.

## 6. Fail-closed decision table

| Condition | Required disposition |
|---|---|
| Trusted-time proof missing for a claim that requires it | BLOCK / quarantine |
| Proof does not bind exact subject/event/signature | REJECT |
| Trust anchor, policy or source status unknown/unavailable | BLOCK / quarantine |
| Revocation state stale, contradictory or unavailable | BLOCK / quarantine |
| Claimed precision/uncertainty absent or invalid | BLOCK |
| Time intervals overlap or boundary equality is unresolved | HOLD / quarantine |
| Client timestamp conflicts with trusted evidence | Do not prefer client time; investigate and fail closed |
| Evidence is valid but no current dependency/hold/policy recheck exists | Lifecycle decision BLOCKED |
| Authorization has expired or was revoked | Reject execution; never auto-run |
| Restore epoch or event-history ordering cannot be verified | Restore NOT_READY |
| V08 commit/seal order cannot be established | Checkpoint/lifecycle closure BLOCKED |
| A later material revision changes the protected decision vector | Invalidate pending authorization and re-evaluate |

The future frozen fixture set must include at least:

| ID | Scenario | Required result |
|---|---|---|
| TIME-X01 | Exact signature-bound TSA proof clearly precedes revocation | Only the narrow historical-existence claim may pass |
| TIME-X02 | Payload-only timestamp presented as signature-time proof | Reject |
| TIME-X03 | Timestamp uncertainty overlaps revocation boundary | Quarantine |
| TIME-X04 | Client `signed_at` conflicts with trusted `genTime` | Client time cannot override proof |
| TIME-X05 | Valid old timestamp but current hold is active | Lifecycle blocked |
| TIME-X06 | Valid old timestamp but dependency registry is unavailable | Lifecycle blocked |
| TIME-X07 | Authorization expires exactly at an unresolved precision boundary | Reject/HOLD; no execution |
| TIME-X08 | Revocation arrives after authorization issue but before mutation fence | Fresh recheck; invalidate if decision vector changes |
| TIME-X09 | V08 commit and seal timestamps are present but commit boundary proof is absent | BLOCK |
| TIME-X10 | Watermark reaches window end but clock uncertainty overlaps boundary | HOLD |
| TIME-X11 | Restore snapshot time appears newer but governance epoch is stale | NOT_READY |
| TIME-X12 | Restore epoch is valid but operation-history high-water mark has a gap | NOT_READY |
| TIME-X13 | Mutation uses trusted time from a different event/object | Reject evidence binding |
| TIME-X14 | Trusted-time evidence source becomes unavailable during final recheck | Fail closed |
| TIME-X15 | Same exact evidence is replayed idempotently | No duplicate authority or side effect |

These are contract-level cases only; no fixture code or execution is claimed.

## 8. OPEN parameters

No numeric or provider-specific value is approved by this contract. The following remain OPEN:

- trusted-time authority/provider and proof profile;
- accepted algorithms, imprint encoding and canonicalization;
- trust-anchor distribution, rollover, compromise and historical validation;
- revocation authority, effective-time precision and conflict semantics;
- timestamp accuracy/uncertainty representation and maximum uncertainty;
- evidence freshness limits by class, source guarantees and units;
- cache age, propagation bounds and measurement method;
- authorization lifetime, expiry equality and clock-error handling;
- V08 clock source, watermark precision and seal/commit proof;
- restore epoch issuer, ordering and event-history high-water mark;
- mutation-fence trusted-time validation and independent observer requirements;
- role separation, quarantine resolution and reason-code taxonomy.

No OPEN item may be silently filled with a default or inherited from an unrelated domain.

## 9. Explicit prohibitions

This contract does not authorize provider selection, trust-anchor installation, key generation/signing/rotation/revocation, TSA calls, data collection, time-source probing, staging, restore, workflow dispatch, runtime changes, mutation, archive, cleanup or deletion.

It does not modify T0, T1, Feeder, database, VPS, ledgers, strategy, risk engine or the paper-only execution boundary.
