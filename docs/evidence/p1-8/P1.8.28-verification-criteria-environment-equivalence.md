## 1. Decision rule

A staging result is valid only when the tested implementation and environment are demonstrably equivalent to the declared production candidate for the property under test. Similarity of service names, API compatibility, or use of the same database family is insufficient.

Each case has exactly one terminal status:
- **PASS:** all required assertions and evidence are present and independently verifiable.
- **FAIL:** an observed result violates an invariant.
- **BLOCKED:** a prerequisite, equivalence claim, safety control, or required evidence is missing.
- **NOT VERIFIED:** no qualifying execution evidence exists.

A test may not be marked PASS when any required assertion is skipped, any unexplained difference remains, or evidence cannot be bound to the exact source and environment.

## 2. Environment equivalence matrix

Complete this matrix for the declared candidate before provisioning staging. Values must be exact, not phrases such as "compatible" or "same class".

| Dimension | Required record | Equivalence requirement | BLOCKED when |
|---|---|---|---|
| Application | Repository, branch, source SHA, build digest, runtime version | Exact candidate source and immutable build artifact | SHA or artifact cannot be verified |
| Database | Engine, edition, exact version, extensions, driver/client version | Exact engine/version and relevant extensions | Different engine/version or unknown extension behavior |
| Transactions | Isolation level, write ordering, uniqueness constraints, locking, retry policy | Same semantics for tested transaction paths | Staging weaker isolation or different constraints |
| Durability | Commit acknowledgement semantics, WAL/journal mode, fsync/synchronous settings, replication acknowledgement | Same or strictly stronger documented durability; differences explicitly tested | Acknowledgement can precede durability without an approved proof |
| Storage | Provider, volume type, filesystem, mount options, encryption, cache/write policy | Same failure semantics for the durability claim | Storage semantics unknown or materially weaker |
| Topology | Node count, primary/replica roles, quorum/failover, region/AZ, network path | Same topology for distributed claims; single-node cannot prove multi-host behavior | Topology omits a component needed by the claim |
| Concurrency | Worker count, process/host placement, lease service, clock source | At least the production concurrency topology | Fewer independent actors than the claim requires |
| Identity/security | Observer auth, key-management provider/interface, authorization policy, rotation/revocation path | Same trust boundary and authorization semantics, with test-only identities/keys | Static fixture substitutes for required production key integration |
| Time | Clock source, synchronization, measured uncertainty, timestamp precision | Same timestamp semantics; uncertainty bounded by declared policy | Clock uncertainty exceeds test bound or is unmeasured |
| Network | Egress policy, DNS, service endpoints, TLS, retry/timeout behavior | Same internal trust boundaries; exchange/order egress denied | Unexpected egress or inability to prove endpoint blocking |
| Backup/restore | Snapshot mechanism, consistency mode, retention, restore path | Same backup mechanism and restore procedure as intended candidate | Only an in-memory copy or unverified filesystem copy is tested |
| Observability | Structured logs, metrics, traces, audit events, retention | Required evidence fields available without secrets | Missing telemetry prevents reconstructing the decision |
| CI/evidence | Runner image, test harness SHA, workflow/job/run IDs, artifact hashes | Immutable identifiers for every result | Evidence cannot be independently fetched or hashed |

For each row record: `candidate_value`, `staging_value`, `evidence_ref`, `equivalent=true|false`, and reviewer. No blank cells are permitted for a claim being evaluated.

### Permitted deviations

A deviation is allowed only when it cannot weaken the property under test, is justified in writing, and has a dedicated test demonstrating the effect. A stronger setting does not automatically prove equivalence for different transaction, locking, replication, or failure semantics. Any deviation affecting the tested invariant makes that case BLOCKED until separately justified.

## 3. Quantified acceptance criteria

These are proposed minimum test-design thresholds, not claims about current infrastructure. Final values must be recorded in the run manifest before execution; changing them after observing results invalidates that run.

| Area | Minimum deterministic coverage | PASS threshold |
|---|---|---|
| Duplicate/idempotency (V01, V13) | 100 duplicate replays per event across restart boundary; at least 2 independent workers | Exactly one logical durable effect; all retries resolve to same event/checkpoint identity |
| Changed bytes (V02) | 100 mutated payload/metadata variants for an existing event ID | 100/100 rejected; original bytes, digest and state unchanged |
| Sequence/hash (V03, V04) | Missing, delayed, reordered and malformed predecessor cases; at least 20 repetitions per scenario | 100% fail-closed or deterministic hold/recovery; no silent sequence/checkpoint advancement |
| Signature/key (V05–V07) | Valid, invalid, unknown, revoked, expired, rotated, unavailable-revocation cases; cold and warm cache; restart | 100% match predeclared key policy; no unknown/revoked trust fallback |
| Checkpoint race (V08) | At least 100 deterministic barrier-controlled interleavings at each boundary class | Every event included exactly once or explicitly held/rejected; no silent omission |
| Crash recovery (V09) | 20 repetitions at each defined crash point: before write, after durable write/before ACK, after ACK, during replay | Acknowledged writes survive; unacknowledged writes replay safely; recovered state digest matches expected |
| Ledger transitions (V10) | All transition classes in the protocol; 20 replay/restart repetitions per sequence | Exact quantity conservation; invalid transitions rejected; zero unexplained ledger differences |
| Fee/funding (V11) | Missing, explicit-unknown, delayed-final, duplicate-final and changed-final fixtures | Unknown never coerced to zero; final reconciliation idempotent; incomplete state cannot be marked ready |
| Mark freshness (V12) | Fresh, boundary-age, stale, future, missing and uncertain-clock fixtures | All decisions match the predeclared age/uncertainty policy; invalid marks never reach ready valuation |
| Multi-process | At least 2 independently started processes and 2 observer identities | No double ownership or duplicate side effect; stale fenced actor cannot commit |
| Multi-host | At least 2 separate hosts when production claim is multi-host | Same fencing and idempotency invariants under network delay/restart; otherwise multi-host assurance is NOT VERIFIED |
| Restore | 3 independent restore rehearsals from separately captured consistent snapshots | 3/3 restore successfully; integrity and reconciliation checks pass |

Randomized stress may supplement these deterministic tests but cannot replace them. Report actual iteration counts and scenario coverage; never summarize an incomplete run as 100% coverage.

## 4. Durability and failure-level claims

Report each level separately. Passing a lower level does not imply a higher one.

| Level | Fault model | Required evidence | Claim allowed after PASS |
|---|---|---|---|
| D0 | Application/process termination | Process exit code, transaction state, reopen/replay digest | Process-crash recovery only |
| D1 | Database process restart | DB logs, acknowledged transaction IDs, post-restart query and digest | Database-process restart only |
| D2 | Host restart | Provider/host event, storage reattach, transaction reconciliation | Host-restart recovery only |
| D3 | Storage/provider interruption | Provider-approved isolated fault, storage events, integrity scan, reconciliation | Only the exact tested storage failure |
| D4 | Power loss/device failure/filesystem corruption | Exact disposable-device fault method, provider evidence, filesystem/database integrity and restore proof | Only the specifically induced fault; never general hardware resilience |

No D3/D4 test is authorized by this document. Use only provider-approved fault methods in a disposable isolated environment after separate approval. Never corrupt shared storage or the current evaluation VPS.

## 5. Revocation and event-time policy contract

Before V07 runs, the system owner must select and version one explicit policy. At minimum it must define:
- `signed_at`: trusted signing time, including how it is established.
- `received_at`: first trusted ingress receipt time.
- `revoked_at`: authoritative effective revocation time.
- Whether events signed before revocation but received later remain valid.
- Whether revocation is immediate, scheduled, or effective after a defined propagation bound.
- Maximum key-cache age and behavior when revocation state is unavailable.
- Rotation overlap window and the exact old/new key acceptance intervals.

Default fail-safe for unknown revocation state: reject or quarantine; do not silently accept. A pre-revocation signature is not automatically valid: acceptance depends on the selected, auditable policy and trusted timestamp evidence. Policy changes require a new test run and cannot be applied retroactively to reinterpret a failed run.

## 6. Checkpoint time and boundary contract

Every event/checkpoint fixture must distinguish:
- `occurred_at`: source-reported event occurrence time.
- `received_at`: trusted ingress receipt time.
- `committed_at`: durable commit time.
- `boundary_at`: logical event-time cutoff covered by a checkpoint.
- `sealed_at`: time the checkpoint becomes immutable.

Required boundary cases: event before/equal/after `boundary_at`; commit before/after `sealed_at`; delayed arrival; missing timestamp; invalid/future timestamp; duplicate replay; and concurrent commit/seal.

The implementation must predeclare whether checkpoint membership is based on event-time plus a watermark, commit-time, or another formally specified rule. PASS requires deterministic membership, no silent omission, no double inclusion, and a replayable audit trail. If no policy is selected, V08 is BLOCKED.

## 7. Reconciliation fixture contract

Create versioned, synthetic fixtures with immutable expected outputs before executing V10–V12. Each fixture must include:
- ordered source events and unique event IDs;
- opening position state and independent CORE/AI ledger identifiers where applicable;
- fills, reductions, closes and reversal references;
- fee and funding records, including explicit unknown and delayed-final states;
- mark values with source time, receive time and declared freshness bound;
- expected quantity, realized/unrealized PnL, fees, funding, equity-readiness and rejection/hold reasons.

Acceptance:
1. Exact quantity conservation and transition validity.
2. Zero unexplained differences between event journal, observer ACKs, checkpoints and ledger.
3. Unknown fee/funding remains explicitly unknown and blocks any output requiring complete valuation.
4. Mark data outside freshness/clock policy cannot produce a ready valuation.
5. Opposing LONG/SHORT ledgers remain separately represented; no netting to conceal exposure or discrepancy.
6. Re-running reconciliation yields byte-identical normalized output or an explicitly versioned deterministic equivalent.

No tolerance is assumed for event counts, quantities, IDs, sequence, checkpoint digests or unexplained ledger differences. Numeric PnL tolerances, if floating-point arithmetic requires them, must be declared per field and justified before test execution; use decimal/fixed-point arithmetic where the candidate does so.

## 8. Backup/restore targets — provisional, approval required

Proposed staging-only targets for planning:
- Acknowledged transaction RPO: **0** for the tested durability boundary.
- Snapshot recovery-point objective: **no more than 5 minutes** of committed synthetic data.
- Staging service recovery-time objective: **no more than 60 minutes** from declared restore start to verified ready state.
- Restore rehearsal: **3 independent runs**, each from a distinct consistent snapshot.

These are proposed acceptance targets, not measured service capabilities or an approved production SLO. The system owner must approve or replace them before any restore test. A run cannot be marked PASS if targets were selected after the restore result was known.

Restore validation must verify source snapshot digest, database integrity, event-chain continuity, sequence/checkpoint consistency, ledger reconciliation, observer ACK state and absence of duplicate logical application. Record restore start/end times and all excluded data. Snapshot creation alone is not a restore proof.

## 9. Pre-execution and abort checklist

A staging batch remains BLOCKED until every item is checked and independently evidenced:
- [ ] Separate disposable account/project/network/storage; no shared T0/T1/VPS resources.
- [ ] Exact candidate SHA/build digest pinned; clean source tree and dependency lock recorded.
- [ ] Environment equivalence matrix complete with no unresolved material deviations.
- [ ] Test-only accounts, identities and keys; no production credentials present.
- [ ] Egress deny-by-default verified; exchange/order endpoints unreachable.
- [ ] `AI_EXECUTION_ENABLED=false`; no order-capable component enabled.
- [ ] Baseline snapshot created and restore/teardown rehearsal verified.
- [ ] Fault injector and test harness pinned by SHA; deterministic seed and barrier plan recorded.
- [ ] Clock uncertainty measured and within declared limit.
- [ ] Expected outputs and thresholds frozen before execution.
- [ ] Evidence collector tested; artifact upload and independent hash verification available.
- [ ] Separate explicit authorization for the specific staging batch and fault classes obtained.

Abort immediately on unexpected egress, credential leakage, write outside disposable resources, source/environment drift, missing audit telemetry, unexplained state difference, failed restore, unbounded retry, or inability to tear down safely. Preserve evidence; do not retry a failed batch under changed conditions and reuse its PASS claim.
