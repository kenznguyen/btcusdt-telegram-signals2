## 3. Finding F-01 — Trusted timestamp must bind the signature itself

**Severity:** HIGH — V07 security-contract ambiguity  
**Status:** OPEN; V07 remains BLOCKED.

P1.8.33 describes trusted timestamp evidence as establishing signing time inside the key's permitted validity interval. P1.8.34 correctly warns that a timestamp proves only that the timestamped data existed no later than the authority's asserted time, and leaves the concrete proof profile OPEN. However, neither document normatively freezes which exact bytes are covered by the timestamp token.

If the timestamp token covers only the event payload or an unsigned envelope, it proves that payload existed by the timestamp time; it does not prove that the particular digital signature being verified already existed then. A signature could be created later over an older payload, including after key revocation. Treating the payload timestamp as proof of pre-revocation signing would weaken DEC-01.

**Required clarification before V07 fixtures can be frozen:**
1. The timestamp message imprint must bind the exact signature value being verified, or a canonical signed object that cryptographically includes that exact signature value and all identity/context fields required by the verifier.
2. Verification must bind the timestamp token to the same event bytes, signature bytes, key ID, algorithm and canonicalization/version that are subsequently verified; substitutions or re-encoding must fail closed.
3. The timestamp authority's asserted time must be checked against the key's approved validity interval and authoritative revocation effective-time policy, including exact equality semantics.
4. A timestamp over payload-only bytes, client-supplied `signed_at`, or an unbound detached envelope must not qualify as proof that the signature existed before revocation.
5. The chosen RFC 3161 or other proof profile, imprint construction, canonicalization and trust-anchor lifecycle remain OPEN for owner/security review; this finding does not select a provider or standard by itself.

**Disposition:** Clarify the proof-binding contract in a versioned documentation update and independently review it. Do not change implementation or perform key operations. Do not close V07 or freeze its fixtures until the binding rule and test vectors are explicit.
