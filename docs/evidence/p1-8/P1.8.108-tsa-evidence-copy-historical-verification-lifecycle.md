# P1.8.108 — TSA Evidence Copy and Historical Verification Lifecycle

**Version:** P1.8.108-v1  
**Type:** Documentation-only evidence lifecycle contract  
**Depends on:** P1.8.26, P1.8.34–P1.8.37, P1.8.93–P1.8.107  
**Status:** CONTRACT DRAFT RECORDED — TRUST/RETENTION PARAMETERS OPEN — NOT EXECUTED  
**Authorization:** Documentation only. No TSA/provider selection, key operation, evidence export, staging, restore or deletion is authorized.

## 1. Purpose and boundary

This contract closes P1.8.104 CCX-04 by defining the identity, lineage, copy lifecycle and historical verification requirements for trusted timestamp and revocation evidence.

A timestamp token cannot remain independently verifiable if its exact imprint inputs, trust-policy history, trust-anchor material, certificate-chain evidence, revocation evidence or verifier context are lost. Conversely, retaining token bytes alone does not prove that the token remains valid or that the historical claim can still be reproduced.

TSA evidence is therefore a governed evidence dataset with linked dependencies and separately managed copies. It is not disposable metadata attached to a payload, and it is not deletion authority.

This is a design-only contract. It does not select a TSA, trust-anchor provider, revocation source, storage provider, evidence format or retention period. It does not authorize any evidence export, backup, restore or deletion operation.

## 2. Binding invariants

1. **Exact claim preservation.** Evidence must preserve the exact signed object and context to which the timestamp imprint was bound under P1.8.36.
2. **No token-only assurance.** A timestamp token without the required imprint inputs and applicable trust/revocation history is insufficient for future independent verification.
3. **Independent evidence lifecycle.** Tokens, imprint inputs, trust-policy revisions, trust anchors, certificate chains, revocation records, verification results and manifests have explicit identities and lifecycle obligations.
4. **No evidence co-deletion.** Deleting a payload, signature envelope, model, dataset or source object does not implicitly delete its timestamp or verification evidence.
5. **No cascade across copies.** Source evidence, replicas, backups, exports and recovery copies each have independent identities, lineage and lifecycle state.
6. **Historical policy is immutable evidence.** Preserve the exact trust-policy and verification-profile revisions used for the original decision; do not replace historical policy with today's configuration.
7. **Current trust is distinct from historical trust.** Historical re-verification evaluates the applicable historical policy and the evidence available now; it does not silently rewrite the original decision.
8. **Restore does not revive authority.** Restored evidence cannot revive pre-restore authorization or bypass current hold, dependency, revocation and lifecycle checks.
9. **Fail closed.** Missing, corrupt, mismatched, incomplete or unverifiable evidence remains BLOCKED/QUARANTINED.
10. **No authority escalation.** Timestamp validity proves only the bounded claim in P1.8.36; it never grants deletion eligibility, approval, execution authority or precedence over current holds.
11. **T0 and ledgers remain protected.** T0 canonical data and CORE_LEDGER/AI_LEDGER protections are unchanged.

## 3. Evidence object model

The evidence registry, if later implemented, must represent the following as distinct immutable or versioned objects. The logical model does not prescribe a database schema.

| Object class | Required identity and content | Lifecycle relationship |
|---|---|---|
| Signed event/envelope | Event ID, envelope version, exact payload digest, signer/key ID, algorithm/profile, exact signature bytes or independently preserved exact signed bytes | Parent subject of timestamp claim |
| Imprint input | Exact canonical/binary input bytes or reproducible immutable components, domain/version, digest algorithm and recomputed imprint | Required to re-compute P1.8.36 binding |
| Timestamp token | Exact token bytes, token digest, TSA identity, policy/profile, asserted genTime and declared accuracy | Evidence for bounded existence claim |
| TSA trust material | Trust-anchor identity/fingerprint, chain certificates, policy and validation context | Required for historical token validation |
| Revocation evidence | Authority/source identity, signed record or immutable response, effective-time semantics, revision and observation provenance | Required for historical/current trust assessment |
| Verification profile | Exact verifier/profile/software version, accepted algorithms, parsing/canonicalization rules and policy revision | Required to reproduce verification |
| Verification result | Input evidence digests, recomputed imprint, chain/revocation result, time interpretation, reason code and reviewer/automation identity | Decision evidence; must not replace raw inputs |
| Evidence manifest | Exact object IDs/digests, parent/child references, copy IDs, completeness marker and manifest version | Binds evidence set and copy lineage |
| Copy/backup/export record | Copy ID, source evidence version, destination identity, generation, digest, creation/verification proof and independent lifecycle state | Separate governed copy |
| Historical decision record | Original decision ID, applicable policy revisions, exact evidence manifest, outcome and rationale | Immutable record of what was decided and why |

Private keys, credentials, API secrets or unnecessary personal data MUST NOT be embedded in evidence manifests or ordinary audit records. Public certificates and trust-anchor material may be preserved only under an explicitly governed evidence classification.

## 4. Evidence completeness and dependency closure

A historical verification package is complete only when it can identify and retrieve, or deterministically reproduce, all required components:

1. exact signed bytes or exact signature bytes and immutable verification context;
2. exact imprint input and independently recomputable digest;
3. timestamp token bytes and token digest;
4. TSA identity, policy/profile and the applicable trust-anchor/chain history;
5. certificate validity and revocation evidence required by the applicable historical policy;
6. algorithm and canonicalization rules effective for the original event;
7. verifier implementation/profile and version sufficient to reproduce the validation;
8. trusted-time uncertainty/accuracy interpretation and boundary semantics;
9. original verification result, reason code and evidence manifest;
10. current copy lineage and integrity verification for every retained copy.

If any required component is missing, the package is INCOMPLETE. Token presence or a previously recorded PASS does not override missing source evidence.

The package must distinguish:

- **historical verification reproducibility:** ability to recompute the original bounded claim under the historical policy;
- **current trust assessment:** current assessment of the authority, algorithms, anchors and revocation information;
- **original decision integrity:** proof of what inputs and policy were used when the original decision was made.

These are related but not interchangeable claims.

## 5. Copy identity and lifecycle

### 5.1 Independent copy records

Every source, replica, backup, export, archive and recovery copy must have:

- unique copy ID and immutable source evidence version;
- exact object identities and generation/version;
- source and destination storage-domain identity;
- copy operation ID and provenance;
- content/manifest digest and verification method;
- creation/commit evidence under the selected provider's contract;
- current lifecycle policy, holds and dependency references;
- last independently verified integrity result;
- restore lineage and known shared failure-domain dependencies.

A copy's existence does not prove the source is recoverable, and a successful copy job does not prove end-to-end historical verifiability.

### 5.2 Independent lifecycle evaluation

Each copy is evaluated separately for preservation, archive or deletion. A copy must remain protected while it is needed for:

- historical signature/revocation verification;
- security, incident or audit investigation;
- legal/contractual preservation where applicable;
- restore and recovery validation;
- reproducibility of a lifecycle or mutation decision;
- proof of a previous authorization, operation or object outcome;
- integrity verification of another retained copy.

No global TTL or default retention period is created by this contract. Exact retention floors, review periods, legal holds, grace periods and deletion criteria remain OPEN.

### 5.3 No cascading deletion

Removing a payload or source evidence object cannot cascade to its timestamp token, trust chain, revocation proof, historical policy, verification result, manifest, tombstone or other copy.

If a parent object is proposed for deletion while child evidence remains, the child must retain sufficient immutable parent identity/digest and the exact bytes or independently reproducible inputs required for its own claim. If this cannot be demonstrated, deletion eligibility is BLOCKED.

## 6. Historical verification procedure

A future verifier must perform a read-only, reproducible procedure:

1. Resolve the exact evidence manifest and verify its digest and completeness.
2. Resolve the exact signed event/envelope and signature bytes; reject mutable aliases or substitutions.
3. Reconstruct the P1.8.36 imprint using the frozen encoding/profile and compare it byte-for-byte/digest-for-digest with the token's message imprint.
4. Validate timestamp token integrity, TSA identity, historical policy and applicable trust chain using preserved policy/anchor history.
5. Evaluate certificate validity and revocation evidence under the correct historical effective-time semantics.
6. Interpret `genTime`, precision and uncertainty without claiming exact signature creation time.
7. Reproduce the original verification result and compare it with the preserved result and reason code.
8. Separately record any current trust/algorithm assessment; do not overwrite the historical result.
9. Verify the exact copy identity/generation and content digest for the copy under review.
10. Record a new append-only verification event referencing all inputs and outputs.

If the historical trust policy or required revocation evidence is unavailable, the verifier must report INDETERMINATE/NOT_VERIFIED rather than substitute today's policy or assume validity.

Historical verification is read-only. It does not clear quarantine, approve lifecycle changes, release dependencies or authorize deletion.

## 7. Restore integration

P1.8.105 governs the restore epoch and post-restore reconciliation boundary. For TSA evidence, restore reconciliation must additionally:

- identify the exact source evidence manifest and every restored copy/generation;
- compare restored token, imprint, trust-policy, anchor, chain, revocation and verification-result digests against independent evidence manifests;
- replay or reconcile post-snapshot evidence-copy, trust-policy, revocation, hold, tombstone and lifecycle events through an independently verified high-water mark;
- invalidate all pre-restore deletion authorizations and preserve historical authorization records as evidence only;
- detect a restored copy that is stale, incomplete, rolled back or inconsistent with a newer source/copy generation;
- preserve separate lifecycle state for source evidence, replicas, backups and exports;
- keep affected evidence and dependent decisions quarantined until completeness and integrity are independently verified.

A successful database restore or matching token digest alone is not sufficient. Missing post-snapshot revocation or trust-policy history makes the affected historical decision NOT_VERIFIED.

Restore cannot transform an incomplete historical package into a complete one by generating substitute evidence.

## 8. Deletion and lifecycle decision integration

TSA evidence may be considered in lifecycle review only as evidence supporting a bounded historical claim. It cannot:

- authorize deletion or archive;
- release a consumer dependency or preservation hold;
- override current policy, revocation, quarantine or legal obligations;
- prove a durable storage mutation;
- prove that another copy is recoverable;
- establish exact signature creation time;
- make T0 canonical data disposable after a downstream checkpoint or successful verification.

Before any future evidence deletion, the ordinary central lifecycle process must establish exact identity, demand/dependency closure, legal/audit/recovery obligations, independent approval, exact-scope authorization, final fencing and independent post-operation verification. This contract adds evidence-specific prerequisites; it does not relax the general deletion contract.

## 9. Required negative cases

Future frozen fixtures must include at least:

| ID | Scenario | Required result |
|---|---|---|
| TSA-C01 | Token exists but exact signature/imprint inputs are missing | INCOMPLETE / NOT_VERIFIED |
| TSA-C02 | Payload digest matches but signature bytes differ | REJECT; imprint mismatch |
| TSA-C03 | Token is valid but historical trust-anchor/policy revision is missing | INDETERMINATE |
| TSA-C04 | Current trust policy differs from historical policy | Preserve historical result; report current assessment separately |
| TSA-C05 | Revocation evidence is unavailable or contradictory | FAIL CLOSED / quarantine |
| TSA-C06 | Timestamp token is retained but its only required revocation evidence copy is missing | INCOMPLETE |
| TSA-C07 | Source payload deletion proposal implicitly cascades to token/chain evidence | Reject cascade; independent review required |
| TSA-C08 | Backup copy exists but digest/generation is not verified | Copy NOT VERIFIED |
| TSA-C09 | Restored evidence omits a post-snapshot trust-policy or revocation event | Restore scope NOT_READY |
| TSA-C10 | Restored token digest matches but imprint inputs are incomplete | Historical package INCOMPLETE |
| TSA-C11 | Two copies share one failure domain but are declared independent | Reject independence claim |
| TSA-C12 | Verification result is replayed with same evidence manifest | Idempotent audit; no duplicate authority |
| TSA-C13 | Historical verification PASS is used to release a current hold | Reject authority escalation |
| TSA-C14 | Token genTime is described as exact signature creation time | Reject overstated claim |
| TSA-C15 | Evidence copy deletion is proposed while an audit/recovery dependency remains | Lifecycle BLOCKED |

These are specification cases only. No fixture code, evidence export or test execution is included.
