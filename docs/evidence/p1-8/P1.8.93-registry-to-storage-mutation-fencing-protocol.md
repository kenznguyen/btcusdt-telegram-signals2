# P1.8.93 — Registry-to-Storage Mutation Fencing Protocol

Date: 2026-11-09  
Closes: SR-02 (MAJOR)  
Status: DOCUMENTARY PROTOCOL — NOT IMPLEMENTED / NOT ACTIVE / NOT AUTHORIZED

## 1. Purpose and hard boundary

This protocol defines the minimum ordering and fencing properties required between authoritative lifecycle decisions and a storage mutation. It addresses the race where a hold, dependency, policy, cancellation or authorization revision changes after preflight but before a backend side effect.

It is an abstract capability contract, not a selected distributed-lock product, registry, transaction coordinator, database schema, API, storage adapter or implementation plan. No provider capability is assumed.

**Eligibility rule:** a storage adapter is not eligible for destructive use unless it can prove the required linearization property at the mutation boundary. A preflight read followed by an unrelated storage write, periodic polling, heartbeat, cache invalidation, best-effort event delivery or an expiring lease alone is insufficient.

## 2. Protected decision vector

For each exact object mutation, the authorization package must bind a protected decision vector containing:

- request ID and immutable approval-package digest;
- exact operation and exact object identity;
- object generation/version/ETag or backend-equivalent immutable precondition;
- dataset and immutable dataset-version identity;
- authoritative lifecycle-policy revision;
- authoritative dependency-registry revision and unresolved-dependency result;
- authoritative hold-registry revision and exact applicable hold scope;
- copy/backup/recovery disposition revision and evidence references;
- authorization ID, authorized executor identity and revocation epoch;
- unique per-object mutation ID and idempotency key;
- trusted ordering/validity evidence;
- verifier and audit-evidence requirements.

The vector is not a mutable pointer or alias. Any material change invalidates the prior decision vector for not-yet-committed mutations.

## 3. Required abstract capability

A conforming adapter must provide one indivisible decision at the point where the object side effect becomes committed:

**COMMIT_MUTATION_IF**
- the exact object identity and generation still match;
- the request and authorization remain valid and unrevoked;
- the current policy, dependency and hold decision revisions are still admissible;
- no applicable hold or unresolved protective dependency has appeared;
- the object mutation ID has not been applied with conflicting semantics;
- the exact operation remains within the approved manifest;
- the durable intent/audit precondition is satisfied.

The decision must have a single authoritative linearization point shared with, or transactionally coupled to, the relevant lifecycle decision revisions. The mutation and the check cannot be separate operations whose interleaving is uncontrolled.

The protocol deliberately does not prescribe how a backend supplies this capability. A future implementation may be considered only if its provider-specific proof demonstrates the atomic relationship. If the registry and backend cannot share or establish this linearization property, the adapter is INELIGIBLE for destructive execution. The design must not downgrade this rule to read-then-write plus polling.

## 4. Ordering semantics

For a given object and protected decision scope, the authoritative ordering must resolve the race into exactly one of these cases:

1. **Mutation linearizes first:** the object operation is durably committed before the protective hold/dependency/policy/revocation change. The operation is recorded as completed under the prior valid revision; the later protective change blocks every subsequent object mutation. The already committed operation is not silently rolled back.
2. **Protective change linearizes first:** the hold/dependency/policy/revocation/cancellation change is durably committed before the mutation decision. COMMIT_MUTATION_IF rejects the stale decision vector; no object side effect occurs.
3. **Ordering cannot be proven:** neither side may infer precedence. The object/request becomes UNKNOWN or RECONCILIATION_REQUIRED; no retry or next object mutation is permitted until independent reconciliation.

A client submission time, response arrival time, wall clock, event publication, queue receipt or stale replica is not the linearization point.

For hold creation and scope expansion, the authoritative protective commit must prevent any later mutation from committing against the earlier revision. For hold revocation, the hold remains protective until the authorized revocation commit is ordered; a requested but uncommitted revocation changes nothing.

## 5. Per-object protocol

Each object in a multi-object request follows an independent sequence:

1. Resolve exact immutable object identity and generation from the authoritative source.
2. Pin the complete protected decision vector and approval/authorization references.
3. Persist a unique mutation intent before attempting the backend operation.
4. At the mutation boundary, invoke the adapter's atomic conditional capability with the exact object identity, generation, decision vector and idempotency identity.
5. The backend/authority returns one of:
   - COMMITTED with durable operation identity and committed decision revision;
   - REJECTED_STALE with proof that no mutation was applied;
   - REJECTED_SCOPE with proof that no out-of-scope target was touched;
   - OUTCOME_UNKNOWN where side effect cannot be excluded.
6. Persist the result and evidence before advancing to another object.
7. If COMMITTED, proceed only to independent verification of that object.
8. If REJECTED_STALE, stop the current batch, refresh the full decision vector and return through governed final recheck/authorization; do not silently reuse the old authorization.
9. If OUTCOME_UNKNOWN, enter reconciliation. Do not retry or process the next object until actual backend state is independently established.

The protocol does not assume a batch is atomic. A multi-object request is a set of separately fenced object operations with explicit partial-outcome handling.

## 6. Hold, dependency, policy and authorization changes

The same mutation fence must account for all decision domains that can make the operation unsafe:

- **Hold creation/expansion:** new hold revision invalidates prior mutation decisions for affected objects.
- **Hold revocation:** only a durably authorized revocation changes the protective state; a pending or failed revocation leaves the hold active.
- **Dependency registration/release:** registration or unresolved consumer evidence must block if it changes eligibility; ACK alone has no effect.
- **Policy/classification change:** a material policy or classification revision invalidates approval and authorization as defined by the policy contract.
- **Cancellation:** cancellation ordered before the mutation's linearization point blocks it; cancellation after a committed object mutation stops later objects and requires partial reconciliation.
- **Authorization revocation/expiry:** revocation/expiry ordered first rejects the mutation; if ordering is unknown, outcome is UNKNOWN and reconciliation is mandatory.
- **Object generation change:** replacement or version change rejects the operation; the replacement is never silently substituted.
- **Audit continuity loss:** if the required intent/decision/outcome evidence cannot be made durable, the mutation must not begin. If a side effect may already have occurred, stop and reconcile.

## 7. Multi-object batch and interruption rules

- A batch has no implied all-or-nothing semantics.
- Each object has its own immutable identity, generation, decision revision, mutation ID and result.
- A protective revision change after object A commits must block object B unless B receives a newly reviewed and authorized decision vector.
- Previously committed objects remain historical facts; they are not represented as rolled back.
- Process crash, network loss, registry partition, backend timeout or audit outage after submission produces OUTCOME_UNKNOWN unless independent evidence proves no side effect.
- Resume requires per-object reconciliation and a new governed decision for every remaining object.
- No blind retry, skip-ahead or scope expansion is allowed.

## 8. Required adapter capability proof

Before an adapter could be considered, its separate capability dossier must demonstrate:

1. exact object identity and immutable generation checks;
2. atomic or transactionally coupled comparison of all relevant decision revisions at the mutation linearization point;
3. stale-token/revision rejection under concurrency, failover and partition;
4. durable idempotency and duplicate-submission behavior;
5. cancellation/revocation ordering;
6. per-object intent/outcome durability and audit continuity;
7. interruption and ambiguous-outcome reconciliation;
8. no cascade to unlisted copies/objects;
9. independent observation of actual postcondition and residual state;
10. negative tests using isolated synthetic storage and an independent oracle.

A provider API's conditional write, ETag, generation precondition, transaction or lock is not assumed sufficient by its name. The adapter dossier must prove that it fences the complete protected decision vector, not merely object overwrite. Provider semantics, transaction boundaries and failure guarantees remain OPEN until independently researched, measured and approved.

## 9. Fail-closed decision table

| Condition at mutation boundary | Required result |
|---|---|
| Authoritative decision vector current and atomic precondition succeeds | One exact object mutation may commit |
| Hold/dependency/policy revision changed before mutation linearization | Reject stale vector; no mutation |
| Object generation changed | Reject; replacement untouched |
| Authorization revoked/expired before linearization | Reject; no mutation |
| Registry unavailable or split-brain | Block; no mutation |
| Cannot prove cross-system ordering | UNKNOWN / RECONCILIATION_REQUIRED |
| Adapter only supports read-then-write or polling | Adapter INELIGIBLE |
| Audit intent cannot be durably recorded before operation | Do not start |
| Audit/result continuity lost after possible side effect | Stop; reconcile; NOT_VERIFIED |
| Earlier object committed and later object fence fails | Preserve earlier result; block later objects; reconcile |
| Idempotency identity reused with different scope | Reject and audit |
| Independent verifier unavailable | No completion claim |

## 10. Deterministic race requirements

The future synthetic test suite must include at least:

- hold commit immediately before mutation linearization;
- hold commit immediately after mutation linearization but before client response;
- hold scope expansion between object A and B;
- revocation request without durable revocation commit;
- authorization revocation racing with mutation;
- policy revision racing with object B;
- dependency registration racing with final decision;
- object generation replacement between preflight and mutation;
- registry partition after backend submission;
- audit sink failure after backend side effect;
- process crash after side effect but before outcome persistence;
- duplicate mutation submission after an ambiguous response.

Expected results are defined by the authoritative linearization order, not sleeps or assumed network timing. Tests remain design-only and require separate synthetic-only approval.
