# P1.8.118 — TSA Graph Orientation, Closure and Hold-Propagation Semantics

**Version:** P1.8.118-v1  
**Closes:** IR115-03 (documentary design clarification)  
**Status:** DOCUMENTARY CONTRACT — NOT IMPLEMENTED / NOT ACTIVE / NOT AUTHORIZED

## 1. Purpose and boundary

This contract fixes edge orientation and deterministic traversal semantics for the evidence/copy graph described in P1.8.108 and P1.8.113. It defines conservative hold propagation and graph-completeness requirements. It does not claim a runtime inventory exists or authorize any hold release or deletion.

## 2. Canonical graph model

Every node MUST have immutable node ID, node type, object identity, generation/version, dataset/version where applicable, lifecycle identity, authoritative registry revision and evidence provenance.

Every edge MUST have immutable edge ID, edge type, source node ID/version, target node ID/version, authoritative revision, creation/effective ordering evidence, scope and provenance. Edges are directed; source and target are not interchangeable.

The canonical orientation is **from the dependent, derived, claim or copy node to the node it depends on, represents or copies**. The following meanings are normative:

| Edge type | Directed meaning: source → target | Reverse traversal meaning |
|---|---|---|
| CLAIM_REQUIRES | Claim → required evidence | Evidence → claims that require it |
| REPRODUCES | Reproduction/representation → represented source | Source → reproductions/representations |
| VALIDATED_UNDER | Verification result → policy/profile/trust basis | Basis → results validated under it |
| DERIVED_FROM | Derived object → parent/source object | Parent → derived descendants |
| COPY_OF | Copy/replica/backup/export → exact source object/version | Source → copies |
| RESTORE_DEPENDS_ON | Restored/reconstructed object → required restore evidence/source | Dependency → restored objects |
| AUDIT_REQUIRES | Audit record/package → required evidence | Evidence → audit records requiring it |
| CONSUMER_DEPENDS_ON | Consumer identity/scope → exact dataset/version | Dataset/version → dependent consumers |
| HOLD_APPLIES_TO | Hold record → exact object/scope it protects | Object/scope → applicable hold records |
| SUPERSEDES | New immutable version → superseded version | Superseded version → successors |

A node may have multiple outgoing edges of the same or different types. Edge deletion or supersession is itself an authoritative lifecycle event and MUST remain historically auditable.

## 3. Canonical traversal

For a starting node N:
- **Prerequisite closure** follows outgoing edges from N for the edge types that express requirements or derivation.
- **Dependent/descendant closure** follows incoming edges in reverse orientation.
- **Hold discovery** evaluates direct HOLD_APPLIES_TO edges for the exact object/scope and then computes conservative dependent/descendant closure through REPRODUCES, DERIVED_FROM and COPY_OF reverse traversal.
- **Consumer discovery** follows reverse CONSUMER_DEPENDS_ON from exact dataset/version.
- **Restore/audit discovery** follows reverse RESTORE_DEPENDS_ON and AUDIT_REQUIRES to identify objects or evidence that rely on the held node.
- **Historical supersession** follows SUPERSEDES in both directions only for lineage/history reconstruction; supersession never erases a dependency, hold or copy identity.

The traversal MUST be cycle-safe, version-aware and deterministic. It MUST record the starting node, edge-type allowlist, direction, visited node/edge IDs, registry revision and traversal result. Cycles, dangling edges, conflicting versions or non-deterministic ordering produce UNKNOWN/HOLD rather than silently truncating closure.

## 4. Hold propagation and exclusion

A hold directly applicable to a source object MUST conservatively protect every known copy, replica, backup, export, representation and derived descendant reachable through reverse COPY_OF, REPRODUCES and DERIVED_FROM traversal, unless an authorized, evidence-bound decision under the governing copy lifecycle contract proves the hold does not apply to one exact copy.

A hold on evidence required by a claim, audit record or restore object MUST be visible to those dependent nodes through reverse CLAIM_REQUIRES, AUDIT_REQUIRES or RESTORE_DEPENDS_ON traversal. This is a protective dependency signal; it does not make all such nodes the same lifecycle object and does not authorize cascade mutation.

The graph MUST preserve separate lifecycle identities and disposition decisions for every copy and dependent object. Propagating a hold is not cascading deletion, and clearing a hold on one node does not automatically clear it on another.

An exclusion MUST identify exact node/version, excluded hold ID/scope, applicable policy revision, evidence proving non-applicability, authorized reviewer and immutable decision record. Missing evidence, incomplete lineage or ambiguous scope means the hold remains protective.

## 5. Completeness proof and absence-of-edge claims

A graph query MUST NOT claim “no dependency”, “no copy” or “no hold” from an empty result alone.

Before an absence claim is admissible, the evidence package MUST establish:
1. authoritative registry/source set and versioned schema;
2. complete inventory scope and object/version manifest;
3. authenticated high-water mark or equivalent consistent snapshot for every graph source;
4. complete pagination/partition/shard coverage with no gaps;
5. reconciliation of asynchronous/outbox/queue/delegated-worker records where applicable;
6. tombstone, supersession and edge-revocation history sufficient to distinguish absent from removed;
7. cross-source ordering/consistency proof for the same decision cut;
8. independent completeness oracle or reconciled count/hash evidence;
9. explicit unresolved/unknown-edge count equal to zero for the exact scope.

If any source is unavailable, inventory incomplete, history truncated, pagination uncertain, or HWM not contiguous, the graph result is INCOMPLETE and the affected decision remains HOLD. Missing worker or consumer heartbeat is not proof of no dependency.

## 6. No cascade and lifecycle isolation

- Each source, copy, backup, replica, export, checkpoint, correction, token, certificate/revocation record, verifier profile and audit package remains a distinct lifecycle object.
- Graph edges describe relationships; they do not merge identities or lifecycle authority.
- A hold propagates protectively according to §4; a release requires exact-scope authority for each affected hold/object.
- Deletion or mutation of one node MUST NOT implicitly delete or mutate adjacent nodes.
- Unknown edge types or schema versions are protective until explicitly qualified.
- No automatic edge removal, dependency release or graph pruning is permitted.

## 7. Acceptance criteria

- [x] All edge types have a single directed meaning.
- [x] Prerequisite and dependent traversal directions are distinguished.
- [x] Hold propagation includes copy, representation and derived descendants.
- [x] Exclusions require exact, independently reviewable evidence and authority.
- [x] Absence claims require authenticated inventory/HWM/completeness proof.
- [x] Cycles, gaps and unknown edges fail closed.
- [x] Per-copy lifecycle identity and no-cascade rules are preserved.
