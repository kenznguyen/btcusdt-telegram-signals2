# P1.8.67 — Provider-Neutral TSA Architecture Assessment

**Date:** 2026-11-09  
**Scope:** E0 documentary architecture assessment only  
**Status:** DESIGN ASSESSMENT COMPLETE — INDEPENDENT REVIEW REQUIRED  
**Provider decision:** NONE SELECTED  
**Execution:** NOT EXECUTED; no provider, endpoint, OCSP responder, credential, trust anchor or key operation used

## 1. Purpose and decision

Define a provider-neutral timestamp-evidence boundary for T0. A TSA may strengthen proof that a specific immutable checkpoint object existed no later than the TSA-asserted `genTime`; it does not establish that market data is true, that an underlying event actually occurred at `genTime`, or that T0's database commit was durable.

**Architecture decision:** TSA is an asynchronous, optional evidence service outside T0's authoritative write path. T0 must continue to accept and durably record valid data when every TSA provider is unavailable. A timestamp that cannot be fully verified is never promoted to VERIFIED evidence.

This assessment does not select GlobalSign or any other provider and does not authorize implementation or operational testing.

## 2. Non-negotiable invariants

1. **Write-path independence:** market-data/event ingestion, ledger commit and ordinary reads do not wait for TSA network calls.
2. **Durability before timestamping:** only an immutable checkpoint whose underlying data has crossed the implementation's proven durable-commit boundary may be submitted. The actual T0 transaction/WAL boundary must be established from implementation evidence; it is not assumed here.
3. **Exact-object binding:** the timestamp imprint binds the exact immutable signed checkpoint object and verification context required by P1.8.36, not a mutable payload reference or an unsigned envelope.
4. **Fail closed for evidence, not for ingestion:** invalid, missing, stale, contradictory or unverifiable timestamp/revocation evidence is marked REJECTED or QUARANTINED. It must not be represented as trusted; it must not roll back or block an already valid T0 data commit.
5. **No silent evidence loss:** pending work, retries, provider responses, verification results and exceptions are durably accounted for. Retention and cleanup policies must preserve unresolved evidence.
6. **Provider portability:** provider-specific transport, endpoint, policy OID and response quirks stay inside an adapter/configuration boundary. The core evidence model is provider-neutral.
7. **No false assurance:** a TSA token is proof-of-existence for its imprint under the applicable trust and policy conditions, not proof of source correctness, completeness, event truth, database durability or commercial/legal admissibility by itself.

## 3. Logical architecture

```text
T0 ingestion
    |
    v
Authoritative ledger / durable commit
    |
    v
Immutable checkpoint + exact signed-object digest
    |
    +----> T0 continues normal operation (no TSA dependency)
    |
    v
Durable timestamp-intent queue / outbox
    |
    v
Provider-neutral TSA coordinator
    |
    +---- Provider adapter A
    +---- Provider adapter B (future, optional)
    |
    v
Raw RFC 3161 response archive
    |
    v
Independent local verifier
    |                 |
    v                 v
VERIFIED          REJECTED / QUARANTINED
    |
    v
Evidence manifest + long-term verification package
```

The queue/outbox is a logical requirement, not a claim that T0 currently has such a table or implementation. If the implementation supports a transactionally coupled outbox, the checkpoint and intent should be committed atomically. Otherwise, a recoverable reconciliation mechanism must detect committed checkpoints lacking intents and create them idempotently. This choice requires a later implementation-specific design review.

## 4. Evidence object and checkpoint contract

The timestamp subject should be a stable digest over the exact immutable signed checkpoint object, including the context needed to interpret it. The P1.8.36 contract remains authoritative for exact-signature binding. Do not timestamp only a mutable database row, an unsigned payload, a URL, or a re-serialized object whose canonical bytes are not frozen.

A future checkpoint manifest should identify, at minimum:

- checkpoint ID and format/schema version;
- covered ledger range or immutable event-set reference;
- previous checkpoint digest, where chaining is used;
- exact canonical signed-object bytes or a content-addressed immutable reference;
- digest algorithm identifier and digest value;
- source/watermark and window metadata, clearly separated from commit-time facts;
- durable-commit evidence/reference and the semantics of that boundary;
- creation software/version and the policy/configuration version.

No Merkle-tree format, canonical serialization, digest algorithm, signature algorithm, checkpoint cadence, or DB/WAL commit definition is selected by this assessment. Those remain OPEN pending compatibility with the actual T0 implementation and approved policy.

## 5. Asynchronous lifecycle and state model

Suggested logical states:

| State | Meaning |
|---|---|
| CREATED | Checkpoint is sealed and eligible for evidence processing |
| PENDING | Durable timestamp intent exists; no provider response accepted |
| SUBMITTED | Request attempt recorded; outcome may still be unknown |
| RESPONSE_STORED | Raw response bytes retained; not yet trusted |
| VERIFIED | Full local verification passed against the approved profile |
| RETRYABLE | Transient transport/provider failure; intent remains durable |
| QUARANTINED | Response or required trust/revocation evidence is missing, ambiguous or contradictory |
| REJECTED | Cryptographic/profile verification failed |
| EXHAUSTED | Automated retry policy stopped; manual review/reconciliation required |

State transitions must be append-only/auditable. A timeout after submission is an **unknown outcome**, not proof that the TSA did not issue a token. Retrying may produce more than one token for the same checkpoint; retain every received response and bind each to its request attempt. Local deduplication must not discard distinct signed evidence.

Retry limits, backoff, queue age, alert thresholds, concurrency and retention durations are all OPEN. Do not invent numeric values.

## 6. Request, response and verification boundary

The provider adapter may perform protocol transport and return raw bytes plus transport metadata. It must not decide whether a token is trusted. The independent verifier must validate at least:

1. strict parsing and supported RFC 3161 structure/version;
2. message-imprint algorithm and digest exactly match the submitted immutable object;
3. request nonce matches the response when the request included one;
4. policy OID is present/allowed under the versioned project profile;
5. TSA signature, signer identity, certificate path, timestamping EKU/profile and applicable critical extensions;
6. `genTime`, `accuracy` semantics and any approved clock-uncertainty rule;
7. signer certificate validity and applicable revocation evidence under the approved historical-time policy;
8. token uniqueness/serial and issuer identity consistency;
9. algorithm strength and deprecation policy at the relevant verification time;
10. the exact verification profile and trust-material version used for the decision.

A missing `accuracy` field is not zero accuracy. A published vendor accuracy statement is not automatically a per-token guarantee; its applicability, version and legal status must be preserved. The project must not infer ordering across independent TSAs or infer durable database commit from `genTime`.

RFC 3161 requires the response nonce to match when a nonce was supplied in the request. Project nonce/profile choices and all numerical acceptance bounds remain OPEN. See [RFC 3161](https://www.rfc-editor.org/rfc/rfc3161.html).

## 7. Revocation and long-term verification

For the exact TSA signer chain, preserve and verify issuer-authorized status evidence. OCSP validation must check responder authorization, signature, exact CertID, status and the response's time fields/freshness under the approved policy. CRLs must be signature/path-checked and associated with the correct issuer and validity interval.

Archive original signed OCSP responses and CRLs, not only a parsed GOOD/REVOKED result. A current OCSP GOOD response is not, by itself, proof that a certificate was valid at an earlier timestamp. An absent, stale, unauthorized or contradictory response must not be silently interpreted as GOOD.

The long-term evidence package should preserve:

- original RFC 3161 request and response bytes (DER), including nonce and transport attempt metadata;
- exact timestamped object bytes or immutable content-addressed reference and digest;
- TSA signer certificate and complete certificate chain as observed;
- applicable policy/CPS/TPS/terms snapshots with version, effective date and retrieval provenance;
- original signed OCSP responses and CRLs, including retrieval time and all validity fields;
- trust-anchor and verifier-policy version identifiers used at verification time;
- verifier software/version, result, failure codes and verification timestamp;
- immutable manifest and integrity digest for the complete package.

Future algorithm migration or re-timestamping must add evidence without overwriting the original token or historical verification record. The precise archival format, storage tier, retention, migration and legal admissibility requirements remain OPEN.

OCSP status semantics are specified by [RFC 6960](https://www.rfc-editor.org/rfc/rfc6960.html), with the nonce extension updated by [RFC 9654](https://www.rfc-editor.org/rfc/rfc9654.html). RFC 9654 updates RFC 6960 and obsoletes RFC 8954; implementation must not rely on the superseded nonce text alone.

## 8. Failure isolation and recovery

| Failure | Required T0 behavior | Evidence behavior |
|---|---|---|
| TSA timeout/unreachable | Continue ingestion and commit | Keep intent pending; retry under approved policy |
| Provider returns malformed token | No impact to committed data | Store raw response; reject/quarantine |
| Wrong imprint or nonce | No impact to committed data | Reject; preserve request/response for audit |
| Unknown policy OID or signer | No impact to committed data | Quarantine; do not trust |
| OCSP/CRL unavailable or stale | No impact to committed data | Verification remains pending/quarantined |
| TSA certificate revoked/chain invalid | No impact to committed data | Reject/quarantine according to historical policy |
| Queue worker crash | No impact to committed data | Resume from durable intent; idempotent local processing |
| Duplicate submission/response | No impact to committed data | Retain each distinct token; link attempts to same checkpoint |
| Provider contract/endpoint changes | No impact to committed data | Adapter/profile version changes require review and new evidence |
| Archive integrity failure | No impact to ingestion | Mark package integrity failure; restore/reconcile evidence separately |

A queue backlog can degrade evidence freshness but must not silently change the status of the underlying market data. Operational alerts and service-level targets are separate from the data-ingestion SLO and must not be represented as existing capabilities.

## 9. Provider-neutral interface boundary

The core should depend on an abstract contract equivalent to:

- `submit(imprint, requested_policy, nonce, request_context) -> raw_response + attempt_metadata`
- `parse(raw_response) -> protocol_structure`
- `verify(request, response, trust_profile, revocation_bundle) -> structured_verification_result`
- `archive(evidence_package) -> immutable_reference`

The interface is illustrative, not an approved API or implementation contract. Provider adapters may differ in endpoint, transport, authentication, policy OID, request limits and error mapping. Those differences must be explicit configuration with versioned provenance. No provider-specific trust decision may be hidden in the adapter.

Provider switching must not rewrite historical tokens or reinterpret them under a new provider's policy. Each historical record retains the provider identity and exact policy/trust profile applicable when it was issued.

## 10. Commercialization relevance

This design can support future products such as tamper-evident market-data history, data provenance and independent audit evidence. It does not make T0 commercially ready and does not establish regulatory compliance, legal admissibility, a customer SLA, or data correctness. Commercial claims require separate evidence for source quality, completeness, retention, security, availability, support and applicable legal terms.

TSA remains an optional evidence enhancement, not the product's sole trust foundation and not a reason to delay reliable T0 ingestion.

## 12. Acceptance criteria for P1.8.67

P1.8.67 may be marked PASS after independent review confirms:

- TSA is outside the authoritative T0 write path;
- failure isolation, unknown submission outcomes, retry and duplicate handling are explicit;
- the timestamp subject is bound to the exact immutable signed checkpoint object;
- token, certificate, policy and historical revocation verification boundaries are explicit;
- long-term evidence preservation and provider migration do not rewrite historical proof;
- all implementation-dependent and numerical parameters remain explicitly OPEN;
- no claim of runtime implementation, production assurance or commercial readiness is made.
