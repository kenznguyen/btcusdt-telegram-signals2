## 5. Finding

### IR122-01 — GitHub-hosted automation identity classes must be explicitly enumerated before enforcement claims
**Severity: MODERATE — FOLLOW-UP CONTROL-MAPPING REQUIRED; NO CURRENT AUTHORITY CREATED**

P1.8.121 §2–§3 prohibits enabling workflow permissions, credentials or storage capabilities that permit destructive actions, and rejects authority through alternate identities. This is directionally correct and does not weaken Option C.

For this repository's GitHub-centered execution model, a future effective-permission assessment must explicitly include, at minimum:
- GitHub Actions workflow/job `GITHUB_TOKEN` permissions and reusable-workflow inheritance;
- repository, organization and environment secrets and variables that can mint or convey storage credentials;
- OIDC trust relationships and cloud role-assumption policies;
- GitHub App installation tokens, deploy keys and personal access tokens;
- self-hosted runner identities, runner groups, persistent workspaces and host-level credentials;
- branch/environment protection and approval bypass paths relevant to workflow activation or credential release.

The list is an inventory requirement, not an assertion that any such credential currently has destructive access. It must be mapped to effective permissions and the exact storage/provider scope before a future claim that Option C is technically enforced.

**Required disposition:** retain Option C as the default; keep effective-permission enforcement **NOT VERIFIED** until a separately authorized, read-only identity/control-plane inventory and independent review are completed. No credential inspection requiring secret disclosure, permission change, IAM grant, workflow activation or destructive test is authorized by this finding.
