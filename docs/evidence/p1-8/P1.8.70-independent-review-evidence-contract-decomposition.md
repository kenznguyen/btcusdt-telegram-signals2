## 3. Finding F-17 — Aggregate intent status can conceal unresolved attempts

**Severity:** MEDIUM  
**Location:** Section 4.1, intent lifecycle.

P1.8.69 defines intent state VERIFIED when at least one token has a valid verification record, while the same intent may have multiple attempts, including an UNKNOWN attempt. It also defines REJECTED when all available candidate tokens fail. These proof outcomes can coexist with an unresolved delivery/reconciliation state.

The current single derived status does not explicitly distinguish:
- whether the checkpoint has at least one usable verified timestamp proof; and
- whether all request attempts have reached a known/settled outcome.

A consumer could read VERIFIED as “the intent is fully settled” even though an earlier timed-out request may still have produced an unobserved token. Conversely, REJECTED could be read as terminal while an unresolved attempt may later return evidence.

**Required clarification:** model at least two independent projections:
1. **Proof availability:** NONE, VERIFIED, QUARANTINED, REJECTED (derived from token-level verification records under an approved profile).
2. **Attempt/reconciliation state:** OPEN, IN_PROGRESS, UNKNOWN_OUTCOME, RETRYABLE, EXHAUSTED or SETTLED (derived from append-only attempt records).

The combined display may say, for example, `PROOF_VERIFIED / ATTEMPTS_UNRESOLVED`; it must not imply all attempts are settled merely because one token verifies. A later response must append evidence and trigger a new projection, never erase the prior UNKNOWN attempt.

No additional numeric retry policy or provider behavior is needed to clarify this distinction.
