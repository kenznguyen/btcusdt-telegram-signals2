## 2. IR124-01 — Multi-source snapshot consistency and drift protocol

### 2.1 Inventory cut and source observations

A future read-only inventory must declare a bounded inventory cut before collection:
- unique inventory run ID and immutable scope manifest;
- exact GitHub owner/repository/organization, environments, runner groups, OIDC trust relationships and provider/account/resource scopes included;
- explicit exclusions and inaccessible scopes;
- collector identity and its independently verified read-only permission boundary;
- collection start/end time, clock source and uncertainty where available;
- API version, endpoint/resource family, pagination state, source revision/ETag/version where exposed;
- per-record observation time and immutable evidence reference.

A single wall-clock timestamp must not be used to imply that independently queried systems were observed atomically. Each source observation retains its own interval and source revision.

### 2.2 Collection sequence and consistency

The collector must:
1. Freeze the scope manifest and inventory schema version.
2. Enumerate principals, roles, workflow/configuration controls, credentials metadata, runners, federation and resource policies without reading secret values.
3. Capture pagination completion and source revision/ETag markers for each page/resource where supported.
4. Re-read high-impact control-plane bindings after the initial pass: organization/repository Actions policy, workflow and reusable-workflow revisions, rulesets/protection bypass, environment protection/bypass, runner-group access, OIDC trust, app installations and provider role/resource policies.
5. Compare before/after observations and record any changes, missing revisions, inaccessible pages or inconsistent source states.
6. Seal the inventory manifest with hashes of all included non-secret evidence and the exact source revision/observation window.

Where a source provides no atomic snapshot, immutable revision or comparable drift marker, the inventory must state this limitation. It must not fabricate atomicity or claim cross-system snapshot consistency.

### 2.3 Drift and reconciliation outcomes

- If a high-impact binding changes during collection, recollect the affected dependency closure under a new inventory run ID; do not silently combine pre-change and post-change records.
- If a source changes repeatedly, cannot be stabilized, or lacks sufficient metadata to detect relevant change, affected scope is PARTIAL/UNKNOWN.
- If pagination is incomplete, a source is unavailable, a page is omitted, or source revisions conflict, affected scope is NOT VERIFIED.
- Any material change after final revalidation invalidates the affected conclusion and requires a new inventory cut.
- The final conclusion must be cryptographically bound to the exact evidence-manifest digest, source revisions, scope and observation window.
- A PASS applies only to the bounded scope and observation window recorded in that manifest. It is not a continuing guarantee.

No numeric freshness interval, permitted collection duration or maximum clock uncertainty is set here. Those values remain OPEN and require owner approval based on source semantics and operational evidence.

### 2.4 Final revalidation boundary

Immediately before issuing any bounded Option C technical-enforcement conclusion, an independent reviewer must verify that the high-impact control-plane bindings were revalidated after the inventory graph was assembled and that no unresolved drift exists.

If the revalidation cannot be performed read-only, cannot be independently evidenced, or discovers a material change, the result is PARTIAL/NOT VERIFIED. This review does not authorize collection or revalidation now.

## 3. IR124-02 — Opaque secret-derived credential provenance

### 3.1 Secret-safe metadata only

The inventory must never retrieve, reveal, print, export, copy, hash, transform or include secret values, token values, private keys, passwords, recovery codes or authentication material.

Where safely exposed through metadata or approved documentation, record:
- secret/credential metadata identifier and scope (repository, organization, environment or external secret manager);
- credential class and asserted issuer/type, if known without inspecting its value;
- accountable owner or issuing principal, if known;
- intended resource/audience/scope and documented permission boundary;
- issuance, expiry, rotation and revocation metadata/state, if exposed;
- consuming workflows, jobs, applications, runners and environment bindings;
- downstream token exchange, OIDC assumption, service-account or provider-role path;
- evidence source and limitations.

A metadata label or secret name is not proof of the credential's actual permissions.

### 3.2 Provenance and effective-scope rule

For each known consumer, trace the non-secret provenance chain from binding to consumer, credential issuer or exchange mechanism, assumed identity and target resource. Reconcile the resulting scope against independently available issuer/provider policy evidence.

If credential type, issuer, effective scope, consumer set, downstream exchange or revocation state cannot be established without inspecting the secret value, classify the affected credential path as `UNKNOWN / NOT VERIFIED`.

Do not infer a harmless or read-only credential from its name, workflow purpose, variable name, repository role or the absence of a visible delete command.

### 3.3 Option C conclusion restriction

A bounded Option C technical-enforcement PASS is prohibited if an in-scope opaque credential path could plausibly convey destructive capability and its effective scope cannot be independently bounded by non-secret evidence.

The appropriate result is PARTIAL/NOT VERIFIED, with the unresolved resource and path explicitly identified. The protective no-destructive-authority rule remains in force.

An opaque credential may be excluded from the destructive-capability uncertainty only where independent non-secret evidence proves that its reachable scope is constrained so it cannot mint, assume, delegate or exercise destructive authority. The exclusion rationale and evidence must be reviewed independently.

No secret value may be disclosed to close this finding. If safe evidence is insufficient, uncertainty remains.

## 4. IR124-03 — Explicit GitHub administration and bypass graph

P1.8.123's graph must include the following edges or a documented, semantically equivalent mapping. Edges are principal-to-capability/resource relations and must preserve exact scope, source and evidence.

### 4.1 Organization and repository administration

- `CAN_ADMINISTER_ORGANIZATION_SETTINGS`
- `CAN_ADMINISTER_REPOSITORY_SETTINGS`
- `CAN_TRANSFER_OR_DELETE_REPOSITORY`
- `CAN_CHANGE_MEMBER_OR_TEAM_ACCESS`
- `CAN_INSTALL_OR_ADMINISTER_GITHUB_APP`
- `CAN_CREATE_OR_REVOKE_DEPLOY_KEY`
- `CAN_CREATE_OR_REVOKE_TOKEN`

### 4.2 Actions and workflow policy

- `CAN_CHANGE_ACTIONS_ORG_POLICY`
- `CAN_CHANGE_ACTIONS_REPOSITORY_POLICY`
- `CAN_CHANGE_WORKFLOW_PERMISSION_DEFAULTS`
- `CAN_CHANGE_ALLOWED_ACTIONS_OR_PINNING_POLICY`
- `CAN_CHANGE_FORK_WORKFLOW_APPROVAL_POLICY`
- `CAN_EDIT_WORKFLOW_OR_REUSABLE_WORKFLOW`
- `CAN_APPROVE_PRIVILEGED_WORKFLOW`
- `CAN_TRIGGER_OR_RERUN_PRIVILEGED_WORKFLOW`

### 4.3 Rulesets, environments and deployment gates

- `CAN_CHANGE_RULESET_OR_BRANCH_PROTECTION`
- `CAN_BYPASS_RULESET_OR_BRANCH_PROTECTION`
- `CAN_CHANGE_ENVIRONMENT_PROTECTION`

### 4.4 Runner and execution infrastructure

- `CAN_ACCESS_RUNNER_HOST_OR_WORKSPACE`
- `CAN_CHANGE_RUNNER_NETWORK_OR_EXECUTION_POLICY`

### 4.5 Artifact, cache and dependency trust

- `CAN_PUBLISH_PRIVILEGED_WORKFLOW_ARTIFACT`
- `CAN_WRITE_OR_POISON_SHARED_CACHE`
- `CAN_CHANGE_ARTIFACT_OR_CACHE_RETENTION_AND_ACCESS`
- `CAN_PUBLISH_DEPENDENCY_CONSUMED_BY_PRIVILEGED_WORKFLOW`
- `CAN_CHANGE_ACTION_OR_REUSABLE_WORKFLOW_REFERENCE`

These edges supplement, not replace, the P1.8.123 base edges. The graph must also record negative/denied capabilities when authoritative evidence exposes them, but absence of a positive edge is not proof of a deny.

### 4.6 Trigger and untrusted-input analysis

Enumerate every enabled trigger and its effective trust context. Explicitly assess high-risk patterns including, where present:
- `pull_request_target`;
- `workflow_run`;
- privileged `workflow_dispatch` and `repository_dispatch`;
- reusable workflows callable from less-trusted contexts;
- privileged jobs consuming artifacts, caches, packages or outputs produced by less-trusted workflows;
- third-party actions and mutable/unpinned references;
- issue, comment, release and other event payloads reaching privileged workflow inputs.

This is not a closed list. The inventory must include all enabled triggers and platform-specific mechanisms that can cause privileged code to execute or alter its inputs.

For each path, trace who can modify the source, trigger execution, approve/bypass gates, supply inputs/artifacts, change dependencies, administer the runner, mint credentials and reach the target resource. Any untraceable transition is UNKNOWN.

## 5. Consolidated evidence and acceptance rules

The evidence package must bind:
- inventory run ID, schema version and frozen scope manifest;
- per-source observation interval, API version, pagination completion and revision/drift markers;
- graph and source evidence digests;
- secret-safe credential provenance and all UNKNOWN opaque paths;
- explicit administrative/bypass edges and trigger analysis;
- final high-impact revalidation result;
- independent reviewer identity, scope, disposition and residual risks.

A technical Option C PASS is limited to the declared inventory cut and scope and requires all of the following:
1. all in-scope identity/resource classes and enabled execution paths are enumerated;
2. direct, inherited, delegated, federated and credential-mint paths are resolved;
3. no unresolved drift or snapshot conflict remains;
4. opaque credential paths cannot conceal an unbounded destructive capability;
5. administrative, bypass, runner and artifact/cache trust paths are fully mapped;
6. no enabled principal or reachable path has destructive capability or uncontrolled ability to mint/delegate it;
7. an independent reviewer validates completeness and evidence-manifest binding.

If any condition is unknown, inaccessible, inconsistent or incomplete, result is PARTIAL/NOT VERIFIED. No destructive test is permitted to improve the result.
