# P1.8.113 — TSA Evidence Dependency / Copy / Hold Graph Crosswalk

**Version:** P1.8.113-v1  
**Closes:** P1.8.109 IR109-04 (MODERATE)  
**Depends on:** P1.8.34, P1.8.93, P1.8.105, P1.8.108, P1.8.109  
**Type:** Documentation-only evidence lifecycle crosswalk  
**Status:** GRAPH CONTRACT RECORDED — INVENTORY/REGISTRY/RETENTION OPEN — NOT IMPLEMENTED

## 1. Purpose and boundary

This contract makes the dependency, hold and copy relationships among TSA evidence objects explicit. It closes the ambiguity between preserving a token and preserving all material required to reproduce the bounded historical claim.

It is a logical graph contract, not a database schema, registry implementation, retention schedule or deletion plan. No evidence export, provider selection, restore, archive, cleanup or deletion is authorized.

## 2. Node identity

Every evidence node MUST be identified by an immutable tuple containing, as applicable:

- evidence_object_id and object_class;
- immutable object version/generation;
- exact content digest and digest algorithm/profile;
- parent claim/event ID and historical decision ID;
- manifest ID/version/digest;
- copy ID, source/destination domain and generation for each physical/logical copy;
- policy/profile revision and classification;
- provenance and verification status.

A mutable alias, filename or token-only reference is not an identity. Every copy is a separate lifecycle object, not merely a location attribute.

## 3. Required logical node classes

The graph must represent distinct nodes for:

1. exact signed event/envelope and signature bytes;
2. exact P1.8.36 imprint inputs and canonicalization context;
3. timestamp token bytes and token digest;
4. TSA identity and policy/profile revision;
5. trust-anchor and certificate-chain history;
6. revocation authority, records and observation evidence;
7. verifier implementation/profile and version;
8. original verification result and each later historical/current assessment;
9. evidence manifest and historical decision record;
10. source evidence objects and each replica, backup, export and recovery copy;
11. dependency/hold declarations and their revisioned scope;
12. integrity/restore verification records and operation history.

Secrets and private keys must not be placed in ordinary evidence manifests.

## 4. Typed dependency edges

Edges MUST be typed and versioned. At minimum:

| Edge type | Meaning | Lifecycle effect |
|---|---|---|
| CLAIM_REQUIRES | A bounded historical claim requires this exact evidence node/version | Node is protective while claim is retained |
| REPRODUCES | Node is required to recompute imprint or historical verification | Missing node makes claim INCOMPLETE |
| VALIDATED_UNDER | Verification result used this exact trust/profile revision | Preserve historical revision; do not substitute current policy |
| DERIVED_FROM | Evidence/result/manifest was derived from exact parent version | Parent identity/digest remains traceable |
| COPY_OF | Copy represents exact source evidence version | Copy gets independent identity and disposition |
| RESTORE_DEPENDS_ON | Recovery proof requires this evidence/copy | Protective recovery dependency |
| AUDIT_REQUIRES | Audit/incident decision requires the evidence | Protective audit hold |
| CONSUMER_DEPENDS_ON | Named consumer requires exact evidence version | Only that consumer can release its own exact dependency |
| HOLD_APPLIES_TO | Exact hold revision applies to node, claim, copy or declared scope | Hold remains protective until authoritative revocation |
| SUPERSEDES | New version supersedes but does not erase historical version | Old version remains if historical claims depend on it |

Edges MUST identify source node/version, target node/version, edge ID/type, owner/authority, policy revision, effective scope, provenance and current state. Unknown or unresolvable edges are protective blockers.

## 5. Claim-to-evidence dependency closure

For each retained historical claim, the manifest must enumerate all evidence required to reproduce the claim, including exact signature/imprint inputs, token, historical trust policy, applicable anchor/chain and revocation evidence, verifier profile, original result and the manifest itself.

A token cannot be declared independently complete merely because it is present and cryptographically parseable. If any required dependency is absent, corrupt, stale in a way material to the historical policy, or cannot be independently resolved, the claim is INCOMPLETE / NOT_VERIFIED and its required evidence remains protective.

Current trust assessment is a separate node/event; it cannot overwrite the historical decision or silently replace historical evidence.

## 6. Copy and hold crosswalk

Each copy node MUST have its own:
- exact source node/version and COPY_OF edge;
- destination identity, generation and failure-domain declaration;
- copy operation identity and commit/provenance evidence;
- digest and independent integrity result;
- applicable hold/dependency revisions;
- restore lineage and last verification;
- separate lifecycle/disposition state.

Holds and protective dependencies apply to the exact node/claim/copy scope recorded by the authoritative hold or dependency revision. A copy cannot infer that a sibling copy is disposable or recoverable.

If the hold's applicability to a child, parent or copy is uncertain, that node remains HOLD. No automatic cascade deletion or automatic hold release is allowed. A protective hold may be released only by its authorized owner through the authoritative, audited revocation process; the release does not itself establish deletion eligibility.

## 7. Independent disposition gate

Any future disposition proposal for one exact evidence node or copy must evaluate:

1. all CLAIM_REQUIRES and REPRODUCES edges;
2. all consumer-owned dependencies and explicit release evidence;
3. all AUDIT_REQUIRES, RESTORE_DEPENDS_ON and legal/operational holds;
4. parent/child lineage and whether remaining nodes retain sufficient identity and bytes to reproduce their claims;
5. all copy-specific integrity, recoverability and failure-domain obligations;
6. policy, dependency and hold revisions pinned in the P1.8.93 protected decision vector;
7. separate approval, exact-scope authorization, atomic final fence and independent post-operation verification.

A node with an unresolved incoming protective edge is BLOCKED. Deleting a node does not delete, release or mutate any connected node. Every node is assessed independently; no graph traversal may be interpreted as permission to cascade.

## 8. Graph integrity and failure cases

The graph manifest must be immutable/versioned and independently verifiable. Required future fixtures include missing parent edge, dangling child edge, duplicate copy ID, wrong generation, digest mismatch, missing trust-anchor history, missing revocation record, stale hold revision, uncertain hold scope, consumer ACK without release, source copy present but recovery copy unverified, shared failure-domain misdeclared independent, attempted cascade, and graph revision changing during final mutation recheck.

Missing graph partitions, incomplete enumeration, conflicting edge revisions or unavailable registry result in INCOMPLETE/HOLD. No absence-of-edge conclusion is valid unless graph completeness for the exact scope is independently proven.

## 9. OPEN items

Evidence registry and graph storage; inventory completeness; edge authority/ownership; trust and revocation source; copy topology and failure-domain proof; integrity oracle; hold propagation/applicability semantics; retention floors and legal obligations; restore history; consumer inventory; approval and verifier roles; all numeric parameters remain OPEN. No default TTL or retention floor is created.
