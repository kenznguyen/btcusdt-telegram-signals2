## 3. Executive assessment

P1.8.123 correctly responds to IR122-01 at documentary level. It covers GitHub Actions token/workflow permissions, reusable workflows, triggers, environments, secrets metadata without secret-value disclosure, GitHub Apps, PATs, deploy keys, human/bot principals, runner identities, OIDC federation and external provider policy. It also correctly distinguishes control-plane authority from data-plane authority, requires indirect credential-minting paths to be traced, treats unknowns as NOT VERIFIED, and prohibits destructive validation or automatic remediation.

No direct contradiction with Option C or P1.8.93 was found.

However, the contract does not yet define a sufficiently strong temporal snapshot/reconciliation method, does not fully resolve how opaque secret values and secret-derived credentials affect an Option C conclusion, and leaves several GitHub control-plane bypass classes insufficiently explicit in the graph vocabulary and evidence requirements.

## 4. Findings

### IR124-01 — Inventory snapshot consistency and drift revalidation are underspecified
**Severity: MAJOR**

P1.8.123 requires source revisions, observation times, pagination markers and graph completeness, but it does not define how independently collected GitHub, OIDC, runner and provider records form one defensible point-in-time permission view.

A multi-request inventory can be internally inconsistent: a workflow or environment policy may change after workflow metadata is collected but before role/OIDC/provider grants are read. Pagination can also span mutations. A complete set of individually successful API responses is not necessarily a consistent snapshot.

**Required clarification:**
- define collection start/end and per-source observation times, API version, immutable source revision/ETag where available, pagination completion and scope;
- record before/after control-plane revision or equivalent drift markers where available;
- detect changes during collection and mark affected scope PARTIAL/UNKNOWN rather than merging incompatible states;
- require a final read-only revalidation of high-impact policy/identity bindings immediately before any bounded Option C conclusion;
- bind the conclusion to the exact inventory manifest digest and validity/observation window; later material changes invalidate it.

No numeric freshness interval should be invented; it remains an owner-approved policy parameter.

### IR124-02 — Secret opacity and derived-credential provenance need an explicit UNKNOWN rule
**Severity: MAJOR**

P1.8.123 correctly prohibits retrieving secret values. However, the contract does not fully specify how to assess a secret whose value is opaque but whose consuming workflow, credential provenance, scope or downstream exchange cannot be established from safe metadata.

A secret name, scope and consumer list alone cannot prove the effective permissions of the credential it contains. Conversely, reading a secret value is prohibited and must not become a prerequisite.

**Required clarification:**
- require non-secret provenance metadata where available: issuer/type, owning principal, resource scope, rotation/expiry/revocation state and documented credential-mint path;
- map every known consumer and downstream exchange/assumption path without exposing secret material;
- where effective scope or provenance cannot be established without revealing the value, classify the credential path and affected resources as UNKNOWN/NOT VERIFIED;
- prohibit Option C technical-enforcement PASS for any in-scope opaque credential path that could convey destructive capability and cannot be bounded by independent non-secret evidence;
- do not weaken the no-secret-disclosure rule to resolve this finding.

### IR124-03 — GitHub administrative and workflow-bypass edges need explicit graph coverage
**Severity: MODERATE**

P1.8.123 mentions administrators, protection bypass actors, workflow triggers, artifacts/caches and untrusted inputs, but its required graph edge vocabulary does not explicitly require several high-impact control-plane transitions. The generic edge names may allow an inventory to omit how an actor changes repository/organization Actions policy, rulesets, environment bypass, runner groups or approval requirements.

**Required clarification:**
Add explicit edge types or mandatory equivalent mappings for:
- administer organization/repository settings and repository transfer/deletion;
- change Actions policy, allowed actions, workflow permissions and fork approval settings;
- change rulesets/branch protections and bypass actors;
- bypass or alter environment reviewers/deployment protection;
- administer runner groups, registration tokens and runner assignment;
- approve, rerun, cancel or alter privileged workflow execution;
- change artifact/cache trust or publish dependencies consumed by privileged workflows.

Include relevant high-risk trigger classes explicitly (for example `pull_request_target`, `workflow_run`, and privileged workflows consuming artifacts/caches from less-trusted workflows). The list must remain extensible to all enabled triggers and current platform semantics.
