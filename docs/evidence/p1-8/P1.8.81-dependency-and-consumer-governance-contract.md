# P1.8.81 — Dependency and Consumer Governance Contract

Date: 2026-11-09
Status: **DESIGN ONLY — NOT IMPLEMENTED / NOT ACTIVE / NOT AUTHORIZED**

## 1. Purpose and scope

This contract closes the dependency-governance gaps identified by P1.8.79 and P1.8.80. It defines:
- consumer availability, latency, and restore requirements that must be declared before archive can be considered;
- the logical authority and consistency requirements for dependency state;
- reconciliation behavior for registration, release, stale consumers, ownership transfer, decommissioning, and ambiguous outcomes.

This is a logical contract, not an API, database schema, registry implementation, scheduler, lease service, notification integration, archive service, or runtime behavior. No provider, storage engine, topology, numeric SLA, RPO/RTO, review cadence, or retention period is selected.

## 2. Non-negotiable invariants

1. Every dependency is pinned to an immutable dataset version and exact consumer identity.
2. A consumer must declare its availability and recovery needs before it relies on a dataset version.
3. Unknown, contradictory, stale, or unverifiable requirements block archive and destructive lifecycle progression.
4. The authoritative registry is the only source that can establish a dependency as durably registered or released.
5. A cache, replica, dashboard, search index, export, or read model cannot prove that no active dependency exists unless its consistency contract explicitly proves completeness at the required decision point.
6. Registry unavailability or loss of authoritative consistency fails closed.
7. A timeout, missed heartbeat, review date, job completion, ACK, or consumer decommissioning never automatically releases a dependency.
8. Reconciliation may add protective state or mark uncertainty; it must never silently remove a dependency.
9. Ownership transfer preserves continuous protection; there must be no interval in which the dependency disappears between owners.
10. Consumer release affects only the exact dependency owned/delegated to that consumer. It does not release producer obligations, holds, other consumers, recovery obligations, or copy dependencies.
11. Registry and reconciliation mechanisms do not grant archive or deletion authority.
12. T0 canonical writer fencing and the T0/T1/T2/T3/T4 responsibility boundaries remain unchanged.

## 3. Consumer availability requirement contract

### 3.1 Required declaration

For each consumer-to-dataset-version dependency, the consumer owner must declare, at minimum:

| Requirement | Meaning |
|---|---|
| Access pattern | Interactive/query, scheduled batch, streaming/continuous, replay, training/backtest, recovery/audit, or durable export |
| Availability class | Whether the dataset must remain online, may tolerate a degraded access path, or may be restored on demand |
| Maximum acceptable access latency | Consumer-specific bound; exact value and unit must be supplied and approved by the consumer owner |
| Maximum acceptable restore delay | Maximum time the consumer can tolerate before restored access is usable; exact value remains owner-supplied |
| Access window | Continuous, scheduled, event-driven, or incident-only |
| Completeness requirement | Full dataset/version, bounded time range, or specified partitions; no implicit partial result |
| Consistency requirement | Whether reads require current authoritative version, immutable snapshot, or a declared consistency point |
| Restore semantics | Exact version, schema, ordering, metadata, lineage and integrity checks required after restore |
| Degraded-mode behavior | Whether consumer can pause, queue, fail, or use a separately approved alternative without substituting unverified data |
| Recovery evidence | Required proof that restored content is complete and usable |
| Owner and purpose | Accountable owner, consumer identity and purpose-bound use |

These are contract dimensions, not preselected numeric service levels. Missing mandatory fields produce UNKNOWN and block archive review for the affected dependency.

### 3.2 Availability classes

The following qualitative classes are introduced as a common vocabulary. They do not set numeric guarantees.

| Class | Contract meaning | Archive consequence |
|---|---|---|
| ONLINE_REQUIRED | Consumer requires the dataset to remain directly available through its normal approved access path | Archive is blocked unless an alternative path is formally shown to meet every declared requirement |
| DEGRADED_ACCESS_ACCEPTABLE | Consumer can tolerate a documented degraded access path while preserving required integrity and completeness | Archive may be assessed only against the declared latency, completeness and degraded-mode requirements |
| RESTORE_ON_DEMAND | Consumer accepts a restore workflow before access, within its explicitly declared restore bound | Archive may be assessed only after restore path and independent restore evidence satisfy the bound |
| REBUILD_FROM_RETAINED_INPUTS | Consumer claims the output can be reconstructed from retained exact inputs and transformations | Archive review requires reproducibility evidence and proof that all exact inputs, code/configuration, model/schema and lineage are retained |
| NO_CURRENT_DEPENDENCY | Consumer has completed and durably released its exact dependency | This removes only that consumer dependency; it does not establish dataset archive/deletion eligibility |
| UNKNOWN | Requirement absent, contradictory, stale, or not verified | Archive and destructive lifecycle progression blocked |

A dataset version may have multiple consumers and multiple requirements. Its effective availability requirement is the most protective compatible requirement across all active and unresolved dependencies. A consumer cannot weaken another consumer's requirement.

### 3.3 Archive admission rule

Archive review requires all of the following:
1. Every registered consumer dependency has a current, owner-attributed availability declaration.
2. All active and unresolved dependencies are included; unknown or unregistered consumers are not assumed absent.
3. The proposed archive/restore path meets the combined access, latency, completeness, consistency, security and recovery requirements.
4. Restore tests and independent integrity evidence exist for the exact dataset class and relevant copy/backup chain.
5. The archive does not break source lineage, replay, training, backtest, audit, recovery or legal/incident obligations.
6. A dataset version and its manifest remain immutable and discoverable.
7. Separate archive authorization exists.

If any consumer requirement is UNKNOWN, if any relevant registry partition is unresolved, or if restore evidence is missing, archive remains BLOCKED. An archive operation is not authorized by this contract.

## 4. Authoritative dependency registry

### 4.1 Logical source of truth

The authoritative registry is the logical system of record for:
- consumer identities and accountable owners/delegations;
- exact dataset/version references;
- dependency registrations and state transitions;
- ACK and release events;
- ownership transfers and decommissioning records;
- review flags, unresolved conflicts and reconciliation evidence;
- idempotency claims and operation outcomes;
- audit references and policy/contract versions.

This contract does not choose a database, service, consensus protocol, cloud provider, replication topology, or deployment environment.

### 4.2 Required consistency properties

The future implementation must demonstrate these properties before it can govern archive or deletion eligibility:

**A. Durable acknowledgement**
- A registration or release is not reported as committed until its authoritative state and corresponding audit event are durably recorded under the approved consistency model.
- A success response must identify the exact dependency/event and committed registry revision or equivalent verifiable position.
- If the response is lost, the caller queries/retries with the same idempotency key; it must not create a new intent blindly.

**B. Atomic uniqueness and transition**
- Dependency identity and idempotency claims must be protected against concurrent duplicate creation.
- Conflicting use of one idempotency key with different semantic content is rejected and audited.
- A release and an ownership transfer must have one unambiguous durable ordering.
- A check-then-write sequence without atomic conflict protection is insufficient.

**C. Authoritative read for lifecycle decisions**
- Before archive eligibility or deletion eligibility is evaluated, governance must obtain an authoritative view that includes all committed registrations, releases, holds and transfers up to a defined decision barrier.
- The decision record must identify the registry revision/consistency point used.
- A stale replica, asynchronous read model, cache, or dashboard cannot be used to prove absence of dependencies.
- If the authoritative view cannot be established, the result is BLOCKED_UNKNOWN.

**D. Partition and recovery behavior**
- During a network partition or uncertain registry leadership, no side may independently declare dependencies released or absent.
- Recovery must preserve acknowledged committed events and surface any uncertain operation for reconciliation.
- Split-brain, rollback of acknowledged events, or an unproven recovery point blocks lifecycle decisions.
- No numeric RPO, RTO, quorum, or consistency technology is selected here.

**E. Audit continuity**
- Dependency state changes and audit evidence must be correlated and recoverable together.
- If state and audit evidence disagree, preserve the more protective dependency interpretation and block lifecycle progression.
- Audit retention and immutable evidence-store implementation remain governed by the separate evidence lifecycle contract.

### 4.3 Read models and replicas

Read models may support operational visibility and search. They are not authoritative for release or absence proofs unless a separately reviewed mechanism establishes freshness, completeness, ordering and consistency for the exact decision.

- A stale read model is marked stale/unknown, not silently refreshed into a claim of no dependencies.
- A missing dependency in a read model is not proof that it does not exist.
- Reconciliation between authoritative state and read models must be monotonic with respect to protection: uncertainty may add a protective flag but may not remove protection.
- Read model lag thresholds and freshness windows remain OPEN pending measurement and approval.

## 5. Dependency lifecycle and reconciliation

### 5.1 Registration

1. Authenticate the consumer and resolve owner/delegation.
2. Resolve the immutable dataset/version and validate manifest, schema, classification and access.
3. Require the availability declaration in Section 3.
4. Submit the exact dependency with a stable idempotency key.
5. Atomically record the dependency and audit event in the authoritative registry.
6. Return a verifiable committed result.
7. Consumer verifies the result before depending on the dataset.

If the registry cannot confirm durable registration, dependent work must not proceed under the assumption that the dependency is protected.

### 5.2 ACK and release

- ACK is a processing event only; it is not release.
- Release is a separate authenticated owner action scoped to one dependency ID.
- Release must capture purpose completion, retry/replay obligations, retained reproducibility evidence, and owner attribution.
- A consumer may not release another consumer's dependency or a producer/hold/recovery obligation.
- An uncertain release response leaves the dependency protective until the same intent is reconciled.
- Duplicate release with identical intent resolves to the durable prior outcome; conflicting payload is rejected and audited.

### 5.3 Stale or disconnected consumer

Signals such as heartbeat loss, service outage, missing owner, passed review date, repeated job failure or identity rotation set a review condition only.

Required behavior:
1. Preserve the dependency as protective.
2. Record the stale signal and evidence provenance.
3. Identify the last authoritative dependency state and owner/delegation.
4. Seek owner confirmation through an approved channel, if one exists.
5. Reconcile with consumer job/run, retry queues, replay requirements, model/experiment references and any durable exports.
6. If evidence remains insufficient, keep the dependency unresolved.
7. Escalation may request human review but cannot expire or release the dependency.

No heartbeat TTL, grace period, escalation SLA, notification channel or automatic orphan cleanup is established.

### 5.4 Ownership transfer

A transfer must:
- identify old and new accountable owners and consumer identities;
- be authorized by the relevant governance process;
- preserve the same dependency identity and dataset/version scope;
- record a durable transfer event and audit evidence;
- establish the new owner's acceptance before the old owner's responsibility ends;
- preserve the protective state continuously.

If transfer acknowledgement is missing or ambiguous, retain the prior owner/dependency as unresolved and do not release.

### 5.5 Consumer decommissioning

Before service/account decommissioning:
- enumerate all dependencies under that identity from the authoritative registry;
- reconcile them against active jobs, scheduled workflows, retries, replay, model/experiment and export lineage;
- explicitly release, transfer, or preserve each exact dependency;
- retain identity and audit history after credentials are revoked.

Deleting credentials, a service account, a repository, a VM, or a consumer process must not delete its dependency history or imply release.

### 5.6 Reconciliation outcomes

| Outcome | Meaning | Lifecycle effect |
|---|---|---|
| CONSISTENT_ACTIVE | Authoritative and consumer evidence agree that dependency remains active | Protective |
| CONSISTENT_RELEASED | Valid owner release is durably recorded and corroborated | Removes only that dependency |
| OWNER_TRANSFER_PENDING | Transfer incomplete or acceptance uncertain | Protective |
| CONSUMER_UNREACHABLE | Consumer cannot currently be queried | Protective |
| OWNER_UNKNOWN | Accountable owner cannot be verified | Protective |
| REGISTRY_UNAVAILABLE | Authoritative state cannot be read/committed | Fail closed |
| EVIDENCE_CONFLICT | Registry and consumer-side evidence disagree | Protective; adjudication required |
| STATE_AMBIGUOUS | An operation may have committed but outcome is unknown | Protective; reconcile same intent |
| UNREGISTERED_CONSUMER_SUSPECTED | Source/job/export evidence suggests an unregistered dependency | Block lifecycle review until investigated |
| RECONCILED_WITH_ADJUDICATION | Authorized review resolves a documented mismatch with evidence | Exact scope only; audit retained |

These are conceptual reconciliation outcomes, not approved runtime enums.

## 6. Unregistered and indirect dependencies

A registry cannot prove absence if consumers can read data without registering. Before using registry state to support archive/deletion eligibility, the system must establish:
- controlled access paths for relevant datasets;
- identity attribution for each access path;
- registration enforcement or a separately approved acquisition protocol;
- discovery of durable downstream copies, exports, derived artifacts and scheduled jobs;
- a way to detect and investigate consumers that bypass the registry.

Access logs alone do not automatically establish a durable dependency, and absence of access logs does not prove absence of replay, recovery, legal, training or audit obligations.

If a bypass path or unregistered consumer is suspected, the dataset is BLOCKED_UNKNOWN until the path is understood and its dependency disposition is governed.

## 7. T0–T4 application

| Layer | Dependency expectations | Governance boundary |
|---|---|---|
| T0 | Declare internal validation, correction, recovery and source obligations where applicable; publish immutable dataset identity/version and availability metadata | T0 remains canonical producer and fenced writer; no independent deletion authority |
| T1 | Pin exact T0 versions; declare availability needs for raw observations and derived intelligence; preserve input hashes and snapshot lineage | Cannot release another consumer's dependency or delete T0 |
| T2 | Pin T0 inputs, feature/label/model/experiment/backtest versions needed for reproducibility | Preserve CORE_LEDGER and AI_LEDGER independence; no cross-ledger release |
| T3 | Declare market/signal/risk input versions needed for paper reconstruction, reconciliation and audit | Paper-only; no live execution authority |
| T4 | Read-only view dependencies; durable reports/exports register their own dependency and copy identity | UI dismissal or cache eviction is not dependency release |
| Backup/replica/export | Declare copy identity, lineage, restore/access requirement and copy-specific consumers | Separate copy lifecycle; no implicit cascade |

This table is a target contract, not proof of current runtime registration.

## 8. Failure and recovery matrix

| Failure | Required response |
|---|---|
| Registry unavailable | No new dependency is assumed committed; no release/absence proof; block archive/deletion |
| Stale replica/read model | Do not use for lifecycle decision; obtain authoritative state |
| Concurrent registration | Atomic uniqueness; identical retry returns prior result; conflicting intent rejected |
| Concurrent release/transfer | One durable ordered result; unresolved race remains protective |
| Lost response after mutation | Query/retry same idempotency key; preserve uncertainty |
| Consumer heartbeat lost | Mark review; keep dependency protective |
| Owner cannot be resolved | Preserve dependency and escalate; no automatic release |
| Consumer service decommissioned | Reconcile all dependencies before decommission; retain audit identity |
| Registry restore/rollback uncertain | Block lifecycle decisions until acknowledged-event continuity is proven |
| Registry/audit mismatch | Preserve more protective state; reconcile |
| Unregistered consumer suspected | Block eligibility review until scoped investigation resolves it |
| Availability declaration missing | Archive blocked |
| Restore test or integrity check fails | Archive blocked; retain source and copy protection |
