# P1.8.87 — Storage Disposition Semantics and Bounded Claims

Date: 2026-11-09  
Status: DOCUMENTARY DESIGN ONLY — NOT IMPLEMENTED / NOT ACTIVE / NOT AUTHORIZED  
Closes review finding: DR-04 (MAJOR)

## 1. Purpose and claim boundary

This contract defines the meanings of archive, logical removal, physical deletion, cryptographic erasure and verified disposition across storage classes. It prevents a backend's local success response from being represented as global or irreversible deletion.

A disposition result must always state:
1. exact object/version and storage boundary;
2. operation requested and operation actually performed;
3. representation affected;
4. residuals and known copies not affected;
5. recovery/replay possibilities;
6. verification method and observation time/evidence;
7. bounded final claim.

No adapter, operation or storage provider is approved by this document.

## 2. Normative operation vocabulary

- ACCESS_RESTRICTION: access is denied or withdrawn; bytes may remain.
- LOGICAL_UNLINK: an index, row, pointer or namespace reference is removed; underlying bytes may remain recoverable.
- VERSION_DISPOSITION: one exact immutable object generation/version is removed or transitioned; other versions remain separate.
- PHYSICAL_ERASURE: payload bytes are overwritten or otherwise rendered unrecoverable within a precisely declared media and threat boundary; generally cannot be inferred from an API response.
- CRYPTOGRAPHIC_ERASURE: specified encryption key material is destroyed so ciphertext within the declared key domain is no longer decryptable; only valid if all alternate keys, plaintext copies, caches, snapshots and key backups are accounted for.
- ARCHIVE_TRANSITION: object is moved to a declared archive tier or location while preservation and availability obligations remain.
- COPY_DISPOSITION: an independently identified replica, backup, export, local copy or derived object is handled under its own authorization.
- METADATA_DISPOSITION: selected metadata is removed; audit, tombstone and legal/governance records may remain.
- VERIFIED_WITHIN_SCOPE: independent evidence supports the exact declared operation and boundary; it is not a global deletion claim.

Terms “deleted”, “erased”, “purged” or “gone” must not be used without the exact operation semantics and scope.

## 3. Adapter-specific semantic requirements

### 3.1 SQLite and filesystem

Object identity must include canonical database/file identity, dataset/version or row/partition scope, filesystem identity and relevant generation/inode or equivalent precondition. The adapter must account for WAL, SHM, rollback journal, temporary files, snapshots, filesystem copies, hard links, symlinks, open handles and backup artifacts.

Deleting a row or logical record does not prove its bytes are absent from WAL, free pages, snapshots, backups or filesystem recovery. VACUUM/compaction is a separate storage mutation and is not implicitly authorized by row deletion. Path resolution must prevent symlink/path substitution and verify the exact target at mutation time.

### 3.2 PostgreSQL and compatible stores

Scope must identify database/cluster, schema, relation/partition, row identity or immutable key range, transaction/snapshot boundary and relevant WAL/replication state. DELETE, TRUNCATE, DROP PARTITION, retention policy, vacuum and WAL recycling have different semantics and must not be conflated.

Logical row visibility is not proof that WAL, replicas, snapshots, backups, replicas, exports or point-in-time recovery copies no longer contain the payload. Partition/table operations require exact dependency and foreign-key review. No broad predicate or unbounded cascade is permitted.

### 3.3 Object storage

Scope must identify account/project, bucket/container, key, immutable version/generation, region/replication destinations, retention lock/legal hold and lifecycle policy. A delete marker is not version purge. Version deletion does not prove replica or provider backup deletion. Lifecycle jobs and asynchronous replication require independent completion evidence and bounded provider guarantees.

### 3.4 Backups and recovery chains

A backup object is identified as part of a complete recovery point, including base, incremental, log/WAL chain, metadata, manifests, encryption keys and restore dependencies. Removing one chain member may invalidate recovery for unrelated datasets. No chain pruning or expiry may proceed without proof of unaffected recovery points and approved recovery obligations.

A checksum or successful backup job is not restore proof. Restore validation is a separate governed activity; no restore is authorized here.

### 3.5 Exports and recipient copies

Each export requires exact payload/version, format, destination, recipient, transfer event, access state and acknowledgement evidence. A sender-side delete or link revocation does not prove recipient-side deletion. Unknown recipient or uncontrolled download means global disposition cannot be claimed.

### 3.6 Caches, materializations and model artifacts

A cache entry, feature materialization, model, prediction or derived artifact requires exact lineage and version identity. Rebuildability must be proven from retained inputs and transformation provenance before any disposition review. A derived artifact may contain information not trivially reversible to source; lineage alone does not prove safe deletion or irrelevance.

## 4. Result vocabulary and residual handling

Per-object operation result:
- NOT_ATTEMPTED
- PRECONDITION_FAILED
- SUBMITTED
- CONFIRMED_WITHIN_BACKEND
- AMBIGUOUS
- PARTIAL
- RESIDUALS_KNOWN
- RESIDUALS_UNKNOWN
- INDEPENDENTLY_VERIFIED_WITHIN_SCOPE
- NOT_VERIFIED
- CONFLICTED

A backend return code maps at most to CONFIRMED_WITHIN_BACKEND. It cannot by itself produce INDEPENDENTLY_VERIFIED_WITHIN_SCOPE.

Residuals include WAL/journal pages, replicas, object versions, delete markers, snapshots, backup chains, exports, local copies, caches, plaintext/key copies, provider retention remnants and audit metadata. Unknown residuals block a global claim. A partial operation moves to reconciliation and prohibits blind retry.

## 5. Bounded claims

Allowed claim examples:
- “The specified row IDs are no longer visible in database X at transaction boundary Y; WAL/backup copies were not assessed.”
- “Object generation G was removed from bucket B; replica and provider backup disposition remain unverified.”
- “Access to export E was revoked at destination D; recipient-held copies are unknown.”

Prohibited claim examples:
- “All copies are deleted” when inventory is incomplete.
- “Permanently erased” based only on logical delete or API success.
- “Backup deleted” based only on source deletion.
- “Cryptographically erased” without complete key-domain and plaintext-copy evidence.

Global deletion is not an available result while any relevant copy boundary is UNKNOWN, PARTIAL, STALE or CONFLICTED.

## 6. Independent verification

Verifier must use an evidence path independent of the executor's success response and, where feasible, independent control plane. It must validate exact identity/generation, postcondition, operation semantics, residual inventory, replication/provider state and audit continuity.

If independent observation is impossible, report NOT VERIFIED or VERIFIED_WITHIN_DECLARED_LIMITATION, never VERIFIED_COMPLETE. Verification evidence must not rely on deleted payload or secret key material.

## 8. Restrictions

This is a design contract only. It does not authorize SQLite row deletion, VACUUM, PostgreSQL mutation, object purge, lifecycle policy, backup expiry, replica removal, key destruction, export deletion, cache eviction, restore or any real-storage test.

T0 remains protected and independently governed. CORE_LEDGER and AI_LEDGER remain separate. Tests/CI NOT RUN; workflow run/artifact NONE; runtime evidence NOT VERIFIED.
