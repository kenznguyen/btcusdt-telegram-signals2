## 2. Independent review findings

### F01 — Replay denominator and event population are ambiguous

P1.8.28 states "100 duplicate replays per event" for V01/V13, while V02 uses 100 mutated variants per existing event ID. It does not state how many distinct base events, event classes, or lifecycle states must be represented. A large replay count over one trivial fixture would not establish broad scenario coverage.

**Required clarification before execution:**
- Freeze a versioned base-event corpus covering all applicable event classes and lifecycle states.
- Report distinct base event count separately from replay/variant count.
- Preserve per-event identity, payload digest, sequence, observer, and checkpoint context.
- Treat the threshold as repetitions per defined scenario, not as a substitute for scenario breadth.

**Disposition:** PARTIAL. Add corpus size and scenario inventory to each run manifest before any run.

### F02 — Observer identity and worker independence need stronger proof

"Two workers" and "two observer identities" do not prove independent security principals if both share credentials, host identity, signing key, or authorization scope.

**Required clarification:**
- Distinct test principals with independently provisioned credentials.
- Record principal ID, credential/key fingerprint (public metadata only), host/process identity, and authorization scope.
- Demonstrate that one principal cannot submit ACKs as the other.
- For multi-host claims, run on distinct hosts and record network/topology evidence.
- Test same-principal retry separately from cross-principal duplicate ACK.

**Disposition:** PARTIAL. A shared process or shared credential cannot satisfy independent-observer coverage.

### F03 — Durability levels must not be conflated

D0–D4 are correctly separated in principle. However, a successful process crash or database restart cannot prove host, storage, device, or power-loss resilience. Provider-approved D3/D4 fault methods may not exist or may be unsafe to induce.

**Required clarification:**
- Record exact fault model and provider-supported mechanism for each level.
- State which levels are not safely testable; mark them NOT VERIFIED rather than infer from lower levels.
- Never describe a generic restart as power-loss testing.
- D4 requires a disposable device/volume and an explicitly approved method; otherwise it remains NOT TESTED.

**Disposition:** PASS for claim separation; PARTIAL for execution feasibility. No D3/D4 execution is authorized.

### F04 — Acknowledged-transaction RPO=0 needs a defined boundary

"RPO 0" is meaningful only relative to the system's acknowledgement contract, failure domain, and commit durability point. It must not imply zero data loss across every provider failure mode.

**Required clarification:**
- Define exactly when the application may emit durable ACK.
- Bind ACK to the database/provider's documented durable commit guarantee and the declared failure domain.
- Specify whether target applies to process, DB restart, host, zone, or provider-wide failure.
- For each tested failure, compare acknowledged transaction IDs with recovered durable state.
- Any acknowledged transaction missing after the claimed failure model is FAIL; if the failure model was not tested, that scope remains NOT VERIFIED.

**Disposition:** PARTIAL. The proposed RPO=0 remains unapproved and must be scoped to an explicit failure domain.

### F05 — Revocation policy is intentionally unresolved

P1.8.26 and P1.8.28 correctly require a versioned policy, but neither selects the semantics for late-arriving pre-revocation events, propagation, cache age, or unavailable revocation service.

**Decision required:** see §3, DEC-01.

**Disposition:** BLOCKED for V07 execution until the owner selects and versions a policy.

### F06 — Checkpoint membership policy is intentionally unresolved

The documents list timestamps and boundary scenarios but do not select event-time/watermark, commit-time, or another membership rule. Without this choice, expected outcomes for delayed arrivals and commit-after-seal cannot be fixed.

**Decision required:** see §3, DEC-02.

**Disposition:** BLOCKED for V08 execution until the owner selects and versions a policy.

### F07 — RPO/RTO are proposed targets, not service capabilities

The 5-minute snapshot RPO, 60-minute staging RTO, and 3 restore rehearsals are planning thresholds. They are not measured and should not be represented as a production SLO.

**Decision required:** see §3, DEC-03.

**Disposition:** BLOCKED for restore acceptance until the owner approves or replaces the targets and identifies the failure domain.

### F08 — Environment equivalence must be claim-specific

A single global "production-equivalent" label can conceal differences. For example, a staging environment might match transaction semantics but not multi-host topology or storage failure behavior.

**Required clarification:**
- Produce an equivalence result per test claim and per matrix dimension.
- A case may PASS only for the exact property and failure domain whose prerequisites are equivalent.
- Non-equivalent dimensions must remain explicit limitations; they cannot be waived by an overall environment label.

**Disposition:** PARTIAL. Use claim-scoped equivalence; no blanket equivalence assertion.

### F09 — Deterministic thresholds require frozen scenario definitions

Iteration counts alone do not establish coverage if barrier placements, timing windows, scenario variants, or expected outcomes are not frozen before execution.

**Required clarification:**
- Version and hash scenario inventory, barriers, seeds, fixtures, expected outputs, and thresholds before the run.
- Report planned versus actual counts and every skipped scenario.
- A skipped or altered scenario invalidates the corresponding coverage claim.
- Random stress is supplemental, not a replacement for deterministic interleavings.

**Disposition:** PARTIAL. Freeze a test plan digest before any execution.

### F10 — Evidence provenance and reviewer independence

P1.8.26/P1.8.28 require source SHA, workflow and artifact references, but independence should include verifying the evidence from immutable GitHub identifiers and reproducing hashes without relying solely on the generating job's summary.

**Required clarification:**
- Independent reviewer fetches run, job, artifact and source metadata.
- Recompute artifact hashes independently.
- Bind all outputs to source SHA, harness SHA, configuration digest, environment matrix digest, fixture digest and policy versions.
- Record reviewer identity and review timestamp; no self-attested PASS based only on a generated summary.

**Disposition:** PARTIAL. Add an independent verification record to each staging evidence package.

## 3. Owner policy decision register

No policy choice is inferred or made on behalf of the system owner.

### DEC-01 — Signing-key revocation semantics (required before V07)

Options to consider:
- **A. Immediate revocation:** events received after authoritative revocation are rejected, regardless of signing time.
- **B. Trusted signing-time exception:** events provably signed before revocation may be accepted when received later, subject to trusted timestamp and audit requirements.
- **C. Quarantine on ambiguity:** if signing time, revocation state, or propagation freshness cannot be proven, event is quarantined pending review.

Whichever policy is selected must define propagation bound, cache maximum age, unavailable-service behavior, rotation overlap, and trusted time source.

**Current decision:** OPEN — V07 BLOCKED.

### DEC-02 — Checkpoint membership semantics (required before V08)

Options to consider:
- **A. Commit-time membership:** checkpoint includes only events durably committed before its defined seal/commit boundary.
- **B. Event-time plus watermark:** membership is based on event time and a predeclared watermark/late-arrival policy.
- **C. Explicit hybrid:** a formally specified combination with deterministic treatment of late events and post-seal arrivals.

The selected policy must define equality at the boundary, delayed events, missing/future timestamps, reopening/correction behavior, and audit representation.

**Current decision:** OPEN — V08 BLOCKED.

### DEC-03 — Restore objectives (required before restore tests)

Proposed targets in P1.8.28:
- Acknowledged transaction RPO: 0, only for a declared failure domain and durable-ACK contract.
- Snapshot RPO: at most 5 minutes of committed synthetic data.
- Staging RTO: at most 60 minutes from declared restore start to verified ready.
- Three independent restores from distinct consistent snapshots.

Owner may approve, modify, or reject these targets. The decision must define the failure domain, measurement start/end points, excluded data, and evidence needed.

**Current decision:** OPEN — RESTORE ACCEPTANCE BLOCKED.
