## 3. V07 — Approved revocation and trusted-time controls

The owner-approved control direction is:

1. Use an independently verifiable trusted timestamp authority/proof, with trust anchors managed and validated independently. The concrete authority, accepted proof profile, trust-anchor distribution and rollover process remain OPEN pending security/provider review.
2. Keep `signed_at`, trusted timestamp generation time, `received_at` and `revoked_at` semantically distinct. A trusted timestamp proves that the timestamped data existed no later than the authority's asserted time; it must not be misrepresented as an exact client-side signature-creation time.
3. Use an authoritative, auditable revocation source with explicit effective-time semantics. The concrete source, precision and conflict-resolution contract remain OPEN.
4. Revocation state that is unavailable, stale, contradictory or unverifiable fails closed; ambiguous events are quarantined. Exact reason-code taxonomy and freshness thresholds remain OPEN.
5. Do not treat cache age as a propagation guarantee. Maximum cache age and propagation bound, including measurement method and units, remain OPEN until supported by authority guarantees and evidence.
6. Do not assume key-rotation overlap. Old-key signing cutoff and new-key activation must be explicit, with deterministic interval and equality semantics. Exact cutover instants and any permitted overlap remain OPEN.
7. Quarantine release requires explicit authorization, append-only audit evidence and deterministic reprocessing. Authorized roles, dual-control requirements and operational workflow remain OPEN.
8. A claimed pre-revocation event may be considered only when independently verifiable trusted timestamp evidence places the timestamped data within the key's permitted validity interval and the approved historical-event rule allows it. Otherwise quarantine/fail closed.
9. Client-supplied timestamps alone never establish trusted signing time.

**V07 parameters still OPEN:** concrete TSA/provider and proof profile; trust-anchor lifecycle; revocation authority and effective-time precision; maximum cache age; propagation bound; reason-code mapping; key rotation cutover/overlap values; quarantine-release roles and controls; historical-event acceptance details; all numerical thresholds.

**V07 status:** Policy direction APPROVED; detailed parameterization OPEN/BLOCKED; fixtures NOT FROZEN; NOT EXECUTED.

## 4. V08 — Approved checkpoint membership controls

The owner-approved control direction is:

1. Use UTC and half-open event-time windows `[start, end)`, avoiding double membership at adjacent boundaries.
2. Use a monotonic watermark derived from explicitly tracked source progress; do not infer completeness from a wall-clock timer alone.
3. Determine allowed lateness from measured event/ingestion lateness distributions plus an explicit risk margin. No guessed duration is accepted.
4. Seal eligibility uses the explicit equality rule `watermark >= window_end`; the exact precision and watermark source remain implementation/evidence dependent.
5. Record the authoritative clock source and measured uncertainty. If uncertainty exceeds the subsequently approved bound, HOLD/quarantine rather than guess.
6. Durable commit-time must come from the actual durable commit boundary of the selected persistence implementation. That implementation/provider and its proof contract remain OPEN; no provider is selected by this decision.
7. Establish one deterministic seal/commit linearization point: a transaction committed before the seal gate is eligible for the sealed checkpoint; a transaction committed after the gate is excluded from that sealed checkpoint and routed through correction.
8. Sealed checkpoint contents are immutable. Late events use an append-only, separately sequenced correction stream with parent-checkpoint lineage, reason, digest and idempotent replay.
9. Missing, malformed or future-dated timestamps are rejected/quarantined. The future-skew limit remains OPEN and must be measured/approved.

**V08 parameters still OPEN:** source-progress/watermark algorithm details; idle-partition handling; allowed-lateness duration and units; event/clock precision; clock source and uncertainty bound; durable commit evidence tied to a selected implementation; seal barrier implementation; correction schema/version and sequence contract; future-skew threshold; exact reason codes.

**V08 status:** Policy direction APPROVED; detailed parameterization OPEN/BLOCKED; fixtures NOT FROZEN; NOT EXECUTED.

## 5. Restore — Approved measurement and acceptance contract direction

The owner-approved measurement direction is:

1. Declare a narrow, explicit failure domain before making any RPO claim. Process, database, host, storage/provider, zone, region and provider failures are distinct claims; no broad resilience claim is implied.
2. A transaction is acknowledged only after the selected implementation's documented durable commit boundary has been reached and independently evidenced.
3. Measure acknowledged-transaction RPO against a frozen population of acknowledged transaction IDs and payload digests, not timestamps alone. RPO=0 applies only to the declared and tested failure domain.
4. Measure snapshot RPO using both elapsed time and the exact missing committed-transaction population relative to the declared failure cut and snapshot consistency point.
5. Start RTO at one predeclared, auditable failure-declaration event, used consistently across rehearsals.
6. Stop RTO only when frozen service-ready, integrity and reconciliation checks all pass; process startup alone is insufficient.
7. Require three genuinely separate rehearsals, each with a unique run ID, snapshot ID, isolated restore target, manifest, raw logs, restored-state digest and independent artifact-hash verification. Disclose shared dependencies.
8. The integrity oracle covers event chain, sequence, checkpoint, duplicate/replay, ACK population and ledger/business-state reconciliation. Any unexplained difference fails.
9. Before any future execution, define rollback, access revocation, resource cleanup and post-cleanup inventory verification.
