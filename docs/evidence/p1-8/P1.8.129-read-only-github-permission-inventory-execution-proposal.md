## 4. Read-only permission design

The principle is least privilege and endpoint-level necessity, not a broad role label.

| Data family | Minimum permission class to validate before approval | Restriction |
|---|---|---|
| Repository identity/basic metadata | Repository metadata read | No writes |
| Actions policy and workflow metadata | Actions read, plus any separately documented read permission required by the exact endpoint | No workflow execution or modification |
| Rulesets, branch protection and repository administration metadata | Administration read or exact narrower endpoint permission if supported | No ruleset/protection mutation or bypass |
| Environment protection metadata | Exact environment/deployment read permission supported by the endpoint | No deployment or environment change |
| Runner/group assignment metadata | Exact self-hosted-runner read permission supported by the endpoint | No runner registration, host access or job |
| Organization membership/inherited role metadata | Organization members/administration read only if strictly necessary and separately approved | No org-wide sweep |
| Secret metadata | Exact secrets metadata/list permission only, if safely available | Never access secret values |
| App/deploy-key metadata | Exact read-only administration metadata permission | No app installation, key retrieval or creation |

The table intentionally uses permission classes pending endpoint-by-endpoint validation against the current GitHub API and fine-grained token/GitHub App permission model. It does not assert that one permission name authorizes every listed endpoint.

Before execution, create an endpoint matrix with:
- HTTP method and exact endpoint path;
- resource scope;
- required fine-grained token or GitHub App permission as documented;
- whether the endpoint returns metadata or sensitive values;
- pagination behavior and maximum page size;
- rate-limit behavior;
- source revision/ETag or other drift marker availability;
- explicit reason the endpoint is necessary.

Any endpoint whose method is not read-only, whose response may include secret material, or whose required permission is broader than approved scope must be excluded and marked NOT VERIFIED.

### 4.1 Authentication choice

Prefer an already existing, independently attributable read-only identity only if its effective permissions can be proven without exposing credential values. Do not create a new PAT, GitHub App, deploy key or OIDC trust relationship under this proposal.

If an existing identity has mixed read/write permissions or an opaque effective scope, do not use it for collection. A broad credential must not be treated as safe merely because the planned requests are GET operations.

## 5. Snapshot, drift and evidence protocol

Apply P1.8.125:
1. Freeze the exact scope manifest and inventory run ID.
2. Record collector identity, permission proof, API versions and collection start time.
3. Enumerate all approved endpoint families with complete pagination.
4. Record per-resource observation time, source revision/ETag where available and evidence digest.
5. Re-read high-impact policy bindings after graph assembly.
6. Compare observations and invalidate/recollect changed dependency closures under a new run ID.
7. Bind the final inventory, limitations and reviewer disposition to one immutable evidence manifest.

No global atomic snapshot is claimed. If the API provides no revision marker, document the limitation and use the P1.8.125 bounded observation/drift protocol. If meaningful drift cannot be detected, the affected result is PARTIAL/NOT VERIFIED.

Freshness limits, maximum collection duration and clock uncertainty remain OPEN until supported by source semantics and separately approved. Do not invent numeric thresholds.

## 7. Stop conditions

Stop collection immediately and preserve the already collected non-secret evidence if:
- the credential's effective permissions are broader than approved or cannot be proven;
- any endpoint requires write/admin permission not explicitly approved;
- any response unexpectedly contains secret values or authentication material;
- pagination, source revision or observation consistency cannot be established;
- a high-impact policy changes during collection and cannot be reconciled;
- destructive capability or an unapproved credential-mint/delegation path is discovered;
- API visibility or rate limits prevent a defensible bounded conclusion;
- collection would require workflow execution, runner host access, provider probing or scope expansion.

Do not remediate or revoke anything after a stop condition. Report the finding and request a separate owner decision.

## 8. Acceptance criteria and result vocabulary

A read-only inventory may be reported PASS only for the exact bounded repository/control-plane scope if:
- all approved endpoint families were collected with complete pagination;
- collector identity and effective read-only permission boundary were independently evidenced;
- no secret values were accessed or included;
- all high-impact control-plane bindings were revalidated and no unresolved drift remains;
- all visible direct/inherited/delegated paths are represented;
- all exclusions and UNKNOWN paths are explicit;
- an independent reviewer confirms evidence-manifest integrity and scope completeness.

If any required path is unavailable, opaque, inconsistent or excluded, report PARTIAL/NOT VERIFIED. A PASS does not establish provider permissions, runner host safety, workflow source safety or global Option C enforcement.
