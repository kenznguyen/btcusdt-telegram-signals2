# P1.8.105 — Restore Governance Epoch and Post-Restore Reconciliation Contract

**Version:** P1.8.105-v1  
**Type:** Documentation-only lifecycle safety contract  
**Depends on:** P1.8.26, P1.8.28, P1.8.30, P1.8.34, P1.8.93, P1.8.100–P1.8.104  
**Status:** CONTRACT DRAFT RECORDED — RESTORE READINESS BLOCKED — NOT EXECUTED  
**Authorization:** Documentation only. No restore, staging, fault injection, provider selection, deletion, or runtime mutation is authorized.

## 1. Purpose and boundary

This contract closes the design gap identified by P1.8.104 CCX-01 and CCX-05: restoring a data snapshot must not restore stale lifecycle authority, and a restored object snapshot must not be mistaken for authoritative proof of a prior storage mutation.

A restore is a recovery operation over data and service state. It is not a rollback of governance history, a new approval, a deletion authorization, or proof that a previous mutation did or did not commit.

This document defines a post-restore governance boundary. It does not select a database, provider, event-log technology, trusted-time provider, identity system, or deployment topology. It does not establish runtime capability or grant permission to perform a restore.

## 2. Binding invariants

1. **Restore starts quarantined.** A restored environment is not READY for consumers, lifecycle decisions, or destructive operations until reconciliation passes.
2. **Governance is not rolled back with a snapshot.** Current policy, dependency, hold, revocation, tombstone, authorization-revocation and operation-history state must be reconciled from an authoritative source independent of the restored snapshot.
3. **Pre-restore execution authorizations are invalid.** Every authorization issued before the restore boundary is unusable after restore, regardless of its original expiry or apparent status in the snapshot.
4. **No snapshot-only mutation conclusion.** Object presence/absence in a restored snapshot cannot establish COMMITTED, NOT_COMMITTED, or VERIFIED_DELETED for a prior operation.
5. **Exact identity and generation.** Reconciliation binds dataset ID, immutable dataset version, storage object identity, object generation/version, copy identity and operation ID. Mutable aliases or broad selectors are insufficient.
6. **No authority escalation.** Restore completion, database startup, replay completion or a matching digest does not grant deletion eligibility, approval or execution authority.
7. **Fail closed.** Missing, stale, conflicting, incomplete or unverifiable governance evidence keeps the affected scope quarantined.
8. **No cascade.** Source, replica, backup, export, correction and evidence-copy lifecycles remain independent and separately reconciled.
9. **T0 independence is preserved.** T0 remains the canonical data asset; consumers cannot use restore to gain write/delete authority over T0. CORE_LEDGER and AI_LEDGER remain separate and protected.
10. **No paper/live boundary change.** `AI_EXECUTION_ENABLED=false`; this contract does not enable live orders.

## 3. Restore and governance epochs

### 3.1 Distinct concepts

The design MUST distinguish:

- **Restore run ID:** unique identifier for one restore attempt.
- **Restore epoch:** monotonically distinguishable recovery generation assigned to the restored environment.
- **Governance epoch:** authoritative lifecycle-governance generation used to reject stale decisions and authorizations.
- **Source snapshot identity:** immutable identity and consistency point of the restored data snapshot.
- **Operation-history high-water mark:** last independently evidenced lifecycle/storage operation included in the reconciliation input.
- **Policy/dependency/hold/revocation revisions:** independently versioned current governance state.

These are separate values. A snapshot timestamp, database sequence, host clock or restore run ID MUST NOT be substituted for a governance epoch.

### 3.2 Epoch issuance and authority

A future implementation must obtain a new restore/governance epoch from an independently governed, monotonic authority or an equivalently proven mechanism that cannot be rolled back by restoring the data snapshot.

The concrete authority, persistence mechanism, identity model, epoch encoding, uniqueness scope, trust model and availability requirements remain OPEN. No provider or numeric value is selected here.

If a new epoch cannot be independently established, the restore remains QUARANTINED. The restored snapshot MUST NOT self-assert that it is current.

### 3.3 Authorization invalidation

At the restore boundary:

- all pre-restore deletion execution authorizations are invalidated;
- pending authorizations and unconsumed tokens are invalidated;
- in-flight operations are marked for reconciliation, not assumed cancelled or committed;
- any new destructive operation requires fresh eligibility evaluation, approval where required, exact-scope authorization and final fencing under the new governance epoch;
- authorization records from the snapshot are retained as historical evidence only and cannot be reactivated.

Invalidation applies even if the authorization's original expiry is later than restore completion.

## 4. Post-restore reconciliation sequence

The following is a normative logical sequence, not an executable workflow or implementation state machine.

| Step | Required action | Failure disposition |
|---|---|---|
| R0 | Assign restore run ID; place restored scope in quarantine; block consumers and lifecycle mutation | Remain quarantined |
| R1 | Establish a new independently verifiable restore/governance epoch | BLOCKED if unavailable |
| R2 | Identify exact snapshot, consistency point, dataset versions, object generations and copy lineage | BLOCKED on ambiguity |
| R3 | Retrieve append-only governance and operation history from an independent source | BLOCKED if incomplete/unavailable |
| R4 | Replay or reconcile policy, dependency, hold, quarantine, revocation, tombstone and authorization-invalidation events through a proven high-water mark | BLOCKED on gaps, conflicts or unknown ordering |
| R5 | Compare restored revisions with current authoritative revisions; identify missing, stale, duplicate and conflicting state | Quarantine affected scope |
| R6 | Reconcile every in-flight/uncertain mutation against operation history and an independent object-generation oracle | RECONCILIATION_REQUIRED if indeterminate |
| R7 | Verify backup/replica/export/evidence-copy lineage and restore consistency without merging their lifecycle state | BLOCKED on missing copy lineage |
| R8 | Produce a complete, immutable reconciliation manifest and independent verification result | NOT_READY until complete |
| R9 | An authorized readiness authority may decide whether the exact scope can leave quarantine | No automatic READY transition |

A replay process must be idempotent and preserve original event identity and order evidence. It must not synthesize missing governance events from current snapshot state.

## 5. Governance state that must be reconciled

At minimum, the reconciliation manifest must identify the exact revision and provenance of:

- lifecycle policy and policy-revocation state;
- dataset registry, immutable versions, classification and steward;
- consumer registrations, dependency ownership, ACK and release events;
- preservation holds, legal/operational obligations and quarantine constraints;
- V07 signing-key status, revocation records, trust-policy revisions and quarantine decisions;
- V08 source progress, checkpoint seals, durable commit evidence and correction lineage;
- deletion requests, approvals, execution authorizations and authorization revocations;
- per-object operation intents, provider operation receipts, reconciliation outcomes and tombstones;
- backup, replica, export, archive and evidence-copy manifests and their independent lifecycle state;
- audit records, trusted-time evidence and event-log high-water marks.

Unknown consumer owners, stale dependencies, missing holds, unavailable registries or incomplete operation history remain protective blockers. Timeout, absent heartbeat, service decommission or snapshot age cannot release them.

## 6. Operation history and independent object oracle

### 6.1 Two independent evidence planes

A future restore acceptance must reconcile at least two distinct evidence planes:

1. **Operation-history plane:** immutable request/intent ID, exact target identity and generation, authorization and governance epoch, operation attempt, provider receipt/operation ID, outcome evidence and reconciliation record.
2. **Object-state plane:** independently queried exact object identity and generation/version, existence state, content/metadata digest where applicable, and observation provenance.

Neither plane alone is sufficient for an ambiguous prior mutation. Their independence and trust boundaries must be documented and tested for the selected storage implementation.

### 6.2 Determinate outcomes

For each exact manifest item, the reconciliation result must distinguish:

- **COMMITTED:** authoritative operation history proves the mutation committed for the exact target generation.
- **NOT_COMMITTED:** authoritative operation history proves no mutation committed and the object oracle is consistent with that conclusion.
- **PARTIAL:** only part of a multi-object operation is proven complete.
- **UNKNOWN / AMBIGUOUS:** history, object state, generation or ordering cannot establish a unique outcome.
- **CONFLICT:** operation history and object oracle disagree.
- **VERIFIED_DELETED:** a separate post-operation verification proves the exact authorized target is absent under the required verification contract; this is not inferred from a restored snapshot.

PARTIAL, UNKNOWN and CONFLICT require quarantine and reconciliation. Never retry a mutation merely because the restored snapshot shows an object present or absent. Never infer NOT_COMMITTED from absence alone or COMMITTED from a deletion tombstone alone.

### 6.3 In-flight and uncertain operations

An operation that was in flight at the restore cut must be reconciled against its original idempotency key, provider operation identity and exact object generation. If the provider cannot prove whether it committed, no blind retry is permitted. The affected object remains protected until an independently reviewed resolution is recorded.

## 7. READY gate

A restored scope may be proposed as READY only when all applicable conditions are evidenced:

- a new independently verified restore/governance epoch exists;
- the restored snapshot and exact object manifest are identified;
- the authoritative governance event stream is complete through a declared high-water mark;
- policy, dependencies, holds, revocations, tombstones and authorization invalidations are reconciled;
- all pre-restore authorizations are demonstrably unusable;
- all in-flight/uncertain operations have determinate outcomes or remain explicitly isolated;
- independent object-generation checks reconcile with operation history;
- backup/copy/evidence lineage is complete for the declared scope;
- integrity, checkpoint, correction, consumer and ledger reconciliation checks pass where applicable;
- independent evidence-hash verification and reviewer sign-off are recorded;
- no unresolved blocker is hidden by a global readiness flag.

READY is scoped to the exact restored environment and manifest. It does not grant deletion authority or bypass a new lifecycle decision.

## 8. Required negative cases

The future frozen test plan must include at least:

| ID | Scenario | Required result |
|---|---|---|
| RST-G01 | Restore snapshot contains an unexpired pre-restore deletion authorization | Authorization invalidated; no execution |
| RST-G02 | Snapshot omits a newer hold or dependency release/re-registration event | Reconcile from authoritative history; quarantine until resolved |
| RST-G03 | Snapshot resurrects a released dependency | Current dependency state wins only after authenticated event reconciliation |
| RST-G04 | Snapshot omits a newer revocation, quarantine or policy revision | Fail closed; quarantine |
| RST-G05 | Snapshot predates a tombstone or operation receipt | No deletion conclusion from snapshot; reconcile history and object oracle |
| RST-G06 | Object absent but operation history is missing | UNKNOWN; no VERIFIED_DELETED claim |
| RST-G07 | Object present but provider history proves commit for a prior generation | Generation-aware reconciliation; no blind retry |
| RST-G08 | Provider history and object oracle disagree | CONFLICT; quarantine |
| RST-G09 | Event-history high-water mark has a gap or cannot be authenticated | NOT_READY |
| RST-G10 | Restore epoch source is unavailable or can be rolled back with snapshot | NOT_READY |
| RST-G11 | One backup/replica/export lineage is missing | Affected copy scope remains blocked |
| RST-G12 | Reconciliation is replayed twice | Idempotent result; no authority or state duplication |
| RST-G13 | Restore completes but consumer/ledger/checkpoint integrity has not passed | NOT_READY |
| RST-G14 | Only one of multiple manifest objects is reconciled | PARTIAL; no aggregate success |
| RST-G15 | A post-restore request attempts to reuse old approval or idempotency authorization | Reject; require fresh exact-scope decision |

These are specification cases only. Fixtures, test code and execution are NOT included in this work item.
