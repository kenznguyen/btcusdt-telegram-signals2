## 1. Executive result

The inspected T0 implementation is currently a **closed-candle market-data store and Feeder**, not an implemented event ledger with signed checkpoints.

The source establishes:
- Binance USD-M BTCUSDT 15m/1h candle records;
- SQLite and optional PostgreSQL storage paths;
- fenced writer/lease behavior;
- per-page/per-batch transaction boundaries;
- read-window coverage and a SHA-256 `datasetVersion` response field.

The inspected source does **not** establish:
- a canonical event-ledger object model;
- a durable checkpoint/seal record;
- a signed checkpoint or signing-key lifecycle;
- a timestamp-intent/outbox queue;
- RFC 3161 client/verifier integration;
- token, certificate, OCSP/CRL or TSA evidence archive;
- a persisted scheduler watermark/checkpoint contract.

Therefore, P1.8.67/P1.8.69 are valid provider-neutral target architecture documents, but they are **not a description of current T0 capability**. TSA integration cannot be implemented by simply attaching a provider adapter to the current Feeder.

## 3. Current data object and write path

### 3.1 Data model

The canonical PostgreSQL table `market_data.candles` stores:
- exchange, market type, symbol and timeframe;
- candle open time;
- OHLCV numeric values;
- `available_at_ms`;
- nullable `ingestion_batch_id`.

Its primary key is the market/timeframe/open-time identity. The SQLite store has the equivalent candle-oriented shape. The inspected canonical writer does not populate `ingestion_batch_id`.

This is a time-series candle model. It is not a general event ledger with immutable event IDs, signed event envelopes, append-only correction events or checkpoint membership manifests.

### 3.2 SQLite write boundary

The SQLite writer:
- requires an existing database and schema;
- opens the existing DB in read-write mode;
- starts `BEGIN IMMEDIATE`;
- validates the current lease and generation;
- inserts or idempotently compares candles;
- rechecks lease validity before commit;
- explicitly commits or rolls back the batch.

WAL mode is enabled by the store initialization/WAL keeper. The inspected source does not set or document a project-specific `PRAGMA synchronous` value, checkpoint policy, fsync guarantee or host/storage failure-domain guarantee. Therefore, source inspection alone does not establish a production durability class or RPO.

### 3.3 PostgreSQL write boundary

The PostgreSQL writer:
- validates the batch before opening the DB transaction;
- invokes `market_data.write_canonical_candle()` for each candle;
- the SECURITY DEFINER function locks/checks the canonical lease and performs insert-or-conflict comparison;
- the outer `connection()` context uses a PostgreSQL transaction around the write batch; transaction completion occurs when the context exits successfully.

The inspected application code does not set `synchronous_commit`, prove `fsync`/storage behavior, configure synchronous replication, or document the actual provider failure domain. Database transaction completion is not by itself proof of the project's required power-loss/host-loss durability claim. These require deployment/configuration evidence and bounded durability testing.

## 4. Scheduler and checkpoint distinction

`FeederScheduler` keeps `_last_completed_end_ms` in process memory. It derives UTC close boundaries and uses coverage/recovery logic to fill missing windows. The inspected scheduler state is not itself a durable immutable checkpoint or persisted monotonic watermark.

The API's `datasetVersion` is a SHA-256 over the returned read-window JSON representation, including its selected range and returned candle content. The README explicitly says it is not a hash of the entire database. It is a useful response/version fingerprint, but it is not currently:
- a persisted checkpoint manifest;
- proof that a specific complete dataset was sealed;
- proof of durable commit at a defined storage boundary;
- a signed object;
- an RFC 3161 timestamp subject.

Do not repurpose `datasetVersion` as a trusted checkpoint without a separate frozen canonicalization, completeness, immutability and commit-boundary contract.

## 5. Finding F-19 — Timestamp subject and assurance use case are not yet grounded in current T0

**Severity:** HIGH — blocks implementation planning for a direct P1.8.36/V07 integration.

P1.8.36 defines a timestamp imprint that includes exact signature bytes and immutable signature-verification context, so the token can support a narrowly scoped historical signature-existence claim. The inspected T0 candle path contains no signed event/checkpoint object, signing key, signature verification context or signature revocation lifecycle.

There are therefore two distinct possible use cases that must not be conflated:

**A. Dataset/checkpoint proof-of-existence**
- Freeze a deterministic manifest for a defined, complete candle dataset or checkpoint.
- Timestamp its digest.
- This can support a claim that the exact manifest/dataset commitment existed no later than the TSA assertion, subject to token/policy validation.
- It does not prove who signed the dataset, signer intent, exchange truth, or a signature's existence before key revocation.

**B. Signed-object historical verification (P1.8.36/V07)**
- Requires a real immutable signed object, exact signature bytes, signer/key identity, signature profile, trust and revocation lifecycle.
- Timestamp imprint must bind that exact signature and required context.
- The inspected T0 source does not currently supply this object or lifecycle.

**Required owner decision before source design:** choose whether T0's initial TSA use case is A (dataset/checkpoint proof-of-existence), B (signed-object historical verification), or two separately versioned evidence products. Do not silently weaken P1.8.36 or claim that an unsigned dataset hash satisfies its signature-binding contract.

## 7. Compatibility conclusion

P1.8.67 remains a valid target architecture for a future optional evidence subsystem, but the correct first integration boundary is not yet “TSA adapter into Feeder.”

Before implementation, T0 needs an owner-approved evidence subject and contract:
- define whether the subject is a dataset manifest or a signed object;
- define deterministic bytes and completeness/membership semantics;
- define how the subject references exact committed candle rows/batches;
- map the DB/WAL durability boundary and its failure domain;
- define how the immutable manifest and evidence intent survive restart and reconcile missing/duplicate attempts;
- define whether signature/key lifecycle is in scope or explicitly out of scope.

TSA must remain outside the candle write transaction and Feeder scheduling critical path. No network call may be made inside the transaction or scheduler callback.
