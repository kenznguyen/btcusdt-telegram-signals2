# P1.8.36 — Trusted Timestamp to Signature-Binding Contract

**Version:** P1.8.36-v1  
**Type:** Documentation-only security contract  
**Depends on:** P1.8.26, P1.8.28–P1.8.35  
**Status:** CONTRACT DRAFT RECORDED — SECURITY PARAMETERS OPEN — V07 BLOCKED  
**Authorization:** No implementation, key operation, staging, data probe or workflow dispatch is authorized.

## 1. Purpose and security claim

Resolve P1.8.35 finding F-01 by defining what trusted timestamp evidence must bind before it can support a historical signing-time decision.

The intended claim is deliberately narrow:

> A valid trusted timestamp over a cryptographic imprint that includes the exact signature value and its immutable verification context establishes that this exact signed object existed no later than the timestamp authority's asserted generation time (`genTime`), subject to successful validation of the timestamp token, authority trust chain, policy and clock/accuracy requirements.

It does **not** prove the exact instant the signer generated the signature, signer intent, or that the signature was created at `genTime`. It does not make a revoked key valid. It supplies an independently verifiable upper bound on the existence of the timestamped signed object.

A timestamp over payload-only bytes, a client-supplied `signed_at`, or an envelope that does not cryptographically include the exact signature value is insufficient to establish that the signature existed before revocation.

## 2. Normative binding contract

### 2.1 Timestamped object

The timestamp message imprint MUST be computed over a deterministic, domain-separated encoding that includes, at minimum:

1. a fixed protocol/domain identifier and contract version;
2. immutable event identifier;
3. exact payload digest and payload digest algorithm identifier;
4. signer key ID and independently pinned public-key fingerprint;
5. signature algorithm identifier and relevant parameter/profile identifier;
6. the exact signature value bytes that the verifier will later verify;
7. immutable envelope/schema version and any context fields required to prevent cross-protocol or cross-event substitution.

The timestamp MUST bind the signature value itself, not merely the payload digest or an unsigned/pre-signature envelope. The precise encoding, field ordering, length-prefixing, digest algorithm and canonicalization/profile are OPEN pending security review. Implementations MUST NOT invent an ad hoc encoding and claim conformance to this contract.

Where a canonical signed object is used instead of a direct signature-value imprint, its canonical representation MUST cryptographically contain the exact signature value and all verification context above. Any alternate serialization must either reproduce the exact canonical bytes or fail verification; semantic equivalence alone is insufficient.

### 2.2 Imprint construction and token validation

The eventual profile MUST specify and freeze:
- domain separation and unambiguous binary encoding;
- imprint hash algorithm and algorithm-agility policy;
- exact signature byte extraction and envelope version;
- timestamp request/response profile, including nonce handling where applicable;
- accepted timestamp policy identifiers and authority trust anchors;
- token signature, certificate path, policy, validity and revocation validation;
- timestamp accuracy/uncertainty interpretation and equality semantics;
- trust-anchor rollover, compromise and historical validation rules.

If an RFC 3161 Time-Stamp Token is selected, its `messageImprint` MUST equal the independently recomputed imprint for the exact signed object being verified. The token's `genTime` is the authority's asserted time for the timestamp operation, not a client-supplied signing time. Selection of RFC 3161, a concrete TSA, policy OID, trust anchor, hash algorithm or numeric accuracy bound is NOT made by this document; those remain OPEN.

### 2.3 Verification binding

A verifier MUST:
1. parse the immutable event envelope under its declared version;
2. independently recompute payload digest and the timestamp imprint from the exact received signature bytes and required context;
3. validate the timestamp token and its authority chain/policy under the frozen trust configuration;
4. reject if the token imprint differs, required context is absent, algorithms are disallowed, or validation is ambiguous;
5. verify the event signature using the identified key and declared algorithm/profile;
6. evaluate key validity and authoritative revocation state under the separately approved V07 policy;
7. record the token digest/reference, recomputed imprint, key fingerprint, policy versions, trusted `genTime`, receipt time, revocation effective time and final reason/disposition.

The event, signature and timestamp token are immutable evidence inputs. Replacing the payload, signature, key ID, algorithm, event ID, envelope version or other bound context MUST invalidate the binding. Unknown, stale, unavailable or contradictory trust/revocation state remains fail-closed and quarantined.

### 2.4 Historical revocation decision

A timestamp can support historical acceptance only if:
- its imprint is bound to the exact signature and context being verified;
- the token and TSA trust chain validate under the applicable historical policy;
- the asserted `genTime`, including its declared uncertainty, is demonstrably within the key's permitted validity interval;
- the authoritative revocation source and effective-time semantics are known;
- the owner-approved equality/boundary rule yields a pre-revocation result.

A timestamp whose `genTime` is after revocation cannot establish that the signature existed before revocation, even if the payload is old. A timestamp at or overlapping the revocation boundary is indeterminate until exact precision, uncertainty and equality rules are approved; it MUST fail closed/quarantine. Do not infer a favorable ordering from rounded timestamps or client clocks.

The relationship between timestamp generation time and revocation effective time, including equality and uncertainty handling, remains OPEN pending the detailed V07 decision. This contract does not approve historical acceptance by itself.

## 3. Required positive and negative fixtures

Fixture bytes and expected outcomes must be frozen and hashed before V07 can leave BLOCKED. The following is a contract-level test matrix, not executed test evidence.

| ID | Scenario | Expected contract outcome |
|---|---|---|
| TB-P01 | Valid timestamp imprint includes exact signature bytes and full required context; token and signature validate; trusted time is clearly before revocation | Binding PASS; historical policy decision proceeds |
| TB-P02 | Same signed object timestamped before revocation, received after revocation | Binding PASS; historical policy decision proceeds using trusted time, not receipt time |
| TB-N01 | Timestamp covers payload digest only; signature bytes are not included | REJECT as historical signing-time proof |
| TB-N02 | Timestamp covers unsigned/pre-signature envelope | REJECT as historical signing-time proof |
| TB-N03 | Signature is replaced while payload and timestamp token remain unchanged | REJECT; imprint mismatch |
| TB-N04 | Event ID, key ID, algorithm, payload digest or envelope version is substituted | REJECT; context/imprint mismatch |
| TB-N05 | Timestamp token is copied from a different event or signature | REJECT; imprint mismatch |
| TB-N06 | Client `signed_at` claims a pre-revocation time but no valid bound timestamp exists | REJECT/quarantine; client time is not trusted proof |
| TB-N07 | Bound timestamp `genTime` is after revocation effective time | Not eligible for pre-revocation acceptance; fail-closed/quarantine |
| TB-N08 | Timestamp is exactly at or overlaps revocation boundary under unresolved precision/uncertainty | HOLD/quarantine until boundary policy is frozen |
| TB-N09 | Token signature, TSA chain, policy or trust status is invalid/unverifiable | REJECT/quarantine |
| TB-N10 | Timestamp imprint algorithm or envelope profile is disallowed/unknown | REJECT/quarantine |
| TB-N11 | Signature bytes are changed through re-encoding or normalization | REJECT unless exact frozen profile proves byte-identical binding |
| TB-N12 | Duplicate delivery/replay of the same valid event and token | Idempotent decision; no duplicate acceptance side effect |
| TB-N13 | Valid signature exists but timestamp token is missing | Signature may be cryptographically valid, but historical pre-revocation claim is NOT PROVEN; quarantine/fail closed under V07 |

For every fixture preserve exact event bytes, signature bytes, timestamp token bytes, recomputed imprint, key fingerprint, algorithm/profile, token policy, trusted time/uncertainty, receipt time, revocation record/version and expected reason code. Never include private keys or credentials.

## 4. Failure and ambiguity behavior

The following conditions MUST NOT produce a positive historical-time result:
- payload-only or unsigned-envelope timestamp;
- missing, malformed or detached token without a verified binding;
- imprint mismatch or any context substitution;
- unknown/unsupported algorithm, encoding or envelope version;
- invalid timestamp signature or untrusted/ambiguous TSA chain;
- unknown, stale, unavailable or contradictory revocation state;
- timestamp uncertainty that overlaps a validity/revocation boundary;
- reliance on client clock, local receive time or rounded timestamps as signing-time proof.

Disposition is fail-closed with quarantine and append-only audit. A later authorized resolution must not rewrite the original evidence or original decision.

## 6. Exit criteria for F-01 / V07

F-01 may be marked RESOLVED only after a versioned contract freezes:
1. exact timestamped-object bytes and domain-separated encoding;
2. cryptographic inclusion of the exact signature value and required context;
3. token validation profile and trust lifecycle;
4. deterministic revocation/validity boundary semantics, including uncertainty;
5. positive and negative fixture bytes, hashes and expected outcomes;
6. independent security review confirming no payload-only or unsigned-envelope bypass.
