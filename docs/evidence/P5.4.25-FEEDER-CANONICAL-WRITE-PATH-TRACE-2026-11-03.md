## Trace

### T1 — Runtime startup and lease acquisition

`FeederRuntime.start()`:
1. validates the start timestamp and lifecycle state;
2. calls `lease_store.acquire(owner_id, ttl_seconds=...)`;
3. stores the returned lease generation;
4. publishes STARTING status when a status store is configured;
5. invokes the injected recovery coordinator, if present;
6. renews the lease once after recovery;
7. starts the scheduler;
8. marks runtime RUNNING, publishes status and starts the heartbeat thread.

A failed recovery prevents scheduler startup and attempts to release the acquired generation.

### T2 — Runtime heartbeat supervisor exists in source

`_start_heartbeat()` creates a daemon thread named `t0-feeder-lease-heartbeat`. The loop waits `config.lease_heartbeat_seconds` (default 15 seconds), then calls `LeaseStore.heartbeat(owner, generation, now_ms, ttl_seconds)`.

If heartbeat returns anything other than True or raises, the runtime calls `on_lease_lost()`. That method changes lifecycle state to LEASE_LOST, stops the heartbeat and scheduler, marks health not-ready and publishes the lease-lost status.

**Conclusion:** the heartbeat supervisor is implemented in this class. This source review does not prove that a production process constructs and runs this class.

### T3 — Scheduler callback is guarded before sync

`FeederRuntime._configure_retry()` wraps the scheduler's injected `sync_callback`. For each invocation, the wrapper:
- captures the current runtime generation;
- calls `LeaseStore.authorize_write(owner, generation, now_ms=clock())`;
- calls the original callback only when authorization returns True;
- otherwise calls `on_lease_lost()` and raises PermissionError;
- passes the guarded operation through the configured retry policy.

`FeederScheduler.run_due()` calls its configured `sync_callback(timeframe, start_ms, end_ms)`. The scheduler itself does not fetch or write data; its module documentation describes the injected callback as the hand-off to the existing `sync_window()` ingestion path.

This establishes a pre-callback authorization boundary for the scheduler path, not atomic authorization of the eventual database mutation.

### T4 — TOCTOU remains between authorization and canonical write

`authorize_write()` delegates to lease validity checking, which completes its own SQLite transaction. The original sync callback runs after that transaction returns.

The inspected `CandleStore` provides schema initialization and the separate `read_window()` API; the actual canonical `sync_window()` implementation and its candle upsert transaction were not established from the inspected source set. Therefore this review cannot prove that the lease generation is checked again inside the same SQLite write transaction that mutates canonical candles.

A lease can theoretically expire or be taken over after the preflight authorization and before the canonical commit. A stale process could then continue its callback unless the write path has an additional transactional fence.

**Conclusion:** atomic fencing with candle mutation is NOT VERIFIED.

### T5 — Recovery callback is a separate boundary

`FeederRuntime.start()` calls the injected `recovery.recover_all()` before scheduler activation. The inspected `RecoveryCoordinator` invokes its own injected `sync_callback` to repair gaps. `FeederRuntime._configure_retry()` wraps the scheduler's callback, but the inspected code does not wrap or replace the recovery coordinator's callback with the same lease-authorization wrapper.

The lease is acquired before recovery and renewed after recovery, but this alone does not prove that every recovery write is fenced at the mutation transaction. The recovery callback could be the same guarded callable by construction, but that wiring was not found or proven.

**Conclusion:** recovery write fencing is NOT VERIFIED and must be treated as a blocker until the construction path proves the guard or recovery itself enforces the fencing generation transactionally.

### T6 — Shared canonical DB path is not proven

- `LeaseStore` takes its own `db_path`.
- `CandleStore` takes its own `db_path`.
- `SQLiteCandleStore` takes a path from `MARKET_DATA_DB`.
- `FeederRuntimeStatusStore` takes its own `db_path` and reads both runtime status and `feeder_leases` from that file.
- The inspected source set does not show a production composition root constructing these components with one shared canonical path provider.
- The T0 manual validation workflow leaves `MARKET_DATA_DB` and `T0_FEEDER_LEASE_DB` empty and asserts that they remain empty; it is an isolated validation safety gate, not production wiring evidence.

**Conclusion:** one physical SQLite file for Market Data, LeaseStore, runtime status and Paper Ledger remains NOT VERIFIED at application composition level.

## Recommendations — PROPOSED, NOT ACCEPTED

1. Make the fencing generation a required argument/context for canonical writes. Validate it inside the same SQLite `BEGIN IMMEDIATE` transaction that performs candle inserts/upserts, before any mutation; reject stale generation before commit.
2. Route scheduler and recovery writes through one guarded ingestion service, rather than separately injected unverified callbacks.
3. Ensure lease takeover and candle write serialize against the same lease row/database transaction. Define the lock ordering and retry behavior to avoid deadlocks.
4. Introduce one canonical Android DB-path authority and pass the same resolved physical DB identity to CandleStore, LeaseStore, FeederRuntimeStatusStore and Paper Ledger. Fail closed on mismatch.
5. Add fixture-only adversarial tests for takeover between preflight and write, recovery callback bypass, and mismatch among component DB paths. These tests must use isolated temporary databases and must not open the canonical DB.

No implementation or test changes are made by this report.
