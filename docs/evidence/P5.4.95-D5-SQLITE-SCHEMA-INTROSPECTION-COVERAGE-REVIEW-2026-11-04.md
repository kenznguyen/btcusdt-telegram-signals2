## 4. Evidence from official SQLite documentation

1. `PRAGMA table_info` omits generated and hidden columns; SQLite directs applications to `table_xinfo` for the more complete column list. The same documentation says `table_list` identifies ordinary tables, views, shadow tables and virtual tables, but `table_list` was added in SQLite 3.37.0 and its output may gain columns in future releases.
   - https://www.sqlite.org/pragma.html#pragmatable_info
   - https://www.sqlite.org/pragma.html#pragma_table_list

2. `PRAGMA index_info` reports key columns only. `index_xinfo` includes auxiliary columns and additional per-column metadata; `index_list` reports uniqueness, origin and partial-index status.
   - https://www.sqlite.org/pragma.html#pragma_index_info
   - https://www.sqlite.org/pragma.html#pragma_index_xinfo
   - https://www.sqlite.org/pragma.html#pragma_index_list

3. `PRAGMA module_list` returns virtual-table modules registered with the current database connection. It is not a cryptographic or build-provenance identity for the implementation.
   - https://www.sqlite.org/pragma.html#pragma_module_list

4. SQLite documents that virtual-table module names must be registered on the connection before a CREATE VIRTUAL TABLE statement can be used; the module receives its arguments from the declaration. The module implementation interprets those arguments.
   - https://www.sqlite.org/lang_createvtab.html
   - https://www.sqlite.org/vtab.html

5. SQLite explicitly warns that unknown PRAGMAs are silently ignored. Therefore an empty result from a potentially unsupported PRAGMA must not be interpreted as proof that no modules/objects exist. Feature availability must be established before interpreting its result.
   - https://www.sqlite.org/pragma.html

## 5. Recommended D5 source-contract delta — proposal only

The following is a design recommendation for a later owner-reviewed source change. It is not implemented or authorized by this report.

### 5.1 Catalog remains the root of authority

- Keep the deterministic `sqlite_schema` catalog query and exact SQL text as D5 input.
- Keep the fixed `sqlite_` internal-object exclusion rule versioned and explicit.
- Do not normalize SQL whitespace, case, quoting or tokens under the approved conservative policy.
- Preserve object types beyond table/index/view/trigger as an explicit unsupported-object failure, not silent omission.

### 5.2 Table and view structure

- Use `table_xinfo` for every catalog table and view so generated/hidden columns are represented.
- Keep `index_list` and `foreign_key_list` scoped to actual tables; do not issue them indiscriminately for views.
- Capture all documented `table_xinfo` fields, including the hidden/generated classification.
- If a required PRAGMA is unsupported or its result shape is unexpected, return NOT VERIFIED / READ_UNCERTAIN. Do not silently fall back to `table_info`.

### 5.3 Index structure

- Retain `index_list` for unique/origin/partial attributes.
- Use `index_xinfo` for full key and auxiliary-column metadata, including expression/rowid markers, sort direction, collation and key-vs-auxiliary flag.
- Keep exact index SQL from `sqlite_schema`; introspection supplements rather than replaces it.

### 5.4 Virtual tables and modules

- Explicitly identify every persisted virtual-table declaration from its catalog SQL using a reviewed parser; do not use a permissive regex or guess module names from arbitrary SQL text.
- Require each declared module to be present in the connection's verified module inventory.
- Establish support for `module_list` before using its result. SQLite's silent-ignore behavior for unknown PRAGMAs means an empty cursor alone is not evidence of an empty module inventory.
- A registered module name is only a name. Require a separately maintained allowlist/provenance record binding module name to implementation version/build/source identity and supported configuration. If that provenance cannot be established, fail closed.
- Unknown declaration syntax, missing module, unsupported module, unverified implementation provenance or unclassified shadow objects => NOT VERIFIED.
- Include exact virtual-table declaration SQL and the versioned module identity/provenance record in the D5 canonical envelope. Do not claim module behavior is fully represented by SQL text alone.

### 5.5 Runtime feature negotiation

- Do not infer SQLite engine feature support from Android API level alone.
- Record `sqlite_version()` and `sqlite_source_id()` as already specified.
- Pin the supported SQLite runtime/feature matrix before choosing required PRAGMAs.
- Use an explicit capability check with a known result schema; unknown/unsupported feature means NOT VERIFIED, not an empty/default value.
- `table_list` is a potential classification input, but its documented minimum version and evolving output shape mean it cannot be made a cross-version assumption until runtime policy is frozen.
