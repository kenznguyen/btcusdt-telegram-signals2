## 3. Test safety contract

### 3.1 Mandatory isolation

Every GitHub Actions job that executes a backup/restore test must satisfy all conditions:

- Checkout a single exact commit SHA; record `git rev-parse HEAD` and fail on mismatch.
- Use only a per-job temporary directory (for example `$RUNNER_TEMP/p5-4-8/<run-id>/<attempt>`) and database names generated inside that directory.
- Set `MARKET_DATA_DB`, `T0_FEEDER_LEASE_DB`, `PAPER_DB`, `PAPER_TRADING_DB`, `BINANCE_API_KEY`, `BINANCE_API_SECRET`, `OKX_API_KEY`, and `OKX_API_SECRET` to empty strings.
- Set `AI_EXECUTION_ENABLED=false`; assert it before test execution.
- Do not provide production credentials, canonical paths, connected app secrets or reusable runner volumes.
- Do not use a path supplied by an untrusted workflow input. Reject absolute paths outside the job temp root, symlinks escaping the root, and pre-existing DB files.
- Assert that each fixture DB did not exist before the fixture setup and that it exists only under the temp root after setup.
- At job end, emit a file inventory and ensure no DB/WAL/SHM file was created outside the temp root. If path audit cannot be performed, the isolation gate is NOT VERIFIED and the suite cannot PASS.
- Use no network access in the test process. No exchange client, market-data downloader, Feeder service, scheduler or API server is started.
- Never run a test against `MARKET_DATA_DB` inherited from a runner environment; fail if any DB variable is non-empty.

The workflow must use least privilege (`contents: read`), no deployment permissions, no environment secrets, and no workflow_dispatch parameter that accepts a database path. Concurrency must not share a mutable fixture directory across attempts.

### 3.2 Read-only verification

Restore verification must open the candidate with SQLite read-only URI semantics (for example `mode=ro`) and must not call code paths that initialize schema or repair missing state. In particular, the verifier must not instantiate `PaperLedger`, invoke `initialize_schema()`, `ensure()`, migrations, or default-state constructors.

The verifier must fail on a missing required table, missing singleton row, unexpected schema version, malformed manifest, missing source fingerprint, missing required domain cursor, failed integrity check or invalid invariant. It must not synthesize FLAT, zero equity, unpaused, un-killed, or default strategy state.

### 3.3 No side effects / no execution

Tests may create paper intents/orders only inside fixture DBs to establish known test states. They must never contact an exchange or place real orders. Any code path with `ai_execution_enabled=true`, LIVE mode, non-empty credentials or a canonical DB path is an immediate test failure.

## 4. Deterministic fixture contract

### 4.1 Fixture topology

Use two fixture profiles so the test contract exercises both supported storage layouts without pretending they are one atomic database:

| Profile | Fixture files | Purpose |
|---|---|---|
| `single_sqlite` | `canonical-shadow.sqlite3` (name is logical only; file exists only in temp root) | Candles, lease, Paper Ledger, Risk State and Paper State in one SQLite file |
| `split_store` | `market-data-shadow.sqlite3` + `paper-state-shadow.sqlite3` | Candles in one SQLite file; Paper Ledger/Risk/Paper State in another, coordinated by one test snapshot epoch |

The word "canonical" must never be used in an actual fixture path. The profile name above is conceptual; actual files must be named `fixture-<profile>-<run-id>.sqlite3`.

### 4.2 Fixture seed data

Use deterministic values; no wall-clock or external market data:

- Market identity: `BTCUSDT`, exchange `binance`, market type `USDT_PERPETUAL`.
- Timeframe: `15m`; aligned candle open times at 15-minute intervals.
- Candle decimals stored as strings; include at least three closed candles, one deliberate internal gap, and `available_at_ms` after close.
- Paper Ledger: one filled intent/order, one canceled order, one audit sequence, one consumed book snapshot ID; all IDs fixed and unique per fixture namespace.
- Paper State: one non-zero signed position with known average entry, realized PnL, fees, owner and DCA-used flag.
- Risk State: persistent pause state and Kill Switch state seeded independently in separate fixture variants; include reason and timestamp.
- Equity: at least two ordered snapshots spanning a UTC day boundary; include a known high-water mark, drawdown and daily baseline.
- Lease: owner and generation seeded with known generation (g); record (g) in fixture metadata.
- Strategy/config: fixed strategy/model/dataset versions and sanitized risk-config fingerprint. No API keys or secrets.

The fixture builder must expose a deterministic expected-state JSON generated from the seed specification, not by querying the backup under test.

### 4.3 Minimum schema inventory

The verifier must check the expected tables for the selected schema version. At minimum, the logical inventory includes:

| Domain | Required logical tables / state |
|---|---|
| Candles | `candles` |
| Paper Ledger | `paper_orders`, `paper_books`, `paper_audit` |
| Risk State | `paper_risk_control`, `paper_equity_history`, `paper_daily_baselines`, `paper_account_config` |
| Paper State | `paper_state`, `paper_strategy_state` |
| Operational | `feeder_leases`; `paper_control_budget` where present in the declared schema |

The exact table/column contract must be pinned to the implementation schema version when code is later implemented. Do not weaken a required table to optional because one fixture happens not to use it.

## 7. Evidence and artifact contract

### 7.1 Required artifacts per run

A successful or failed test run must publish a single evidence bundle containing:

1. `source-sha.txt` — exact `git rev-parse HEAD`.
2. `run-metadata.json` — repository, branch, workflow name, workflow run ID/URL, attempt, runner OS/image, Python and SQLite versions, start/end timestamps in UTC.
3. `isolation-audit.json` — sanitized environment assertions, temp root, path inventory, network-disabled assertion, no canonical path and no secrets.
4. `fixture-spec.json` — fixture profile, seed version, schema version, snapshot ID, expected domain cursors and expected-state digest.
5. `backup-manifest.json` — see manifest contract below.
6. `test-results.xml` or equivalent machine-readable report — test IDs, outcomes, duration and failure details.
7. `integrity-check.txt` — integrity and foreign-key check outputs.
8. `restore-validation.json` — per-domain comparisons, schema/invariant results, fencing and Kill Switch results.
9. `sha256sums.txt` — SHA-256 for every published artifact, including the backup database and manifest.
10. `execution-boundary.txt` — explicit confirmation: fixture-only, no canonical DB, no exchange, no Feeder, no market-data sync, `ai_execution_enabled=false`.

Failed runs must retain diagnostic logs and failure artifacts where safe. Do not upload credentials, raw environment dumps, personal device identifiers, database paths containing personal usernames, or production data.

### 7.2 Backup manifest minimum fields

The versioned JSON manifest must contain:

- `manifest_version`
- `snapshot_id` and `restore_epoch`
- `repository`, `branch`, `source_sha`
- `workflow_run_id`, `workflow_run_url`, `run_attempt` (CI context only)
- `created_at_utc`, `snapshot_barrier_started_at_utc`, `snapshot_barrier_released_at_utc`
- `topology` (`single_sqlite` or `split_store`)
- `databases[]`: logical role, artifact filename, byte size, SHA-256, SQLite version, journal mode, schema version/fingerprint, table inventory and row counts
- `domain_cursors`: candle cursor/dataset version, max order/intent cursor, max audit cursor, equity cursor, lease generation
- `barrier`: writers stopped/drained, writer identities, lease owner/generation, active transaction count (must be zero), barrier result
- `risk_config_fingerprint`: sanitized version/fingerprint, never secret values
- `checks`: integrity_check, foreign_key_check, read-only verification and per-domain invariants
- `result`: PASS/FAIL with explicit reason list

The manifest must not contain exchange API credentials, access tokens, passwords, encryption keys or private user data. Artifact checksum and manifest checksum are separate values; avoid self-referential hashing by hashing the manifest file externally in `sha256sums.txt`.

### 7.3 Artifact-to-run provenance

Every run report must bind the same exact source SHA across preflight, test report, fixture metadata, manifest and uploaded artifact metadata. The final report must record:
- GitHub workflow run URL and run ID.
- Exact source SHA.
- Artifact name, artifact ID, download URL when available and locally recomputed SHA-256.
- Test case counts by unique ID (not total invocations).
- PASS/FAIL/SKIPPED counts and skip reasons.
- Whether the artifact payload itself was downloaded and independently re-hashed.
- Any runner/platform limitation.

A green workflow without a retrievable artifact is not a complete evidence PASS. An artifact metadata digest without a downloaded payload is not an independently verified payload checksum.

## 8. Acceptance rules

### 8.1 Per-test status

- **PASS:** assertion succeeded; test ID and output present; fixture isolation proven.
- **FAIL:** assertion failed or unsafe side effect detected.
- **BLOCKED:** required environment, approval, fixture or platform is unavailable.
- **NOT RUN:** no execution occurred.
- **NOT VERIFIED:** evidence is insufficient to support the claim.
- **SKIPPED:** explicit, justified and counted; never silently included in PASS totals.

### 8.2 Suite status

A suite can be PASS only if:
- All mandatory cases for its stage passed.
- No safety/isolation assertion failed or was unverified.
- No required case was silently skipped.
- Exact source SHA and workflow run identity are recorded.
- Evidence artifact is retrievable and payload hash independently recomputed.

Any failed mandatory case makes the stage **BLOCKED/FAIL**. Platform-specific cases not run remain NOT RUN and cannot be inferred from another platform.

### 8.3 Recovery approval is separate

Even if every fixture test passes:
- It proves behavior only for the tested source SHA, schema version, runner and fixture topology.
- It does not prove a production backup exists or that a canonical restore is safe.
- It does not certify PostgreSQL/TimescaleDB cross-store atomicity unless that topology receives its own tests.
- It does not authorize canonical path selection, runtime activation, Feeder restart, Kill Switch reset, exchange connection or trading execution.
