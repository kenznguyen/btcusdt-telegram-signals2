## Findings

### 1. Canonical sync function uses the Gateway

`market_data.sync.sync_window()` requires:
- a concrete `T0WriteGateway`;
- a typed `LeaseFence` capability;
- a callable lease-validation clock.

It fetches and validates closed Binance USD-M OHLCV candles, then sends each page to:

```python
gateway.insert_batch(candles, lease_token=lease_token, now_ms=lease_clock)
```

A page is submitted atomically. A later page failure does not roll back an earlier page already committed; the explicit window can be retried and identical candles are idempotent.

### 2. Gateway enforces fencing in the candle-write transaction

`T0WriteGateway.insert_batch()`:
1. Opens the configured SQLite database using `mode=rw`; it will not silently create a missing DB.
2. Executes `BEGIN IMMEDIATE` on one connection.
3. Reads `feeder_leases` and verifies lease name, owner, generation and expiry.
4. Inserts the batch, rejecting conflicting candle history.
5. Re-reads and validates the lease using a fresh clock value.
6. Commits only after the final lease check; failures roll back the transaction.

The lease checks and candle mutations therefore occur in one SQLite write transaction. SQLite's `BEGIN IMMEDIATE` serializes competing writers against that database file. A lease takeover/update using the same database cannot interleave between the gateway's lease validation and commit.

The Gateway's documented final check is the write-admission linearization point. The transaction may commit after the lease wall-clock expiry if it passed that final admission check; another SQLite writer cannot complete a takeover against the same file until this transaction releases its write lock.

**Conclusion:** atomic fencing is implemented for writes that actually pass through `T0WriteGateway.insert_batch()` and use the authoritative lease row in the same physical database. This resolves the generic TOCTOU concern for that path, conditional on shared DB identity and actual routing.

### 3. Store API does not expose a legacy candle write path

`CandleStore` exposes explicit schema initialization; `read_window()` provides read access. `market_data/test_store.py` includes a test asserting that `CandleStore` has neither `insert` nor `insert_fenced` methods. The current inspected sync writer uses Gateway rather than a direct CandleStore insert.

### 4. Fixture tests demonstrate shared-file wiring, but only in fixtures

`market_data/test_sync.py` creates a TemporaryDirectory database and constructs:
- `CandleStore(self.path)`;
- `LeaseStore(self.path)`;
- `T0WriteGateway(self.path)`.

It acquires a lease through LeaseStore, constructs a LeaseFence from that lease, and passes the Gateway and token to `sync_window()`.

`market_data/test_store.py` similarly uses one temporary path for CandleStore, LeaseStore and Gateway.

These fixtures establish that the tested setup intentionally shares one database path. They do not prove production Android composition or that every runtime callback uses the same construction pattern. The inspected tests cover ingestion, duplicate replay, validation and lease ownership contracts, but do not establish a deterministic concurrent takeover interleaving against the Gateway's final admission/commit boundary. Tests were not run in this review.

### 5. CLI path is wired to Gateway, but does not establish FeederRuntime composition

The `market_data.sync.main()` CLI:
- reads `--db` / `MARKET_DATA_DB`;
- constructs the read facade and `T0WriteGateway(args.db)`;
- constructs a typed LeaseFence from command-line lease name, owner and generation;
- calls `sync_window()`.

Thus this explicit CLI path uses the Gateway. The CLI does not construct LeaseStore or acquire the lease itself; the Gateway validates the supplied token against the `feeder_leases` row in the DB. This is fail-closed if that row is absent or mismatched, but the source does not explain who securely supplies the token in a production orchestration.

### 6. Feeder scheduler/recovery composition remains unverified

`FeederRuntime` receives an injected scheduler and optional recovery coordinator. Its scheduler wrapper calls the preflight `LeaseStore.authorize_write()` before invoking the scheduler's injected callback. That preflight is useful as an early stop check, but the actual mutation-level protection comes from Gateway.

The inspected files do not show a production composition root that constructs the scheduler callback as `sync_window(... gateway=... lease_token=...)`, nor prove that the recovery coordinator's independently injected callback routes through the same Gateway. If both callbacks use `sync_window()` with the canonical Gateway, the mutation is transactionally fenced; that wiring is not established by the reviewed source.

### 7. Canonical DB identity remains unproven at production composition level

Gateway, LeaseStore, CandleStore, FeederRuntimeStatusStore and Paper Ledger accept database paths independently. The sync CLI passes the same `args.db` to its read facade and Gateway, while the tests pass one temporary path to the stores. No inspected production composition root establishes a single Android path authority and injects it into every component.

A path mismatch normally causes the Gateway to find no authoritative lease row and reject the write. However, the architecture still needs an explicit canonical DB identity invariant so independent or copied DB files cannot be treated as equivalent by configuration.

## Correction to P5.4.25

P5.4.25 reported atomic candle-write fencing as NOT VERIFIED because it had not yet traced `sync_window()` and Gateway. P5.4.26 now confirms that the Gateway primitive performs the lease checks and candle batch mutation in one SQLite write transaction.

The unresolved question is no longer whether the primitive exists. It is whether all production scheduler and recovery writers are routed through it and share the canonical Android DB identity. The P5.4.25 report remains historical evidence of the earlier partial trace; this report supersedes its provisional atomic-fencing conclusion.

5. Keep production runtime and canonical DB untouched until wiring and DB identity are proven.
