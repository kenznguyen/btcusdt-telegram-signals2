## Findings

### F1 — One-file owner decision is not yet enforced by source wiring

- `CandleStore` receives a `db_path` independently. Its constructor is inert; `initialize_schema()` explicitly creates the candle table and enables WAL.
- `market_data.storage.create_store_from_env()` selects SQLite by default and reads `MARKET_DATA_DB`.
- `PaperLedger` receives its own `db_path` argument.
- The inspected code does not demonstrate a single canonical path provider or a startup invariant proving both components resolve to the same physical file.

**Conclusion:** the owner-approved one-file topology is recorded in ADR-001, but enforcement of that topology in application wiring is NOT VERIFIED.

### F2 — Schema ownership and startup side effects differ

- Market Data schema creation is explicit through `CandleStore.initialize_schema()`.
- `PaperLedger.__init__` creates/ensures multiple tables, may seed singleton state, ensures risk/equity structures, and enables WAL.
- This creates different initialization semantics across domains sharing one file.

**Required design constraint:** schema provisioning/migration must be an explicit controlled operation. Read-only backup/restore verification must not instantiate `PaperLedger` or call schema-initializing helpers. It must inspect an existing file read-only and fail closed on missing or unknown schema.

### F3 — Transaction boundaries are domain-local in inspected code

- Paper Ledger write paths use SQLite transactions, including `BEGIN IMMEDIATE` for submit/state mutation.
- CandleStore schema initialization uses its own connection and commit.
- The inspected CandleStore source does not expose a shared transaction/connection coordinator with Paper Ledger.

**Conclusion:** a shared physical file enables SQLite-level atomic transactions when both domains deliberately participate in the same connection/transaction, but this review does not establish such a cross-domain transaction contract. Separate connections and independent commits are not one atomic unit merely because they target one file.

### F4 — WAL is enabled by both initialization paths, but backup integration is unproven

Both inspected initialization paths request `PRAGMA journal_mode=WAL`. This is not evidence that a production backup publisher correctly coordinates active writers, WAL state, checkpointing or SQLite Online Backup API snapshots.

**Conclusion:** WAL-consistent production backup remains NOT VERIFIED.

### F5 — Lease/fencing ownership is not established by the inspected source set

The three inspected files do not define or wire a Feeder lease coordinator, monotonic fencing generation, or restore-epoch authority. This is a bounded finding about these files, not proof that no such implementation exists elsewhere in the repository.

**Required design constraint:** ordinary runtime lease ownership and post-restore fencing must be specified separately. Any generation that can be rolled back by restoring the same SQLite file cannot, by itself, prevent a stale pre-restore owner from resuming. The production design needs a monotonic authority or recovery latch outside the restored snapshot, plus an explicit writer-start gate.

## Architecture recommendations — PROPOSED, NOT ACCEPTED

1. Introduce one canonical Android DB-path/configuration authority. Both Market Data and Paper Ledger must receive the same resolved path from that authority; fail startup if their resolved physical identities differ. Do not hardcode or infer the exact Android path in this report.
2. Keep domain table ownership explicit even inside one file. Define which module owns each table and which transactions are allowed to span domains.
3. Separate schema provisioning/migration from normal object construction. A read-only verifier must not invoke constructors with schema side effects.
4. Define a shared connection/transaction boundary only where a use case truly requires cross-domain atomicity. Otherwise document domain-local transactions and their consistency guarantees.
5. Define WAL-aware backup publication using SQLite's supported online backup/snapshot mechanism, with writer coordination and post-snapshot integrity checks. Fixture tests do not certify this production behavior.
6. Specify the Feeder lease store, owner identity, generation allocation, heartbeat/expiry semantics, stale-owner rejection and restore re-fencing. Do not assume that the shared database alone is a safe monotonic restore authority.

These recommendations do not select the exact Android path, lease placement, migration framework, backup destination or operational policy.
