### 2.2 Critical topology distinction

The current paper runbook uses `MARKET_DATA_DB` for the paper ledger and, with SQLite selected, for canonical candles and lease state. However, `market_data.storage` also supports PostgreSQL for market reads, while `pipeline.api` still constructs the Paper Ledger from `MARKET_DATA_DB`.

Therefore:
- **Single-file SQLite topology:** one SQLite online backup can capture the physical database snapshot, provided all relevant logical writers and state transitions are coordinated.
- **PostgreSQL candles + SQLite Paper Ledger topology:** these are two databases. A single SQLite backup cannot capture Candles plus Paper Ledger/Risk/Paper State atomically. A coordinated cross-store snapshot protocol and manifest are mandatory.
- PostgreSQL/TimescaleDB canonical writer is not certified by this review. Do not switch the target topology based on this document.

The Android P4 Termux evidence is a separate historical evidence context. Its observed checkout SHA does not prove that the current server paper database and Android P4 shadow database are the same physical store or schema. Do not merge those identities.

## 3. Architecture risks found

### R1 — WAL file-copy hazard

The candle store and Paper Ledger enable SQLite WAL mode. Copying only the main `.sqlite3` file while a database is active can omit committed pages still present in `-wal`, causing lost committed data or corruption. Copying a live `.db`, `-wal` and `-shm` as unrelated files is not an acceptable backup protocol.

**Required design:** use SQLite Online Backup API (Python `sqlite3.Connection.backup()`) to produce a standalone snapshot. Do not depend on copying the live main file. Do not require a manual checkpoint as a substitute for a consistent backup. SQLite documents the backup as a snapshot and documents WAL as persistent state while connections are open:
- https://sqlite.org/backup.html
- https://www.sqlite.org/wal.html
- https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup

### R2 — Cross-domain consistency is not automatic

Candle pages are committed through their own write transactions. Paper intents/fills/risk/audit are committed through Paper Ledger transactions. A valid SQLite page-level snapshot can still represent a logical point between separate domain operations.

**Required design:** add a maintenance snapshot barrier before taking a recovery-grade backup:
1. Stop admission of new paper intents and new canonical candle writes.
2. Stop or drain every writer through its supported lifecycle; verify no write transaction remains active.
3. Confirm all feeder writer processes are stopped or fenced and record the current owner/generation.
4. Record a unique snapshot ID/epoch and per-domain high-water marks (candle key/time range, max audit ID, order/intent cursor, equity history cursor, lease generation).
5. Keep the barrier held while the backup snapshot and manifest are produced.
6. Release only after the snapshot has been verified and atomically published, or leave the system in maintenance/fail-closed state if any step fails.

A backup that cannot prove the barrier and high-water marks is a file copy, not a certified cross-domain recovery point.

### R3 — Restore can roll back the fencing generation

The `feeder_leases` generation is stored in the database. Restoring an older snapshot can roll the generation backward. A stale process holding a generation that is valid in the restored database could be admitted if it remains alive and writes before a new generation is issued.

**Required design:** restore is allowed only after proving all prior writer processes are stopped. Before any writer restarts, rotate/increment the fencing generation beyond the pre-restore high-water mark using a controlled recovery procedure. If the pre-restore high-water mark cannot be proven, do not restart the Feeder; remain BLOCKED until a safe external/monotonic recovery epoch is established. A restored lease row must never be treated as proof that the old owner is still authorized.

### R4 — Restore can roll back the Kill Switch

The kill latch is persisted in `paper_risk_control`. Restoring a backup taken before a later kill event can restore `killed=0`, silently clearing the newer stop condition.

**Required design:** every restore enters maintenance/read-only mode. Before any paper writer can resume, explicitly assert the Kill Switch in the restored target and preserve the restore event in an append-only recovery record outside the rollback-prone snapshot. Clearing it requires a separate, explicit acknowledged recovery decision and readiness checks. A generic resume must not clear it.

### R5 — Initialization helpers can mask incomplete restore

`PaperLedger.__init__` creates tables and can initialize default state on a new database. `risk_control.snapshot()` returns a default unpaused/unkilled result if the risk table is absent. `read_snapshot()` tolerates an absent strategy-state table by returning fallback values. Equity helpers can ensure/create tables.

**Required design:** forensic restore validation must use a dedicated read-only verifier that does not instantiate `PaperLedger`, call `initialize_schema()`, call `ensure()`, or repair missing rows. Missing required tables/rows must fail the restore gate, not be silently initialized to FLAT, unpaused, un-killed, or default strategy state.

### R6 — Idempotency and state watermarks can roll back

Restoring an older snapshot removes later paper intents/orders, audit events, consumed book IDs and equity points. If old intents, snapshots or decision watermarks are replayed after restore, the restored ledger may process events that existed after the backup point.

**Required design:** assign a new restore epoch; invalidate pre-restore decision outputs and book snapshots; require fresh closed-candle and fresh-book observations before paper evaluation; record the recovery point and last accepted intent/audit cursors. Never automatically replay post-backup AI/Core intents.

### R7 — Risk configuration is not wholly in the database

The risk limits and several runtime paths are environment/configuration inputs. A database-only backup cannot reproduce the effective policy.

**Required design:** include a sanitized, versioned configuration fingerprint and the effective non-secret risk limits in the backup manifest. Never archive exchange credentials, bearer tokens or secrets in the backup manifest.

## 4. Recommended backup protocol

This is a proposed protocol, not an implemented command.

1. **Preflight:** resolve the canonical DB path from an approved runtime configuration; reject empty, relative/ambiguous, non-canonical or unexpected paths. Record SQLite version, journal mode, schema inventory, source commit and host/device identity label.
2. **Maintenance barrier:** stop new writes; drain/stop Feeder and paper writers; confirm no active writer; capture lease owner/generation and domain cursors.
3. **Snapshot:** create a new temporary destination file on the target backup volume and use the SQLite Online Backup API. For a multi-database topology, snapshot each database under the same global barrier and record one shared snapshot ID; do not claim cross-database atomicity unless the barrier/cursors prove it.
4. **Verify candidate:** close all handles; run `PRAGMA integrity_check` and require exactly `ok`; run `PRAGMA foreign_key_check` and require zero rows; verify required tables/rows and domain invariants using read-only SQL.
5. **Publish:** compute SHA-256 over the final standalone database bytes; write a manifest containing snapshot ID, source SHA, timestamps, SQLite version, schema inventory/fingerprint, DB path label (not secrets), journal mode, table counts, per-domain high-water marks, integrity results, backup method, hash, and config fingerprint. Publish the completed versioned backup and manifest atomically from a staging location; incomplete artifacts remain unpublished.
6. **Retention:** retain prior known-good backups until a newer backup has passed a restore drill. Retention period, destination and encryption are decisions still required; do not delete older backups based solely on successful file creation.

For a multi-file or cross-backend layout, the manifest must list each database/artifact with its own SHA-256 and prove that all entries belong to the same snapshot epoch.

## 5. Recommended restore protocol

Restore into a **new isolated path**, never overwrite the canonical file during initial verification.

1. Stop and prove stopped every writer, API worker and process that could access the target.
2. Place the system in maintenance/read-only mode. Do not allow Feeder startup or paper intent evaluation.
3. Verify backup and manifest hashes before opening the candidate.
4. Restore/copy to a new path; use read-only verification first. Do not run schema migrations or constructors that create/repair tables.
5. Require SQLite `integrity_check=ok`, no foreign-key violations, exact required schema/table set, required singleton rows, valid decimals/timestamps, uniqueness constraints and expected table counts/high-water marks.
6. Validate domain invariants:
   - Candles: key uniqueness, aligned timestamps, valid OHLCV, closed-candle availability, expected range and explicit gaps (no silent forward fill).
   - Paper Ledger: intent/order ID uniqueness, payload hash consistency, legal status transitions, fill/remaining arithmetic, fee totals, audit sequence monotonicity and no duplicate intent.
   - Risk State: kill/pause row present; preserve reason/time; equity points, high-water marks, drawdown and UTC daily baseline internally consistent; initial capital unchanged.
   - Paper State: singleton row present; position sign/average-entry relation valid; realized PnL/fees finite; strategy owner and DCA-used state preserved.
   - Cross-domain: each equity snapshot references its candle dataset version; audit cursor and ledger order cursors do not exceed the recovered audit/order history; no stale intent or book snapshot is accepted after restore.
7. Record recovery epoch and recovery audit outside the snapshot. Keep kill active and all writers blocked until the recovery gate is explicitly approved.
8. Only after validation and explicit approval may the operator select the recovered path. Re-fence the lease above the old generation before any Feeder process can start. Paper-only constraints remain in force.

If any required table/row, manifest, hash, source/config fingerprint or domain invariant is missing or mismatched, verdict is **BLOCKED**. Never repair the backup in place and then claim it was restored faithfully.
