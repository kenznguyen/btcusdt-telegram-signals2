# P5.4.70 — D3 Snapshot Barrier & Cross-Domain Consistency Proposal

Date: 2026-11-04 (Asia/Ho_Chi_Minh)

## Status and scope

**D3 PROPOSED / NOT DECIDED.** This document proposes a snapshot contract for the owner-approved Android canonical topology: one Android-hosted SQLite database file shared by Market Data and Paper Ledger. It does not record owner approval and does not authorize implementation or runtime activation.

Baseline decisions:
- D1 is partially accepted for Android-hosted SQLite and one shared physical file for Market Data + Paper Ledger.
- D2.1–D2.5 are owner-approved and recorded in ADR-001.
- D3 is unresolved. D4–D7 remain unresolved.
- The regular Android variant is the intended canonical host and sole writer after separate activation. The .paper variant is an IPC client, not a database writer.

This is a design proposal only. No code, schema, migration, Android device access, canonical DB access, Feeder startup, exchange connection, market-data synchronization, backup/restore execution or writer activation is performed.

## Problem statement

D2 defines domain-specific high-water evidence:
- per-partition contiguous closed-candle coverage and separate gap/backfill state;
- a dedicated monotonic Paper Ledger commit sequence with idempotency and atomic state/audit advancement;
- Risk State versions bound to the Ledger sequence for same-transaction changes, with a separate version for independently committed risk-only transitions;
- a separate Feeder Lease generation checked at every canonical write boundary;
- a vector of domain cursors which is descriptive, not proof of atomic observation.

D3 must define how those values and the underlying Market Data, Paper Ledger, Risk State and audit rows represent one recoverable point in time. The shared SQLite file removes the need to coordinate independent database files, but it does not by itself prove that a backup was captured while writers were quiescent or that the backup includes committed WAL content.

## Recommended D3 model

### A. One host-owned snapshot coordinator and write barrier

The regular Android Canonical Host owns a single snapshot coordinator and a single canonical write gate for every mutation path that can change any state represented by the manifest.

Recommended sequence:

1. Authenticate the coordinator request and verify the current host/lease fencing generation.
2. Allocate a globally unique, non-reused barrier ID and a monotonically increasing barrier generation from the host recovery-control authority. The barrier ID is an identifier, not proof of consistency.
3. Close admission for new canonical mutations across Market Data, Paper Ledger, Risk State, audit and any other included domain.
4. Allow already admitted transactions to finish or roll back. Establish an explicit drain result; timeout or unknown transaction outcome aborts the barrier.
5. Revalidate the active lease generation and prove that no stale writer can pass the host-side write gate.
6. Commit a barrier marker/control record, then hold the write gate closed. The marker must not masquerade as a business Paper Ledger event or advance the D2 Ledger sequence unless it represents a genuine ledger mutation.
7. Open one SQLite read transaction against the canonical connection after the barrier marker is committed. Read the complete D2 evidence vector and all manifest metadata through that same read snapshot.
8. Capture the database using SQLite's supported Online Backup API (sqlite3_backup or an equivalent platform-supported wrapper) into a staging destination. Do not copy only the main database file while WAL is active.
9. Verify the staged image independently: SQLite integrity check, schema/version metadata as defined by the future D4 decision, logical/domain invariants, D2 cursor-vector consistency and physical digest. Do not run constructors or repair helpers during verification.
10. Publish the immutable backup and manifest atomically only after every verification step passes. A manifest must never point to a partial or unverified image.
11. Record completion/abort evidence, release the read snapshot and write barrier, then reopen mutation admission only if the same current host authority still owns the writer gate. A fencing mismatch or uncertain release fails closed.

The exact SQLite API, connection lifetime and Android wrapper remain implementation choices and require source/API review before coding.

### B. Consistency guarantee

Preferred guarantee: **single-database point-in-time consistency**.

Because all included domains reside in one physical SQLite database, a single SQLite read snapshot can observe Market Data, Paper Ledger, Risk State and audit rows at one database snapshot boundary. The coordinator's writer barrier prevents new canonical mutations during capture, while the Online Backup API produces a consistent destination image.

The manifest must record:
- barrier ID and barrier generation;
- canonical host identity and observed lease/fencing generation;
- database identity (opaque stable ID; never raw path);
- snapshot start/completion timestamps as diagnostics only;
- D2 domain-cursor vector read from the same SQLite snapshot;
- schema authority/version fields reserved for D4 (not invented by D3);
- backup method and implementation version;
- physical digest and verification results;
- canonicalization version/digests only when D5 defines them;
- explicit completion state and provenance.

Do not use timestamps as ordering authority. Do not claim cross-system atomicity for external configuration, exchange state, Android process state, external lease authority or a Kill Switch/recovery latch unless those are separately captured by an approved protocol.

### C. WAL handling

- Use SQLite's Online Backup API or a documented equivalent that reads a consistent database view including committed transactions represented in WAL.
- Never treat a raw copy of the main .db file as a complete backup while WAL may contain committed state.
- Do not manually copy .db, -wal and -shm as an ad hoc three-file protocol.
- A checkpoint may be considered an operational optimization only after SQLite-version and connection behavior are verified; it is not a substitute for a consistent backup API.
- Do not delete, truncate or reset WAL/SHM as part of snapshot verification.
- Record SQLite library/runtime version and backup method in evidence once D4/implementation choices are approved.

### D. Failure and partial completion

| Failure point | Required result |
|---|---|
| Barrier admission fails | No snapshot; no manifest publication; writers remain governed by normal host fencing |
| In-flight transaction does not drain or outcome is unknown | Abort; do not claim a barrier was established |
| Lease/fencing changes before or during capture | Abort and fail closed; stale coordinator cannot publish |
| Read transaction or backup API fails | Mark attempt ABORTED; partial staging output is quarantined or removed; no manifest references it |
| Integrity or domain verification fails | Do not publish; preserve diagnostic evidence without promoting the image |
| Process dies while barrier is held | On restart, treat barrier as interrupted; require recovery reconciliation and a fresh fencing generation before writers resume |
| Manifest publication fails after image verification | Keep image unpublished in staging; retry publication idempotently or quarantine; never create a dangling accepted manifest |
| Barrier release is uncertain | Keep readiness false and mutations blocked until the host proves safe ownership and releases the barrier |

A partial artifact is never a recoverable backup merely because it has a file and a digest. A failed attempt must not advance D2 business cursors or Paper Ledger sequence.

### E. Barrier ownership and stale-writer fencing

- Only the regular Canonical Host can acquire/release the barrier.
- Every canonical write path must consult the current host-side lease generation and barrier state at the transaction boundary.
- The .paper client receives only typed IPC outcomes; it never receives a database handle, path, file descriptor, lease token or barrier-release capability.
- The barrier coordinator must not rely on a client-side mutex, process-local flag alone, local expiry timestamp or an old lease token.
- If host ownership, lease generation or barrier state is uncertain, fail closed.
- External restore epoch and post-restore lease re-fencing remain D6 decisions; D3 does not define or approve them.

## Alternatives considered

### 1. SQLite Online Backup API under a host write barrier — preferred

Advantages:
- One consistent image for all included domains in the shared SQLite file.
- Avoids an ad hoc copy protocol for main DB and WAL files.
- The barrier gives an explicit operational boundary and prevents mutation races during capture.

Costs/limitations:
- Requires every canonical mutation path to participate in one host-owned gate.
- Long backup duration may pause writes; duration and availability objectives are not yet defined.
- Does not capture external control-plane state or decide restore semantics.

### 2. Raw filesystem copy of the main database file — rejected

A main-file-only copy can omit committed WAL state and is not accepted as a production snapshot protocol while WAL may be active.

### 3. Copy main DB, WAL and SHM independently — rejected

Independent file copies can represent different instants and do not form a proven atomic SQLite snapshot. SHM is transient coordination state, not a substitute for the backup contract.

### 4. Per-domain snapshots with a shared barrier string — rejected for this topology

The owner selected one shared physical SQLite file. Splitting the snapshot into separately captured domain images adds coordination complexity and does not improve consistency. A matching barrier ID alone is not proof of a common snapshot.

### 5. Keep writes active during backup without a host barrier — not preferred

SQLite's backup API can provide a consistent database image, but without a host-level barrier the D2 vector, lease evidence, external audit and operational publication protocol may be sampled at different times or require retry/restart semantics. This weaker design is not proposed as the canonical recovery contract.

## Fixture-only acceptance plan (specified, not implemented)

All tests must use isolated temporary fixture databases, deterministic fake clocks/IDs and fake writer/lease authorities. They must not resolve or open the Android canonical path, invoke production constructors, start Feeder, contact an exchange or mutate production state.

1. Barrier closes admission to every registered canonical mutation domain.
2. An already admitted transaction drains before the barrier is declared established.
3. A transaction with unknown outcome prevents barrier completion.
4. A new Market Data mutation is rejected while the barrier is held.
5. A Paper Ledger mutation is rejected while the barrier is held; no sequence or audit row advances.
6. Same-snapshot reads return a mutually coherent D2 vector for Market Data, Ledger and Risk State.
7. A known Market Data gap remains represented in the vector and cannot be hidden by a later maximum timestamp.
8. Risk State's referenced Ledger sequence exists in the same snapshot; mismatched versions are rejected.
9. A stale lease generation cannot acquire, hold, publish or release a barrier.
10. A lease-generation change during capture aborts publication.
11. WAL-backed committed fixture rows are present in the Online Backup API output; main-file-only copy is explicitly rejected by the test contract.
12. Injected backup failure leaves no accepted manifest and no false completion marker.
13. Integrity/domain verification failure prevents publication.
14. Manifest publication is idempotent and cannot reference a partial staging artifact.
15. Simulated process death while the barrier is held leaves readiness blocked until recovery reconciliation and fresh fencing.
16. Barrier release is permitted only to the current host authority; uncertain release keeps writes blocked.
17. Barrier metadata does not advance the business Paper Ledger sequence unless it is explicitly modeled as a real business ledger transition.
18. A successful fixture snapshot has one barrier ID, one database snapshot identity and a D2 vector captured from one read transaction.
19. The verifier rejects a vector assembled from multiple independent read transactions.
20. The fixture demonstrates that external Kill Switch/recovery latch state is outside this database snapshot and must not be claimed as captured by D3.

## Owner decisions requested

D3 remains **PROPOSED / NOT DECIDED** until the owner responds. Recommended choices:

1. Approve one Canonical Host-owned write barrier covering all canonical mutation domains, with drain-before-snapshot and fail-closed timeout behavior?
2. Approve a single SQLite read snapshot plus SQLite Online Backup API as the preferred shared-file capture method, rather than raw DB/WAL/SHM copying?
3. Approve capturing the complete D2 vector and manifest metadata from the same SQLite read transaction, with timestamps diagnostic only?
4. Approve staging → integrity/domain verification → atomic publication, with no manifest for partial/failed snapshots?
5. Approve stale fencing, uncertain transaction outcome, process death or uncertain barrier release as fail-closed conditions that block writers until recovery reconciliation?
