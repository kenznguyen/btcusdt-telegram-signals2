## 1. Objective and constraints

Define where verified snapshots may be stored, how they are protected and retained, what recovery objectives apply, and who may authorize backup publication and restore.

D7 completes the policy layer around D3 snapshot consistency, D4 schema migration authority, D5 digest identity and D6 recovery fencing. D7 must not weaken those contracts.

Constraints:

- Paper-only; `AI_EXECUTION_ENABLED=false`; no live orders.
- The user currently does not authorize PC usage. This proposal does not select or require a PC/VPS destination.
- No exact Android path, external storage provider, key custody mechanism, retention duration, RPO/RTO target or restore approver has yet been selected.
- A destination is not approved merely because it is reachable or convenient.

## 2. Proposed backup publication and destination policy

### D7.1 — Destination classes and trust boundary

Separate:
1. **Canonical active database** — Android-owned SQLite file; never treated as a backup destination.
2. **Temporary staging area** — restricted, non-canonical, inaccessible to ordinary app writers; partial outputs are never published as backups.
3. **Published backup repository** — independent storage boundary from the canonical DB and its normal writer process; immutable/versioned objects with stable Backup ID.
4. **Recovery audit authority** — durable records of backup/restore operations and D6 epoch/latch events, not erasable by restoring an older database.

Proposed policy:
- No backup may exist only beside the active canonical database or on the same failure domain.
- Destination must support access control, integrity verification, durable publication and retention enforcement.
- If the selected destination cannot provide these properties, status remains BLOCKED; do not silently downgrade.
- Destination provider, region, account ownership, data residency, offline/export path and Android compatibility remain owner decisions.

### D7.2 — Encryption and key custody

- Encrypt backup payloads before they leave the trusted capture boundary; use an authenticated encryption construction from a maintained platform/library implementation, not custom cryptography.
- Use a unique data-encryption key (DEK) per backup object or approved key scope; bind authenticated metadata to Backup ID, manifest identity, schema/migration evidence and format version.
- Protect DEKs with a separately managed key-encryption key (KEK) or platform-backed key-wrapping mechanism.
- Separate encryption, decryption and administrative authorization roles where supported.
- Keys must not be stored in the backup object, repository source, ordinary app preferences, logs, GitHub, workflow artifacts or the same unprotected destination.
- Define key generation, non-exportability where supported, rotation, revocation, recovery escrow, loss recovery and destruction before enabling encrypted backup.
- Loss or revocation of a required key makes the corresponding backup unrecoverable; report this explicitly and never claim successful recoverability based only on ciphertext integrity.
- Key access must be auditable and gated by the restore authorization process.

No algorithm, provider, Android keystore mode, escrow owner or key rotation period is selected by this proposal; these require a compatibility/security review and explicit approval.

### D7.3 — Integrity, authenticity and publication

- Preserve D3 immutable Backup ID, Barrier ID, source DB identity, D2 evidence vector, physical SHA-256, verification result and completion status.
- Preserve D4 migration authority/ordered chain evidence and D5 canonicalization/algorithm identity and schema digest.
- Authenticate the manifest independently of the payload encryption where required, so metadata substitution or rollback is detectable.
- Publication sequence: capture → staging → integrity/domain verification → encryption/authenticated manifest → durable upload/write → read-back verification → atomic/immutable publication.
- Never mark a backup AVAILABLE until full read-back verification and manifest authentication succeed.
- Keep the last known-good backup until the new backup is fully verified and published.
- Partial upload, timeout or uncertain publication remains STAGING/UNKNOWN and must be reconciled by Backup ID; do not overwrite or delete the last known-good copy.
- Periodically verify stored object readability, authentication and physical digest without opening the canonical DB.

### D7.4 — Retention and deletion

- Retention policy must preserve multiple independently verified restore points across distinct failure windows; a single latest backup is insufficient.
- Define minimum daily/weekly/monthly or event-based retention only after RPO, storage capacity and user cost are known.
- Retention must include a protected last-known-good set and a deletion safety window.
- Deletion requires explicit policy authorization, confirmation that minimum recoverable coverage remains, and append-only audit evidence.
- Legal hold, corruption quarantine and key-revocation cases must prevent automatic deletion where applicable.
- Never delete the only verified backup or a backup needed to meet the approved recovery objective.
- Do not infer retention periods or storage budget without owner approval.

## 3. Proposed recovery objectives

### D7.5 — RPO and RTO

RPO (maximum acceptable data loss) and RTO (maximum acceptable time to restore service) are distinct, measurable policy targets.

Proposed rules:
- RPO is measured against committed Paper Ledger sequence and contiguous closed-candle Market Data cursors, not backup timestamps alone.
- Any target must state whether it applies to Market Data, Paper Ledger, risk/audit state and external recovery authorities; D3/D6 external authorities are not included in the SQLite snapshot.
- RTO begins at declared recovery incident start and ends only when the restored target passes D3/D4/D5 verification, D6 re-fencing and readiness acknowledgement. It does not end at file copy completion.
- Measure capture pause, capture duration, transfer, staging verification, publication, restore verification, re-fencing and human approval separately.
- If the measured system cannot meet the approved RPO/RTO, report the gap; never claim compliance from an untested schedule.
- Until numerical targets are approved, RPO/RTO status is **NOT SET / NOT VERIFIED**.

No numerical RPO/RTO values are proposed as defaults because acceptable loss and recovery time are owner risk decisions and storage/runtime capability has not been validated.

## 4. Proposed authorization and separation of duties

### D7.6 — Backup and restore authorization

- Backup capture scheduling may be automated only after destination, key custody, retention and verification are approved and implemented.
- Backup publication must require a verified D3–D5 result and authenticated destination acknowledgement.
- Restore is a separate high-risk operation; it must not be initiated by a health check, app startup, scheduled backup task or automatic rollback.
- Require an authenticated human approver with an explicit restore role and reason, referencing incident ID, Backup ID, manifest identity, expected data-loss window and RPO/RTO impact.
- Where practical, separate requester and approver; record both identities. Define emergency single-person exception explicitly rather than silently permitting it.
- Restore approval authorizes only the specific recovery operation. D6 readiness acknowledgement, Recovery Latch release, Kill Switch clearing and writer admission remain separate gates.
- No authorization in this proposal grants permission to enable live execution or place exchange orders.
- GitHub/Codemagic credentials, CI tokens or repository write access are not restore credentials and must never substitute for recovery authorization.

## 5. Operational monitoring and evidence

Required backup inventory fields:
- Backup ID, Barrier ID, source DB identity and creation time;
- D2 cursor vector and Ledger/Risk sequence evidence;
- D3 barrier/capture verification and immutable completion state;
- D4 migration authority and ordered chain digest;
- D5 canonicalization ID/version, digest algorithm, schema digest and physical digest;
- destination identity, object version, byte length and read-back result;
- encryption format/key reference (never key material), key status and manifest authentication result;
- retention class, expiry eligibility and protected/last-known-good status;
- last integrity/readability verification time and outcome;
- associated restore/recovery operation IDs and audit references.

Monitoring must distinguish AVAILABLE, STAGING, UNKNOWN, CORRUPT, KEY_UNAVAILABLE, EXPIRED_PENDING_APPROVAL and DELETED. Unknown/corrupt/key-unavailable backups are not counted as recoverable restore points.

## 6. Fixture-only acceptance plan (specified, not implemented)

1. Backup cannot target the active canonical DB path.
2. Destination must be outside the canonical DB failure domain.
3. Staging output is not listed as AVAILABLE.
4. Failed verification does not replace last known-good backup.
5. Partial/uncertain upload is reconciled by Backup ID.
6. Read-back physical SHA-256 mismatch marks backup CORRUPT.
7. Manifest tampering/authentication failure is rejected.
8. Wrong Backup ID or manifest binding is rejected.
9. Ciphertext tampering fails authenticated decryption.
10. Missing/revoked key marks KEY_UNAVAILABLE and backup not recoverable.
11. Key material never appears in logs, manifests, artifacts or repository content.
12. Rotation preserves access to backups under the approved recovery policy.
13. Retention cannot delete protected last-known-good backup.
14. Deletion cannot reduce verified restore points below approved minimum.
15. Retention expiry requires auditable policy authorization.
16. RPO calculation uses Ledger sequence and Market Data cursor vector, not timestamp only.
17. RTO measurement includes D6 readiness acknowledgement, not only file restore.
18. Unmet RPO/RTO target is reported as failure, not rounded or silently waived.
19. Restore request without authorized principal/reason/Backup ID is rejected.
20. Requester/approver separation is enforced when policy requires it.
21. Restore approval does not clear Kill Switch or enable writer admission.
22. CI credentials cannot satisfy restore authorization.
23. Inventory excludes STAGING, UNKNOWN, CORRUPT and KEY_UNAVAILABLE objects from recoverable count.
24. Audit records remain available if the restored DB is older than the recovery event.
25. No fixture path can open or mutate the canonical database or contact an exchange.

All tests use disposable fixtures, fake destinations and fake key/authorization authorities only. No Android device, PC, production key, canonical DB, live storage account, Feeder or exchange is involved.
