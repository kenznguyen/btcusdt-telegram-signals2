# P5.4.80 — Digest Domains and Authenticated Backup Manifest Proposal

Date: 2026-11-04
Status: **OWNER-APPROVED — ARCHITECTURE/CONTRACT ONLY (2026-11-04)**
Branch: `feature/p5-4-1-post-merge-validation-20261103`
Related approvals: D3.1–D3.6, D4.1–D4.7, D5.1–D5.4, D6.1–D6.7, D7.1–D7.6.
Scope: clarify digest byte domains and backup-object binding only. No code, schema, key, storage or runtime change.

## 1. Problem

D5 physical SHA-256 identifies exact SQLite snapshot bytes. D7 requires encryption before data leaves the trusted capture boundary, immutable destination publication and authenticated read-back verification. These are different byte sequences and cannot share one ambiguous `physical_sha256` field.

The contract must distinguish:
- the verified SQLite backup image before encryption;
- the exact encrypted payload object stored by the destination;
- the authenticated manifest that binds both to one immutable Backup ID and object version.

This proposal does not change the approved D5 digest algorithm (SHA-256), D7 encryption requirement or D3 snapshot consistency contract.

## 2. Proposed digest domains

### D1 — Snapshot image digest

Field: `snapshot_image_sha256`

Definition: SHA-256 over the exact byte sequence of the completed SQLite Online Backup API output, after D3/D4/domain verification and before encryption.

Rules:
1. Hash the exact staged SQLite image bytes; no reserialization, normalization, recompression or line-ending conversion.
2. The image is immutable after hashing. Any mutation requires a new capture/Backup ID and a new digest.
3. This digest identifies the snapshot image, not the encrypted object and not the complete manifest.
4. Record byte length and the snapshot format/runtime identity alongside the digest.
5. The source image remains within the trusted capture boundary and is not published as an unencrypted backup object.

### D2 — Encrypted destination-object digest

Field: `encrypted_object_sha256`

Definition: SHA-256 over the exact encrypted payload bytes, as stored and read back from the destination object version.

Rules:
1. Encryption output is treated as opaque bytes. Do not parse, normalize or re-encode it before hashing.
2. Compute a pre-upload digest for transfer diagnostics, then independently hash the complete read-back bytes.
3. Publication requires read-back byte length and digest to match the authenticated manifest's expected values.
4. The authoritative stored-object digest is the digest verified from read-back bytes, not merely the local pre-upload value.
5. Object version/generation and immutable object identity are required; a mutable key/path alone is insufficient.
6. Retries for the same Backup ID must reconcile the same immutable object identity. They must not silently replace bytes or point the manifest at a different version.

### D3 — Manifest authentication

Fields:
- `manifest_format`
- `manifest_version`
- `backup_id`
- `object_id`
- `object_version`
- `payload_format`
- `encryption_format`
- `key_reference` (non-secret identifier only)
- `snapshot_image_sha256`
- `snapshot_image_byte_length`
- `encrypted_object_sha256`
- `encrypted_object_byte_length`
- D3 barrier/source DB identity and D2 evidence vector
- D4 migration authority identity and ordered migration-chain digest/evidence
- D5 canonicalization ID/version, schema digest and SQLite runtime identity
- integrity/domain verification outcome and verifier version
- creation/capture metadata needed for audit (timestamps diagnostic only; never identity)

The manifest must be authenticated by an approved mechanism. The authentication value covers a versioned canonical encoding of every security-relevant field above, including both digest domains and object version. The authentication field itself is excluded from its own authenticated input.

No encryption key, signing key, MAC key, secret, credential or recovery token may appear in the manifest, logs, fixtures, repository or CI artifacts. `key_reference` is only a lookup identifier.

**Not selected by this proposal:** signature versus MAC mechanism, algorithm suite, key custody/escrow/rotation, canonical manifest serialization profile, key service/provider or signature envelope format. These require separate security review and explicit approval before implementation.

## 3. Proposed object layout and publication sequence

Use two logically distinct immutable objects:
- encrypted payload object;
- authenticated manifest object referencing the exact payload object ID/version.

The manifest is not included in `encrypted_object_sha256`; this avoids a circular digest. The manifest's own authentication covers its payload digest and object reference. If a future storage provider requires a bundled container, it must define a separate container digest and preserve the two inner digest domains.

Proposed sequence:
1. D3 host-owned barrier closes write admission and drains transactions.
2. Create isolated SQLite Online Backup API image.
3. Verify SQLite integrity, foreign keys, domain invariants, D2 vector, D4 migration chain and D5 schema digest from the same read snapshot/evidence contract.
4. Freeze the verified snapshot image and compute `snapshot_image_sha256` plus byte length.
5. Encrypt the frozen image using a separately approved encryption/key contract.
6. Compute encrypted payload byte length and transfer digest.
7. Upload payload to an immutable destination object version in STAGING state.
8. Read back the entire stored payload; compute `encrypted_object_sha256` and byte length independently.
9. Require read-back values to match the exact uploaded bytes; verify object identity/version and destination immutability controls.
10. Build and authenticate the manifest binding both digest domains and the exact payload object version.
11. Publish manifest and payload as one logical AVAILABLE backup only after both are durable and verified. If the destination cannot atomically publish both, use a fail-closed commit marker/state transition whose semantics are documented and tested.
12. Preserve the previous last-known-good backup until the new backup is fully AVAILABLE and recoverable.

Any timeout or uncertain outcome remains STAGING/UNKNOWN. It must not create an AVAILABLE manifest or displace last-known-good. Retries reconcile by immutable Backup ID, object ID and version.

## 4. Proposed restore verification order

1. Authenticate the manifest before trusting its fields.
2. Resolve the exact immutable payload object ID/version.
3. Read the complete encrypted payload and verify `encrypted_object_sha256` and byte length.
4. Decrypt only through the separately approved key authority; reject unavailable, revoked or mismatched key references.
5. Hash the resulting exact SQLite image and compare `snapshot_image_sha256` and byte length.
6. Verify D3 barrier/source identity, D2 vector, D4 migration chain, D5 schema digest, SQLite integrity and domain invariants.
7. Only then may the image proceed to D6 isolated restore staging and the separately authorized restore/re-fencing protocol.

No single successful digest substitutes for manifest authentication, decryption authentication, D3/D4/D5 checks, domain verification or D6 recovery gates.

## 5. State model

Allowed logical states:
- `CAPTURED`: verified immutable plaintext snapshot exists only inside trusted capture boundary.
- `ENCRYPTED_STAGING`: encrypted payload generated; not yet published.
- `PAYLOAD_STORED_UNVERIFIED`: destination write acknowledged but read-back not yet verified.
- `PAYLOAD_VERIFIED`: read-back digest/length/object version verified.
- `MANIFEST_STAGED`: manifest constructed and authentication verified, but backup not yet AVAILABLE.
- `AVAILABLE`: payload and manifest durable, immutable, mutually bound and independently verified.
- `UNKNOWN`: outcome cannot be established; excluded from recoverable inventory.
- `CORRUPT`: digest/authentication/identity mismatch; excluded from recoverable inventory.
- `KEY_UNAVAILABLE`: required key reference unavailable/revoked; excluded from recoverable inventory.

Only `AVAILABLE` counts as a recoverable backup. State transitions and retry reconciliation must be append-only auditable and idempotent by Backup ID/operation ID.

## 6. Failure and security requirements

- Same Backup ID with different snapshot digest, encrypted digest, object ID or object version is a conflict; fail closed.
- Ciphertext tampering, truncation, extension, object substitution, version rollback or manifest tampering is rejected.
- Missing/unknown manifest version, digest algorithm, encryption format, key reference or verifier capability is rejected.
- No fallback to plaintext publication, alternate bucket/path, local shadow database or unverified previous object.
- No automatic deletion of last-known-good during uncertain publication or restore.
- Logs may include IDs, states, digest values and non-secret key references; never key material or credentials.
- CI fixtures use fake keys and fake destination only. CI credentials are not backup/restore authorization.
- The encrypted-object digest provides byte identity, not authenticity by itself. Manifest authentication and the approved encryption authentication mechanism remain mandatory.

## 7. Acceptance tests to add to P5.4.79 fixture plan

1. Snapshot-image digest is calculated before encryption and remains distinct from encrypted-object digest.
2. Different encryption nonce/output for identical snapshot image produces same snapshot digest but different encrypted-object digest.
3. One-byte snapshot mutation changes snapshot-image digest.
4. One-byte ciphertext mutation changes encrypted-object digest and fails read-back verification.
5. Truncation/extension fails byte-length and digest verification.
6. Manifest authentication binds both digest fields, Backup ID, object ID and object version.
7. Changing any bound field invalidates manifest authentication.
8. Manifest is not included in encrypted payload digest; no circular construction.
9. Upload acknowledgement without full read-back cannot transition to AVAILABLE.
10. Read-back digest mismatch yields CORRUPT and preserves last-known-good.
11. Same Backup ID with conflicting object version/digest fails closed.
12. Missing/revoked key yields KEY_UNAVAILABLE and excludes backup from recoverable inventory.
13. Restore verifies manifest authentication, ciphertext digest, decrypts, then verifies snapshot digest in that order.
14. Successful digest checks do not bypass D2/D3/D4/D5/domain checks or D6 authorization/fencing.
15. Partial manifest/payload publication remains STAGING/UNKNOWN; no partial AVAILABLE state.
16. Retry after uncertain publication reconciles immutable IDs and does not overwrite last-known-good.

These 16 cases are proposed additions to the existing 60-case plan; they are NOT IMPLEMENTED / NOT RUN.
