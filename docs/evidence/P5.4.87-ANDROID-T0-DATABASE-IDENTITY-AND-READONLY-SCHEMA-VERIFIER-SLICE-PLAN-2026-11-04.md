## 3. Slice 3A — Database identity contract

### 3.1 Separate identity domains

Do not overload one string/token for multiple purposes. The proposed contract distinguishes:

| Identity | Meaning | Stability | Permitted use |
|---|---|---|---|
| CanonicalDatabaseRoleId | Logical role of this database in the application architecture, e.g. the one canonical T0 database role | Stable across app installs and restore/clone | Routing/configuration and contract matching only |
| CanonicalDatabaseInstanceId | Identity of one physical database lineage/instance | Allocated only during an explicitly authorized database provisioning/adoption operation; preserved by verified backup/restore; changed only by an explicit clone/fork operation | Detect wrong DB, accidental parallel DBs and lineage mismatch |
| BackupId | One immutable backup operation/object pair | Unique per backup | D3–D7 backup/restore evidence only |
| RestoreEpoch | Monotonic recovery authority epoch external to the DB | Monotonic and independent of restored DB bytes | D6 fencing/recovery only |
| LeaseGeneration | Monotonic writer fencing generation | External/authoritative as defined by D2/D6 | Reject stale writers/intents |

### 3.2 Rules

- CanonicalDatabaseRoleId must not be described or used as a physical DB instance ID.
- No identity may be derived from package name, app version, file path, timestamp, file length, device ID, Android ID, user/account identifier or a content hash alone.
- CanonicalDatabaseInstanceId must be opaque, collision-resistant and created only by a separately approved provisioning/adoption protocol. The exact generator, storage field and lifecycle are not selected in this plan.
- A verified backup preserves the instance lineage ID because it is the same logical database lineage restored from a prior point. A deliberate fork/clone must receive a new instance ID and explicit lineage metadata; it must not silently masquerade as the original canonical DB.
- A restore must not reset or allocate RestoreEpoch from data inside the restored database. D6 remains independent and mandatory.
- BackupId, Restore Epoch and Lease Generation are not substitutes for CanonicalDatabaseInstanceId.
- If an existing database lacks an accepted instance identity, classify it as IDENTITY_UNKNOWN / LEGACY; do not auto-stamp during ordinary startup or read-only verification.
- If a present identity conflicts with the expected host/role/manifest, fail closed. Do not repair or rewrite identity in a verifier.

### 3.3 Decision still required

This plan recommends the logical/physical split above, but the owner has not approved the detailed instance-ID lifecycle, UUID/ULID/random format, registry storage location, clone/fork procedure or legacy adoption protocol. These remain proposed/open. No instance ID is generated or provisioned.

## 4. Slice 3B — D4 schema migration authority and verifier boundary

D4.1–D4.7 is already owner-approved in P5.4.71. This slice translates that approved contract into an Android implementation interface and fixture acceptance plan; it does not re-open or weaken D4.

### 4.1 Migration catalog contract

Each immutable migration descriptor contains:
- migrationId: immutable, unique ID;
- sequence: strictly increasing sequence in one DB-wide chain;
- ownerDomain: market_data, paper_ledger, risk or shared;
- checksumSha256: SHA-256 of exact immutable migration bytes;
- migrationBytes: packaged immutable source bytes or a trusted descriptor reference;
- compatibility metadata only if separately standardized.

Applied history is append-only. A correction is a new forward migration, never a rewrite of an applied migration.

### 4.2 Read-only verifier interface (proposed)

The future verifier must be a read-only capability. It must not receive a migration runner, writable SQLite connection, filesystem create permission or repository constructor that performs schema initialization.

Proposed conceptual input:
- expected CanonicalDatabaseRoleId;
- expected/known CanonicalDatabaseInstanceId, if already established by an authorized protocol;
- trusted immutable migration catalog;
- a read-only database inspection adapter;
- optional authenticated D3 manifest declaration for cross-checking.

Proposed result:
- verification status;
- observed role/instance identity state;
- ordered applied migration chain and its deterministic digest;
- physical schema descriptor/digest according to the separately approved D5 canonicalization rules;
- structured mismatch diagnostics.

Allowed terminal outcomes include D4 states:
VERIFIED, LEGACY_UNVERSIONED, MISSING_REGISTRY, CHECKSUM_MISMATCH, SEQUENCE_GAP_OR_DUPLICATE, UNKNOWN_MIGRATION, SCHEMA_DRIFT, INCOMPLETE_OR_UNCERTAIN.
Identity-specific outcomes include:
IDENTITY_UNKNOWN, ROLE_MISMATCH, INSTANCE_MISMATCH, MANIFEST_IDENTITY_MISMATCH.

Only VERIFIED may satisfy a later migration-dependent readiness gate. This does not by itself admit writers, release Recovery Latch, clear Kill Switch or satisfy D6.

### 4.3 Strict read-only boundary

- No database open/create or file creation is part of this design-only increment.
- Future read-only inspection must target an existing file using a documented SQLite read-only mode; exact Android/JVM API and SQLite runtime support must be proven before implementation.
- No call to CandleStore.initialize_schema(), PaperLedger constructor, ensure helpers, migration runner, PRAGMA mutation, CREATE/ALTER/DROP, INSERT/UPDATE/DELETE, schema repair, baseline stamping or user_version repair.
- A missing file remains missing; verifier returns an explicit missing/unknown state rather than creating it.
- Legacy/unversioned DB remains LEGACY_UNVERSIONED until a separately reviewed, owner-approved baseline adoption.
- Any uncertain transaction, registry/schema mismatch or unsupported SQLite feature fails closed.

### 4.4 D3/D5 integration

- D3 snapshot manifest captures role/instance identity and the D4 applied migration chain from the same SQLite read snapshot as the other D2 evidence.
- D5 logical schema digest must use its approved conservative canonicalization contract; this plan does not invent SQL normalization or substitute a migration-chain digest for a physical schema digest.
- Snapshot byte digest, migration-chain evidence and logical schema digest are distinct evidence domains. None substitutes for the others.
- Restored DB bytes cannot allocate Restore Epoch or prove old writers stopped.

## 5. Slice 3C — Fixture/static acceptance plan (not implemented)

All current tests in this slice are pure JVM/domain fixtures or static checks. They must not open SQLite, create a canonical DB, touch Android device storage or invoke a migration.

Identity fixtures:
1. Logical role ID remains stable independently of app package/build variant.
2. Role ID is not accepted as a physical instance ID.
3. Unknown instance identity remains UNKNOWN; no generated/default identity is inferred.
4. Expected-vs-observed role mismatch fails closed.
5. Expected-vs-observed instance mismatch fails closed.
6. Backup lineage preserves instance identity in the model.
7. Explicit clone/fork model requires a new instance identity and records parent lineage.
8. BackupId, RestoreEpoch and LeaseGeneration cannot be substituted for DB instance identity.
9. File path, package, app version, timestamp, device ID or file hash cannot be used as the sole instance identity.
10. Legacy fixture is not silently stamped or upgraded.

Migration/verifier fixtures:
11. One DB-wide ordered migration catalog across domains.
12. Exact-byte SHA-256 match verifies; one-byte mutation fails.
13. Unknown migration, duplicate ID, duplicate sequence and sequence gap fail.
14. Applied history is append-only; attempted rewrite/delete is rejected by contract.
15. DDL failure/interrupted transaction never advances registry in the model.
16. Registry/schema descriptor mismatch returns SCHEMA_DRIFT.
17. Missing registry returns LEGACY_UNVERSIONED or MISSING_REGISTRY according to explicit expected state; never infer latest.
18. Read-only verifier contract cannot call a migration runner or write-capable adapter.
19. Missing DB path does not cause file/directory creation.
20. Non-VERIFIED result cannot satisfy later readiness in a pure gate model.
21. D3 manifest migration evidence must match the same-snapshot fixture.
22. D5 schema digest remains separate from migration-chain digest.

Variant/CI fixtures:
23. Build regular debug unit-test variant.
24. Build and run the .paper parallel unit-test variant; verify PARALLEL_INSTALL=true and application ID suffix .paper.
25. Static scan confirms .paper has no CanonicalRuntime owner, path resolver, SQLite capability, shadow DB or fallback writer.
26. CI evidence is tied to one exact source SHA; no device/signer claim from JVM fixtures.

These are acceptance cases to implement only after a separate Slice 3 implementation approval. They are NOT IMPLEMENTED / NOT RUN.
