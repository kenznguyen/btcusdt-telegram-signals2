# P5.4.36 — Android Canonical Storage Architecture Contract (Design Only)

## 1. Scope and authority

- Repository: `kenznguyen/btcusdt-telegram-signals2`
- Branch: `feature/p5-4-1-post-merge-validation-20261103`
- Design baseline: P5.4.35 inventory and the current `docs/decisions/ADR-001-PRODUCTION-BACKUP-MANIFEST-CONTRACT.md`.
- Type: design contract only; no implementation or runtime validation.
- Owner-confirmed decisions recorded in ADR-001:
  - Android is the canonical T0 host and initial sole writer after separately approved activation.
  - T0 Market Data and Paper Ledger use **one shared physical SQLite file hosted on Android**.
  - PC is an AI training/FreqAI/backtest/research consumer, not a canonical writer.
- This contract does not activate the database, feeder, paper execution or any exchange integration.

## 2. Reconciliation of prior evidence

P5.4.34 correctly recorded that Android-first by itself did not imply a shared physical database. ADR-001 subsequently records the explicit owner selection of one shared Android SQLite file. P5.4.35's statement that the shared-file decision was not made is therefore stale relative to ADR-001.

The distinction is:

- **NOT VERIFIED:** source implementation of that topology, canonical Android path provider, Android Feeder composition and Android Paper Ledger composition.

This reconciliation changes documentation interpretation only; it does not claim that source integration has been implemented.

## 3. Target architecture contract

### 3.1 Single canonical database identity

A future Android application composition root must own one canonical database identity and pass it by dependency injection to every canonical component.

Required properties:
1. One app-private durable SQLite file on Android.
2. One canonical path provider/resolver; no independently configured path in Market Data, Paper Ledger, Risk State or Feeder modules.
3. Every component receives the same resolved database identity from the composition root.
4. Startup fails closed if any canonical component resolves a different physical file, backend, or store identity.
5. No fallback to PC paths, environment-specific shadow DBs, a second SQLite file, or silent in-memory stores.
6. The exact Android path, filename, directory policy and backup exclusion behavior remain **OPEN**. They must be selected in a separate explicit path decision and verified without exposing private absolute paths in evidence.

Lexical path equality alone is insufficient for a future runtime identity check. The implementation must define canonicalization and, where supported, filesystem identity checks (for example, resolved path plus stable file identity after provisioning). CI fixtures must use temporary isolated paths and must never open or create the production canonical path.

### 3.2 Domain ownership inside the shared file

The physical file is shared; logical table ownership remains explicit.

| Domain | Logical ownership | Source-grounded existing objects / state | Required boundary |
|---|---|---|---|
| T0 Market Data | Market Data store | `candles` | Closed, validated OHLCV only; key by exchange, market, symbol, timeframe and open time; gap/continuity metadata must not be inferred from max timestamp alone |
| Feeder coordination | T0 Feeder | `feeder_leases` exists in the Python LeaseStore implementation | Lease name, owner, monotonic generation and expiry; writes require current fencing authority |
| Paper ledger | Paper Execution | `paper_state`, `paper_orders`, `paper_books`, `paper_audit`, `paper_strategy_state` | Idempotent intent/order transitions, state, audit and strategy state |
| Risk and equity | Shared Risk / Equity modules | Risk latch is persisted in paper state; equity history is ensured/recorded by the PaperLedger composition | Kill Switch, exposure/loss controls and equity observations must be durable and auditable; exact table ownership/migration is to be enumerated from implementation before coding |
| Runtime/health metadata | T0 Feeder / app runtime | Existing Python runtime status store abstraction; Android implementation not established | Health is not a substitute for canonical data or a lease; define durable status fields and freshness separately |
| UI preferences/cache | Android UI | Current `strategy_state_v1` SharedPreferences includes UI/monitor/strategy/scanner/alert state | Remains noncanonical; no candles, order ledger, risk latch or lease authority may silently be promoted into preferences |

The contract selects a single physical file for Market Data and Paper Ledger. It does not require every transient UI preference or external control-plane signal to be stored in that file.

### 3.3 Connection and transaction boundaries

A shared file does not automatically make operations atomic across components. The implementation must provide a single connection/transaction coordination boundary for operations that require cross-domain atomicity.

Required transaction rules:
- Schema provisioning/migration is a controlled, explicit operation; ordinary constructors must not silently create or seed canonical tables.
- Read-only verification uses a read-only connection and must not instantiate schema-mutating services.
- Every canonical candle write is gated by current writer fencing immediately before mutation.
- Lease generation validation and the protected write must be serialized so a stale owner cannot pass a check and write after ownership changes. A check in a separate transaction followed by an unguarded write is insufficient.
- Paper intent acceptance, idempotency record, risk decision, order/state mutation and audit event must commit or roll back as one defined transaction where they represent one state transition.
- Kill Switch assertion and risk-latch changes must be durable and fail closed. No AI/Core intent bypasses the same shared risk gate.
- Cross-domain transactions are permitted only where explicitly specified. A single SQLite file is not proof that separate connections or sequential commits form one atomic unit.
- No strategy calculation, network request or long-running model inference should hold a SQLite write transaction open.

The precise transaction APIs, connection pool policy, busy timeout, WAL/checkpoint policy and contention budget remain implementation design items and must be covered by fixture tests before runtime activation.

### 3.4 Single-writer and fencing contract

- Android is the only canonical writer after activation.
- PC access is read-only through a controlled export/snapshot or read interface. PC must never open the live Android DB as a writable shared filesystem database.
- CI uses isolated temporary fixtures and never has credentials or paths to the canonical store.
- Feeder lease ownership must use owner identity, TTL, heartbeat and strictly increasing fencing generations. Every canonical write must carry the current generation.
- The source implementation already has a SQLite-backed `LeaseStore` with `feeder_leases` and generation checks, and the production factory enforces the lease DB path to resolve to the candle DB path. This is Python source behavior; Android composition is **NOT VERIFIED**.
- Candidate runtime lease placement is the shared canonical DB, consistent with the same-file T0 identity contract. Final Android lease wiring and same-transaction enforcement remain **NOT ACCEPTED / NOT VERIFIED** until the implementation contract and fixture tests prove it.
- A database-restored lease generation can roll back with the database. Therefore ordinary lease generation alone cannot be the post-restore authority. A monotonic recovery epoch or external maintenance latch outside the restored snapshot is required; its authority and storage location remain **OPEN**.
- If lease validity, writer identity, recovery epoch or Kill Switch state cannot be verified, all canonical writes and paper intent acceptance remain disabled.

### 3.5 Paper execution and shared risk boundary

- Strategy Core and independent AI may produce separate LONG/SHORT intents, but neither has direct persistence or execution authority.
- Both intent sources submit through the same paper intent boundary and Shared Risk Engine/Kill Switch.
- The ledger must persist intent identity, payload hash, accepted/rejected reason, state transitions, fills/fees (where simulated), strategy attribution and audit history.
- Duplicate intent ID with identical payload is idempotent; the same ID with a different payload fails closed.
- Risk state, paper position/state, orders, strategy state and audit records must be recoverable from the same selected database snapshot, subject to the external restore latch/epoch.
- Paper-only remains mandatory: no live orders, no exchange execution credentials, `AI_EXECUTION_ENABLED=false`.

### 3.6 Backup and restore boundary

- The shared SQLite file permits one database-level consistent snapshot of rows inside that file, but does not by itself capture external configuration, external recovery latch/epoch, app preferences, exchange inputs or PC model artifacts.
- Production backup must use a WAL-aware supported SQLite snapshot/online-backup mechanism; copying only the main DB file while WAL is active is not accepted.
- Snapshot creation must coordinate writers or use a proven SQLite online backup boundary; a manifest barrier string alone does not establish atomicity.
- Verification must be read-only and must not create missing tables, seed singleton rows or repair the DB.
- Restore must keep the external maintenance latch asserted, verify the complete required snapshot, allocate a new monotonic recovery epoch, re-fence every writer above restored generations, assert Kill Switch and require explicit readiness/approval before writer startup.
- Backup destination, encryption/key management, retention, cadence, off-host copy, RPO/RTO, restore approver and exact operational sequence remain **OPEN**. No backup/restore is authorized by this design.

## 4. Android application composition requirements

The future Android composition root must explicitly construct and inject:
1. Canonical SQLite identity/path authority.
2. Migration/provisioning coordinator.
3. T0 CandleStore and write Gateway.
4. Feeder lease/fencing and runtime health/status services.
5. Paper Ledger and order/audit repositories.
6. Shared Risk Engine/Kill Switch and equity history repositories.
7. Read-only query interfaces for UI and PC export.

The composition root must expose a readiness result that remains false until database identity, schema version, integrity, lease fencing, recovery latch, Kill Switch and all required repositories are verified. UI/service startup must not silently mark the system ready on partial construction.

This is a required target interface list, not a claim that those Android classes currently exist.

## 5. Migration and schema authority

- Define one explicit SQLite migration authority for the shared file.
- Each migration must have stable ID, checksum, ordered application record and transaction semantics.
- Do not use fixture-only `PRAGMA user_version` as production authority unless production migrations explicitly own and maintain it.
- Market Data and Paper Execution may own separate migration modules, but a single coordinator must apply compatible ordered migrations against the one database identity.
- Unknown, missing, duplicate or checksum-mismatched migration records fail closed.
- No automatic schema repair or destructive downgrade is allowed during normal app startup.
- Exact migration framework, initial schema version and compatibility policy remain **OPEN**.

## 6. Required fixture-only acceptance gates before any device/runtime work

1. One canonical path provider injects the same isolated temporary DB identity into T0, Paper Ledger, Risk and lease components.
2. Distinct resolved DB identities fail before any canonical component initializes or any network/exchange object is constructed.
3. Constructors do not create schema; explicit provisioner creates schema only when called with an isolated fixture.
4. Read-only verifier rejects missing/unknown schema without creating files or rows.
5. Concurrent/stale lease owner cannot write after a newer fencing generation is granted.
6. Lease check and canonical mutation cannot be separated by a race window.
7. Paper intent + risk decision + ledger/audit state are atomic and idempotent under duplicate/reordered requests.
8. Kill Switch and risk latch fail closed on missing/corrupt/unknown state.
9. WAL-aware snapshot/restore fixture proves database integrity and logical state identity; external restore epoch is independently advanced.
10. Partial restore, manifest mismatch, unknown schema and stale writer all prevent startup.
11. PC export/read interface cannot mutate the canonical store.
12. Tests assert no live execution path and `AI_EXECUTION_ENABLED=false`.

All gates run only in GitHub Actions against isolated fixtures. No production DB path, Android device or exchange is available to CI.
