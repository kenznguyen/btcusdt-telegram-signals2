## 3. Identity Pin — implementation vs contract

### Implemented in source (pure Kotlin only)

- `CanonicalDatabaseRoleId` represents the stable logical database role.
- `CanonicalDatabaseInstanceId` parses an already-persisted lowercase UUIDv4; no generator/default/auto-stamp path exists.
- `CanonicalIdentityPinCodec` encodes/parses a canonical four-line versioned record and distinguishes Missing, Malformed, UnsupportedVersion and Valid.
- `CanonicalIdentityStateClassifier` distinguishes missing DB, legacy, unknown/unconfirmed identity, invalid/unsupported pin, role/instance mismatch and provisioning-interrupted/finalization states.
- `IdentityProvisioningPlanner` is a pure decision planner for explicit START, RESUME_SAME_ID and FINALIZE_PENDING operations. It requires explicit preconditions and does not perform those operations.
- `IdentityProvisioningPreconditions` models maintenance authorization, writer/lease absence, identity/legacy state and bootstrap path conditions.
- Pure fixture tests and the recorded P5.4.90 / P5.4.91 / P5.4.88 evidence establish domain behavior for their exact tested SHAs.

### Not implemented

- No Android `noBackupFilesDir` pin file reader/writer.
- No bounded file read, atomic temp-write/flush/rename, directory durability handling or promotion durability reconciliation.
- No Android storage adapter that supplies the serialized pin to the classifier.
- No actual UUIDv4 generation under an explicit provisioning command.
- No executable two-resource provisioning transaction coordinating pin and SQLite identity.
- No real bootstrap, legacy adoption, migration execution or pin activation.
- No Android runtime proof of the selected noBackupFilesDir backup/exclusion semantics.

Important limit: the pin is documented as a local consistency anchor, not cryptographic authenticity or anti-clone protection. The current codec is not a persistence implementation.

## 4. Native SQLite read-only adapter — implementation vs contract

### Implemented in source

- Kotlin session wrapper exposes narrow open/close/D5-read calls; it rejects non-absolute paths and invalid handles, and provides idempotent close semantics.
- Native open uses `sqlite3_open_v2` with `SQLITE_OPEN_READONLY | SQLITE_OPEN_FULLMUTEX`; no CREATE or READWRITE flag is supplied.
- Native code checks `sqlite3_db_readonly(main) == 1`, exact pinned SQLite source ID and minimum engine version.
- Native code checks WAL journal mode and requires readable existing `-wal` and `-shm` sidecars; it fails closed if unavailable and does not create them intentionally.
- Native code starts `BEGIN DEFERRED`, executes and consumes a database-backed `SELECT count(*) FROM sqlite_schema` anchor, then retains the same `sqlite3*` handle in a mutex-protected registry.
- D5 queries are fixed statements; each prepared statement is checked with `sqlite3_stmt_readonly()==1` and exact result-column names/counts. No arbitrary SQL API is exposed.
- D5 query/close calls use the same registered handle. Registry mutex serializes read and close operations.
- Kotlin D5 wire decoder validates bounded framing, statuses, UTF-8, counts, row shapes and cross-section relationships.
- Native in-memory fixture hook is compile-time Debug-only; Release excludes that hook.
- Pinned SQLite/NDK build, native CTest and host-side JNI ABI/lifecycle evidence exist for earlier exact source SHAs.

### Not implemented / not proven

- The native session accepts a raw absolute path; it is not yet bound to a capability/token issued by `CanonicalPathAuthority`. The Kotlin wrapper does not prove the path is the canonical host path.
- `NativeSqliteReadOnlySession` is not composed by `CanonicalApplication` or `CanonicalRuntime`.
- No persisted Identity Pin is read and compared with the DB identity through this native session.
- The native D5 reader currently gathers SQLite runtime identity and schema introspection. It does **not** yet read the `canonical_database_identity` row or `schema_migrations` chain on that same handle.
- The Kotlin `CanonicalSqliteReadContract.fixedReadQueries` declares identity and migration query families, but the native D5 wire path does not yet return those records. The contract and concrete native query implementation are therefore not yet a complete end-to-end reader.
- No adapter-owned `CanonicalDatabaseReadSnapshot` is assembled from the native read result.
- No exact-current-HEAD CI run is recorded for the entire native + identity + snapshot combination.
- No WAL concurrency, missing-sidecar, rollback-journal, process-death, filesystem race, no-create or device runtime proof is available.

### Specific constraints requiring explicit closure

1. The current native adapter is WAL-only. This is consistent with the recorded ADR-003 design boundary, but the canonical writer must be required to establish and maintain WAL/sidecar lifecycle. The reader cannot silently switch journal mode or create sidecars.
2. The pre-open `access()` checks for DB/WAL/SHM are advisory and can race with later filesystem changes. They are not proof against TOCTOU. Runtime behavior and safe failure on sidecar removal/connection invalidation remain unverified.
3. The native open method checks absolute path syntax, not canonical-path ownership or symlink/alias identity. The future Kotlin host boundary must be the only source of accepted paths.
4. ADR-003 requires engine version, source ID and compile-option evidence. Current native D5 envelope includes SQLite version/source ID; a complete runtime compile-options/feature-probe evidence record is not yet connected to the snapshot verifier.
5. Native read transaction implementation is present in source, but instrumentation/runtime verification is paused. Source code is not proof that API 26/33/35 runtime matrix works.

## 5. D5 Snapshot — implementation vs contract

### Implemented

- `CanonicalD5Serializer` provides deterministic binary envelope v1 serialization and SHA-256 over supplied in-memory envelope values.
- Empty and populated golden vectors are frozen; independent decoder tests validate the vectors without calling the production serializer.
- D5 schema envelope models catalog, table/view columns, indexes, index columns and foreign keys.
- Native D5 wire decoder transforms native payload into a typed `D5SchemaEnvelope`.
- `CanonicalDatabaseReadSnapshot` is an immutable DTO with defensive list copies and fields for DB state, consistency claim, observed role/instance, migration chain, expected/observed schema digest and SQLite runtime identity.
- `CanonicalDatabaseReadSnapshotVerifier` rejects missing/legacy/identity-missing/uncertain DB states, unproven or multiple-transaction consistency, incomplete evidence and schema verifier failures.

### Not implemented / not proven

- Snapshot DTO consistency is supplied as an enum by the caller; the DTO explicitly documents that this is a claim, not proof.
- The public capture function permits a caller to construct a `SINGLE_SQLITE_READ_TRANSACTION` snapshot from arbitrary values. It does not prove that the values came from the native handle.
- The current native D5 payload is not assembled with the DB identity row, migration registry and external pin.
- The snapshot verifier checks expected/observed digest equality but does not itself recompute the digest from a native-origin envelope. A trusted assembler must compute the observed digest from decoded D5 bytes and compare it with a trusted expected schema digest.
- SQLite version/source ID are checked for nonblank completeness in the snapshot verifier; actual supported runtime/compile-option policy must be enforced by the native capture/assembler boundary.
- No one-call capture API owns open → anchor → identity/migration/catalog/PRAGMA reads → digest → rollback/close and returns one all-or-nothing immutable result.
- No real SQLite read transaction has been used to produce a `CanonicalDatabaseReadSnapshot`.

## 7. Recommended next implementation slice (proposal only)

### T0.10 — Trusted Read-only Evidence Assembly, SOURCE-ONLY / IN-MEMORY FIXTURE

Purpose: bridge the already existing pin/domain, native read-only D5 query and snapshot verifier without touching the canonical file or Android device.

Bounded implementation:
1. Extend the native fixed-query wire contract to include all `canonical_database_identity` rows and all `schema_migrations` rows on the same registered `sqlite3*` and already-pinned DEFERRED transaction as D5 introspection.
2. Extend the Debug-only in-memory fixture to include identity and migration tables, a valid UUIDv4 identity row, deterministic bootstrap migration bytes/checksum and malformed/duplicate/partial variants.
3. Extend Kotlin decoder to return one typed read-evidence object containing runtime identity, identity rows, applied migrations and D5 envelope; reject unknown/missing/reordered fields and partial payloads.
4. Add a pure `CanonicalReadSnapshotAssembler` that accepts the decoded native evidence plus an injected parsed pin value. It must not read files, open SQLite, generate IDs or mutate pins.
5. The assembler must compute the observed D5 digest from the decoded envelope itself; it must not accept a caller-supplied observed digest or consistency enum as proof.
6. Construct a `VERIFIED` snapshot only from a successful adapter-owned capture result with one opaque transaction/handle token and complete evidence. All failures discard partial evidence and return typed NOT VERIFIED/READ_UNCERTAIN.
7. Add host-side CTest/JNI ABI and regular + `.paper` JVM fixtures covering same-handle behavior, pin/DB mismatch, missing/duplicate identity, unknown/gapped/duplicate migration, checksum mismatch, schema drift, unsupported objects, malformed wire data, connection invalidation and close failure.
8. Keep all database fixtures `:memory:`; no filesystem DB and no canonical path. No Android instrumentation while T0.9 is paused.
