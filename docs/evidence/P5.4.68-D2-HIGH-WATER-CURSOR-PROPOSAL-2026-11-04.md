## Design constraints

1. A high-water cursor must represent a precisely defined contiguous prefix or committed sequence, not the largest observed value.
2. Cursor advancement must be atomic with the state mutation it represents.
3. Gaps, rejected input, duplicate delivery, out-of-order events and transaction retries must not advance a cursor past uncommitted state.
4. A single SQLite file does not imply one global counter is semantically correct for every domain.
5. D3 owns snapshot/barrier consistency; D4 schema authority; D5 canonical digest; D6 restore epoch and fencing. D2 must not decide these.

## Proposed D2 model

### 1. Market Data — per-partition contiguous closed-candle cursor

Partition identity should include venue, market type, stable instrument identity, timeframe and price basis. Exact enum values and canonical instrument identity remain to be specified.

Each partition cursor should record:
- stable partition key and expected interval;
- coverage start boundary;
- latest contiguous **closed and validated** candle boundary;
- explicit gap/coverage state;
- monotonically increasing cursor revision;
- diagnostic update time, not used as ordering authority.

Advance only when every expected candle from the previous contiguous boundary to the new boundary is validated and committed. A missing, malformed, rejected or still-open candle blocks advancement. Record gaps separately. An older backfill may close a gap but must not move the forward cursor backward or imply coverage outside the verified range.

Candle upserts, coverage/gap updates and cursor advancement must commit in one SQLite transaction. Duplicate delivery is idempotent and does not create a false cursor advance.

Reject maximum timestamp alone, candle row count, exchange response end time or a single global market-data cursor: none proves contiguous per-partition coverage.

### 2. Paper Ledger — dedicated monotonic commit sequence

Use a dedicated ledger commit sequence rather than accepting `paper_audit.id` as the cursor without proof.

Each accepted state-changing Paper command should have a stable idempotency key and allocate the next committed ledger sequence in the same SQLite transaction as all affected order/book/position/strategy state, its audit/event record, and any risk state changed by that logical transition.

Rollback must leave no visible sequence advance. A retry with the same idempotency key returns the original committed result and must not create a second transition. Audit records should carry the committed sequence.

`paper_audit.id` is only a candidate if every relevant mutation is proven to emit an append-only or explicitly corrected audit event in the same transaction, with no bypass path. Existing evidence does not establish this.

Reject timestamps, row counts, SQLite rowid/autoincrement alone, or MAX(audit.id) without mutation-coverage proof.

### 3. Risk State — version bound to ledger sequence

When risk state changes in the same logical transaction as a Paper Ledger command, persist its risk version and referenced ledger sequence atomically. If independent risk-only transitions are allowed, they need a typed idempotent transaction and their own monotonic risk version committed with the risk row and audit record.

Every snapshot/read model must identify the ledger sequence and risk version it represents. Do not combine values from different SQLite read snapshots and label them coherent. Kill Switch and restore latch safety remain D6 concerns; a risk cursor cannot replace external recovery control.

Reject deriving risk progress from exposure, open-position count, updated timestamp or row count.

### 4. Feeder Lease — separate fencing generation, not a data cursor

Keep lease generation separate from Market Data and Paper Ledger cursors. Candidate evidence includes lease name, owner instance, monotonic generation, expiry/heartbeat diagnostics and state. Every canonical write must be checked against the current host-side generation at the transaction boundary. A stale generation must fail even if its local expiry appears valid.

Lease location, generation survival across restore and old-owner fencing procedure remain D1 residual details and D6 decisions. This proposal does not choose an external lease authority or reset process.

## Proposed snapshot evidence vector

The owner approved a vector containing per-partition Market Data coverage, Paper Ledger commit sequence, Risk State version and Lease fencing evidence. This vector is descriptive evidence only; it does not prove that all values were observed atomically. D3 must define the barrier/snapshot protocol, D5 digest rules and D6 restore/fencing behavior.

A verifier must reject a cursor that crosses a known gap, an unreconciled Paper sequence, a risk version without its referenced committed state, stale lease evidence, unknown partition semantics, or a vector assembled from independent reads without an accepted D3 boundary.

## Fixture-only acceptance tests proposed

1. Missing intermediate candle prevents contiguous cursor advancing to a later timestamp.
2. Backfill closes the gap only after validation and commit.
3. Open, malformed or rejected candle never advances closed-candle cursor.
4. Duplicate candle delivery is idempotent.
5. Failure between candle upsert and cursor update rolls back both or leaves an explicitly recoverable non-complete state.
6. Paper command failure before audit/sequence commit leaves no partial ledger mutation or visible sequence advance.
7. Same idempotency key retry does not allocate a second ledger sequence.
8. Mutation path bypassing audit/sequence writer is rejected or detected.
9. Risk mutation and referenced ledger sequence/version are atomic; mixed-snapshot reads are rejected.
10. Stale lease generation cannot write even when local expiry is in the future.
11. Restored lower lease generation is not considered safe merely because D2 cursors reconcile; D6 gate remains mandatory.
12. A valid cursor vector is not treated as proof of D3 barrier consistency.

All tests must use isolated fixtures and fake clocks/identities. They must not open/create the Android canonical DB, invoke production constructors, start Feeder, contact an exchange or mutate production state. These tests are specified, not implemented.

## Alternatives

| Model | Assessment |
|---|---|
| One global integer | Reject: hides partition gaps and independent domain mutations. |
| Market-data max timestamp + audit ID | Reject as insufficient: neither proves contiguous coverage nor complete atomic mutation coverage. |
| Per-partition candle coverage + ledger commit sequence + risk version + separate lease generation | Preferred proposal: matches domain semantics, supports gap detection, idempotency and fencing; still requires D3/D6. |
| Full event sourcing for all domains | Defer: major architectural expansion not justified by current evidence or required to define D2. |

## Owner decisions — recorded 2026-11-04

1. Approve per-partition contiguous closed-candle cursor with separate gap/backfill coverage records?
2. Approve dedicated Paper Ledger commit sequence with idempotency key and same-transaction state/audit advancement, rather than `paper_audit.id` alone?
3. Bind same-transaction risk changes to the ledger sequence, with a separate monotonic risk version only for independently committed risk transitions?
4. Keep Feeder lease generation separate from data cursors and require host-side fencing validation on every canonical write?
5. Accept a vector of domain cursors as D2 manifest evidence, explicitly not as proof of atomic consistency until D3 is approved?

The owner explicitly approved all five items with no additional notes:

1. **APPROVED — D2.1:** per-partition contiguous closed-candle cursor with separate gap/backfill coverage.
2. **APPROVED — D2.2:** dedicated Paper Ledger commit sequence with idempotency key and same-transaction state/audit advancement; `paper_audit.id` alone is not sufficient.
3. **APPROVED — D2.3:** same-transaction risk changes bind to Ledger sequence; independently committed risk-only transitions use a separate monotonic risk version.
4. **APPROVED — D2.4:** Lease generation remains separate from data cursors; host-side fencing is checked on every canonical write.
5. **APPROVED — D2.5:** manifest uses a vector of domain cursors, not a synthetic global integer, and the vector is not proof of atomic consistency pending D3.

No additional owner notes were supplied. D2 is **ACCEPTED**. D3–D7 remain **NOT DECIDED**. Approval is limited to semantics and does not authorize implementation.
