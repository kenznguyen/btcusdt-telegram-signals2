## 1. Scope and authorization

Question: can the canonical read-only snapshot adapter on minSdk 26 open SQLite read-only and hold one stable DEFERRED read transaction across all evidence queries?

## 2. Official API findings

Sources:
- Android `SQLiteDatabase` API: https://developer.android.com/reference/android/database/sqlite/SQLiteDatabase
- AndroidX `SupportSQLiteDatabase` API: https://developer.android.com/reference/androidx/sqlite/db/SupportSQLiteDatabase
- AndroidX change adding read-only transaction: https://android.googlesource.com/platform/frameworks/support/+/2ad50e94e4806509ee3d710491a60a1153b43a1f
- AndroidX framework implementation at that change: https://android.googlesource.com/platform/frameworks/support/+/2ad50e94e4806509ee3d710491a60a1153b43a1f/sqlite/sqlite-framework/src/main/java/androidx/sqlite/db/framework/FrameworkSQLiteDatabase.kt
- Android 8.0 framework source (API 26): https://android.googlesource.com/platform/frameworks/base/+/android-8.0.0_r1/core/java/android/database/sqlite/SQLiteSession.java

Findings:
1. Framework `SQLiteDatabase.OPEN_READONLY` exists from API 1 and is the documented read-only open flag.
2. Framework `beginTransaction()` exists from API 1 but begins EXCLUSIVE mode.
3. Framework `beginTransactionNonExclusive()` exists from API 11 but begins IMMEDIATE mode.
4. Framework `SQLiteDatabase.beginTransactionReadOnly()` is only available from API 35. It begins DEFERRED mode with Android's read-only transaction constraint. It is not a direct minSdk-26 framework API.
5. AndroidX added `SupportSQLiteDatabase.beginTransactionReadOnly()` in the 2.5.0 line. Its contract is DEFERRED/read-only. However the interface's default implementation delegates to `beginTransaction()`; therefore method presence alone does not prove the implementation supplies a read-only DEFERRED transaction.
6. The AndroidX framework driver implementation found in the reviewed source attempts a reflective call into framework `SQLiteSession.beginTransaction(TRANSACTION_MODE_DEFERRED,...)`. If that reflective path is unavailable, its fallback is `beginTransaction()` (EXCLUSIVE). That fallback does not meet the canonical adapter requirement and may fail on a read-only-opened connection.
7. The reviewed implementation source has a TODO to replace reflection with the Android V framework API once available. This reinforces that the pre-API-35 route is compatibility-sensitive and must be runtime-proven for the app's target SDK and device images.

## 3. Decision

**Do not mark the minSdk 26 transaction blocker resolved.**

A plausible candidate exists: AndroidX `androidx.sqlite:sqlite-framework` using `SupportSQLiteDatabase.beginTransactionReadOnly()`, provided the selected implementation successfully executes the reflective DEFERRED path on every supported API-26+ runtime.

It is not safe to assume that:
- any `SupportSQLiteDatabase` implementation overrides the default method;
- the reflective path remains accessible under the app's target SDK and hidden-API enforcement;
- fallback to EXCLUSIVE is acceptable;
- a successful method call alone proves all evidence queries used one stable read snapshot.

## 4. Required proof before accepting an adapter

A separately authorized test plan should cover API 26 and representative newer supported Android versions, with the exact app target SDK and pinned AndroidX SQLite artifact:

1. Open an existing test DB using explicit `OPEN_READONLY`; test missing path separately and prove no file/database is created.
2. Confirm the actual driver implementation and pinned library version.
3. Begin `beginTransactionReadOnly()`; verify the actual transaction mode/path is DEFERRED and that no EXCLUSIVE fallback occurred. If implementation cannot expose reliable proof, the adapter must remain NOT VERIFIED.
4. With two independent connections, establish the first read snapshot, commit a writer-side change where the storage mode permits it, then prove all later adapter queries still observe the original snapshot until transaction end. Repeat for WAL and rollback-journal modes if both are in scope.
5. Verify writes through the read-only transaction are rejected and no DB/WAL/SHM bytes are changed by the adapter's read operation.
6. Inject failures at begin, query, cursor iteration, connection close and end; every uncertain case must discard partial evidence and return READ_UNCERTAIN.
7. Capture exact Android API, build fingerprint, target SDK, SQLite version/source ID, AndroidX artifact coordinates/version, implementation class and test evidence.

Do not use `beginTransaction()` or `beginTransactionNonExclusive()` as substitutes. Do not hand-issue `BEGIN`/ `COMMIT` through `execSQL` or raw query unless a separately reviewed API contract proves session-state tracking, rollback and cleanup semantics. Do not rely on reflection outside the reviewed AndroidX implementation.
