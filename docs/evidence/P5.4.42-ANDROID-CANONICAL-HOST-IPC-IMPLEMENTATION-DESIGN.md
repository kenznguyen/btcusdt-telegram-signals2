## 3. Component and permission design

### 3.1 Service boundary

- Implement one explicit, exported host-side bound service only for the approved client relationship.
- Require a dedicated Android signature-level bind permission declared by the host and required by the service.
- The client binds with an explicit component reference; implicit service discovery is forbidden.
- Use a narrow AIDL contract with closed, versioned DTOs. Do not expose a generic transaction dispatcher, arbitrary parcel payload, callback with broad authority, raw database object, file descriptor, URI-based CRUD interface or SQL operation.
- Binder entry points perform bounded validation and enqueue bounded host-owned work. Long-running operations return a durable command identifier and are queried through a read-only command-status operation.

### 3.2 Two-layer caller authorization

For every Binder invocation, the host:
1. Captures Binder calling UID before any identity-clearing or asynchronous dispatch.
2. Confirms the required signature permission.
3. Resolves UID-to-installed-package association; rejects ambiguous or unexpected package sets.
4. Confirms the exact approved `.paper` application ID.
5. Verifies installed signing certificate/current signing lineage against the host's pinned allowlist.
6. Authorizes the principal for the requested operation and API version.
7. Revalidates authorization at the host execution boundary for queued work; never trusts a caller-supplied package name or signer claim.

Unknown/revoked signer, package mismatch, permission denial, ambiguous UID mapping, unsupported contract or malformed DTO is rejected without side effects. Common signing identity is approved as a policy, but the actual installed certificate digest and lineage are still **OPEN / NOT VERIFIED**.

## 4. IPC v1 contract

### 4.1 Read-only operations

| Operation | Request | Response intent |
|---|---|---|
| `getHostStatus()` | Empty/version envelope | Host lifecycle, readiness, recovery and capability status; no filesystem path |
| `getRiskStatus()` | Empty/version envelope | Kill Switch state and bounded risk summary; no mutation capability |
| `getPaperPortfolio(query)` | Bounded pagination/filter | Read-only paper positions/equity summary |
| `getMarketDataSummary(query)` | Symbol/timeframe/window | Data freshness/coverage summary, not raw DB access |
| `getRecentAuditEvents(query)` | Bounded cursor/limit | Redacted audit projection with stable event IDs |
| `getCommandStatus(commandId)` | Opaque command ID | Durable state/result projection scoped to authenticated principal |

### 4.2 Paper-only mutations

| Operation | Request intent | Host-side mandatory gates |
|---|---|---|
| `submitPaperIntent(command)` | Submit a typed Strategy Core or AI intent for paper acceptance | Authentication, authorization, DTO bounds, durable idempotency, host readiness, recovery epoch, lease/fencing, Kill Switch, freshness, Shared Risk Engine, atomic paper-ledger + audit commit |
| `requestPaperCancel(command)` | Request cancellation of a paper position/order state | Same authorization/idempotency/readiness/fencing/Kill Switch and ledger consistency gates; cancellation semantics must be explicit and auditable |

No API v1 operation may alter risk limits, clear Kill Switch, change lease/fencing, run migrations, start Feeder, select DB paths, access raw candles, change canonical storage or initiate exchange execution. No live-order method exists. `AI_EXECUTION_ENABLED=false` remains mandatory.

### 4.3 Common envelope and DTO constraints

Every request carries:
- `contractVersion` (major/minor; unknown major rejected; additive minor fields only when explicitly declared optional),
- `requestId` (transport correlation only),
- operation-specific typed payload.

Every mutation additionally carries:
- `idempotencyKey` (opaque, bounded, scoped to authenticated principal + operation),
- `createdAt` and explicit expiry/deadline semantics,
- `source` enum: `STRATEGY_CORE` or `AI_INDEPENDENT`,
- stable strategy/model/config revision identifiers and signal timestamp,
- symbol, side, intent type and bounded numeric fields using decimal-safe representation (no binary floating-point money/quantity serialization).

Responses carry a typed status, durable command ID where applicable, stable error code, retryability classification and contract version. Never expose stack traces, paths, secrets, signer private material or internal DB details. Exact field widths, decimal scales, payload byte limits, collection limits and numeric ranges are **OPEN** and must be fixed before code implementation.

## 5. Idempotency and atomic transaction protocol

For each mutation:
1. Authenticate caller and authorize operation; validate contract version, DTO schema, bounds and idempotency-key syntax.
2. Apply transport quotas and per-principal rate limits.
3. Look up the durable idempotency record in the authenticated principal/operation scope.
4. If the same key and canonical payload has a terminal result, return that stored result without re-running current risk or mutating state. If the same key has a different canonical payload, return conflict.
5. If the record is nonterminal, reconcile it from durable host state; do not treat it as a new command.
6. For a genuinely new command only, check host readiness, recovery latch/epoch, lease/fencing generation, Kill Switch, market-data freshness and Shared Risk Engine limits.
7. In one host-owned database transaction, persist command/idempotency receipt, paper-ledger transition and required audit event. If atomicity cannot be achieved, implementation is blocked until a separately reviewed recovery protocol is specified.
8. Return the durable outcome; client timeout does not imply failure and must be resolved through command status or same-key retry.

The idempotency lookup occurs before dynamic risk/Kill Switch evaluation only for authenticated, authorized, valid requests, so a legitimate retry returns its original terminal outcome. It never grants authority to read another principal's command. Duplicate concurrent submissions must serialize at the durable uniqueness boundary.

## 6. Shared risk and strategy separation

- Strategy Core (RSI + ADX + Smart DCA) and independent AI strategy remain distinct signal producers.
- Both submit typed intents through the same host service; neither producer nor the client is allowed to bypass host policy.
- Host validates source attribution and applies one Shared Risk Engine, exposure/account limits, position limits, freshness gates and Kill Switch.
- Rejection is durable/audited with a stable reason; no paper-ledger transition occurs on rejection.
- AI may independently emit LONG/SHORT when Core has no signal, but this design does not authorize model deployment, strategy changes, live execution or weakening the shared risk gate.

## 7. Lifecycle, recovery and compatibility

- Host unavailable/not-ready/recovering/fenced => reject or report unavailable; never create client-side fallback storage/writer.
- Host process death during a command => client reconnects and queries/retries with the same idempotency key; host reconciles durable state before any re-execution.
- Host upgrades must preserve canonical DB ownership and schema migration authority. Client/host version skew is handled by an explicit compatibility matrix; unsupported major versions fail closed.
- Host uninstall/reinstall, app-data clear, signing-key rotation, downgrade and backup restore are destructive/authority-changing events and remain blocked pending a separate lifecycle/migration/recovery plan.
- No automatic host takeover by `.paper` or PC.

## 8. Fixture-only acceptance plan (future; not run here)

GitHub Actions may run isolated fixture tests only, with temporary fixture storage and explicit guards proving the canonical Android DB cannot be opened or created. Required suites:

1. Permission denied, wrong UID/package, wrong signer, revoked signer, ambiguous UID/package, and caller identity capture before asynchronous dispatch.
2. Explicit binding/contract version mismatch, malformed parcel/DTO, oversized fields, invalid decimals, unknown enums and unsupported operations.
3. Duplicate same-key/same-payload replay, same-key/different-payload conflict, concurrent duplicate requests, terminal replay after Kill Switch activation, and nonterminal crash reconciliation.
4. Atomicity: command/idempotency receipt + paper ledger + audit either all commit or all roll back.
5. Host not-ready, recovery latch, stale fencing generation, stale market data, Kill Switch active, risk limit exceeded and fail-closed responses.
6. Host process death before commit and after commit-before-response; client reconnect and same-key retry.
7. Shared Risk Engine parity for Strategy Core and independent AI; no alternate writer or shadow DB path.
8. Paper-only invariant: no exchange client/order method; `AI_EXECUTION_ENABLED=false`.
9. Static manifest checks: only approved service exported; signature permission required; no unintended exported components/provider; package IDs and signer declarations match approved inventory.

Fixture CI cannot certify Android Binder behavior, installed signer lineage or device process lifecycle. Those require a separately authorized device acceptance phase.
