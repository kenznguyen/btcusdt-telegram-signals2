## 2. Critical Android package boundary

P5.4.37 found the regular app and parallel `.paper` variant use distinct application IDs. Android app-private storage is sandboxed by application identity. Consequently:
- Two packages must not independently resolve their own `filesDir`/database path and claim those paths identify one shared physical SQLite file.
- Identical filenames, identical signing certificates or identical source code do not make app-private paths shared.
- A database path must never be passed to another package as a raw filesystem path or treated as a portable shared-storage contract.
- The selected topology is one physical SQLite file, but the package/process that owns it remains an OPEN implementation decision.

**Required invariant:** exactly one installed package/process owns the canonical SQLite file, migration authority, lease/fencing authority and canonical write capability. Other packages are clients, never alternate owners.

## 3. Packaging and access options — decision remains open

### Option A — One canonical application package (preferred design direction)
- The canonical host package contains the application-scoped composition root and owns the DB in its private storage.
- UI/build variants that must access local canonical state are delivered under the same application ID, so Android app-private storage identity remains the same across upgrades.
- Only one runtime coordinator/service is allowed to own canonical write lifecycle.
- Parallel UI surfaces are clients of the same in-process application graph; no second DB helper or independent writer.

Trade-off: variants cannot be installed side-by-side under different application IDs. This may conflict with the existing parallel-install requirement.

### Option B — Dedicated canonical host package plus authenticated IPC
- One designated package owns the DB and the only canonical writer.
- A separately installed `.paper` package communicates through a narrowly scoped bound service or ContentProvider protected by signature-level permission and caller/package verification.
- IPC exposes typed domain operations and read projections, not raw DB paths, arbitrary SQL, file descriptors or a general write connection.
- Host rejects callers that are not explicitly authorized; client cannot initialize schema, obtain lease authority or bypass the Shared Risk Engine/Kill Switch.
- Host unavailability means client is unavailable for local canonical operations; no local shadow DB fallback.

Trade-off: adds IPC lifecycle, authorization, version compatibility and host-install dependency. It needs separate threat-model and process-death testing.

### Option C — Remote API client only
- The separate `.paper` package continues to use the HTTPS API and server-side paper ledger.
- It does not claim to access the Android canonical SQLite file.
- Suitable only for remote projections/control explicitly authorized by server policy; it does not satisfy local shared-file access for that package.

**Not acceptable:** two packages each creating/opening a DB under their own sandbox and attempting to reconcile or synchronize them as if they were one canonical file.

No option is accepted by this document. The product owner must explicitly choose packaging/ownership before implementation.

## 4. Target dependency graph

The canonical host's application-scoped composition root is the sole construction authority:

```text
Android Application
  └── CanonicalRuntime (single process owner)
       ├── CanonicalDatabaseIdentity
       ├── ReadOnlyDatabaseVerifier
       ├── ExplicitMigrationCoordinator
       ├── SharedSqliteConnection / TransactionCoordinator
       ├── T0
       │    ├── CandleStore
       │    ├── FencedCandleWriteGateway
       │    ├── LeaseStore / LeaseCoordinator
       │    └── FeederRuntime (constructible only after activation gate)
       ├── Paper
       │    ├── PaperLedger
       │    ├── Order / Book / StrategyState repositories
       │    └── Audit repository
       ├── SharedRisk
       │    ├── RiskEngine
       │    ├── KillSwitch / durable risk latch
       │    └── Equity repository
       ├── RuntimeReadiness / RecoveryEpochGate
       └── Read-only query/export interfaces
```

All canonical repositories receive the same opaque database identity and transaction coordinator from this root. Modules must not:
- construct a new database by filename;
- accept independent production DB paths;
- create schema in ordinary constructors;
- silently fall back to SharedPreferences, memory, a second SQLite file or remote Paper API;
- create their own lease/risk/ledger writer;
- construct exchange/network clients before required local readiness checks pass.

The UI depends on read-only projections and explicit command interfaces. Strategy Core and independent AI submit intents to one Paper intent boundary; neither receives a database handle or execution authority.

## 5. Application and service lifecycle

1. **Application process start:** construct lightweight configuration and a single `CanonicalRuntime` owner. Do not start Feeder, connect to an exchange, create schema or write canonical state.
2. **Identity resolution:** resolve one opaque canonical DB identity using the one selected host package's private storage authority. Do not publish its absolute path in logs/evidence.
3. **Read-only preflight:** inspect existing DB presence, file identity, schema/migration registry, integrity, recovery latch and required metadata without schema mutation. Missing DB/schema is NOT READY, not an invitation to initialize implicitly.
4. **Explicit provisioning/migration:** only a separately authorized maintenance operation may create or migrate schema, with backup/recovery prerequisites and exclusive maintenance fencing. Normal app launch must not do this.
5. **Repository wiring:** inject the same DB identity and transaction boundary into T0, Lease, Paper Ledger, Risk, audit and equity repositories. Reject construction if any component reports a different identity.
6. **Fencing and recovery checks:** prove owner identity, current lease generation, external monotonic recovery epoch/maintenance latch and Kill Switch state. Unknown, stale or unavailable state fails closed.
7. **Readiness publication:** publish a typed readiness result only after all required checks succeed. UI may display NOT READY; it cannot override readiness.
8. **Writer activation:** Feeder/canonical write capability is separately enabled only after explicit owner approval and a successful activation procedure. Readiness alone does not authorize activation.
9. **Shutdown/process death:** stop accepting new writes, cancel/finish bounded work, release or expire lease safely, and persist no optimistic readiness. After restart, re-run all gates; never trust cached in-memory readiness.

## 6. Typed boundary contracts

Names below are conceptual contracts, not existing source classes or finalized Kotlin signatures.

| Contract | Responsibility | Must not do |
|---|---|---|
| `CanonicalDatabaseIdentity` | Opaque stable identity for the one physical DB; exposes safe equality/diagnostic token | Expose raw path to UI/client packages |
| `CanonicalPathAuthority` | Host-only resolver from Android app-private storage to DB identity | Accept per-module path overrides |
| `ReadOnlyDatabaseVerifier` | Read-only presence, integrity, schema and identity verification | Create file, table, singleton row or repair |
| `MigrationCoordinator` | Explicit ordered/checksummed migrations under maintenance fence | Run silently during ordinary app startup |
| `SharedTransactionCoordinator` | Owns connection/transaction boundaries and serializes fenced writes | Allow uncoordinated module connections for mutations |
| `WriterLeaseAuthority` | Owner, TTL, heartbeat, generation and fenced mutation authorization | Treat a stale/restored generation as current authority |
| `RecoveryEpochGate` | External monotonic epoch and maintenance-latch validation | Trust epoch solely from restored DB rows |
| `RuntimeReadiness` | Typed readiness and reasons per required subsystem | Infer ready from process alive or API reachable |
| `CanonicalWriteGateway` | Narrow commands requiring valid fencing and transaction | Expose arbitrary SQL or direct DB handles |
| `ReadOnlyProjection` | UI/PC-safe snapshots and query access | Mutate canonical state |
| `PaperIntentBoundary` | Idempotency, shared risk decision, ledger transition and audit | Bypass Kill Switch or split one state transition across commits |

All interfaces need explicit error states for missing, mismatched, corrupt, stale, unauthorized, busy and unsupported schema/contract versions.

## 7. Cross-domain transaction requirements

- A canonical candle mutation and its lease/fencing validation must be serialized against ownership changes; a check-then-write race is prohibited.
- Paper intent identity/idempotency, Shared Risk decision, Kill Switch check, accepted/rejected transition, order/state changes and audit event must follow one specified atomic transaction boundary.
- Risk latch and equity state must use the same canonical DB identity and be durable.
- Core and AI intent attribution must remain separate, while both pass through the exact same risk and paper acceptance path.
- No network call or AI inference may hold a SQLite write transaction open.
- Read projections must not mutate state or create missing schema.
- SQLite busy/locked, IO, disk-full, corruption or unknown transaction outcome must fail closed and require reconciliation before retrying non-idempotent commands.

## 8. Duplicate-writer prevention

- There is one owner package/process and one writer coordinator.
- Every writer command carries a current fencing generation; mutation is serialized with generation validation.
- Service start is idempotent within the owner process and cannot create a second FeederRuntime.
- A separately installed client package has no canonical write credential, DB path or lease capability.
- If multiple Android processes are ever required, process ownership and IPC arbitration must be designed explicitly; an in-memory singleton is not cross-process fencing.
- A second app instance, stale service, old owner or restored lease cannot write after a newer generation is granted.
- PC exports are immutable/read-only snapshots or controlled read interfaces, never writable access to the live Android DB.

## 9. Fixture-only acceptance gates before implementation can be considered complete

Run only in GitHub Actions with isolated temporary fixtures; never use a production path or device:
1. One root injects one identical DB identity to every canonical repository.
2. Mismatched identities fail before repository initialization, schema mutation or network client construction.
3. Two package/client abstractions cannot obtain canonical path, DB handle or writer capability.
4. Unauthorized IPC caller/package/signature/version is rejected (if IPC option is selected).
5. Client process death/reconnect cannot create a second owner or shadow DB.
6. Repeated service-start requests produce at most one writer coordinator.
7. Constructors and read-only verification do not create files/tables/rows.
8. Explicit migration is ordered, checksummed, exclusive and rejects unknown/mismatched history.
9. Lease validation and mutation are race-safe under stale-owner/new-generation interleavings.
10. Paper intent + risk + Kill Switch + ledger + audit is atomic and idempotent under duplicate/reordered requests.
11. Process restart, stale readiness and unknown commit outcome remain NOT READY until reconciled.
12. PC/client projection has no mutation capability.
13. Failure injection covers IO error, busy/locked DB, disk full, corrupt DB, missing recovery authority and unknown schema.
14. Tests assert paper-only behavior and `AI_EXECUTION_ENABLED=false`; no live exchange execution path is enabled.

Passing these fixture tests would certify only the tested interfaces/fixtures, not Android device behavior or production readiness.
