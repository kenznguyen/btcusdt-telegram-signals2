## 2. Architecture baseline — decisions already made

The following are treated as owner-approved constraints, not open design alternatives:

1. Existing regular package/variant is the canonical host.
2. Existing `.paper` package/variant is a separately installed client only.
3. IPC is an explicit Android Bound Service with a narrow typed Binder/AIDL contract.
4. The host declares a custom signature-level bind permission and verifies caller UID, package identity and installed signing identity on every call. Package allowlist and operation authorization remain separate from same-signer permission.
5. Regular host alone owns the one canonical Android SQLite file, schema/migrations, transaction coordinator, writer lease/fencing, readiness/recovery authority, Market Data, Paper Ledger, audit, Shared Risk Engine and Kill Switch.
6. Client never receives DB path, file descriptor, connection, SQL, lease token or writer credential; no second DB, fallback writer or independent ledger.
7. Strategy Core and independent AI remain separate signal producers. Both submit typed intents to the same host-side Shared Risk Engine and Kill Switch before a paper-ledger state transition.
8. Host unavailable, caller invalid, incompatible contract, stale fencing, uncertain transaction result or risk gate failure must fail closed.
9. PC is a read-only research/backtest consumer in the initial topology.
10. Runtime activation remains separately gated.

### ADR-002 documentation inconsistency to resolve

The ADR's earlier “Open implementation decisions” list still says the IPC mechanism is undecided, although its P5.4.41 owner addendum explicitly selects Bound Service + typed Binder/AIDL, regular host and shared signing identity. The addendum is authoritative. A documentation-only ADR reconciliation should mark those items resolved and retain only genuinely unresolved details; do not reopen the selected mechanism or package roles.

## 3. Ownership and capability boundaries

| Capability | Regular canonical host | `.paper` client | Remote service/API |
|---|---|---|---|
| Canonical SQLite open/create/migrate/write | Sole owner | Forbidden | Not a second canonical owner |
| Market Data ingestion and durable candle writes | Host-owned orchestration and storage | Read projections only | May provide external market data only through an explicitly approved source adapter |
| Paper Ledger state and order lifecycle | Sole owner | Typed commands/read projections | Must not maintain a competing canonical ledger |
| Shared Risk Engine / Kill Switch | Sole authority; re-check on every mutating command | Display state; cannot override | No bypass or alternate acceptance path |
| Lease/fencing/recovery readiness | Sole authority | No lease credentials | No alternate writer lease |
| Strategy Core / AI inference | May host or receive typed signal producers; ownership of inference process remains a later deployment decision | May display/submit a signal intent only through IPC | Remote inference is not automatically authorized as a writer |
| Dashboard and noncanonical research telemetry | Exposes approved read-only projection | Displays local canonical projections | Remote read-only research/analytics may remain separate if clearly labeled noncanonical |
| Audit | Appends durable host-side audit in the same accepted state transition | Reads approved audit projection | Remote audit cannot replace host audit |

**Critical distinction:** remote API availability is not evidence of canonical local state. Any remote dashboard or research endpoint must be labeled as remote/noncanonical unless it is explicitly backed by the host's approved canonical data and consistency contract.

## 4. Existing remote Paper API disposition

P5.4.65 observed that `FiveLayerPanel` calls HTTPS operations for `paper/evaluate`, pause, kill, reset and cancel, plus read endpoints for paper, audit, equity, signals, candles, order book, quality and system/intelligence.

### Must migrate behind host IPC for canonical local Paper operation

- Submit/evaluate an intent from Strategy Core or AI.
- Pause/resume Paper.
- Enable Kill Switch and request reset.
- Cancel a paper order.
- Read canonical Paper state, open orders, positions, equity/ledger history, risk-control state and canonical audit.
- Any future manual adjustment or Paper Ledger mutation.

All mutating operations must be re-authorized by the host at execution time, validate host readiness and fencing generation, and pass the shared risk policy. Kill Switch reset requires explicit confirmation and host-side policy; client confirmation alone is insufficient.

### May remain remote, subject to explicit separation

- Remote service health and deployment status.
- Remote research/backtest/FreqAI analytics that are not presented as the Android canonical Paper Ledger.
- External market-data provider access, if later approved and invoked by the canonical host's source adapter rather than a client-side alternate writer.
- Read-only remote telemetry, clearly labeled with its source, timestamp and noncanonical status.

### Prohibited transitional behavior

- Do not dual-write Paper state to Android SQLite and remote server ledger.
- Do not automatically fall back to HTTPS mutation when host IPC is unavailable.
- Do not interpret a successful remote HTTP response as local canonical acceptance.
- Do not silently redirect a Core/AI intent to a remote writer.
- Do not remove remote endpoints until their consumer inventory and migration compatibility are recorded; remote endpoint deprecation is a separate, evidence-backed step.

## 5. Ordered implementation slices and gates

The slices below are a proposed dependency order. They are not authorization to implement.

### Slice 0 — Contract and ADR reconciliation (documentation/source-only)

Deliverables:
- Reconcile ADR-002's stale open-decision text against P5.4.41 owner addendum.
- Freeze package roles, one-host/one-writer boundary, command/read-projection boundary and forbidden capabilities.
- Record version-skew and compatibility policy as an explicit decision, not an implicit default.
- Inventory every current remote Paper API consumer and classify read-only vs mutating.

Acceptance:
- No contradictory statement remains about IPC primitive or host/client roles.
- Every current Paper API operation has an owner and disposition.
- No unresolved requirement is silently converted into an implementation assumption.

### Slice 1 — Host application composition and capability boundary

Design/implementation target:
- A single application-scoped canonical host composition root, created once per host process.
- Explicit lifecycle/readiness state machine; no Activity-owned DB or writer lifetime.
- One database identity authority and one migration authority, instantiated only by host.
- Explicitly separate existing Chart Pro monitoring service from T0 Feeder/canonical storage; do not repurpose `StrategyMonitorService` by assumption.
- Host startup must not open/create the canonical DB until the relevant runtime gate is approved.

Fixture acceptance:
- Exactly one declared canonical-host owner.
- Client source sets cannot instantiate database, migration, lease or ledger owners.
- No Activity recreation creates a second host/repository/writer.
- Host-not-ready and startup-in-progress are not reported as ready.

### Slice 2 — Authenticated Bound Service contract

Design/implementation target:
- Explicit component binding to the regular host package; no implicit intent resolution.
- Custom signature-level permission on the exported service.
- Typed AIDL/Binder request/response/error contract; API version and capability negotiation.
- Host verifies calling UID, resolves UID-to-package mapping, checks exact approved client package and installed signer/lineage, then authorizes the specific operation.
- Revalidate identity/authorization on each transaction; never trust a package name supplied in the payload.
- Bounded request size, execution timeout, cancellation semantics and deterministic error categories.
- No generic execute, raw SQL, arbitrary path, file descriptor, DB handle, lease token or writer credential method.

Fixture acceptance:
- Untrusted UID, wrong package, wrong signer, missing permission and unknown operation all fail closed.
- Explicit binding only; no accidental service exposure.
- Unknown API version/capability mismatch fails closed without a remote-write fallback.
- Contract tests cover success, denial, malformed payload, timeout, host death, reconnect and duplicate request behavior.

### Slice 3 — Canonical storage, transaction, lease and recovery contracts

Not ready for schema coding until ADR-001 D2–D7 decisions are resolved.

Required design decisions:
- Canonical DB filename/path identity and app-private ownership (path must not be probed on a device during this specification).
- SQLite driver, journal/WAL mode, durability and checkpoint policy.
- Schema versioning, migration ownership, forward/backward compatibility and failed-migration recovery.
- Transaction boundaries across Market Data, Paper Ledger, risk decision, audit and idempotency.
- Lease scope, owner identity, TTL, heartbeat, fencing generation, stale-writer rejection and process-death behavior.
- Recovery readiness state and the exact rule for blocking writes after incomplete restore/recovery.
- Backup/restore manifest, epoch/fencing reset and D2–D7 acceptance before T0-D.

Fixture acceptance:
- Same logical event cannot partially commit ledger state without corresponding risk/audit/idempotency state.
- Stale fencing generation is rejected.
- Lease loss prevents new mutations; no client takeover.
- Recovery-in-progress blocks all canonical mutations.
- Migration failure leaves host not-ready and does not create a second store.

### Slice 4 — Shared Risk Engine and Dual-Strategy intent path

Design/implementation target:
- Separate typed sources: `STRATEGY_CORE` and `AI_STRATEGY`; do not merge their signal provenance.
- Both produce an intent envelope with stable intent ID, source, symbol, side, timeframe/context reference, generated-at/expiry, strategy/model version and evidence references.
- Host validates freshness, symbol/side/quantity/notional bounds, position/exposure constraints, duplicate identity, data quality, pause/kill state, daily loss and all configured risk limits.
- Risk decision is authoritative only when calculated by the host's shared risk engine; client-provided “approved” flags are ignored.
- Core retains RSI + ADX + Smart DCA logic. AI may independently emit LONG/SHORT even when Core has no signal, but AI does not bypass shared risk.
- AI execution remains disabled; accepted outcomes are signals and paper-only state transitions.

Fixture acceptance:
- Core intent and AI intent traverse the exact same risk gate.
- AI intent can be independently evaluated when Core emits no signal.
- Kill Switch and Pause block risk-increasing intents from both sources.
- Risk-reducing/cancel operations follow explicitly defined safe-command policy.
- Duplicate intent IDs are idempotent; same ID with changed payload is rejected.
- Risk rejection creates no ledger position/order mutation but records an auditable decision.
- No path can set `AI_EXECUTION_ENABLED=true` or issue live exchange orders.

### Slice 5 — Client migration and remote API containment

Design/implementation target:
- Replace canonical Paper mutations in `FiveLayerPanel` with typed IPC client calls.
- Replace canonical Paper/ledger/risk/audit reads with host projections.
- Surface explicit states: host absent, permission denied, incompatible host, host not ready, risk rejected, request pending/unknown, and canonical result.
- Keep remote analytics/health only in separately labeled sections and never as a fallback for local Paper.
- Define a compatibility/deprecation plan for existing HTTPS mutating endpoints and inventory external callers before removal.

Fixture acceptance:
- Static checks ensure no client-side HTTP mutator remains reachable from canonical Paper controls.
- Host-unavailable test proves no HTTP mutation fallback.
- UI cannot claim local success until host returns a confirmed transaction result.
- Remote telemetry is visibly distinguished from canonical local state.

### Slice 6 — GitHub Actions fixture/static acceptance

GitHub Actions may validate source and fixtures without a physical Android device or canonical DB.

Required jobs/tests:
- package IDs and regular/parallel source-set ownership.
- merged-manifest export/permission/service declarations using build-time manifest processing only.
- AIDL/Binder contract compile and contract tests.
- UID/package/signer authorization unit tests with fixtures.
- no raw DB/path/FD/SQL/lease capability exposed to client.
- exactly one DB/migration/lease/ledger owner in source graph.
- no client HTTP paper mutation fallback.
- Core and AI both call one Shared Risk Engine contract.
- idempotency, duplicate payload mismatch, stale fencing and fail-closed fixture cases.
- paper-only invariant and `AI_EXECUTION_ENABLED=false`.
- exact source SHA, workflow run, job IDs and artifact metadata recorded for each acceptance run.

GitHub Actions cannot prove installed signer identity, Android filesystem path semantics, process lifecycle on a real device, actual Binder permission enforcement under installed packages, Doze behavior or canonical DB integrity. Those remain device gates.

### Slice 7 — Android device acceptance (future, separately authorized)

Only after source/fixture acceptance:
1. Request narrowly scoped permission for read-only package/signing/manifest inventory.
2. Separately request read-only app-private path/store identity inspection.
3. Do not open/create/write canonical DB until separate explicit authorization.
4. Do not start Feeder, connect exchange/data source, sync, backup/restore or activate writer without their own scoped authorization.
5. T0-B must pass before T0-C; D2–D7 and separate restore authorization must pass before T0-D.

## 6. Unresolved decisions that block storage implementation

The following must be decided explicitly; do not guess in code:

1. ADR-001 D2–D7 full list: exact accepted/rejected policy for DB identity, schema/migration, transactions, lease/fencing, recovery and backup/restore.
2. SQLite library/driver and minimum supported SQLite version.
3. WAL/journal and checkpoint policy under Android process death and storage pressure.
4. Exact atomicity boundary for candle ingestion, paper intent decision, ledger mutation, audit and idempotency.
5. Lease persistence model, clock source, fencing generation monotonicity and stale owner recovery.
6. Host readiness state machine and startup/migration/recovery transitions.
7. IPC contract version compatibility for host/client upgrades and rollback.
8. Client signer pinning representation, certificate rotation/lineage policy and recovery if release key rotates.
9. Whether Core/AI inference executes inside host or submits signed/validated typed intents from another process; either way only host may authorize canonical mutations.
10. Which remote read-only endpoints remain useful and their noncanonical labeling/retention contract.
