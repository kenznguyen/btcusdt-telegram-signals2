This specification does not choose the host application ID, concrete IPC primitive, serialization library or production package configuration. It does not authorize implementation or runtime activation.

## 2. Architecture and trust boundaries

### 2.1 Components

1. **Canonical Host** — one designated Android package/process. Sole owner of the one physical canonical SQLite file shared by T0 Market Data and Paper Ledger. Owns path resolution, schema/migration authority, transaction coordination, lease/fencing, recovery/readiness gates, Shared Risk Engine, Kill Switch and canonical writes.
2. **.paper Client** — separately installed UI/client package. May request explicitly exposed typed operations and consume bounded read-only projections. It is not a database owner, writer, lease owner or risk-control authority.
3. **Android OS / Binder identity** — trusted platform boundary used to establish the calling UID and enforce a signature-level permission where the selected IPC primitive supports it.
4. **PC research consumer** — separate read-only research/backtest environment. Not an IPC writer and not a canonical owner.
5. **External exchange/network and strategy producers** — untrusted input sources. Their data or intents do not receive authority merely by reaching the host.

### 2.2 Trust zones

- **Zone H — Host private boundary:** canonical database, path, DB handles, migration engine, lease/fencing state, recovery controls, risk engine, Kill Switch and write transaction coordinator.
- **Zone I — IPC boundary:** all incoming client requests and outgoing projections cross a narrow, authenticated, versioned typed interface. Treat every request field as untrusted even after caller authentication.
- **Zone C — Client boundary:** UI state, cached projections, user input and local preferences. Client is not trusted to enforce risk, validate canonical state or preserve idempotency.
- **Zone X — External inputs:** market data, strategy outputs and PC research results. Validate provenance, freshness, bounds and schema before use.

The host must not treat the client UI, package-name strings, client timestamps, client-computed risk decisions, client sequence numbers or cached readiness as authoritative.

## 3. Threat actors and security objectives

| Threat actor / failure | Example capability | Required security objective |
|---|---|---|
| Uninstalled or unrelated app | Attempts to bind/call exported component | Reject before domain operation |
| Same-device malicious app | Forges package name or replays captured command | Derive caller identity from OS; authorize each call; idempotency |
| Repackaged or resigned client | Uses expected package name but untrusted certificate | Reject signing identity not in active trust policy |
| Stale but formerly trusted client | Calls after signing-key rotation/revocation | Enforce current allowlist and contract compatibility |
| Compromised/buggy .paper client | Sends malformed, oversized, repeated or out-of-order commands | Strict schema validation, quotas, rate limits and host-side policy |
| Compromised client UI | Attempts to bypass Kill Switch or submit oversized exposure | Host recomputes all risk and position limits |
| Replay/network-style IPC retry | Resubmits after timeout or process death | Durable idempotency and outcome reconciliation |
| Host crash during mutation | Client cannot tell whether transaction committed | Explicit transaction-unknown state and status lookup |
| Host upgrade/version skew | Client speaks unsupported contract | Negotiated compatibility; fail closed for mutations |
| Local data rollback/restore | Old lease/recovery state reappears | External/non-rollbackable recovery epoch and fencing gate |
| Denial of service | Excessive Binder calls or large payloads | Bounded payloads, per-UID quotas, bounded work and safe rejection |
| Information disclosure | Client requests private path, DB metadata or secrets | Explicit projection allowlist; no generic query interface |

Security objectives:
- Preserve one physical canonical DB and one writer authority.
- Prevent unauthorized reads and every unauthorized mutation.
- Prevent client-side bypass of Shared Risk Engine/Kill Switch.
- Prevent duplicate paper mutations from retries.
- Avoid disclosing paths, DB handles, lease credentials, secrets or unrelated private state.
- Fail closed whenever identity, compatibility, readiness, fencing or transaction outcome is uncertain.

## 4. Caller authentication and authorization

### 4.1 Required caller identity

For every IPC entry point, the host must establish the caller from Android platform state, not from request data:

1. Read the Binder calling UID while still in the Binder transaction context.
2. Resolve package name(s) associated with that UID using PackageManager APIs.
3. Require the expected client package identity and reject ambiguous/unexpected package sets according to reviewed policy. Do not accept a caller-supplied package name as proof.
4. Resolve the installed package signing identity using platform signing-certificate APIs appropriate to the minimum supported Android API level.
5. Compare the verified signer/current signing lineage against an explicit allowlist and rotation policy.
6. Enforce a signature-level permission on the exported IPC surface where supported. Permission enforcement supplements, but does not replace, host-side caller verification and operation authorization.
7. Construct an immutable verified-principal object for downstream dispatch. If work moves to another thread or queue, capture verified identity before leaving the Binder call context; never depend on a later Binder identity lookup.
8. Apply operation-level authorization on every call. Authentication proves who called; it does not prove the caller may perform every operation.

The exact APIs and compatibility behavior must be verified against the selected Android minimum SDK and IPC primitive before implementation.

### 4.2 Signing trust and rotation

- Maintain an explicit allowlist containing expected package ID and approved signer certificate digest(s), with documented active/revoked state and effective version.
- Define certificate rotation as an explicit trust-policy update. Support signing-certificate lineage only when verified by Android platform APIs and accepted by the owner-controlled rotation policy.
- Do not accept a new certificate solely because the package name is unchanged.
- Revocation must take effect for new calls without relying on a client update.
- Unknown, malformed, expired or revoked signer identity is denied.
- Never place private signing keys, keystore material or reusable authentication secrets in the client package or IPC payload.
- Record policy version and verified principal in security audit events without logging sensitive tokens or unnecessary personal data.

### 4.3 Permission and exported-component policy

- Any cross-package IPC component must declare the narrowest viable exported surface.
- If a bound service is selected, require explicit component binding and a signature-level permission for binding; reject implicit/untrusted entry points.
- If a ContentProvider is selected, restrict authorities, exported state, permissions and URI/path grants to the smallest required set. Do not expose generic CRUD or filesystem semantics.
- No component may be exported without explicit threat-model review and an unauthorized-caller test.
- Do not use broad permissions such as unrestricted shared-storage read/write.
- Avoid granting URI/file-descriptor access to the canonical database or its WAL/SHM files.
- Keep diagnostics separate from production mutation interface and free of secrets.
- Exact primitive and manifest declarations remain OPEN; this document does not select one.

## 5. IPC surface: typed operations only

### 5.1 Forbidden capabilities

The client must never receive or invoke:
- canonical absolute path, filename or private storage location;
- SQLite connection, cursor, raw database handle, file descriptor or WAL/SHM access;
- arbitrary SQL, table names, generic query expressions or generic CRUD;
- lease token, fencing credential, writer capability or recovery-epoch authority;
- direct risk-state mutation, Kill Switch clearing or bypass flag;
- arbitrary filesystem access, reflection-based method dispatch or generic command execution;
- live exchange order placement or any real-order capability.

No API may accept caller-selected table, SQL fragment, filesystem path, class name or unrestricted serialized object.

### 5.2 Read-only projections

Candidate bounded projection methods (names illustrative, not frozen API symbols):

- getHostStatus() — coarse state enum, contract version, readiness reason codes and server time. Must not expose path, DB credentials or internal stack traces.
- getMarketDataSummary(query) — bounded symbol/timeframe cursor and data-quality summary; closed-candle semantics explicit.
- getPaperPortfolio() — bounded paper balances, exposure, open-position summaries and equity snapshot.
- getRiskStatus() — Kill Switch state, risk limits and rejection reason codes; read-only.
- getRecentAuditEvents(query) — bounded, redacted, paginated audit projection with stable cursor.
- getCommandStatus(idempotencyKey) — status of a command submitted by the authenticated principal, subject to ownership and retention policy.

Every projection must define explicit DTO schema and maximum response size; pagination/limit bounds and stable ordering; timestamp units/timezone and stale-data indicators; redaction policy and field-level authorization; and behavior when host is starting, recovering, degraded or unavailable.

A projection is not a promise that the underlying service is production-ready.

### 5.3 Typed domain commands

Candidate mutation methods (names illustrative):

- submitPaperIntent(command) — submit a LONG/SHORT paper intent from a recognized source (Strategy Core or independent AI) for host-side risk evaluation.
- requestPaperCancel(command) — cancel a cancellable paper order/intent under host state rules.
- requestUserRiskSettingChange(command) — only if future owner-approved policy explicitly delegates a bounded setting; never permits clearing a latched Kill Switch or weakening immutable safety caps.
- acknowledgeClientObservation(command) — optional, non-authoritative client acknowledgement with bounded semantics.

All commands require a unique idempotency key, typed source/intent, contract version, bounded fields and authenticated principal. The host derives authoritative receipt time, sequence, risk result and ledger state. Client-provided price, ROE, exposure, account equity, leverage or risk approval is advisory/untrusted and must be recomputed from canonical host state and approved market data.

Core and AI remain independent signal sources, but every accepted paper intent passes through the same host-side Shared Risk Engine and Kill Switch. AI cannot call a privileged alternate mutation route.

### 5.4 Command processing order

For every mutation, the host must process in this order:

1. Authenticate platform caller and authorize operation.
2. Validate envelope size, schema version, field ranges, enum values and required identifiers.
3. Enforce per-principal rate/quotas and reject stale/expired commands.
4. Check host lifecycle and canonical readiness.
5. Check maintenance/recovery latch, recovery epoch and current lease/fencing generation.
6. Check Kill Switch and global risk policy.
7. Resolve idempotency key and prior command outcome.
8. Recompute risk using canonical host-side state; reject if data is stale or required state is unknown.
9. Perform one atomic domain transaction covering command receipt, resulting paper state and audit evidence as required by ledger contract.
10. Return a typed result with command ID, final/intermediate state and authoritative host timestamp.

The exact atomic table set and schema are implementation-design items still OPEN. No mutation may proceed if any mandatory gate cannot be evaluated.

## 6. Contract envelope and versioning

Every request should use a versioned envelope conceptually containing:
- contractMajor, contractMinor;
- requestId (unique transport request identifier);
- idempotencyKey (stable across retries of same logical mutation);
- issuedAt and optional expiresAt (client hints; host clock is authoritative);
- operation from a closed enum;
- typed payload.

Every response should contain:
- negotiated/served contract version;
- requestId and, for mutations, commandId;
- closed status enum;
- typed result or structured error code;
- authoritative host timestamp;
- optional retry guidance only where safe.

Rules:
- Unknown major version: reject; no best-effort mutation.
- Unknown minor fields: reject unless explicitly specified as safely ignorable metadata. Do not silently ignore unknown mutation semantics.
- Additive minor evolution must preserve old field meaning and default behavior.
- Breaking changes require a major version and explicit host/client compatibility matrix.
- Host exposes supported version range through read-only handshake before any mutation.
- If no mutually supported version exists, reads may be restricted to a minimal incompatibility status; mutations are denied.
- Serialization must be deterministic enough for validation and bounded in size/depth. Avoid polymorphic arbitrary object deserialization.
- Exact serialization technology remains OPEN.

## 7. Timeouts, retries, idempotency and transaction uncertainty

### 7.1 Timeout behavior

- Each operation class defines a bounded deadline. Binder entry points must not perform long-running market-data work or blocking external network calls.
- Expensive work is rejected or queued through a bounded host-owned worker after authentication and durable request registration.
- Client timeout means OUTCOME UNKNOWN, not failure and not permission to submit a new logical command.
- No automatic retry with a new idempotency key.

### 7.2 Idempotency

- Idempotency key is generated once per logical command and reused unchanged for every retry.
- Host scopes uniqueness by authenticated principal/client identity and operation domain, with durable retention policy.
- Same key + same canonical payload returns recorded state/result and must not repeat mutation.
- Same key + different payload returns conflict and must not mutate.
- Duplicate concurrent requests converge on one durable command record and one state transition.
- Idempotency record and ledger mutation must commit atomically, or a rigorously specified recoverable transaction protocol must provide equivalent guarantees.
- Idempotency retention must exceed maximum supported client retry/reconnect horizon; exact duration is OPEN and owner-approved.

### 7.3 Transaction-unknown reconciliation

Use explicit states such as:
- RECEIVED
- VALIDATING
- REJECTED
- COMMITTED
- FAILED_NO_COMMIT
- OUTCOME_UNKNOWN (temporary reconciliation state only; not a terminal assertion)

After timeout or host death, client calls getCommandStatus(idempotencyKey) using the original key. Host reconciles against durable command/ledger record. If it cannot prove commit or no-commit, it keeps the operation unavailable and fails closed; it must not blindly replay a non-idempotent mutation.

## 8. Host lifecycle, process death and upgrade

- Host lifecycle states must distinguish at least STOPPED, STARTING, NOT_READY, READY_READ_ONLY, READY_WRITER, RECOVERING, DEGRADED and INCOMPATIBLE.
- Process start alone must not create/migrate canonical DB, start Feeder, connect to exchange or enable writer capability.
- Readiness and writer activation are separate gates. Writer activation requires separate explicit authorization and successful fencing/recovery/Kill Switch checks.
- If host dies, client marks canonical operations unavailable and retains only non-authoritative UI state. It must not create a local shadow database or become a writer.
- On reconnect, client performs fresh handshake and re-authentication; it must not trust cached READY state.
- Host revalidates DB identity, schema/migration state, recovery epoch, fencing generation and Kill Switch before returning READY.
- During host upgrade, incompatible client/host pairs fail closed for mutations. No automatic schema migration is authorized by a client request.
- If host package is absent, downgraded, replaced, signer-revoked or in recovery, client reports a precise safe reason code and offers no alternate writer path.
- Host must prevent multiple host processes or duplicate service instances from obtaining writer authority. Exact process model and Android lifecycle mechanism remain OPEN.

## 9. Audit, privacy and operational safeguards

- Record caller principal, operation, request/command ID, contract version, decision, reason code, host timestamp, fencing/recovery generation and transaction outcome for every mutation attempt.
- Record authorization denials and rate-limit events without logging secrets or full sensitive payloads.
- Audit must be append-oriented and protected by host-side write authority. Client cannot edit or delete audit history.
- Bound request/response sizes, collection limits, pagination, concurrent in-flight calls and per-UID request rates.
- Validate every string length, numeric range, enum and timestamp. Reject NaN/infinity and invalid decimal encodings.
- Avoid returning stack traces, raw exception messages, internal paths, signer certificate material beyond approved diagnostic digest, or SQL details to clients.
- Security logs and domain audit events must not be confused; define retention and redaction separately.

## 10. Fixture-only GitHub Actions acceptance plan

This is a proposed plan, not an executed test suite. It must use synthetic identities, fake package/signature verifiers and isolated temporary fixture stores. Tests must never access Android canonical DB or device.

| Test group | Fixture cases | Required result |
|---|---|---|
| Caller authentication | expected UID/package/signer; wrong UID; forged package string; wrong signer; unknown signer; revoked signer | Only verified, currently trusted principal accepted |
| Permission boundary | missing signature permission; unauthorized exported-component caller; implicit/unexpected entry point | Denied before domain handler |
| Contract validation | unsupported major; malformed envelope; unknown operation; oversized payload; invalid numeric/time fields | Typed rejection; no state change |
| Authorization | read-only principal attempts mutation; client attempts Kill Switch clear; client attempts lease/path/SQL operation | Denied; no privileged capability exposed |
| Risk enforcement | Core and AI intent; Kill Switch active; stale market data; exposure cap exceeded; invalid side/size | Both sources use same risk path; unsafe intent rejected |
| Idempotency | same key/same payload; same key/different payload; concurrent duplicate; retry after committed response lost | One mutation maximum; deterministic status |
| Crash/uncertainty | crash before commit; crash after commit before response; status reconciliation | No blind duplicate; durable result recovered or fail-closed unknown |
| Version skew | supported minor; unsupported major; host newer/older than client | Explicit compatibility behavior; mutations denied when incompatible |
| Lifecycle | host stopped/starting/recovering/degraded; stale cached READY; reconnect | No mutation until fresh host readiness and fencing gates pass |
| Information disclosure | request for path/handle/FD/SQL/lease token; malformed projection query | No forbidden data/capability returned |
| Abuse controls | rate flood; deep/large payload; repeated invalid calls | Bounded rejection; host remains isolated and safe |

Acceptance criteria:
- Each denied request leaves fixture canonical state unchanged.
- No fixture test can instantiate production storage paths or start Feeder/exchange adapters.
- Every accepted mutation has one durable command record, one expected ledger transition and an audit record.
- Duplicate/replayed commands do not create additional transitions.
- Every uncertain outcome can be reconciled by the original idempotency key or remains fail-closed.
- CI report states fixture-only and explicitly disclaims Android device, Binder, signing integration and production readiness.

No GitHub Actions workflow is run as part of P5.4.40.

## 11. Residual risks and unresolved decisions

The following remain OPEN and must be resolved before implementation:
- canonical host application ID and which existing variant becomes host;
- concrete IPC primitive and its Android API-level behavior;
- exact manifest permission declaration and exported component configuration;
- signing certificate digest source, rotation, revocation and release-key operational policy;
- caller allowlist storage/update authority;
- DTO field definitions, serialization technology and schema registry;
- command idempotency persistence schema and retention duration;
- transaction boundary for command receipt + ledger + audit;
- timeout/deadline values, rate limits and payload-size budgets;
- host process/service lifecycle and multi-process prevention;
- contract compatibility matrix and upgrade/downgrade policy;
- audit retention, privacy and redaction policy;
- device/Binder/signing integration acceptance plan and required approvals.

Residual threats even after implementation include a compromised canonical host, Android OS compromise/root, signing-key compromise, rollback of any supposedly external recovery authority, denial of service and bugs in host-side risk/ledger logic. IPC authentication alone cannot eliminate them.
