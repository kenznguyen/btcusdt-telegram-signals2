## 1. Objective

Define one authoritative, tamper-evident schema-version contract for the canonical Android SQLite file shared by Market Data, Paper Ledger, Risk State and audit state.

The contract must let a read-only verifier answer:
- Which exact migration set is applied?
- Are migration identities, order and checksums complete and unchanged?
- Does the physical schema agree with the recorded migration history?
- Is the database known, unknown, partially migrated or inconsistent?

A schema version is not a row count, file timestamp, app version, or a fixture-only value.

## 3. Proposed D4 decision

### D4.1 — One database-wide migration authority

Create one authoritative migration registry for the **entire shared SQLite file**, not separate competing registries owned by Market Data and Paper Ledger.

Every schema-changing migration across all included domains is represented in one ordered catalog. Each record has:
- immutable `migration_id`;
- strictly increasing integer `sequence`;
- `owner_domain` (for example, `market_data`, `paper_ledger`, `risk`, `shared`);
- `checksum_sha256` of the exact immutable migration bytes;
- `applied_at` as diagnostic metadata only;
- optional declared minimum application/reader compatibility metadata, if separately standardized.

The proposed registry name is `schema_migrations` in SQLite's main database. Its exact DDL and column types are implementation details, not approved here. Migration identity and sequence must be unique. Registry history is append-only; an applied row is never edited or deleted to make verification pass.

### D4.2 — Migration bytes and order are immutable

- Migration files are immutable after release.
- A correction is a new forward migration, never an edit to an already-applied migration.
- The checksum is computed from the exact canonical migration file bytes; line-ending or encoding conversion must not silently alter the identity.
- The registry must reject a known ID with a different checksum, duplicate sequence, missing sequence in a required contiguous series, unknown applied ID, or unexpected migration ordering.
- A manifest records the migration authority identifier, latest sequence, and ordered applied migration ID/checksum set (or a deterministic digest of that exact ordered set). The manifest's schema version must be derived from this authority, not copied from an app build number.

### D4.3 — Transactional application

- Migrations run only through an explicit maintenance/provisioning command owned by the canonical host.
- Schema changes and insertion of the corresponding registry row commit in the same SQLite transaction.
- A failed migration rolls back both schema changes and registry advancement; never record a migration as applied before its DDL succeeds.
- No constructor, ordinary read, ordinary write, startup health check or verifier may apply migrations implicitly.
- A migration runner must acquire the database's exclusive migration/write authority before changing schema and must reject concurrent migration attempts.
- The runner must validate the previous migration chain and source DB identity before applying the next migration.
- Do not promise automatic downgrade. Recovery is restore from a verified backup or a separately reviewed forward-fix migration.

SQLite DDL transaction behavior, supported SQLite runtime version, lock mode, busy handling and transaction wrapper must be proven in implementation tests before this contract can be claimed operational.

### D4.4 — `PRAGMA user_version` is not the authority

Recommended policy: the migration registry is authoritative. `PRAGMA user_version` may be maintained as a compatibility mirror only if every migration updates it in the same transaction and a verifier checks exact equality with the registry-derived sequence.

If it is not maintained transactionally, it must be ignored for acceptance and reported only as diagnostic metadata. No module may independently set it. A mismatch must fail closed; the verifier must not repair it.

### D4.5 — Legacy/unversioned database adoption

A pre-existing database without a migration registry must be classified as **LEGACY / UNVERSIONED**, not assumed to be schema version zero or the latest version.

Adoption requires a separately reviewed, read-only inventory of:
- SQLite identity and integrity;
- exact schema objects and definitions;
- required tables, indexes, triggers and constraints;
- existing domain data compatibility;
- legacy Paper Ledger state and audit shape;
- exact baseline migration/checksum selected.

Only after that inventory and an explicit owner-approved adoption plan may a controlled migration operation record a baseline. No auto-detection, auto-stamping, schema repair, table creation or data rewrite during read/verify/startup.

### D4.6 — Read-only verification and fail-closed outcomes

The verifier opens an existing file read-only and performs no writes. It must not call `CandleStore.initialize_schema()`, `PaperLedger.__init__`, risk/equity ensure helpers or any constructor that creates tables or seeds state.

Proposed outcomes:
- `VERIFIED`: registry chain, checksums, expected schema objects and manifest declaration agree.
- `LEGACY_UNVERSIONED`: no accepted migration authority is present; no version inferred.
- `MISSING_REGISTRY`: registry absent where a versioned database is required.
- `CHECKSUM_MISMATCH`: migration bytes differ from recorded checksum.
- `SEQUENCE_GAP_OR_DUPLICATE`: migration order is incomplete or ambiguous.
- `UNKNOWN_MIGRATION`: registry references an unknown migration.
- `SCHEMA_DRIFT`: physical schema differs from the expected result of the applied migration set.
- `INCOMPLETE_OR_UNCERTAIN`: interrupted or ambiguous migration result requiring offline reconciliation.

Every outcome other than `VERIFIED` blocks migration-dependent writers and snapshot acceptance. The verifier never repairs or stamps a database.

### D4.7 — D3 snapshot integration

The D3 snapshot's same-read-transaction manifest metadata must include the D4 migration authority identity and the exact applied migration-chain evidence. The schema registry is inside the shared SQLite file and therefore part of the D3 snapshot.

The D3 physical SHA-256 identifies the captured bytes; D4 migration-chain evidence identifies the declared schema evolution. Neither substitutes for the other. Snapshot verification also compares physical schema objects with the expected migration result.

D4 does not extend D3's boundary to external lease authority, restore epoch, Kill Switch/recovery latch, app configuration or exchange state.

## 4. Alternatives considered

### A. Separate per-domain SQLite migration registries

Rejected as the preferred design for this topology. A single physical SQLite file and cross-domain transactions require one unambiguous schema history. Independent registries can disagree on global ordering and shared objects.

### B. `PRAGMA user_version` alone

Not sufficient. It is a single integer with no immutable migration IDs, checksums, ownership, or full history. It becomes authoritative only if a formally owned migration system updates and verifies it transactionally; the proposed registry is stronger and remains the source of truth.

### C. App version or build number

Rejected. App releases and database schema evolution are different lifecycles; an app may support multiple schema versions and a schema may remain unchanged across multiple app builds.

### D. Infer version from table presence or row counts

Rejected. Presence/absence does not prove migration order or checksum; row counts are data-dependent and do not identify schema history.

### E. Reuse PostgreSQL migration registry as proof for SQLite

Rejected. The existing PostgreSQL registry applies only to that backend and does not establish SQLite schema state.

## 5. Fixture-only acceptance plan (specified, not implemented)

1. Fresh fixture receives the exact baseline migration chain and verifies.
2. Ordered multi-domain migrations produce one monotonically increasing sequence.
3. Applied migration file mutation triggers checksum mismatch.
4. Unknown migration ID is rejected.
5. Duplicate migration ID or sequence is rejected.
6. Missing sequence in a required contiguous chain is rejected.
7. Registry row and DDL commit atomically.
8. Injected DDL failure leaves neither schema change nor registry advancement.
9. Interrupted transaction rolls back cleanly; ambiguous outcome is reconciled read-only before any retry.
10. Concurrent migration runner is rejected/serialized under the approved lock contract.
11. Ordinary constructors and reads do not create or migrate schema.
12. Read-only verifier cannot create a missing file, table or singleton row.
13. `user_version` absent/incorrect is diagnostic or a fail-closed mismatch according to the approved mirror policy; verifier never repairs it.
14. Legacy unversioned fixture remains unversioned until explicit baseline adoption.
15. Legacy adoption rejects unexpected schema/data and requires exact baseline approval.
16. Physical schema drift despite a valid registry chain is rejected.
17. D3 manifest migration-chain evidence matches the same read snapshot.
18. D3 snapshot with migration registry mismatch is not accepted.
19. Migration history is append-only; attempted update/delete is rejected by policy/tests.
20. Forward-fix migration succeeds without rewriting prior migration identity.

Tests must use disposable fixtures only. No canonical Android DB, device, Feeder, exchange or production backup/restore is involved.
