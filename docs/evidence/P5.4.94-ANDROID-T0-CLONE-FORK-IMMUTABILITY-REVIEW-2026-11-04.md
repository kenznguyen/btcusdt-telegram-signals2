## 1. Scope

Review whether the approved persisted identity lifecycle (P5.4.89/P5.4.92) and the P5.4.93 pure Kotlin DDL contract define a safe clone/fork operation while keeping the canonical identity and migration history immutable.

This is a source/design review only. No code, DB, device, filesystem, DDL execution, migration, backup/restore, Feeder, writer, APK or exchange operation was performed.

## 2. Verified source facts

- `canonical_database_identity` has a singleton row and unique `instance_id`.
- Its provenance permits `INITIAL_PROVISIONING`, `LEGACY_ADOPTION`, and `CLONE_FORK`.
- A `CLONE_FORK` row requires a non-null parent instance ID different from the child instance ID; other provenance values require a null parent.
- P5.4.93 defines BEFORE UPDATE and BEFORE DELETE abort triggers for `canonical_database_identity`, and append-only triggers for `schema_migrations`.
- The fixed read contract reads all identity and migration rows; it does not provide a fork command, migration executor, data-copy protocol, or transaction coordinator.
- P5.4.89 explicitly says copying a DB file is not a clone protocol, and the clone is not canonical until host pin replacement and D6/lease fencing gates are satisfied.

## 3. Conflict / gap

An ordinary physical copy preserves the parent's identity row and immutable triggers. Updating the copied identity row to a child UUID is rejected by the approved trigger. Deleting/reinserting the row is also rejected. Dropping the triggers temporarily, changing identity, and recreating them would create a privileged immutability bypass and is not an acceptable default protocol.

Therefore, the approved schema and source contract do not yet specify an executable safe fork procedure. The provenance constraint alone does not make a fork safe.

## 4. Candidate design boundary (proposal only)

Preferred direction for review: create a distinct child database through a controlled provisioning/import workflow rather than mutate a byte-for-byte clone.

The future protocol would need to:
1. Obtain a consistent, read-only parent data snapshot under the approved D3 barrier.
2. Provision a fresh destination with a new UUIDv4 child identity and parent lineage.
3. Apply the exact approved schema/migration chain to the destination.
4. Transfer only explicitly allowlisted domain data; never copy the parent's identity row, migration registry rows, SQLite internal objects, WAL/SHM files, host pin, lease/fencing state, or recovery authority.
5. Install immutable identity and migration triggers as part of the destination bootstrap transaction after inserting the child identity and initial migration descriptors.
6. Validate destination schema, migration chain, foreign keys, domain invariants, and data-transfer manifest before it can be considered a candidate child.
7. Keep the child non-canonical and all writers fenced until separate host-pin replacement, D6 restore-epoch/quorum, lease-generation/fencing, and owner admission gates pass.

This proposal is NOT yet implementable: the complete domain-table allowlist, dependency/order rules, cross-domain atomicity, data snapshot/export format, import idempotency, and D3/D6 interaction have not been specified or tested. Cross-database SQLite atomicity must not be assumed.

## 5. Rejected shortcuts

- Do not UPDATE or DELETE the immutable identity row.
- Do not drop/disable immutable triggers to rewrite identity.
- Do not copy a physical DB file and relabel it as a child.
- Do not copy parent host pin, lease generation, writer token, recovery latch, Kill Switch clearance, or restore epoch.
- Do not admit a child writer or clear any safety latch as part of a fork.
- Do not treat a new UUID or parent ID as sufficient proof of safe clone isolation.

## 6. Owner decision required

Before implementation, owner must select/approve the fork model and its acceptance boundary:

- **Option A — Logical child provisioning/import:** fresh destination, new child identity, approved schema replay, allowlisted logical data transfer from a consistent parent snapshot. Requires a separate complete data-transfer contract.
- **Option B — No fork capability in this release:** retain the approved identity schema fields for future lineage, but reject/mark all clone/fork requests BLOCKED until a separately designed and approved protocol exists.

Recommendation for current safety posture: Option B until Option A has a complete domain inventory and fixture-only protocol. This avoids implying that a partially specified fork is supported.

## 9. Owner decision — Option B approved (2026-11-04)

**Decision: APPROVED — P5.4.94 OPTION B.** The owner explicitly selected the no-clone/fork capability boundary for the current release.

Current-release contract:
- Clone/Fork is unsupported. Any request to clone or fork a canonical T0 database must return a deterministic fail-closed rejection; it must not produce a child database or a candidate writer.
- A byte-for-byte copy is not a supported clone. The implementation must not rewrite, delete, or temporarily unprotect the immutable identity row/triggers; it must not relabel a parent database as a child.
- No fallback to physical copy, trigger removal, identity mutation, implicit re-provisioning, or partial import is permitted.
- The CLONE_FORK provenance value remains a schema-level future-compatible value only; its presence does not mean the capability is enabled.
- Reconsideration requires a separate owner-approved design and evidence package. Option A is not approved by this decision.

Bounded next work authorized by this decision: source-only fail-closed capability contract plus pure fixture tests, using the existing Android T0 Foundation GitHub Actions workflow. This does not authorize SQLite/SQL execution, DB or filesystem access, Android device/runtime work, Feeder startup, backup/restore, writer admission, APK work, exchange access or trading.

Status after decision: owner decision RECORDED; source contract/tests NOT YET IMPLEMENTED; exact-SHA CI NOT RUN; runtime capability NOT AUTHORIZED. AI_EXECUTION_ENABLED=false; paper-only.
