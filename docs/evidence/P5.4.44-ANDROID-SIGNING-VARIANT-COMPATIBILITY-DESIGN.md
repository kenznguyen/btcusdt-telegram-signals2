### 2.2 Current build variant and signing source

P5.4.43's static source inventory establishes:
- Regular application ID: `com.kenznguyen.btclivealerts`.
- Parallel/Paper application ID: `com.kenznguyen.btclivealerts.paper`.
- `parallel` is a build type initialized from `debug`, not a product flavor.
- Regular `release` explicitly uses the environment-driven release signing configuration.
- The `parallel` build type does not explicitly select that regular release signing configuration and inherits the debug build type configuration.

Therefore the current checked-in source does not demonstrate that the regular release host and parallel/Paper client are signed with the same controlled installed identity. The expected signing relationship remains **NOT VERIFIED**.

### 2.3 Archived APK verifier is not sufficient evidence

The archived `ci/verify-android-apks.py` checks package identity, version relationship, source SHA, APK hashes and equality of certificate SHA-256 values between `debug` and `parallel` APKs. Its report explicitly labels signing as `DEBUG`.

Its fixture tests exercise verifier behavior with synthetic APK bytes and synthetic tool output. They are unit-test fixtures, not real signed APK evidence.

Consequently:
- A debug/parallel fixture pass cannot prove regular-release/parallel-release signer parity.
- A source-level signing declaration cannot prove the signer embedded in an APK.
- A GitHub artifact metadata digest cannot prove signer identity unless the artifact payload is retrieved and its APK certificate is independently inspected.

## 4. Required build and signing policy before implementation

The following is a proposed acceptance contract, not an approved change to Gradle or workflow configuration:

1. Keep APK packaging manual-only. Do not restore automatic push-triggered APK builds.
2. Use GitHub Actions only. Codemagic remains retired.
3. A future separately approved manual workflow must accept or pin one exact source commit SHA; it must not silently build a moving branch head.
4. Build the owner-selected regular host and parallel/.paper client from that same source SHA.
5. Both installable APKs must use the same controlled signing identity. The build must explicitly select the approved signing configuration for each target; inheriting debug signing is not acceptable evidence of the release signing policy.
6. Verify each APK independently with Android SDK tooling and record:
   - source commit SHA;
   - variant and Gradle task;
   - application ID, versionCode and versionName;
   - signer certificate SHA-256 digest (and signing lineage where applicable);
   - APK SHA-256 and byte size;
   - test results and workflow run ID/URL;
   - artifact ID/name/URL and retention.
7. Gate publication on exact package identities, expected version relationship, valid signatures and identical approved signer/lineage across host and client. Fail closed on missing, ambiguous or mismatched metadata.
8. Download the published artifact payload and independently recompute its checksum; inspect the APK signer from the actual payload. Workflow metadata alone is insufficient.
9. Do not expose private signing material in logs or artifacts. Use GitHub Actions secrets only after a separately approved workflow and key-custody policy exist; never print secret values.
10. Do not install either package or test Binder/permission behavior until device/runtime validation is separately authorized.
