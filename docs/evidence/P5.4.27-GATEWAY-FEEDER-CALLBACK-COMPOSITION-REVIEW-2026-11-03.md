## Critical source finding: G1 is explicitly not integrated

The module header in `market_data/gateway.py` states:

> G1 deliberately implements only the gateway primitive. Existing writer paths are not routed through this module until the separate G2 change.

This is decisive integration-scope evidence. The existence and correctness of the Gateway primitive do not prove that the existing Feeder writer path has been migrated to it.

## Identified call/construction paths

### 1. Gateway primitive

`T0WriteGateway` is constructed from a caller-supplied database path. Its `insert_batch()` performs atomic lease validation and candle mutation under `BEGIN IMMEDIATE`, as recorded in P5.4.26.

This establishes primitive correctness for writes that invoke it, not adoption by every writer.

### 2. Explicit sync CLI

`market_data.sync.main()` constructs:
- a read facade using `create_store(args.backend, sqlite_path=args.db)`;
- `T0WriteGateway(args.db)`;
- a `LeaseFence` from CLI-supplied lease name, owner and generation.

It then passes those objects to `sync_window()`. This is an explicit Gateway-backed sync path with a shared `args.db` between read facade and Gateway. The CLI does not acquire a lease or construct FeederRuntime; the supplied token is checked against the lease row in the selected database.

The CLI is not evidence that the FeederRuntime scheduler or recovery callbacks use this path.

### 3. FeederScheduler and FeederRuntime

`FeederScheduler` accepts an arbitrary injected `sync_callback`. `run_due()` invokes that callback.

`FeederRuntime` accepts an already constructed scheduler and lease store. Its `_configure_retry()` wraps the scheduler callback with a preflight `LeaseStore.authorize_write()` check and retry policy. It does not construct a Gateway, read a canonical DB path, construct a LeaseFence, or bind a Gateway-backed sync adapter.

This means the scheduler callback's actual writer implementation is determined by external composition. The reviewed repository source does not establish that it calls `sync_window()` with `T0WriteGateway`.

### 4. RecoveryCoordinator

`RecoveryCoordinator` accepts a separate arbitrary `sync_callback` and calls it directly for each planned gap. It does not receive a Gateway or LeaseFence. `FeederRuntime.start()` invokes `recovery.recover_all()` before scheduler activation; the scheduler callback wrapper is not applied to the independently injected recovery callback.

The comment in RecoveryCoordinator says the callback must be the existing `sync_window()` path, but that is a contract comment, not a constructor-enforced type or proof of actual production wiring. Even if it is `sync_window()`, the caller must supply a Gateway and LeaseFence, and that composition is not established in the reviewed runtime construction path.

### 5. Tests

`market_data/test_sync.py` directly constructs CandleStore, LeaseStore and Gateway with one TemporaryDirectory path and calls `sync_window()`. It validates the explicit Gateway-backed function in isolation.

`market_data/test_store.py` constructs Gateway and exercises its writes against a temporary DB.

These are unit/fixture constructions, not a FeederRuntime integration test proving scheduler and recovery callbacks are bound to that Gateway. The test source inspected does not establish a complete production composition path.

### 6. Application and workflow

`app.py` constructs `FeederRuntimeStatusStore` only for health/status reads. It does not construct FeederRuntime, LeaseStore or T0WriteGateway in the inspected file.

The T0 manual validation workflow deliberately sets `MARKET_DATA_DB` and `T0_FEEDER_LEASE_DB` empty and asserts they remain empty. This is a CI isolation guard, not production wiring evidence.

## Corrected conclusion

P5.4.26 correctly established that:
- `sync_window()` itself calls Gateway;
- Gateway's transaction performs atomic fencing for its own writes;
- isolated tests pass a common temporary DB path to the stores.

However, P5.4.26 overgeneralized this into the claim that the canonical Feeder writer path uses Gateway. The G1 module header explicitly says existing writer paths are not routed through Gateway until G2. The current reviewed FeederRuntime code accepts arbitrary injected callbacks and does not construct/bind Gateway. Therefore the production scheduler and recovery paths are **NOT VERIFIED and must be treated as NOT INTEGRATED based on the G1 scope statement**, pending G2 source evidence.

This is a material correction to P5.4.26's integration conclusion, not to the Gateway primitive's atomic transaction behavior.

## Required G2 acceptance evidence — proposed

1. A single explicit composition root constructs the canonical Android DB path once and injects it into LeaseStore, Gateway, read facade, status store and Paper Ledger where required by the selected topology.
2. Construct one Gateway-backed ingestion adapter requiring a LeaseFence capability; no unguarded candle write callback is accepted.
3. Inject the same guarded adapter into both FeederScheduler and RecoveryCoordinator. Avoid two separately configured callback implementations.
4. Add fixture-only FeederRuntime integration tests proving:
   - scheduler writes reach Gateway and are rejected for stale generation;
   - recovery writes reach the same Gateway and are rejected for stale generation;
   - both paths share one temporary DB path;
   - a callback cannot write through a legacy/unfenced store;
   - mismatched component DB paths fail closed.
5. Add a source-level check or test preventing direct canonical candle mutation outside Gateway.
6. Record exact tested source SHA, GitHub Actions run, artifact and independent artifact hash after implementation. Do not use Codemagic.
