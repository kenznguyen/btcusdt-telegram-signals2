## 2. Primary-source findings

Reviewed official SQLite documentation:
- PRAGMA semantics: https://www.sqlite.org/pragma.html
- `PRAGMA table_list`: https://www.sqlite.org/pragma.html#pragma_table_list
- Virtual-table shadow-name callback: https://www.sqlite.org/vtab.html#xshadowname
- Registered module inventory: https://www.sqlite.org/pragma.html#pragma_module_list
- Virtual-table implementation catalog: https://www.sqlite.org/vtablist.html

Relevant documented facts:
1. Unknown PRAGMAs are silently ignored; an empty result cannot prove a PRAGMA is supported or that the relevant inventory is empty.
2. `PRAGMA table_list` first appeared in SQLite 3.37.0. It reports object type as `table`, `view`, `shadow` or `virtual`, and documents the columns `schema`, `name`, `type`, `ncol`, `wr`, `strict`. SQLite warns future releases may add output columns.
3. A virtual-table module's `xShadowName` callback determines whether a table is recognized as a shadow table. The callback is module implementation behavior, not derivable reliably from a naming convention alone.
4. `PRAGMA module_list` reports modules registered on the connection. A module name alone does not prove implementation version, build identity, source provenance or safe configuration.
5. SQLite's own virtual-table catalog is explicitly non-exhaustive; deployments can add other modules.

## 3. Recommended runtime feature policy

**Recommendation — minimum feature baseline: SQLite 3.37.0.**

The future adapter should require all of the following before it can claim D5 schema completeness:
- `sqlite_version()` parses and is at least 3.37.0;
- `sqlite_source_id()` is nonblank and recorded exactly;
- the table-list capability is positively established by preparing/executing the read-only table-valued form `SELECT * FROM pragma_table_list` and validating its result-column names, rather than trusting an empty `PRAGMA table_list` cursor;
- the required base columns are present in the exact documented order: `schema,name,type,ncol,wr,strict`;
- any additional/unknown output column fails closed until the canonicalization version explicitly accounts for it;
- the table-list result and `sqlite_schema` catalog agree after the single documented internal-object exclusion rule;
- existing `table_xinfo`, `index_list`, `index_xinfo` and `foreign_key_list` result shapes are validated against fixed expected column names before their rows are accepted.

Rationale:
- The 3.37.0 lower bound is needed for the documented shadow/virtual classification source.
- Table-valued PRAGMA feature probing avoids treating SQLite's silent-ignore behavior as a successful empty inventory. If the table-valued function is unavailable, preparation/query failure means NOT VERIFIED.
- Version alone is insufficient: vendor builds and future output-shape changes must be observed and validated.
- Exact source IDs should be recorded. A runtime allowlist of source IDs is still an owner/design decision; no vendor-specific source ID is selected here.

**Consequence:** Android minSdk 26 does not guarantee the runtime SQLite engine meets this feature floor. Older or unexpected runtime builds must be rejected for canonical D5 verification, not handled with a weaker fallback.

## 4. Recommended shadow/virtual policy for the current release

**Recommendation — reject both `shadow` and `virtual` objects; do not omit or digest them as ordinary tables.**

- If table-list classification reports any `virtual` object, return NOT VERIFIED / unsupported schema.
- If it reports any `shadow` object, return NOT VERIFIED / unsupported schema.
- Do not infer shadow ownership from names such as `fts_*`, `rtree_*`, underscore suffixes or other conventions.
- Do not classify shadow tables by regex or by a hand-maintained name list.
- Do not include only the parent virtual-table declaration while silently excluding shadow objects.
- Do not attempt to infer the module from the virtual-table SQL using a permissive parser.
- Keep the current source contract's fail-closed virtual-table declaration rejection.

Why reject shadow objects too:
- A shadow table's classification depends on the virtual-table module's `xShadowName` implementation.
- Current contract rejects all virtual tables and has no verified module implementation/provenance registry.
- Including a shadow object without verified parent/module association risks an incomplete or misleading schema model. Rejecting the whole schema is the conservative behavior consistent with D5's fail-closed rule.

This policy is scoped to the current release. Supporting virtual tables later requires a separately versioned allowlist binding module name to implementation version/build/source identity, approved declaration grammar and arguments, supported shadow-object set, and complete per-module fixtures. `module_list` alone is not sufficient provenance.

## 5. Proposed D5 canonical envelope v1 field groups

This is a field inventory proposal, not a frozen byte serialization or digest implementation.

### 5.1 Runtime identity
- canonicalization ID and version;
- SQLite version string;
- exact SQLite source ID;
- validated runtime feature set and feature-probe result schema version.

### 5.2 Catalog objects
For each accepted object, sorted deterministically by `schema,type,name,tbl_name`:
- schema;
- object type;
- name;
- owning table name;
- exact `sqlite_schema.sql` text encoded as UTF-8 without whitespace/case/quoting normalization.

Do not include `rootpage` as a logical schema field because it is a physical placement detail, not a schema definition. The existing explicit `sqlite_` internal-object exclusion policy must be versioned and cross-checked against table-list results.

### 5.3 Table and view columns
Capture every documented `table_xinfo` field:
- cid;
- name;
- declared type;
- not-null flag;
- default expression value;
- primary-key ordinal;
- hidden/generated classification.

Use `table_xinfo` for tables and views. Any missing/extra/unexpected result column or failed introspection prevents a complete envelope.

### 5.4 Indexes
Capture all `index_list` fields:
- sequence;
- index name;
- unique flag;
- origin;
- partial flag.

Capture all `index_xinfo` fields:
- sequence number;
- cid;
- column name;
- descending flag;
- collation;
- key-vs-auxiliary flag.

Preserve exact index SQL from the catalog. Expression/rowid markers and auxiliary columns must not be discarded.

### 5.5 Foreign keys
Capture every `foreign_key_list` field:
- id;
- sequence;
- referenced table;
- source column;
- target column;
- update action;
- delete action;
- match mode.

### 5.6 Views and triggers
- Preserve exact view and trigger SQL from the catalog.
- Do not generate table/index/foreign-key PRAGMAs for triggers.
- View columns are captured through `table_xinfo`.

### 5.7 Unsupported objects
- Unknown catalog object types: NOT VERIFIED.
- Missing SQL metadata where required: NOT VERIFIED.
- Virtual/shadow objects: NOT VERIFIED under the recommended current-release policy.
- Missing/unsupported PRAGMA, unexpected result shape, cursor failure or partial evidence: no canonical envelope and no digest.

## 6. Atomicity and failure contract

All catalog and structured introspection evidence must be collected from one read transaction. The source-level contract does not prove this; the future adapter must establish it.

On any transaction, query, cursor, capability-probe, connection or result-shape uncertainty:
- discard all partial evidence;
- return `READ_UNCERTAIN` or a more specific NOT VERIFIED reason;
- do not return a partial canonical envelope or schema digest;
- do not retry automatically until the read-only transaction API and connection state are reconciled.
