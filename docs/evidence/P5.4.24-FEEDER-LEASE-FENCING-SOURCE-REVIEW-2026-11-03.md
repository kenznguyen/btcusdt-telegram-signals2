## Findings

### F1 — LeaseStore is implemented in `market_data/feeder.py`

The source defines:
- `Lease(owner, generation, expires_at_ms)`.
- `LeaseStore(db_path, lease_name="binance-btcusdt-canonical")`.
- `initialize_schema()`, which creates `feeder_leases`.
- `acquire()`, `heartbeat()`, `is_current()`, `authorize_write()`, and `release()`.

The table stores `lease_name`, `owner`, `generation`, and `expires_at_ms`.

Every lease transition goes through `BEGIN IMMEDIATE`. Runtime transactions open the database with SQLite `mode=rw`; a missing database is not silently created by heartbeat/lease transactions. Errors propagate.

### F2 — Implemented lease semantics

- First acquisition inserts generation 1.
- A different owner cannot acquire while the current owner has an unexpired lease.
- Expired or released ownership can be taken over with generation incremented.
- Same-owner acquisition while still unexpired returns the current lease without incrementing generation.
- Heartbeat requires matching owner and generation and a lease that has not already expired.
- Release requires matching owner and generation.
- `is_current()` verifies owner, generation and expiry.
- Default `FeederConfig` values are TTL 60 seconds and heartbeat cadence 15 seconds.

The configuration value does not, by itself, prove a runtime heartbeat loop is actually scheduled or maintained.

### F3 — Fixture tests cover important lease contracts

The inspected `market_data/test_feeder_lease.py` includes tests for:
- only one concurrent unexpired owner;
- two store instances racing to acquire;
- generation increment after expiry;
- stale owner cannot heartbeat or release a takeover lease;
- heartbeat requires matching owner/generation;
- expired owner cannot authorize a write;
- stale writer rejected after takeover;
- default TTL/heartbeat configuration;
- heartbeat extension at 15 seconds;
- storage failure does not grant ownership;
- runtime lease transaction does not create a missing DB.

These are source-level test cases only. This review did not execute them and does not claim a new CI result.

### F4 — Write authorization has a TOCTOU boundary

`authorize_write()` delegates to `is_current()`. That check runs in its own transaction and returns a boolean. It does not atomically include the subsequent candle write.

If a writer performs the lease check on one connection and then writes candles using another connection/transaction, ownership could change between authorization and commit. The comment says to check immediately before each canonical write, but proximity alone does not provide atomic fencing.

**Required unresolved design:** either enforce lease generation inside the same SQLite write transaction as the canonical candle mutation, or define and prove an equivalent serialized writer protocol. A preflight check followed by an unrelated write transaction is insufficient evidence.

### F5 — Shared-file integration remains unverified

- `LeaseStore` accepts an independent `db_path`; no shared canonical path provider or equality assertion was found in the inspected files.
- `FeederRuntimeStatusStore` also accepts a DB path and reads both `feeder_runtime_status` and `feeder_leases` from that file.
- `app.py` health fallback chooses `T0_HEALTH_RUNTIME_STATUS_DB` or `MARKET_DATA_DB`, then constructs `FeederRuntimeStatusStore`.
- This indicates the status reader expects lease and status tables in its selected DB, but it does not prove the runtime LeaseStore and Market Data writer are configured to the same physical Android file.
- The inspected health API is a status reader, not proof of a running lease heartbeat supervisor or a canonical writer integration.

### F6 — CI workflow keeps lease DB environment unset

The inspected T0 manual validation workflow explicitly sets `MARKET_DATA_DB`, `T0_FEEDER_LEASE_DB`, and `PAPER_DB` to empty values and checks that they remain empty. The isolated P3 gate invokes the lease tests, but that workflow definition is not a production runtime wiring specification.

### F7 — Restore rollback risk remains

The lease generation is stored in SQLite. Restoring an older copy of the same database can roll back the generation. A monotonic counter inside the restored file alone cannot prove post-restore fencing against a process holding pre-restore state.

The ADR's requirement for an external restore epoch/re-fencing authority and explicit writer-start gate remains necessary and unresolved.

## Decision and recommendations — PROPOSED, NOT ACCEPTED

1. Keep the owner-approved one-file Android topology, but do not claim it is implemented until one canonical path authority supplies the same resolved file identity to Market Data, LeaseStore, FeederRuntimeStatusStore and Paper Ledger.
2. Resolve the TOCTOU gap by making the generation check part of the same serialized transaction as the canonical write, or document and prove a stronger writer serialization mechanism.
3. Identify the runtime supervisor that acquires, heartbeats, detects lease loss, stops scheduling and gates every write. The 15-second configuration is not proof of this supervisor.
4. Keep the restore epoch/re-fencing authority outside the restored snapshot, with all writers stopped and a fail-closed writer-start gate until re-fencing and Kill Switch recovery are explicitly verified.
5. Do not use `T0_FEEDER_LEASE_DB` as an independent second canonical store under the one-file decision unless the owner explicitly changes that topology.

No code changes are proposed or made in this review.
