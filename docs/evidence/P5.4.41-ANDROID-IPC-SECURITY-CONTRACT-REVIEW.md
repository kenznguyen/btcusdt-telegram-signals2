## 3. Findings and required corrections

### F-01 — Idempotency lookup order needs correction

P5.4.40 lists Kill Switch/risk checks before idempotency resolution. That ordering is unsafe for retries after a successful commit: if the original command committed and the Kill Switch later becomes active, a retry with the same key could be rejected instead of returning the already committed result. A retry must not re-run a domain mutation or reinterpret the original outcome.

Required processing order for a mutation:

1. Capture Binder caller UID synchronously and authenticate package, signer and permission.
2. Authorize the principal for this operation and validate envelope, payload bounds and contract compatibility.
3. Apply transport abuse controls and validate idempotency-key syntax.
4. Look up the durable idempotency record within the authenticated principal/operation scope.
5. If an identical key and canonical payload already has a terminal outcome, return that recorded outcome without re-executing the mutation. A key reused with a different payload returns conflict. Current authorization to read that command's status remains required.
6. For a genuinely new command only, check host lifecycle, canonical readiness, recovery latch/epoch, lease/fencing generation, Kill Switch, data freshness and Shared Risk Engine limits.
7. In one transaction, persist the idempotency/command record, paper-ledger transition and required domain audit event. If one atomic transaction is impossible, a separately reviewed recovery protocol is mandatory before implementation.
8. Return the durable result.

A command left in a nonterminal state after process death must be reconciled from durable host state before another mutation is allowed. It must not be treated as a fresh command.

### F-02 — Bound Service is the preferred IPC primitive

**Recommendation: Android bound Service with explicit component binding and a narrow Binder/AIDL contract.**

Reasons:
- The domain boundary is command/query-oriented, not a general resource provider.
- A service supports an explicit lifecycle and a small operation interface without exposing URI-based CRUD semantics.
- An explicit component binding avoids implicit service resolution.
- A signature-level bind permission can form an OS-enforced first gate, with host-side UID/package/signer checks as a second gate.
- AIDL/Parcelable DTOs can define a closed typed contract for a cross-package process boundary. Only reviewed DTOs and methods should be exposed.

Required constraints if the owner approves this recommendation:
- Export only the one service component required for the .paper client.
- Require a custom signature-level permission on the service.
- Client binds using an explicit component name; no implicit intents.
- Host verifies Binder UID, UID-to-package association, installed package signing identity and operation-level authorization on every call.
- Do not expose a generic Binder transaction dispatcher, arbitrary parcel payloads, callbacks with broad authority or file-descriptor returns.
- Binder entry methods remain short and bounded. Long-running work must use a bounded host-owned queue and a durable command ID.
- Clear/restore Binder calling identity only after the verified principal has been captured; never authorize from a caller identity lost across asynchronous dispatch.
- The service is not a writer merely because it is running. Readiness and writer capability remain separate host-side gates.

ContentProvider is not recommended for this domain contract because its URI/CRUD model can accidentally widen the surface into generic data access. It remains technically possible only after a separate owner decision and equivalent threat review. This recommendation does not itself select or implement the primitive.

### F-03 — Signing and permission model

Recommended policy:
- Host and authorized .paper client are signed by the same controlled application signing identity where operationally possible, so a signature-level permission can restrict access to that signer cohort.
- Host additionally pins the expected .paper package ID and approved signing certificate digest/current signing lineage. Package name alone is insufficient.
- Treat the signing certificate digest as public identity metadata, not a secret. Protect the private signing key through the release-signing process; never ship it in either APK.
- Define rotation as a staged trust update: host accepts old and new approved signer identities for a bounded transition, client release is verified, then old signer is revoked. Emergency revocation must deny new calls.
- If Play App Signing or another signing arrangement causes different installed signing identities, verify the actual installed signer and lineage; do not assume upload-key identity equals installed app signer.
- The permission check and host allowlist check are both required. Neither replaces the other.
- Unknown signer, revoked signer, package mismatch, ambiguous UID/package mapping or permission denial fails closed.

The exact certificate digest(s), package IDs, rotation window and release-key custody policy require owner approval and release-process evidence.

### F-04 — Host package identity remains an owner decision

ADR-002 deliberately leaves the canonical host application ID and current variant open. P5.4.37 source trace indicates the current regular and .paper variants have different application IDs, but this review does not infer which variant should become the host or invent an application ID.

Before implementation, owner must explicitly identify:
- canonical host application ID;
- client .paper application ID;
- whether the current regular app is retained, renamed or replaced;
- upgrade/install coexistence and data migration implications;
- signing identity shared by host/client.

No application ID, manifest or variant changes are authorized by this review.

### F-05 — Contract and transaction details need a bounded implementation design

The following are required in a subsequent implementation design, not guessed here:
- concrete DTO fields and closed enums for each operation;
- serialization and compatibility rules for supported Android API levels;
- maximum request/response bytes, collection sizes, string lengths and decimal precision;
- per-UID quotas, bounded queue depth and operation deadlines;
- durable idempotency key scope, payload canonicalization and retention period;
- atomic boundary for command receipt + ledger + audit;
- exact command states and recovery behavior for crash-before-commit / crash-after-commit-before-response;
- host/client version compatibility matrix and upgrade/downgrade policy;
- audit retention/redaction and principal revocation propagation.

## 4. Recommended minimum interface shape

Keep the external API deliberately small.

**Read-only**
- getHostStatus()
- getRiskStatus()
- getPaperPortfolio()
- getMarketDataSummary(query)
- getRecentAuditEvents(query)
- getCommandStatus(idempotencyKey)

**Mutations**
- submitPaperIntent(command)
- requestPaperCancel(command)

Do not expose user-editable risk configuration in the first IPC version. Do not expose a client command to clear Kill Switch, change fencing, trigger migrations, start Feeder, select DB paths or alter canonical storage.

Both Strategy Core and independent AI remain separate intent sources. Both route through the same host-owned risk gate and paper ledger. The .paper client is not a strategy authority and does not make risk decisions.

## 6. Acceptance gates before implementation

Implementation planning may proceed only after owner decisions in section 5 are recorded. Runtime implementation additionally requires:
1. A reviewed package/signing identity matrix and manifest permission design.
2. Typed contract schema and version compatibility matrix.
3. A transaction/idempotency design that handles crash uncertainty.
4. Fixture-only tests for authentication, authorization, malformed input, replay, duplicate concurrency, version skew and process-crash reconciliation.
5. Static manifest/exported-component checks.
6. A separately authorized Android device/Binder/signing integration test plan.
7. Proof that no code path creates a second canonical DB or writer.
8. Shared Risk Engine/Kill Switch parity for Strategy Core and independent AI.
9. Paper-only guard proof; AI_EXECUTION_ENABLED=false.

Passing fixture tests alone cannot certify Android Binder/signing behavior or production readiness.
