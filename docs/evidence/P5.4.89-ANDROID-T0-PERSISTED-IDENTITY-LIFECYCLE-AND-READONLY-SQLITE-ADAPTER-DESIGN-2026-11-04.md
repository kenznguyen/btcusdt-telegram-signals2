## 2. Design objective

Define how one physical canonical T0 database obtains, retains, restores and deliberately forks a stable CanonicalDatabaseInstanceId without confusing it with:
- CanonicalDatabaseRoleId (stable logical role);
- BackupId (one backup object pair);
- RestoreEpoch (external recovery epoch);
- LeaseGeneration (writer fencing generation).

The design must preserve D4's DB-wide append-only migration registry, D3's same-read-snapshot evidence, D5's separate schema/image/object digest domains and D6's independent recovery authority.

## 3. Approved identity model

### 3.1 Identifier format and creation authority

Approved decision ID-1:
- Use a 128-bit cryptographically random UUIDv4 encoded as canonical lowercase UUID text.
- Generate exactly once inside an explicit Canonical Host provisioning/adoption operation using a platform cryptographically secure random source.
- Never generate in constructors, ordinary startup, reads, verification, unrelated migrations, backup capture or restore verification.
- Never derive identity from package, app version, path, device/account ID, timestamp, file size or content digest.
- Reject malformed, blank, duplicate or conflicting identity values; never auto-replace them.

The UUID identifies one physical canonical database lineage, not an Android installation, user, backup object, restore epoch or lease generation.

### 3.2 Two records, different trust roles

Proposed design:
1. Canonical DB record: singleton `canonical_database_identity` metadata row containing role ID, instance ID, identity format version and creation/adoption provenance. This travels with SQLite backup bytes and preserves lineage on restore.
2. Host identity pin: an expected instance ID held outside the SQLite file by the regular Canonical Host. It is a comparison anchor, not a second database and not a writer/lease authority.

The host pin must not be silently regenerated when missing or mismatched. If DB identity exists but the host pin is missing, return IDENTITY_UNCONFIRMED; if the values differ, return INSTANCE_MISMATCH and fail closed.

Approved decision ID-3: store the host pin in the app's `noBackupFilesDir`. This is a local consistency anchor only. It is not tamper-proof, is not independent of the app sandbox, and does not prevent an attacker with sufficient device/sandbox access from copying or modifying both values. Do not claim cryptographic authenticity or anti-clone security. Do not add a checksum/HMAC and describe it as protection against a hostile writer; no independent key authority has been approved.

The pin is deliberately outside Android's normal app backup set. A database restored from an external D3 backup can therefore exist without its local pin; that state is unconfirmed and must go through D6 recovery. The implementation must verify actual platform backup behavior and storage semantics before relying on them; this design does not assert device-level conformance.

Proposed pin record contract (pure parsing/serialization only in the next source slice):
- Fixed file name: `canonical-database-identity.pin` under `noBackupFilesDir`.
- UTF-8, versioned, canonical representation with exactly one role ID, instance ID, format version and lifecycle state; reject duplicate/unknown fields, malformed encoding, extra records and non-canonical UUID text.
- Lifecycle states: `PENDING` and `ACTIVE`; only `ACTIVE` can participate in a verified identity match. `PENDING` represents an interrupted explicit provisioning operation and never grants readiness.
- Missing, unreadable, malformed or unsupported pin state is an explicit failure; never synthesize a replacement during startup or read-only verification.

### 3.3 Bootstrap and D4 transaction boundary

Approved decision ID-4:
- `canonical_database_identity` contains exactly one immutable identity row after authorized provisioning/adoption.
- `schema_migrations` remains the one DB-wide append-only D4 migration registry; do not duplicate or weaken its authority.
- The explicit host maintenance operation creates the minimum bootstrap schema, identity row and bootstrap migration record atomically inside one SQLite transaction. A failed transaction must not leave a partial DB identity or migration row.
- The host pin is a separate filesystem record; SQLite and filesystem writes cannot be one atomic transaction. Use a fail-closed two-phase provisioning protocol below. Exact DDL, SQLite API/transaction mode and migration bytes remain implementation-contract work. No DB schema is created here.

#### Explicit provisioning protocol (design contract)

1. Preconditions: owner-authorized provisioning command; canonical DB path is confirmed absent or is an explicitly approved empty new DB; no active writer/lease; no existing accepted identity; no legacy data. Ordinary startup/read paths cannot invoke provisioning.
2. Generate one UUIDv4 candidate and atomically persist a `PENDING` pin record using a temp sibling, durable flush and atomic rename where the Android filesystem supports it. Exact fsync/rename guarantees must be verified before implementation.
3. In one SQLite maintenance transaction, create bootstrap objects, insert the same role/instance identity and append the exact bootstrap migration descriptor to `schema_migrations`.
4. Re-open using the future fixed-query read-only verifier contract and confirm the DB identity equals the pending pin and the migration registry/schema evidence is complete.
5. Atomically promote the exact pending pin to `ACTIVE`. Only then may a later read-only identity check report `IDENTITY_MATCH`; this does not admit a writer or release D6 gates.

Crash/retry rules:
- Crash before step 3: pending pin + no DB identity => `PROVISIONING_INTERRUPTED`; no automatic retry or new UUID. Only an explicit maintenance resume/abort decision may proceed.
- Uncertain SQLite commit: retain pending state and report `PROVISIONING_OUTCOME_UNCERTAIN`; reconcile read-only before any explicit resume. Never blindly rerun the transaction.
- Crash after DB commit but before step 5: pending pin + matching verified DB => `PROVISIONING_FINALIZATION_REQUIRED`; do not auto-promote at startup. Explicit maintenance finalization may promote the exact same candidate after full verification.
- Any mismatch, legacy data, unsupported state or incomplete migration chain => `BLOCKED`; do not overwrite either side.
- If promotion durability is uncertain, report `PIN_PROMOTION_UNCERTAIN`; reconcile both records read-only and require explicit maintenance resolution.

This protocol intentionally prefers a recoverable BLOCKED state over silently selecting whichever side appears trustworthy.

### 3.4 Legacy adoption

A database without a valid accepted identity/registry remains LEGACY_UNVERSIONED / IDENTITY_UNKNOWN. Ordinary startup and read-only verification never stamp it.

A separately authorized adoption operation must:
1. Stop/deny writers and obtain the approved host maintenance barrier.
2. Capture a read-only inventory and classify existing schema/data; do not infer the latest migration version.
3. Require an explicit owner-approved baseline descriptor and immutable checksum.
4. Obtain or verify an independently approved identity pin.
5. In one SQLite transaction, insert the identity row and baseline migration registry evidence, with exact schema/data preconditions.
6. Re-open read-only and verify the committed state; on uncertain commit outcome, block and reconcile rather than retrying blindly.

Approved decision ID-5: legacy adoption is inventory-first and explicit; never auto-stamp or infer a baseline. Before any adoption write, require a verified D3 backup of the existing DB, an owner-approved immutable baseline descriptor/checksum and explicit maintenance authorization. If a verified backup or approved baseline is unavailable, adoption is BLOCKED. No existing DB is adopted by this design.

### 3.5 Restore and clone/fork

- Verified restore of the same lineage preserves the DB instance ID and must match the pre-authorized expected host identity or an authenticated recovery declaration.
- Restoring to a fresh device where the host pin is absent must not auto-trust the ID from the DB alone; require the separately authorized D6 recovery/identity process.
- Explicit clone/fork receives a new UUIDv4 child ID and records parent instance ID plus a fork event in immutable audit evidence. The clone is not admitted as canonical until host pin replacement and D6/lease fencing requirements are separately satisfied.
- Copying the DB file is not a clone protocol.
- Restore Epoch and Lease Generation are never read from restored DB content to establish their authoritative values.

## 4. Read-only SQLite adapter boundary — proposed

### 4.1 Capability interface

The adapter should be constructed only from an already existing canonical file path and expose a narrow immutable evidence snapshot:
- existence/open outcome;
- observed identity row (or explicit missing/invalid status);
- complete ordered `schema_migrations` rows;
- schema objects needed by the approved D5 canonicalization contract;
- SQLite runtime/source version and relevant read-only capability metadata.

The verifier must not receive a general writable database handle, migration runner, filesystem create capability, SQL executor or repository that initializes schema.

### 4.2 Open/read rules

- The adapter may open only an existing file in documented SQLite read-only mode; it must never create a file or parent directory.
- If the file is missing, return MISSING_DATABASE without touching the filesystem.
- No `CREATE`, `ALTER`, `DROP`, `INSERT`, `UPDATE`, `DELETE`, migration, baseline stamping, schema repair or `user_version` mutation.
- Any unsupported runtime/API, busy/uncertain read, malformed registry or schema inconsistency fails closed.
- Read identity, migration registry and schema descriptor under one consistent SQLite read transaction/snapshot. Return a single immutable evidence object so the pure verifier cannot accidentally combine different reads.
- The adapter should expose no arbitrary SQL entry point. Query set is fixed and reviewed.
- Verify platform behavior against the exact Android SQLite API and bundled/runtime SQLite version before implementation. Do not assume a JVM JDBC driver or add a dependency without separate review.

### 4.3 D3/D5 evidence

The adapter's snapshot evidence must be collected from the same SQLite read snapshot:
- role/instance identity;
- ordered D4 migration chain and its deterministic evidence;
- D5 logical schema descriptor/digest inputs;
- D2 cursor/ledger/risk evidence once those domains exist.

The migration-chain digest is not the schema digest. Neither replaces the D3 backup image digest or D5 encrypted-object digest. The adapter alone does not prove a D3 backup barrier or D6 restore readiness.

## 5. Required failure states

The implementation contract should distinguish at least:
- MISSING_DATABASE
- IDENTITY_UNKNOWN
- IDENTITY_UNCONFIRMED (DB identity exists, host pin unavailable)
- ROLE_MISMATCH
- INSTANCE_MISMATCH
- LEGACY_UNVERSIONED
- MISSING_REGISTRY
- UNKNOWN_MIGRATION
- DUPLICATE_MIGRATION_ID
- DUPLICATE_OR_GAPPED_SEQUENCE
- CHECKSUM_MISMATCH
- INCOMPLETE_OR_UNCERTAIN
- SCHEMA_DRIFT
- UNSUPPORTED_SQLITE_RUNTIME
- READ_ONLY_OPEN_FAILED
- READ_SNAPSHOT_UNCERTAIN

Only VERIFIED may satisfy a later migration-dependent readiness predicate. VERIFIED alone never clears Kill Switch/Recovery Latch or admits a writer.

## 6. Review findings against P5.4.88 implementation

The existing pure Kotlin contract is useful but not yet a production SQLite verifier. Before expanding it:
1. `ReadOnlySchemaVerifier` currently models role/instance mismatch, unknown migrations, checksum, sequence and schema digest. It has no explicit LEGACY_UNVERSIONED, MISSING_REGISTRY, MISSING_DATABASE, IDENTITY_UNCONFIRMED, unsupported-runtime or uncertain-read statuses.
2. `MigrationDescriptor.create` hashes exact supplied bytes but the descriptor does not retain a canonical immutable catalog identity/version or owner-domain validation policy.
3. The verifier accepts a caller-supplied `expectedSchemaDigest`; it does not calculate D5's approved digest or prove same-snapshot acquisition.
4. `CanonicalDatabaseLineage.restored` models the preserved instance ID but does not retain an audit reference to the source backup/restore case. This should remain separate evidence, not be overloaded into the identity row.
5. No current code allocates or persists an instance ID, opens SQLite read-only, or creates the D4 registry.

These are known implementation boundaries, not reasons to add a database dependency prematurely.
