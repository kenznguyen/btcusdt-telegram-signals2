## 2. Cross-contract consistency findings

### C1 — D2 evidence vector and D3 atomic snapshot
**CONSISTENT.** Market Data uses partition-scoped contiguous closed-candle cursors with gaps/backfill separate; Paper Ledger has a dedicated monotonic sequence and idempotency; Risk State binds to Ledger sequence for same-transaction changes and has a separate version for independent risk-only commits; Lease generation is independent. D3 requires the complete vector to be sampled from the same SQLite read transaction while the host write barrier drains writers. The vector alone is not atomicity proof.

### C2 — D3 snapshot and D4 migration authority
**CONSISTENT.** The database-wide `schema_migrations` registry is the schema authority. D3 manifest evidence must read the migration authority identity and applied chain from the same read snapshot as the D2 vector. No constructor/startup migration, auto-stamping or repair is allowed. Legacy/unversioned databases require separate read-only inventory and approved baseline adoption.

### C3 — D4 migration chain and D5 digest layers
**CONSISTENT WITH OPEN SPECIFICATION.** D5 adds a digest over ordered immutable D4 migration evidence and a versioned logical schema digest. Exact canonical envelope grammar, canonicalization identifier/version, introspection schema, virtual-table/module inventory and SQLite runtime pinning still require specification and fixtures before implementation.

### C4 — Physical digest versus encrypted backup bytes
**BLOCKING CLARIFICATION REQUIRED.** D5 describes physical SHA-256 over exact published snapshot bytes. D7 requires encryption before the payload leaves the trusted capture boundary and read-back verification of the stored object. These are different byte domains:
- snapshot-image digest: SHA-256 over the exact verified SQLite backup image before encryption;
- stored-object digest: SHA-256 over exact encrypted bytes read back from destination;
- authenticated manifest: binds Backup ID, snapshot-image digest, stored-object digest, encryption format/key reference, D3–D5 evidence and object version.
Do not silently overload one `physical_sha256` field to mean both. The manifest field names, digest scope and order of operations must be explicitly reconciled before implementation. This review proposes the separation for owner/design confirmation; it does not amend approved D5/D7 decisions.

### C5 — D3 atomic publication and D7 encryption/read-back
**CONSISTENT IF PUBLICATION IS DEFINED AT OBJECT LEVEL.** Candidate sequence: barrier/capture → staging SQLite image → D3/D4/D5 integrity and domain verification → encrypt and authenticate manifest → durable destination write → read-back ciphertext/manifest verification → immutable publication/AVAILABLE. Partial or uncertain uploads remain STAGING/UNKNOWN and cannot replace last-known-good. D3's atomic publication must refer to the complete verified backup object plus manifest, not a raw plaintext image exposed as AVAILABLE.

### C6 — D6 restore and D3–D5 verification
**CONSISTENT.** Restore must use isolated staging, validate snapshot identity/integrity/domain invariants, D4 migration chain and D5 digest evidence before publication. D6 external Restore Epoch Authority and Recovery Latch cannot be rolled back with the SQLite image. Lease re-fencing must exceed restored and externally issued generation floors. Latch release, Kill Switch clearing and writer admission remain separate gates.

### C7 — D7 RPO/RTO and D2 cursors
**CONSISTENT WITH UNSET TARGETS.** RPO evidence must use Paper Ledger sequence and contiguous Market Data cursor vector, not timestamps alone. D3/D6 external authorities and other external state are outside the SQLite snapshot; any RPO statement must explicitly state their coverage. Numerical RPO/RTO remain **NOT SET / NOT VERIFIED**.

### C8 — Backup authorization versus restore/readiness authorization
**CONSISTENT.** Backup automation is conditional on destination, key custody, retention and verification being implemented. Restore approval is scoped to one incident and Backup ID. It does not release the Recovery Latch, clear Kill Switch or admit writers. CI credentials are not recovery credentials.

### C9 — Operational topology and authority details
**OPEN / BLOCKING BEFORE PRODUCTION.** Android is the intended canonical host and one shared SQLite file is the selected topology, but exact path, stable DB identity, Android runtime/API support, barrier/connection lifecycle, external epoch/latch authority, backup provider/failure domain, key custody, retention values, numerical RPO/RTO and approver roles are not selected or verified.

### C10 — Historical decision text
**DOCUMENTATION RECONCILIATION REQUIRED.** Several historical sections in ADR-001 and D2–D6 proposal records correctly describe the status at their original authoring time but now appear stale when read without chronology (for example, D4–D7 "PROPOSED / NOT DECIDED"). Do not rewrite the historical facts as though they were approved at the earlier date.

## 4. Bounded fixture-only acceptance plan

All tests must use disposable temporary SQLite fixtures, deterministic fake clocks/IDs, fake destination and fake key/authorization/epoch/latch authorities. No canonical DB path, Android device, PC, production key, live storage account, Feeder, exchange, network endpoint or writer is permitted. Tests must fail if a canonical path or non-fixture authority is injected.

### F1 — D2 vector and transaction semantics
1. Market Data cursor is partition-scoped and only advances across contiguous closed candles.
2. Gap/backfill is represented independently; a max timestamp cannot hide a gap.
3. Ledger sequence is monotonic and idempotency prevents duplicate state/audit advancement.
4. Risk change in same transaction references the exact Ledger sequence.
5. Independent risk-only transition increments its own monotonic version and audit.
6. Lease generation is not derived from Market Data or Ledger cursor.
7. Stale lease generation is rejected before every canonical-write adapter call (fixture fake only).
8. Manifest vector preserves each domain and partition without synthetic global ordering.

### F2 — D3 barrier and snapshot
9. Barrier stops admission of new writes and waits for admitted transactions to drain.
10. Drain timeout aborts capture and leaves no published manifest.
11. Unknown transaction outcome aborts capture.
12. Process death while barrier held leaves admission closed pending explicit recovery reconciliation.
13. Snapshot image is created through the selected SQLite backup API abstraction, not raw main-file copy.
14. D2 vector and D4 migration chain are read from the same snapshot transaction.
15. Integrity, foreign-key and domain checks are all required; SQLite integrity alone is insufficient.
16. Failed verification cannot replace last-known-good.
17. Publication interruption leaves STAGING/UNKNOWN, never AVAILABLE.
18. Barrier release uncertainty fails closed and does not auto-reopen writers.

### F3 — D4 migration authority
19. Schema DDL and registry row commit atomically.
20. Duplicate ID, sequence, domain mismatch or exact-byte checksum mismatch fails.
21. Registry is append-only; edits/deletes are detected.
22. Legacy DB remains LEGACY/UNVERSIONED; verifier does not stamp or repair.
23. Read-only verifier invokes no constructor/ensure helper and performs no writes.
24. Unknown migration, missing registry, sequence gap or schema drift fails closed.
25. user_version mismatch follows approved mirror/diagnostic rule and is never silently repaired.
26. Concurrent migration runner is serialized/rejected under the future approved lock contract.
27. Interrupted/ambiguous migration outcome is reconciled without guessing.

### F4 — D5 canonicalization and digest
28. Same schema/runtime/input yields byte-identical canonical envelope and digest.
29. Object/column/index/trigger ordering is deterministic independent of enumeration order.
30. Exact SQL byte change changes schema digest; no ad hoc whitespace/case rewriting.
31. Structured introspection detects column, PK, FK, index, view and trigger drift.
32. Unsupported/unknown virtual-table module fails closed or follows an explicitly approved module inventory.
33. Unknown canonicalization version or digest algorithm fails closed.
34. Physical snapshot-image digest changes when any snapshot byte changes.
35. Optional row/data digest remains disabled unless a separately approved stable encoding exists.
36. No SQLite/PostgreSQL equivalence is asserted by shared digest values.

### F5 — D7 encrypted publication and retention
37. Snapshot-image digest and encrypted-object digest are distinct and independently verified.
38. Authenticated manifest binds Backup ID, snapshot digest, encrypted-object digest, format, key reference and D3–D5 evidence.
39. Ciphertext tampering, manifest tampering, wrong Backup ID or object-version substitution is rejected.
40. Missing/revoked key yields KEY_UNAVAILABLE and is excluded from recoverable inventory.
41. Key material never appears in logs, manifests, fixtures, artifacts or repository.
42. Partial upload/timeout reconciles by immutable Backup ID and never overwrites last-known-good.
43. Read-back digest/authentication failure marks object CORRUPT.
44. Retention cannot delete protected last-known-good or reduce recoverable points below approved minimum.
45. Expiry/deletion requires policy authorization and append-only audit.
46. STAGING/UNKNOWN/CORRUPT/KEY_UNAVAILABLE objects are excluded from recoverable count.

### F6 — D6 restore fencing and authorization
47. Restore without authenticated approver, reason, incident ID or Backup ID is rejected.
48. Restore requires positive prior-owner stop/fence proof.
49. Restore epoch allocation is monotonic, irreversible and idempotent by recovery operation ID.
50. Epoch/latch authority is external to restored SQLite state and cannot be rolled back by fixture restore.
51. Restored lease generation is re-fenced above both restored and external generation floors.
52. Stale intents/capabilities/market assumptions are invalidated.
53. Kill Switch remains asserted through readiness; restore approval alone cannot clear it.
54. Latch release, Kill Switch clearing and writer admission require distinct authorized transitions.
55. CI token/repository write permission cannot satisfy restore authorization.
56. Restoring an older DB does not roll back external recovery audit/epoch/latch evidence.

### F7 — RPO/RTO and negative safety
57. RPO calculation uses Ledger sequence plus Market Data cursor vector and declares excluded external state.
58. RTO ends only after verification, re-fencing and readiness acknowledgement.
59. Missing numerical RPO/RTO yields NOT SET / NOT VERIFIED, never assumed defaults.
60. Any attempt to open canonical DB, use production key/storage, start Feeder, contact exchange or activate writer is rejected by fixture harness.
