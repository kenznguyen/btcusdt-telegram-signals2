# P5.4.81 — Cryptographic Profile and Key Lifecycle Proposal

Date: 2026-11-04
Status: **OWNER-APPROVED — CRYPTOGRAPHIC ARCHITECTURE/PROFILE ONLY (2026-11-04)**
Branch: feature/p5-4-1-post-merge-validation-20261103

Scope: propose a concrete cryptographic profile and key lifecycle for the P5.4.80 backup payload and manifest. Documentation only.

## 1. Objective and boundaries

P5.4.80 requires encryption before backup bytes leave the trusted capture boundary and an authenticated manifest binding both digest domains to an immutable object identity/version. D7 requires separate auditable key custody and fail-closed behavior when keys are unavailable.

This proposal selects no provider and creates no keys. It does not authorize implementation, key provisioning, storage access, backup/restore or production operations.

## 2. Recommended cryptographic profile (owner approval requested)

### 2.1 Payload confidentiality and integrity

Recommend envelope encryption:
- Payload cipher: **AES-256-GCM**.
- Per-backup data-encryption key (DEK): cryptographically secure random 256-bit key, unique for each Backup ID.
- Nonce: 96-bit GCM nonce, unique for every encryption under a given DEK. A fresh one-use DEK per backup makes nonce uniqueness easier to enforce; implementation must still generate and validate nonce according to the selected library/provider contract.
- Authentication tag: full 128-bit tag; truncation is not permitted.
- Associated authenticated data (AAD): versioned immutable context including Backup ID, payload format, encryption format and intended object identity context. Do not include fields that are only known after encryption unless a two-phase envelope explicitly defines them.
- The plaintext input is the frozen snapshot image whose snapshot_image_sha256 was computed under P5.4.80. Ciphertext output is then independently hashed after full destination read-back as encrypted_object_sha256.

Use an external Key Encryption Key (KEK) to wrap the DEK. The wrapped DEK and non-secret key reference/version may be stored in the authenticated manifest/envelope; raw DEK and KEK must never be persisted in repository, logs, CI artifacts or ordinary application preferences.

Rationale: authenticated encryption detects ciphertext/AAD tampering, while envelope encryption permits KEK rotation without rewriting every payload object. This recommendation is conditional on the selected provider/library offering a reviewed AES-256-GCM implementation and durable key-version semantics.

### 2.2 Manifest authenticity

Recommend **Ed25519 digital signatures** over the P5.4.80 versioned canonical manifest bytes, using a signing key separate from the payload KEK.

Requirements:
- Sign exactly the canonical manifest byte sequence; the signature field is excluded from its own input.
- Manifest carries algorithm identifier, signature key reference and key version, not private key material.
- Verifier trusts only an explicitly pinned/approved public-key set and accepted key states.
- Unknown algorithm, canonicalization version, key reference, key version or signature format fails closed.
- Signature verification occurs before trusting object location, object version, digest fields or key references.
- Key rotation permits an explicit overlap period with old public verification keys retained for historical backups; retirement cannot silently make retained backups unverifiable.
- Signing key and encryption KEK have separate identities, permissions, lifecycle and audit events.

Ed25519 is proposed as a portable signature profile; provider support, Android/JVM library support, FIPS or jurisdictional requirements and long-term verification compatibility must be checked before implementation. If a required environment cannot support it, return to owner with an alternative; do not silently substitute HMAC or another signature.

### 2.3 Why not use one key or one mechanism for everything

Rejected:
- Reusing the payload KEK as a manifest signing key: violates key separation and increases blast radius.
- Hash-only manifest integrity: SHA-256 detects byte changes only when expected digest is already trusted; it does not authenticate who created the manifest.
- HMAC with the same secret distributed to every verifier: gives every verifier signing capability and weakens separation of duties.
- AES-CBC/CTR without a separately specified authenticated construction: does not meet the required authenticated-encryption contract.
- Custom encryption, custom nonce construction, truncated GCM tags or home-grown key wrapping: prohibited.

## 3. Proposed key hierarchy and lifecycle

Logical roles:
1. **KEK** — external KMS/HSM-managed key-encryption key; wraps per-backup DEKs.
2. **DEK** — one random 256-bit key per Backup ID; encrypts exactly one frozen snapshot payload.
3. **Manifest signing key** — separate Ed25519 private key protected by an external signing authority/KMS/HSM; public verification keys are distributed as an approved trust set.
4. **Recovery authority** — separate identity and authorization path; CI identity and ordinary app runtime identity cannot authorize restore or key export.

Lifecycle:
- CREATE: provision KEK and signing key only after provider, custody and access policy are approved. Generate DEK only inside the trusted backup capture/encryption boundary or approved KMS generate-data-key operation.
- USE: least-privilege identities; backup writer may request encryption/wrapping and manifest signing but cannot export KEK/private signing key. Restore verifier can verify signatures and request unwrap/decrypt only after D6 restore authorization gates.
- ROTATE KEK: create new KEK version; rewrap retained DEKs through an audited operation where provider supports it. Preserve old key versions until all dependent backups expire or are explicitly re-encrypted and verified.
- ROTATE SIGNING KEY: publish new public verification key before signing with new private key; keep old public key available to verify historical manifests. Record validity intervals and revocation reason.
- REVOKE/COMPROMISE: stop new use immediately, preserve audit evidence, mark affected backups KEY_UNAVAILABLE or UNTRUSTED until a separately authorized recovery decision. Never bypass signature or decryption checks.
- DESTROY: require retention and recoverability checks, dual authorization and append-only audit. Do not destroy any key version required by a retained AVAILABLE backup.
- RECOVERY: escrow/recovery access, if selected, must be separately controlled, tested with non-production fixtures and audited. No single operator or CI token should be able to both approve restore and extract key material.

No key bytes, seed, passphrase, private key, wrapped DEK test value or credential may be committed to GitHub or included in artifacts. Fixtures use synthetic key material only.

## 4. Identity and authorization separation

The following identities must remain distinct:
- backup capture/encryption identity;
- destination write/read-back identity;
- manifest signing identity;
- restore approval identity;
- restore decrypt/unwrap identity;
- recovery audit identity;
- CI test identity.

Minimum policy:
- CI can run fixture tests with fake keys and fake storage only.
- CI cannot access production KMS/HSM, production backup destination, canonical DB or restore authority.
- Backup writer cannot delete or overwrite last-known-good.
- Destination reader cannot sign manifests.
- Manifest verifier cannot sign or decrypt.
- Restore approver cannot directly export keys.
- Key administrators cannot approve restore or clear Recovery Latch/Kill Switch.
- Break-glass access requires separate documented role, reason, incident ID, dual control and immutable audit; no emergency bypass of integrity checks.

## 5. Manifest/envelope fields to add (non-secret only)

Proposed fields:
- encryption_algorithm: AES-256-GCM
- encryption_profile_version
- gcm_nonce: encoded 96-bit nonce; not secret
- authentication_tag_length_bits: 128
- aad_profile_version
- wrapped_dek: ciphertext produced by approved KEK wrapping operation; treat as sensitive metadata and restrict access
- kek_reference and kek_version
- manifest_signature_algorithm: Ed25519
- manifest_signature_profile_version
- signing_key_reference and signing_key_version
- manifest_signature
- key_state_at_publication and non-secret lifecycle event reference

The manifest must not contain raw DEK/KEK/private signing key, passwords, recovery codes, credentials or exportable secrets. Whether wrapped_dek belongs inline or in a separately access-controlled envelope remains subject to provider review; it is not plaintext key material but is security-sensitive.

## 6. Failure behavior

- GCM tag failure or AAD mismatch: reject as CORRUPT; no plaintext publication or restore.
- Manifest signature failure: reject as UNTRUSTED; do not trust any manifest field or follow its object pointer.
- Unknown algorithm/profile/key version: fail closed as UNSUPPORTED_PROFILE or KEY_UNAVAILABLE, never downgrade.
- KEK unavailable/revoked: KEY_UNAVAILABLE; exclude backup from recoverable inventory.
- Signing key revoked/compromised: reject new signatures; historical signatures require an explicit trusted timestamp/audit policy before any continued acceptance.
- Missing nonce/tag/wrapped DEK/key reference: reject.
- Duplicate Backup ID with conflicting DEK/key version/object identity: reject and audit.
- Rotation interruption: retain old key versions and last-known-good; reconcile idempotently.
- Any uncertain crypto or key-service outcome: remain non-AVAILABLE/UNKNOWN; never fall back to plaintext, weaker cipher, local key file or CI secret.
