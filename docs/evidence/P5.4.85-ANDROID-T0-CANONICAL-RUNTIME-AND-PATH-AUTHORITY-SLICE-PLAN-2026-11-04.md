## 3. Proposed bounded implementation slices

### Slice 1 — Regular-host composition root (first implementation candidate)

- Introduce one application-scoped CanonicalRuntime owner in the regular Android application process.
- Runtime construction must be side-effect free with respect to canonical storage: no database open/create, no Feeder start, no lease acquisition, no exchange connection and no market sync.
- Runtime lifecycle must be explicit and idempotent. Repeated access must not create a second owner or second writer capability.
- The `.paper` variant must not instantiate or own CanonicalRuntime.
- Keep existing chart/monitor services separate; do not silently repurpose StrategyMonitorService as the canonical host.

### Slice 2 — Host-owned canonical path authority

- Define one injectable path-authority interface owned by the regular host.
- It returns a canonical app-private candidate path and an opaque stable database identity; callers must not derive either from package strings, SharedPreferences, Termux paths, remote API configuration or PC paths.
- Path resolution is metadata-only. Resolving a path must not create directories or the SQLite file, open SQLite, inspect schema, execute PRAGMA or touch WAL/SHM.
- Keep the concrete filename/root policy behind one implementation and an explicit test seam. Before implementation, review Android backup semantics and app-private storage lifecycle; do not silently choose cloud backup or external storage.
- No raw canonical path, SQLite handle, file descriptor or SQL capability may cross the future IPC boundary.

### Slice 3 — Client exclusion contract

- The `.paper` application remains an authenticated IPC client only.
- It has no canonical DB path resolver, no SQLite open/create/write path, no shadow DB, no lease/fencing authority and no fallback writer.
- If the host is unavailable or unauthorized, the client reports canonical operations unavailable; it must not fall back to remote API or local persistence and claim canonical success.

Slices 2 and 3 are acceptance boundaries for the foundation; they do not authorize implementing storage, IPC, Feeder or paper execution in this increment.

## 4. Acceptance contract — fixture/static CI only

All tests must use fakes, temporary directories or in-memory state. They must not access the Android device or future canonical DB.

| CR-02 | Runtime construction and retrieval are side-effect free | No DB file, directory, Feeder, lease or exchange side effect |
| CR-03 | Path authority returns one app-private candidate path and opaque identity | No guessed path, external/shared path or package-name-derived path |
| CR-04 | Path resolution is metadata-only | No SQLite open, create, PRAGMA, schema read or WAL/SHM mutation |
| CR-05 | Runtime owner is unavailable in `.paper` variant | Client cannot construct or acquire canonical writer capability |
| CR-06 | Runtime lifecycle is idempotent across repeated initialization/teardown | No duplicate runtime or implicit service start |
