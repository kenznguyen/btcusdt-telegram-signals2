# P5.4.73 — D5 Canonicalization and Digest Rules Proposal

Date: 2026-11-04 (Asia/Ho_Chi_Minh)
Branch: `feature/p5-4-1-post-merge-validation-20261103`
Status: **PROPOSED — OWNER DECISION REQUIRED**
Scope: architecture proposal only. No implementation, fixture execution, canonical DB access or runtime operation.

## 1. Objective

Define deterministic, versioned representations for schema identity and (if separately enabled) logical data identity so that manifests can be compared across independent verification runs without confusing:
- physical backup-byte identity;
- applied migration-chain identity (D4);
- logical schema identity;
- logical row/data identity.

These are separate evidence layers. A digest is meaningful only with its algorithm, canonicalization version, scope and input contract.

## 2. Proposed digest layers

### D5.1 — Physical snapshot digest

- Retain SHA-256 over the exact published backup file bytes.
- This digest identifies one byte sequence only; it does not establish semantic equivalence or successful restore.
- Never normalize or rewrite the backup before calculating its physical digest.
- Record digest algorithm, byte length and digest value in the immutable backup identity (D3).

### D5.2 — Migration-chain digest

- Reuse the D4 ordered migration authority evidence: authority identifier, strictly increasing sequence, migration ID and exact migration-file SHA-256.
- Define a deterministic digest over the ordered tuple list using the canonical envelope in Section 3.
- This digest is a compact commitment to declared migration history, not proof that the physical schema matches it.
- Preserve the full ordered list in evidence or an immutable referenced manifest payload; do not rely on the digest alone for diagnosis.

### D5.3 — Logical schema digest

Proposed SQLite schema input:
- Enumerate user schema objects from the same read snapshot using `sqlite_schema`: tables, indexes, views and triggers.
- Include object type, object name, owning table name and SQL definition; include explicit structural metadata for columns, primary keys, foreign keys and indexes from read-only SQLite introspection.
- Exclude SQLite-internal objects only by a fixed, versioned rule (for example internal names beginning with `sqlite_`); record the exclusion rule in the canonicalization specification.
- Include virtual-table/module declarations and required module identity as explicit schema dependencies; if a module cannot be identified or verified, return NOT VERIFIED rather than silently omitting it.
- Treat missing, extra or structurally inconsistent objects as schema drift even if the D4 migration chain is valid.

The schema digest is distinct from D4 migration-chain digest: D4 describes intended evolution; D5 schema digest describes the observed physical schema structure.

### D5.4 — Logical row/data digest (separate optional capability)

Do not make a full-database row digest a prerequisite for D5 schema acceptance. If later required, define it as a separately scoped extension:
- stable table/partition scope and deterministic primary-key ordering;
- explicit handling of tables without a stable primary key (reject or define a separately approved stable identity; never rely on incidental row order);
- canonical representations for NULL, integer, real, text, BLOB, decimal-like values, timestamps and JSON;
- explicit treatment of floating-point edge cases, negative zero, NaN/infinity (reject unless a deterministic policy is approved);
- explicit inclusion/exclusion of volatile fields, with rationale and versioning;
- bounded streaming/chunking rules and per-table/per-partition digest composition.

No row digest is claimed or required by this proposal unless separately approved.

## 3. Canonical encoding proposal

Use a versioned canonical envelope with:
- UTF-8 encoding;
- deterministic object-key ordering;
- deterministic array ordering defined by the relevant schema/migration contract;
- explicit type tags and length-delimited values (or an equivalently unambiguous canonical serialization);
- no locale-sensitive formatting;
- no implicit timezone conversion;
- no lossy numeric conversion;
- explicit distinction among absent, NULL, empty text and empty bytes;
- SHA-256 as the initial digest algorithm, with algorithm identifier stored independently from canonicalization version.

For SQLite schema SQL, proposed initial policy is to hash the exact UTF-8 bytes returned by the pinned SQLite runtime for each `sqlite_schema.sql` value, alongside structured introspection records. Do not perform ad-hoc whitespace, case, quote or token rewriting. This is conservative and may produce different digests across SQLite runtime versions; therefore the manifest must record SQLite runtime/source version and canonicalization version. Any future semantic SQL normalizer requires a new canonicalization version and its own fixtures.

The final serialization grammar, framing bytes, field names and canonicalization version identifier remain open for owner review and implementation specification.

## 4. Cross-backend policy

- Do not claim SQLite/PostgreSQL logical schema or row equivalence in the initial version.
- Backend-specific schema objects and type systems must be represented explicitly.
- A cross-backend canonical model, type mapping and equivalence policy require a separate approved contract and dedicated parity fixtures.
- Never compare hashes produced under different canonicalization versions as if they were directly equivalent.

## 5. Manifest requirements

Proposed manifest fields:
- `digest_algorithm` (initially SHA-256);
- `canonicalization_id` and `canonicalization_version`;
- `schema_digest` and schema input scope;
- `migration_authority_id`, latest sequence and ordered migration-chain digest (with full chain evidence retained);
- `sqlite_runtime_version` and relevant compile/source identity;
- physical snapshot SHA-256 and byte length;
- explicit excluded-object/field policy identifier, where applicable.

All D3 manifest metadata must be read from the same SQLite read snapshot where it describes database state. Runtime/build metadata may be recorded separately and must be labelled as such.

## 6. Fail-closed rules

- Unknown canonicalization version or digest algorithm: reject acceptance.
- Missing or ambiguous schema inputs: NOT VERIFIED / reject acceptance.
- Unsupported virtual-table module or unknown object type: NOT VERIFIED.
- D4 chain valid but schema digest mismatch: SCHEMA_DRIFT.
- Same schema but different physical SHA: distinct physical snapshots; no semantic equivalence inferred without all applicable logical checks.
- Different canonicalization versions: no direct digest equality claim.
- A valid digest never overrides D3 barrier, D4 migration-chain, SQLite integrity, foreign-key or domain-invariant failures.

## 7. Fixture-only acceptance plan (specified, not implemented)

1. Same schema fixture yields byte-identical canonical envelope and digest across repeated runs under the pinned runtime.
2. Object enumeration is independent of SQLite catalog return order.
3. Column, index, foreign-key, trigger or view change alters the schema digest.
4. Missing/extra object is rejected as schema drift.
5. Exact SQL byte change changes the digest under the initial conservative policy.
6. Different SQLite runtime identity is recorded and cannot be silently treated as same canonicalization context.
7. Internal-object exclusion follows only the fixed versioned rule.
8. Unsupported virtual-table module returns NOT VERIFIED.
9. Migration-chain order change alters its digest.
10. D4 valid chain with altered physical schema is rejected.
11. NULL, empty text, empty BLOB and absent values remain distinguishable in the canonical envelope.
12. Locale/timezone changes do not alter canonical output.
13. Unknown canonicalization version fails closed.
14. Unknown digest algorithm fails closed.
15. Different canonicalization versions are not compared as equal.
16. Physical digest is calculated over exact published bytes and is not substituted by logical schema digest.
17. Row ordering is deterministic for any future row-digest extension.
18. No-primary-key table is rejected by any future row-digest mode unless an approved stable identity exists.
19. Unsupported numeric/float values fail closed under the selected row-digest policy.
20. Manifest fields and schema/migration evidence correspond to one D3 read snapshot.

All tests must use disposable fixtures only. No Android device, canonical database, Feeder, exchange, production backup or restore is involved.

## 8. Decisions requested

Owner approval is requested for the D5.1–D5.4 layer boundaries and proposed rules, especially:
- separation of physical, migration-chain, schema and optional row/data digests;
- SHA-256 as initial digest algorithm;
- versioned deterministic canonical envelope;
- conservative exact SQLite SQL bytes plus structured introspection, with runtime identity recorded;
- no initial SQLite/PostgreSQL equivalence claim;
- row/data digest excluded from initial mandatory scope;
- fail-closed handling and fixture-only acceptance plan.

Open implementation details include exact envelope grammar/framing, canonicalization identifier/version, SQLite runtime pinning policy, introspection field schema, virtual-table module inventory, digest composition, and whether/when row digests are needed.
