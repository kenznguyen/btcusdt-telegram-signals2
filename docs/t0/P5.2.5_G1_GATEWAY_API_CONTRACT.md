## 1. Purpose and scope

G1 defines the smallest T0 Single Writer Gateway (SWG) primitive and its atomic fencing contract. It does not implement the Gateway, route existing writers, start the Feeder, connect to an exchange, synchronize market data, initialize the canonical database, or change production runtime configuration.

G1 is limited to the Gateway primitive and its isolated tests. Routing every existing T0 writer through the Gateway is G2. Lifecycle, recovery, and restart behavior are G3.

## 2. Non-goals and safety boundaries

- No live trading or order execution; the wider system remains paper-only.
- No canonical database creation, migration, or activation.
- No Feeder startup, exchange connection, or market-data synchronization.
- No production writer enablement.
- PostgreSQL is not an enabled canonical writer in G1. It remains disabled for canonical writes until equivalent fencing is implemented and independently verified.
- Tests must use isolated temporary databases and synthetic candle/lease data. No network or exchange access.
- A passing G1 primitive does not prove all existing T0 write paths are fenced; that is G2's acceptance scope.

## 3. Proposed API contract

The public interface is aligned with the frozen G0 contract. The implementation must preserve these names and semantics; it must not introduce parallel or unfenced convenience alternatives.

```python
from dataclasses import dataclass
from collections.abc import Sequence
from typing import Callable

@dataclass(frozen=True)
class LeaseFence:
    lease_name: str
    owner_id: str
    generation: int

class GatewayWriteError(Exception):
    """Base class for typed T0 Gateway failures."""

class LeaseRejected(GatewayWriteError):
    ...

class CandleBatchRejected(GatewayWriteError):
    ...

class GatewayStorageError(GatewayWriteError):
    ...

class T0WriteGateway:
    def __init__(self, db_path: str | os.PathLike[str]):
        """Store path/configuration only; do not access the filesystem or SQLite."""

    def insert_batch(
        self,
        candles: Sequence[Candle],
        *,
        lease_token: LeaseFence,
        now_ms: Callable[[], int],
    ) -> int:
        """Atomically commit a validated candle batch; return accepted count."""

    def read_window(self, symbol: str, timeframe: str, start, end):
        """Read candles without DDL or DML."""

    def close(self) -> None:
        """Release this object's resources only; never release another owner's lease."""
```

`T0WriteGateway.insert_batch()` is the sole public write method. `CandleWriteGateway`, `write_batch()` and a separate `CandleBatch` wrapper are not part of this contract.

### 3.0 Construction and connection ownership

- The constructor accepts only the T0 database path. It stores/validates the path value without `stat`, `mkdir`, `sqlite3.connect`, WAL setup, schema creation or any other filesystem/database access.
- The Gateway does **not** accept or retain a `LeaseStore` object. It reads the authoritative `feeder_leases` row using the same SQLite connection and `BEGIN IMMEDIATE` transaction that writes candles. Calling `LeaseStore.is_current()` through a separate connection would violate the atomic fencing contract.
- The T0 candle table and `feeder_leases` table must be in the same physical SQLite database for this SQLite Gateway contract.
- SQLite is the only supported G1 backend. No `backend` selector or PostgreSQL fallback is exposed.
- `close()` releases only Gateway-owned resources; it never releases or mutates the lease.

### 3.0.1 Error hierarchy

- `GatewayWriteError` is the common public base exception, preserving the G0 typed-error boundary.
- `LeaseRejected`, `CandleBatchRejected` and `GatewayStorageError` subclass `GatewayWriteError` and remain distinguishable.
- Callers may catch the base class for compatibility, but tests and internal callers should assert the specific subtype where applicable.

### 3.1 Input invariants

- A non-empty batch requires a `LeaseFence` with non-empty `lease_name`, non-empty `owner_id`, and positive integer `generation` matching the authoritative lease row exactly.
- `now_ms` is a required zero-argument callable returning a nonnegative UTC epoch-millisecond integer. It is evaluated inside the write transaction at the initial and final fencing checks; tests must inject a deterministic clock and must not rely on sleeps.
- Candle validation must reject malformed or internally inconsistent records before commit.
- An empty `candles` sequence is a strict no-op: `insert_batch()` returns `0` without opening or creating a DB, starting a transaction, reading/validating the lease, invoking `now_ms`, or performing DDL/DML. This no-op does not imply Gateway initialization.

### 3.2 Atomic write and fencing semantics

1. Acquire the database write transaction/lock before reading the lease record. For SQLite, use a write transaction mode that serializes competing writers (normally `BEGIN IMMEDIATE`).
2. Within that same transaction, validate the lease name, owner, generation, and expiry against the authoritative lease row.
3. Still within that transaction, validate/write the entire candle batch.
4. Immediately before commit, re-read/validate the authoritative lease row and evaluate expiry using the injected `now_ms()` clock. This final in-transaction check is the write-admission linearization point. If the lease is expired or its owner/generation no longer matches, roll back the entire batch.
5. Commit only when every required operation succeeds and the final fencing check passes.
6. On invalid/expired lease, stale generation, validation error, constraint error, or injected mid-batch failure, roll back the entire batch.
7. Never validate the lease in a separate preflight transaction and then write later. That creates a time-of-check/time-of-use race.
8. Never fall back to direct `CandleStore.insert()`, an optional unfenced path, or another backend when Gateway validation or configuration fails.

The final in-transaction expiry check is the write-admission linearization point. **The contract intentionally permits a batch whose final fencing check passed to commit even if wall-clock lease expiry occurs after that check but before SQLite finishes COMMIT.** Lease validity is evaluated at admission, not continuously through the storage engine's durability boundary. G1-14 must distinguish these two cases with a deterministic clock: (a) expiry before the final check rejects and rolls back the whole batch; (b) expiry advanced only after the final check does not retroactively revoke an already-admitted batch. If the system later requires lease validity at the exact durable-commit instant, this SQLite check-and-commit contract is insufficient and must be redesigned rather than implied by this API.

A takeover that commits before the old writer obtains its write transaction must cause the old writer to fail fencing. If an old writer already owns the serialized write transaction, the takeover must serialize behind it; the old batch may commit only if the final in-transaction fencing check passes. A batch admitted by that final check may complete COMMIT after wall-clock expiry, as stated above. Tests must assert the resulting durable database state, not merely call order.

### 3.3 Error semantics

The implementation must expose stable, distinguishable failure categories:

- `LeaseRejected`: missing, expired, wrong-owner, or stale-generation lease.
- `CandleBatchRejected`: invalid candle/batch content.
- `GatewayStorageError`: database or transaction failure.

Exact class/module names may be finalized during implementation review, but callers must be able to distinguish lease rejection from malformed input and storage failure. No failure may be converted into a successful partial-write result.

### 3.4 Read semantics

- `read_window()` is read-only.
- Gateway construction and read methods must not create schema, initialize tables, run migrations, acquire a writer lease, or mutate runtime status.
- Schema creation/migration is an explicit privileged operation outside normal Gateway construction and reads.

### 3.5 Idempotency and duplicate candles

G1 preserves the source-observed SQLite candle identity and conflict behavior inspected at `c188a4d193f870a93efd348f993a4c1b2f1dfda0` in `market_data/store.py`:

- Identity/primary key: `(exchange, market_type, symbol, timeframe, open_time_ms)`.
- Existing-row comparison fields: `open`, `high`, `low`, `close`, `volume` only.
- Same identity and equal OHLCV: ignore the replay; do not insert another row and do not update the existing `available_at_ms`.
- Same identity and different OHLCV: reject with conflict; never overwrite the existing row.
- Any batch failure: roll back the entire transaction.
- `available_at_ms` is not part of the duplicate equality comparison.

These are source-inspection findings, not permission to open or create the canonical runtime database. G1 tests must reproduce this behavior using isolated temporary SQLite fixtures. Any future change to identity or conflict semantics requires a separate contract decision.

## 4. Atomic Fencing Test Matrix

All tests use isolated temporary SQLite databases, deterministic clocks, and synthetic records. Each negative test must assert both the expected error and the final persisted database state.

| ID | Scenario | Required assertion |
|---|---|---|
| G1-01 | Valid lease, matching owner and generation | Entire valid batch commits; accepted count matches contract |
| G1-02 | Expired lease | Rejected; no candle from batch persists |
| G1-03 | Wrong owner | Rejected; no candle persists |
| G1-04 | Stale generation | Rejected; no candle persists |
| G1-05 | Lease takeover committed before old writer starts | Old generation rejected; no stale write persists |
| G1-06 | Concurrent takeover and batch write | Transaction serialization/fencing prevents a stale write after takeover; assert final lease and candle state |
| G1-07 | Invalid candle within batch | Entire batch rolls back |
| G1-08 | Injected failure after one or more inserts | Entire batch rolls back |
| G1-09 | Retry of identical logical batch | No duplicate candle identities; exact result follows the source-inspected conflict policy |
| G1-10 | Gateway unavailable or not configured | No direct/unfenced fallback write occurs |
| G1-11 | Call read method and construct Gateway | No DDL/DML or schema initialization occurs |
| G1-12 | PostgreSQL canonical write attempt | Remains disabled/rejected until separately approved equivalent fencing exists |
| G1-13 | Empty batch | Returns `0`; no transaction, lease lookup, DDL, or DML occurs |
| G1-14 | Lease expiry boundary around final admission check | (a) Expiry before final check: reject and roll back the entire batch; (b) advance the deterministic clock only after the final check passes: the already-admitted batch may commit even though COMMIT completes after wall-clock expiry |

### 4.1 Concurrency test requirements

G1-05 and G1-06 must use two independent SQLite connections (not a shared connection); separate processes are preferred for the cross-process guarantee. Use deterministic coordination barriers/events rather than timing sleeps. Cover both transaction orderings:
- **Takeover wins first:** the new owner/generation commits before the old writer acquires `BEGIN IMMEDIATE`; the old writer must be rejected and must persist no candle rows.
- **Old writer wins first:** the old writer acquires `BEGIN IMMEDIATE`; takeover must block/serialize until the old transaction completes. If the old writer's final fence check passes, its admitted batch may commit, after which takeover may commit the new generation. The test must assert this exact durable ordering and resulting candle/lease state.

Do not simulate the ordering only with a mocked lease store or a single SQLite connection. Assert persisted rows and the final authoritative lease generation from the independent connection(s).

### 4.2 Rollback test requirements

G1-07, G1-08, and G1-14 must prove atomicity by querying the database after the operation fails. A test that only observes an exception, or only mocks `rollback()`, does not prove rollback.

## 5. G1 acceptance gate

G1 is PASS only when all of the following are evidenced on the exact PR source SHA:

- [ ] Focused Gateway contract tests execute against isolated temporary SQLite databases.
- [ ] Valid, expired, wrong-owner, stale-generation, and takeover cases behave as specified.
- [ ] Concurrency tests prove fencing and transaction serialization through persisted state.
- [ ] Mid-batch failure and expiry-at-final-check prove full rollback; no partial rows remain.
- [ ] Retry behavior preserves candle identity and the source-inspected conflict policy is documented and tested.
- [ ] Empty-batch behavior is a no-op returning zero without DB access.
- [ ] No unfenced fallback path exists in the Gateway API.
- [ ] Constructor/read tests prove no DDL/DML side effects.
- [ ] PostgreSQL canonical writes remain disabled.
- [ ] Codemagic reports the exact tested implementation source SHA, executed test counts, failures, and skips. Skipped tests do not count as PASS. The previously authorized GitHub Actions exception applies only to G0 evidence run `41512015687`, not G1.

A missing module/API assertion or skipped behavioral test is not a behavioral PASS. An isolated-environment check alone does not establish fencing correctness.
